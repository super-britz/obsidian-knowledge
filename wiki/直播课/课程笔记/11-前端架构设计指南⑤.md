# 11 前端架构设计指南⑤

> [!abstract] 核心问题
> 一个部署到 Lambda 的 Node.js 后端，如何组织依赖、分层和运行期对象？

## 本节结论

- Lambda Layer 可以复用共享依赖，但会增加版本、兼容性和部署关系的管理成本。
- Serverless 构建要从函数入口收集真实依赖，避免把整个开发环境打进部署包。
- Router、Controller、Service、中间件和基础设施模块应按职责分层。
- 依赖注入的价值是让业务代码依赖抽象，并集中管理对象创建和生命周期。
- 架构知识只有经过实际部署、排错和记录，才能转化为可复用经验。

## 知识框架

### 1. Lambda 函数与 Layer 的边界

```text
函数代码包
  - handler
  - 业务模块
  - 函数专属依赖

Lambda Layer
  - 多个函数共享的库
  - 公共运行时依赖
```

Layer 适合变化较慢且确实共享的内容。频繁变化的业务代码放入 Layer，会让部署和版本追踪更复杂。

### 2. 构建目标是最小且可运行

构建过程需要：

- 从 handler 识别运行时依赖。
- 排除测试、源码映射之外的开发文件和未使用依赖。
- 正确处理原生模块和运行时版本。
- 让本地、CI 与 Lambda 环境尽量一致。
- 在部署后验证冷启动、日志和错误路径。

### 3. 后端按职责分层

| 层次 | 主要职责 |
| --- | --- |
| Router | 路由与 HTTP 方法映射 |
| Middleware | 鉴权、日志、校验等横切逻辑 |
| Controller | 协议转换和请求编排 |
| Service | 业务规则与用例 |
| Repository / Client | 数据库和外部服务访问 |
| Infrastructure | 配置、日志、容器与云服务适配 |

业务规则不应散落在路由或数据库访问代码中。

### 4. 依赖注入管理创建与生命周期

```text
Controller
  -> UserService
  -> UserRepository
  -> Database Client
```

容器负责创建依赖并注入调用方。常见生命周期包括每次解析创建、请求内复用和应用级单例；选择错误可能导致状态串扰、连接浪费或测试困难。

### 5. 自动发现不能牺牲可追踪性

自动扫描 Controller 或 Service 可以减少注册代码，但命名规则、加载顺序、失败日志和测试入口必须清楚，否则问题会被隐藏在框架魔法中。

## 实践任务

**建议产出：**

- 一个部署到 Lambda 的分层 Node.js API。

**完成标准：**

- [ ] 画出函数代码包与 Layer 的依赖关系。
- [ ] 部署包只包含运行所需文件。
- [ ] Router、Controller、Service 和数据访问层职责清楚。
- [ ] 用替身依赖对 Service 做独立测试。
