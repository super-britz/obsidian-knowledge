# 44 AI 工作流与 RAG 实验

> [!abstract] 核心问题
> 如何让 AI 工作流稳定执行关键步骤，并通过受控实验判断 RAG 问题究竟来自检索、模型还是数据？

## 本节结论

- 只把流程写进长提示词或 Markdown，不能保证每个步骤都会执行；关键约束应进入程序、状态机和验证器。
- 多 Agent 的意义是并行分工和独立验证，不是简单增加调用次数。
- 高推理预算和对抗审计可以发现更多问题，但必须用收益、成本与延迟决定使用范围。
- RAG 效果由文档解析、OCR、分块、Embedding、检索、重排和生成模型共同决定。
- 比较 RAG 方案时一次只改变少量变量，并保留固定问题集、证据集和成本记录。

## 知识框架

### 1. 从说明文档升级为可执行流程

长上下文可能被压缩，模型也可能自行跳过它认为不重要的步骤。关键流程应显式表达为：

```text
输入校验
  -> 任务拆解
  -> 执行
  -> 产物检查
  -> 独立验证
  -> 人工审批
  -> 完成或回退
```

每个节点应定义输入、输出、完成条件、失败处理和最大重试次数。文档继续解释意图，程序负责保证控制流。

### 2. Workflow、Agent 与 Subagent 的协作

- Workflow：决定步骤和状态如何流转。
- Agent：在约束范围内判断下一步或选择能力。
- Subagent：承担一个边界明确、上下文相对独立的子任务。
- Validator：使用验收条件检查产物，不复用执行者的自我判断。

适合并行的任务可以拆开，例如前后端实现、多个审计维度或不同测试类型；存在严格依赖的步骤仍应顺序执行。

### 3. 对抗验证不能只追求“更多推理”

复杂架构审计可以让多个角色分别寻找边界、数据、性能、安全和一致性问题，再由汇总节点去重和排序。

但推理预算越高，Token、延迟和重复建议也越多。应提前设置：

- 问题严重度范围。
- 最大调用和 Token 预算。
- 需要读取的仓库范围。
- 去重与证据要求。
- 何时停止或转人工。

高成本模式适合关键发布和专项审计，不应无差别用于所有日常任务。

### 4. RAG 最小实验链路

```text
文档
  -> 解析 / OCR
  -> 分块
  -> Embedding
  -> 检索候选
  -> 可选 Rerank
  -> 拼接上下文
  -> 对话模型回答
```

Embedding Model 负责生成检索向量，对话模型负责根据证据回答。二者职责不同，不能用“换了大模型”解释所有效果变化。

### 5. 用固定样本定位瓶颈

准备一组包含以下类型的问题：

- 答案直接存在于单个片段。
- 需要组合多个片段。
- 表格、图片或扫描件中的信息。
- 文档中不存在答案的问题。
- 容易被相似词误召回的问题。

记录每个问题的正确证据、召回排名、最终回答、引用、延迟和成本。先查看正确片段是否进入候选，再判断生成模型是否忠于证据。

### 6. 本地与云端方案的选择

| 维度 | 需要回答的问题 |
| --- | --- |
| 效果 | 目标问题的检索与回答是否达标？ |
| 隐私 | 原文、问题和日志是否允许离开本地？ |
| 成本 | 索引、推理、并发和运维成本是多少？ |
| 延迟 | 首次加载、单次响应和高并发是否可接受？ |
| 维护 | 模型、服务、驱动和监控由谁负责？ |

本地方案效果不佳，不代表 RAG 方法无效；云端模型效果更好，也不代表它满足数据合规和长期成本要求。

## 实践任务

**建议产出：**

- 搭建一个小型 RAG 对照实验，并用程序化 Workflow 自动执行评估。

**完成标准：**

- [ ] 准备固定问题集和人工标注的正确证据。
- [ ] 至少比较两组 Embedding 或对话模型配置。
- [ ] 分别记录检索命中、回答忠实度、延迟和成本。
- [ ] 文档缺少答案时，系统明确拒答而不是补写。
- [ ] Workflow 能在步骤失败、超预算或验证不通过时停止。
