# 07 前端架构设计指南②

> [!abstract] 核心问题
> 如何从缓存、运行环境、依赖管理和团队约束出发，做出可解释的前端技术选型？

## 本节结论

- 缓存不是单一开关，而是 HTTP 缓存、浏览器存储和 Service Worker 等多层机制的组合。
- 浏览器与服务端运行环境不同，共享代码必须显式隔离 `window`、`localStorage` 等浏览器 API。
- 包管理器的依赖布局会影响安装速度、幽灵依赖、磁盘占用、构建和部署兼容性。
- 框架选型的依据应是业务、团队、生态和维护成本，而不是热度排名。
- AI 工作流适合自动收集和压缩信息，但信息源、筛选条件与最终判断仍由人负责。

## 知识框架

### 1. 缓存按作用位置分层

| 层次 | 典型机制 | 主要用途 |
| --- | --- | --- |
| HTTP 缓存 | 强缓存、协商缓存 | 减少重复网络传输 |
| 简单本地存储 | Cookie、`localStorage` | 保存少量会话或偏好数据 |
| 结构化本地存储 | IndexedDB | 保存较大、可查询的客户端数据 |
| 请求代理层 | Service Worker | 拦截请求、离线缓存和后台能力 |

设计缓存时先回答：数据允许旧多久、由谁失效、失败后是否可回源、不同用户之间能否共享。

### 2. Service Worker 提供离线能力，也引入一致性问题

```text
页面请求
  -> Service Worker
  -> 命中缓存 / 请求网络
  -> 更新缓存
  -> 返回响应
```

它适合弱网、离线和静态资源缓存，但必须处理版本升级、旧缓存清理和更新生效时机。

### 3. 同构代码要识别运行边界

SPA 代码主要运行在浏览器；SSR、构建脚本和 Serverless 函数可能运行在 Node.js 或边缘运行时。服务端阶段直接访问浏览器全局对象会失败，因此环境判断和模块边界应在架构阶段设计。

### 4. 包管理器不只是安装命令

| 关注点 | 需要理解的影响 |
| --- | --- |
| 依赖提升 | 是否可能引用未声明的依赖 |
| 链接与内容寻址 | 是否减少重复文件和磁盘占用 |
| 锁文件 | 团队与 CI 能否得到一致依赖 |
| workspace | 多包项目能否统一管理和联调 |
| 部署平台 | 构建产物是否能正确收集真实依赖 |

### 5. 框架选型是一项组织决策

选型至少比较：

- 是否满足渲染模式、性能和交互需求。
- 团队是否具备维护能力。
- 生态、招聘和第三方库是否成熟。
- 升级、迁移和长期维护成本是否可接受。
- 出现问题时是否有明确的诊断与替代方案。
