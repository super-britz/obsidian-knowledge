# 18 前端架构设计指南⑦

> [!abstract] 核心问题
> 如何通过 Harness Design 让 Agent 在长时间开发中保持方向、验证结果并从中断处恢复？

## 本节结论

- 长任务失败往往来自上下文污染、目标漂移和缺少独立验证，而不只是模型能力不足。
- Planner、Implementer 和 Validator 分离，可以让规划、执行和验收使用不同关注点。
- Requirements、Design、Tasks 和测试报告是跨会话持久记忆，重开上下文后应从这些事实恢复。
- 实现中的新约束和踩坑必须写回设计，否则下一次执行仍会重复犯错。
- AI 自测只是第一层证据，独立验证和人工验收仍不可缺少。

## 知识框架

### 1. Harness 管理模型的工作环境

Harness 包括任务结构、上下文加载、工具权限、验证器、状态记录和人工确认。目标不是让一次回答无限延长，而是让系统可以反复计划、执行、检查和恢复。

### 2. 三个角色分工

| 角色 | 主要责任 |
| --- | --- |
| Planner | 理解需求、形成设计、拆分任务和定义验收 |
| Implementer | 在限定范围内完成任务并提供实现说明 |
| Validator | 独立运行检查，判断结果是否满足规格 |

角色可以由不同 Agent、不同会话或同一工具的不同阶段承担，关键是上下文和职责要分离。

### 3. 长任务的状态机

```text
待规划
  -> 待实现
  -> 待验证
  -> 验证失败 -> 待修复 -> 待验证
  -> 验证通过 -> 待人工确认
  -> 完成
```

每次转换都应留下产物和原因，避免只记录“正在处理”。

### 4. 上下文重置后从文件恢复

新的会话按顺序读取：

1. 仓库规则和架构。
2. 当前 Requirements 与 Design。
3. Tasks 的完成状态。
4. 最近的 Review 和测试报告。
5. 当前阻塞与下一步。

这比把全部历史对话重新塞回上下文更稳定。

### 5. 验证结果要反哺设计

如果实现暴露了新的接口限制、数据约束或环境差异，应先更新 Design，再修复代码和测试。文档不是开发前的一次性产物，而是系统当前理解。

## 实践任务

**建议产出：**

- 用三角色流程完成一个注册登录或同等规模的前端功能。

**完成标准：**

- [ ] Planner 给出规格、设计、任务和验收。
- [ ] Implementer 只修改分配范围并提交说明。
- [ ] Validator 独立执行类型、测试和浏览器验证。
- [ ] 重开会话后可根据文档准确继续。
