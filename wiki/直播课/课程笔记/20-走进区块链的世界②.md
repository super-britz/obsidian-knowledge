# 20 走进区块链的世界②

> [!abstract] 核心问题
> Web3 前端如何从行业概念进入钱包连接、链上读取和测试交易？

## 本节结论

- Web3 产品必须先识别所在网络、资产类型和业务赛道，再选择前端交互方案。
- L1 负责基础共识和结算，L2 通常通过在上层执行或批处理来扩展吞吐。
- NFT、DePIN 和 RWA 代表不同资产与业务模型，不能只用“发 Token”概括。
- 钱包连接的本质是请求账户访问和签名授权，不是读取用户私钥。
- 开发应使用隔离测试钱包与测试网，并通过库封装网络、账户、读取和交易状态。

## 知识框架

### 1. 先判断产品属于哪类业务

| 方向 | 关注对象 |
| --- | --- |
| L1 / L2 | 网络、执行、结算和跨层消息 |
| NFT | 唯一 Token 的所有权与元数据 |
| DePIN | 物理资源供给、证明与链上激励 |
| RWA | 现实资产映射、托管和合规 |
| GameFi / 市场类产品 | 游戏状态、资产和经济规则 |

技术设计必须匹配实际业务与合规边界。

### 2. 钱包是签名与账户提供者

```text
DApp
  -> 请求连接钱包
  -> 用户选择账户
  -> 读取公开链上数据
  -> 构造交易或消息
  -> 用户确认签名
  -> 广播并等待确认
```

DApp 不应索取助记词或私钥。

### 3. Provider 与 Signer 分工

- Provider 负责连接 RPC 节点和读取链上状态。
- Signer 代表账户签名消息或交易。
- Contract Client 使用 ABI、地址、网络和调用者完成合约交互。

### 4. 前端库按层次选择

ethers、viem 等提供底层 RPC、编码和交易能力；wagmi 等在 React 中进一步管理钱包连接、查询缓存和 Hooks；钱包连接 UI 可以再由专用组件层处理。

### 5. 交易是异步状态机

前端至少处理：未连接、网络错误、等待签名、用户拒绝、已广播、等待确认、成功、链上回滚和超时查询。

## 实践任务

**建议产出：**

- 一个只在测试网运行的钱包连接与转账页面。

**完成标准：**

- [ ] 使用独立测试钱包，不接触真实资产。
- [ ] 显示账户、网络和测试币余额。
- [ ] 正确处理用户拒签、网络不匹配和交易失败。
- [ ] 保存交易哈希并能在浏览器中查询。
