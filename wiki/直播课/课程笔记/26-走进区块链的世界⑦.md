# 26 走进区块链的世界⑦

> [!abstract] 核心问题
> 如何把商品购买需求组织成可由开发者与 AI 协作交付的 Web3 工程？

## 本节结论

- Hardhat 将 Solidity 源码、编译、测试、部署和网络配置组织成可重复执行的工程。
- 前端与合约应共享明确的网络、地址和 ABI 契约，但各自保留独立的构建与测试边界。
- 私钥、RPC 凭证和部署配置不能写入代码或交给不受控的自动化流程。
- 合约应从 `msg.sender` 等链上上下文识别调用者，不能信任前端传入的购买者地址。
- AI 需要同时理解需求、目录职责、测试标准和安全规则，才能在多模块项目中稳定工作。

## 知识框架

### 1. 合约工程不是单个 Solidity 文件

```text
contracts/   业务合约与接口
test/        行为和异常路径测试
scripts/     部署与管理脚本
config       编译器、网络和插件
artifacts/   ABI、Bytecode 等生成物
```

初始化脚手架后，应先理解示例代码的作用，再决定保留或删除。

### 2. 前端与合约通过部署产物连接

```text
Solidity 源码
  -> 编译与测试
  -> 部署到指定网络
  -> 记录 chainId、address、ABI
  -> 前端构造合约客户端
```

地址或 ABI 更新后，前端配置必须同步，不能依赖手工记忆。

### 3. 配置分为可公开与敏感两类

| 配置 | 处理方式 |
| --- | --- |
| Chain ID、合约地址、公开 ABI | 可以版本化管理 |
| 私钥、助记词、付费 RPC 凭证 | 使用环境变量或密钥系统 |
| 测试账户 | 仅用于隔离环境，不复用于真实资产 |

`.env` 只是本地载体，不代表已经具备生产级安全性。

### 4. 合约必须守住信任边界

错误设计：

```text
buy(productId, buyerAddress)
```

若合约直接相信 `buyerAddress`，调用者可能伪造其他用户。购买者、付款者或权限主体应尽量由交易上下文推导，并对必须传入的数据独立校验。

### 5. 给 AI 的上下文要覆盖交付闭环

- 产品需求：商品、价格、支付和购买记录。
- 模块边界：前端、合约、部署脚本与测试各自负责什么。
- 技术约束：网络、依赖、编码规范和目录规则。
- 验收标准：正常路径、异常路径与安全检查。
- 权限规则：哪些操作只能建议，哪些允许自动执行。

## 实践任务

**建议产出：**

- 建立 Web3 Shop 的前端与 Hardhat 合约工作区。

**完成标准：**

- [ ] 合约可以本地编译、部署和重复测试。
- [ ] 前端按网络读取正确地址与 ABI。
- [ ] 敏感配置没有进入仓库。
- [ ] 购买者由可信交易上下文确定。
- [ ] AI 项目规则包含目录职责、测试和安全要求。

- [ ] 哪些部署信息可以公开，哪些必须保密？
- [ ] 为什么不能信任前端传入的购买者地址？
