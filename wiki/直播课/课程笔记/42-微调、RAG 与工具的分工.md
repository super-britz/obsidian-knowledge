# 42 微调、RAG 与工具的分工

> [!abstract] 核心问题
> Prompt、微调、RAG、API 和 Agent 分别应该解决智能客服中的哪类问题？

## 本节结论

- Prompt 定义当前任务与边界，微调稳定回答行为，RAG 提供可更新资料，API 提供实时业务事实。
- RAG 不会把文档写进模型参数，而是在生成前检索相关片段并加入上下文。
- RAG 效果取决于解析、分块、Embedding、召回、重排和引用，不只是向量数据库选型。
- 客服中的订单、物流、退款和库存必须通过业务接口查询，不能由模型或知识库猜测。
- 应先用小规模样本和离线评估验证方案，再扩大数据与训练投入。

## 知识框架

### 1. 五类能力各自负责什么

| 能力 | 主要职责 |
| --- | --- |
| Prompt | 角色、任务、格式与边界 |
| 微调 | 稳定语气、格式、分类与流程行为 |
| RAG | 产品文档、政策、FAQ 等可更新知识 |
| API / Tool | 订单、物流、库存等实时事实 |
| Agent / Workflow | 选择步骤、调用工具和管理状态 |

把所有问题交给微调会导致事实过期、成本高和难以审计。

### 2. RAG 的索引链路

```text
原始文档
  -> 解析与清洗
  -> Chunking
  -> Embedding
  -> 向量或混合索引
  -> 保存元数据与来源
```

分块应保留语义完整性、标题层级和来源定位。

### 3. RAG 的查询链路

```text
用户问题
  -> 查询改写
  -> 召回候选片段
  -> 过滤与 Rerank
  -> 构造上下文
  -> 模型回答
  -> 返回引用
```

没有召回到证据时，系统应说明不知道或转人工，而不是补写答案。

### 4. 评估应拆开检索与生成

- 检索评估：正确证据是否被召回、排序是否靠前。
- 生成评估：回答是否忠于证据、完整且符合格式。
- 系统评估：延迟、成本、权限、拒答和转人工是否正确。

只看最终回答，无法判断问题来自检索还是模型。

### 5. 客服系统的事实分层

```text
稳定公开知识 -> RAG
实时用户数据 -> 业务 API
表达风格与流程 -> Prompt / 微调
高风险与异常 -> 人工客服
```

身份校验应在调用敏感业务接口前完成，模型不能自行决定跳过。

### 6. 先做小实验再扩展

少量高质量样本用于验证数据格式、训练链路和指标；小型知识库用于验证解析、召回与引用。只有确认瓶颈后，才增加数据量、模型规模或复杂编排。

## 实践任务

**建议产出：**

- 搭建一个带来源引用和实时查询 Mock 的客服原型。

**完成标准：**

- [ ] 文档问答能返回可定位来源。
- [ ] 实时问题只能通过 Tool 获取结果。
- [ ] 缺少证据时拒绝猜测并提供转人工入口。
- [ ] 分别评估检索、生成和完整流程。
