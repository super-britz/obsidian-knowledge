# 08 前端架构设计指南③

> [!abstract] 核心问题
> 如何把 AI 生成或从设计稿还原的页面，纳入可复用、可测试、可维护的前端工程？

## 本节结论

- 现代 CSS 选型应以标准能力和浏览器支持为依据，不应停留在“CSS3”这一笼统标签。
- AI 还原设计稿前要先拆页面结构、设计令牌、公共组件和素材，不能把整张图当成唯一规格。
- Monorepo 的价值是统一管理相互关联的应用与包，不是简单地把多个项目放进同一目录。
- `pnpm workspace` 可以支持本地包联调，但包边界、依赖方向和发布方式仍需明确设计。
- AI 生成页面的验收对象不仅是视觉效果，还包括组件复用、资源归档、测试和构建产物。

## 知识框架

### 1. 现代 CSS 先看能力与兼容性

课程涉及嵌套、容器查询、过渡动画和原子化样式等方向。落地时应依次确认：

1. 需求是否真的需要该能力。
2. 目标浏览器是否支持。
3. 是否需要 PostCSS 等编译方案。
4. 不支持时如何降级。

### 2. Tailwind CSS 是样式组织方案

原子类可以减少重复声明，并让样式与组件结构一起演化，但仍需管理：

- 颜色、字号、间距等设计令牌。
- 长类名的可读性。
- 动态类名能否被构建工具识别。
- 公共组件与页面临时样式的边界。

### 3. 设计稿还原先结构化，再生成代码

```text
设计稿
  -> 页面区域与布局
  -> 设计令牌
  -> 公共组件与业务组件
  -> 图片、图标、字体等素材
  -> 页面实现
  -> 视觉与交互验收
```

Figma 或 AI 工具提供的是上下文和初稿，最终代码仍需符合项目目录、组件 API 和响应式规则。

### 4. Monorepo 用包边界管理复用

```text
apps/
  web/
  api/
packages/
  ui/
  hooks/
  config/
  infra/
```

应用负责交付，包负责稳定能力。共享包不应反向依赖具体业务应用，否则复用只是目录层面的假象。

### 5. 工程验收覆盖完整链路

除页面外观，还要检查：

- 图片和字体是否使用真实项目资源。
- 组件是否重复创建。
- 状态、样式与业务逻辑是否放在合适层次。
- 单元测试和端到端测试是否覆盖关键行为。
- 构建、拆包、压缩和部署能否正常工作。

## 实践任务

**建议产出：**

- 把一个 AI 生成页面整理进包含 `apps` 与 `packages` 的小型 Monorepo。

**完成标准：**

- [ ] 提取设计令牌、公共组件和素材目录。
- [ ] Web 应用通过 workspace 引用 UI 包。
- [ ] 页面通过桌面与移动视口验收。
- [ ] 关键交互至少有一种自动化测试。
