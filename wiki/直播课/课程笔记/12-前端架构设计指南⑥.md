# 12 前端架构设计指南⑥

> [!abstract] 核心问题
> AI 可以快速生成 React 状态与 Hooks 代码后，人还必须掌握哪些设计和评审能力？

## 本节结论

- 状态管理应根据状态归属、更新频率、共享范围和业务复杂度选型。
- 不可变更新让状态变化更容易追踪，Immer 只是降低写法成本，不替代状态设计。
- 共享 Hooks 包要提供稳定 API 和测试，不能只是把零散函数移动到 `packages`。
- AI 生成的 Hooks 必须检查闭包、依赖数组、返回类型、渲染次数和卸载行为。
- AI 可以参与 Review，但合并与发布权限应由人和团队流程控制。

## 知识框架

### 1. 先判断状态属于哪里

| 状态类型 | 常见位置 |
| --- | --- |
| 仅影响单个组件 | `useState`、`useReducer` |
| 一棵子树共享 | Context 或组合组件 |
| 跨页面客户端状态 | 外部状态库 |
| 服务端数据 | 查询缓存与服务端状态工具 |
| 显式流程与转换 | 状态机 |

不要因为项目安装了某个库，就把所有状态都放进去。

### 2. 不可变更新强调可追踪变化

直接修改旧对象可能让引用比较、撤销、日志和调试变得困难。Immer 允许通过 `draft` 写出接近可变操作的代码，再生成新的不可变结果。

需要注意：Immer 不能自动修复错误的数据模型，也不能减少本来就不必要的全局状态。

### 3. 状态一致性依赖读取与订阅方式

当同一渲染过程读取到不同版本的外部状态时，界面可能出现不一致。外部状态库需要提供与 React 并发渲染兼容的订阅和快照机制。

### 4. 共享 Hooks 是产品化的内部 API

一个可复用 Hook 应明确：

- 输入、返回值和泛型类型。
- 副作用何时发生和清理。
- 同步与异步错误如何暴露。
- 是否造成不必要的重新渲染。
- 在浏览器、SSR 和测试环境中的行为。

在 Monorepo 中，它还需要独立包边界、版本策略和调用示例。

### 5. AI Code Review 检查责任边界

```text
AI 生成或修改
  -> 自动测试与静态检查
  -> AI 辅助 Review
  -> 人工检查业务与架构
  -> 人工批准合并
```

高风险区域包括权限、支付、状态一致性、数据删除、云资源和部署脚本。

## 实践任务

**建议产出：**

- 在 Monorepo 中实现并评审一个可复用 React Hook。

**完成标准：**

- [ ] 能说明为什么选择当前状态方案。
- [ ] Hook 的类型、清理、错误和渲染行为有测试。
- [ ] Web 应用通过 workspace 使用该包。
- [ ] 评审记录说明 AI 代码被修改或拒绝的原因。

## 复习检查

- [ ] 组件状态、客户端全局状态和服务端状态有何区别？
- [ ] Immer 解决的是哪一层问题？
- [ ] Review 一个自定义 Hook 时要检查什么？
