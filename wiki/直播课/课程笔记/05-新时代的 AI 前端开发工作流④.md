# 05 新时代的 AI 前端开发工作流④

> [!abstract] 核心问题
> AI 生成的前端应用怎样进入真实的接口、云服务和部署架构？

## 本节结论

- 前端交付闭环最终必须落到运行架构：入口、计算、数据、缓存、队列、存储和观测。
- Cloudflare 更适合作为靠近用户的入口与边缘层，AWS 提供更完整的后端与数据服务；两者可以组合而非二选一。
- Serverless 的核心是按事件使用托管计算资源，同时接受无状态、冷启动、权限和平台约束。
- REST、GraphQL、tRPC 等接口方案应根据边界、团队和客户端类型选择，不存在脱离场景的唯一答案。
- MCP 负责连接模型与外部能力，但生产系统仍需要权限控制、日志、验证和回滚。

## 知识框架

### 1. 从页面扩展到完整系统

```text
用户
  -> DNS / CDN / WAF / Edge
  -> Web 应用或 API Gateway
  -> Serverless Function / Node 服务
  -> 数据库 / 缓存 / 队列 / 对象存储
  -> 日志、监控与告警
```

AI 可以帮助生成每一层的代码和配置，但架构决策仍要回答延迟、成本、安全、状态和故障恢复。

### 2. Cloudflare 与 AWS 的职责可以分层

| 层 | 常见职责 |
| --- | --- |
| Cloudflare | DNS、CDN、WAF、边缘函数、静态资源、靠近用户的请求处理 |
| AWS | Lambda、API Gateway、数据库、对象存储、队列、私有网络、权限与观测 |

组合架构的价值是让入口更轻、更近，让核心数据和复杂后端能力留在完整云平台中。代价是系统复杂度、跨云观测和权限管理增加。

### 3. Serverless 的收益与约束必须一起考虑

收益：

- 按使用量付费。
- 自动扩缩容。
- 减少服务器维护。
- 适合事件驱动和波动流量。

约束：

- 冷启动与执行时限。
- 本地状态不可靠。
- 运行时和区域受平台限制。
- 权限、日志和成本可能分散在多个服务。

### 4. 接口方案的选型维度

| 方案 | 优势 | 更适合 |
| --- | --- | --- |
| REST | 边界清晰、生态成熟、客户端通用 | 公共 API、多语言系统 |
| GraphQL | 客户端按需取数、统一查询入口 | 数据关系复杂、多端差异明显 |
| tRPC | TypeScript 端到端类型推导、开发效率高 | 同团队、同仓库、TS 全栈应用 |

选型时要考虑缓存、错误模型、版本、网关、外部消费者和团队能力。

### 5. AI 工具连接不能绕过工程控制

无论通过 MCP、CLI 还是云 API 操作资源，都需要：

- 最小权限凭证。
- 开发、测试和生产隔离。
- 对删除、发布和费用变更设置确认。
- 记录谁在何时执行了什么。
- 能够回滚错误修改。
