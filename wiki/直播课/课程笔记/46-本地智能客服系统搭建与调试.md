# 46 本地智能客服系统搭建与调试

> [!abstract] 核心问题
> 如何把本地 QLoRA 模型接入智能客服系统，并正确划分模型、知识库、业务工具与 Agent 编排的职责？

## 本节结论

- 本地智能客服适合拆成模型服务、业务 API、Agent / Workflow 三层，每层都应能独立启动和验证。
- QLoRA 主要训练客服语气、回复格式和稳定行为；产品文档交给 RAG，订单与物流等实时事实交给 Tool / API。
- 模型会生成客服式回答，不代表它会输出符合协议的 Tool Calling；两种能力必须分开评估。
- 正则或关键词硬编码可以验证工具链路，但不能证明模型具备工具选择和参数生成能力。
- 工具调用能力不足时，可以选择原生支持 Tool Calling 的模型、结构化适配层，或确定性 Workflow / Router。
- 客服系统必须处理身份验证、业务边界、拒答、失败回退和人工转接，不能只验证一条成功对话。

## 知识框架

### 1. 系统按职责拆成三层

```text
用户请求
  -> Agent / Workflow：识别任务、选择工具、控制流程
  -> 业务 API：查询订单、物流、退款、库存等实时事实
  -> 本地模型服务：理解上下文并生成最终客服回复
```

**模型服务层**

- 加载基座模型、Tokenizer 与 LoRA Adapter。
- 通过 FastAPI 等方式提供 HTTP 推理接口。
- 可以采用 OpenAI-compatible API 形态，降低上层框架接入成本。
- 只负责模型推理，不直接承担业务权限和流程控制。

**业务 API 层**

- 提供订单、物流、退款、库存和人工工单等能力。
- 返回结构化、可审计的业务事实。
- 负责身份校验、权限限制、错误码和数据脱敏。

**Agent / Workflow 层**

- 注册工具并决定何时调用。
- 收集和校验工具参数。
- 把工具结果交给模型组织最终回复。
- 处理超时、重试、越界问题、失败回退和人工转接。

### 2. QLoRA、RAG、Tool 与 Prompt 的职责边界

| 机制 | 适合负责 | 不适合负责 |
| --- | --- | --- |
| QLoRA | 客服语气、回复格式、稳定行为、拒答倾向 | 持续变化的产品知识和订单事实 |
| RAG | FAQ、产品说明、安装教程、售后政策 | 需要实时查询或权限控制的数据 |
| Tool / API | 订单、物流、库存、退款状态等实时事实 | 自然语言表达和安抚语气 |
| Prompt / Workflow | 角色边界、流程约束、工具规则、转人工条件 | 替代可靠的数据源或权限系统 |

判断标准是信息如何变化：

- 希望长期稳定地改变模型行为，考虑微调。
- 内容来自文档且会更新，考虑 RAG。
- 数据实时变化或需要权限，使用 Tool / API。
- 需要约束当前任务的流程和边界，使用 Prompt 与 Workflow。

### 3. Tool Calling 的标准链路

```text
用户提出业务问题
  -> 模型或路由器选择工具
  -> 生成结构化参数
  -> Agent 校验参数并执行工具
  -> 业务 API 返回结果
  -> 模型依据结果生成回复
```

模型并不直接访问订单系统。它输出工具名称与参数，由 Agent 执行工具，再将执行结果作为新的上下文交给模型。

因此至少要分别验证：

- 是否选择了正确工具。
- 是否提取了完整、合法的参数。
- 是否真正执行了业务 API。
- 最终回复是否忠实于工具结果。

### 4. 会回复不等于会调用工具

只训练客服问答数据，模型可能学会说“我帮您查询”，却没有输出结构化工具调用。这类回答在语言上像客服，在系统行为上却没有查询任何事实。

如果服务端通过正则识别订单号并直接返回工具调用，可以快速确认以下链路是否可用：

- Agent 能否接收工具调用。
- Tool 能否访问业务 API。
- 工具结果能否返回给模型。

但工具选择是程序规则完成的，不是模型根据上下文做出的决定。它只能作为链路测试或确定性路由方案，不能被描述为模型已经掌握 Tool Calling。

### 5. Tool Calling 的三种实现路线

**路线一：模型原生支持 Tool Calling**

让模型读取工具定义并输出标准化调用请求。系统结构直接，但仍要测试模型是否能稳定选择工具和生成参数。

**路线二：增加结构化适配层**

让模型输出受约束的 JSON 或任务分类，再由适配层转换为框架需要的工具调用格式。它适合模型协议不兼容、但结构化输出尚可控制的情况。

**路线三：确定性 Workflow / Router**

对订单号校验、身份验证、转人工等高确定性流程，用状态机、规则或分类器显式路由。模型只负责理解输入和组织回复。

实际系统可以混合使用：开放问题交给模型，高风险和强流程业务交给 Workflow。

### 6. 客服边界与人工转接

客服 Agent 应明确区分：

- 业务范围内且信息完整：调用工具或检索知识库。
- 业务范围内但信息不足：追问必要字段。
- 非业务问题：简短拒答并引导回客服范围。
- 身份无法验证或工具失败：停止披露业务信息。
- 用户明确要求人工、连续失败或问题高风险：进入人工转接。

人工转接不是失败兜底文案，而是完整业务能力。系统需要生成工单，保留必要上下文，并让用户知道当前状态。

### 7. 按层调试，而不是一次启动全部系统

推荐顺序：

1. 验证本地模型能加载基座模型与 Adapter，并完成一次稳定推理。
2. 验证模型 HTTP 接口的请求格式、超时、流式返回和错误处理。
3. 独立验证每个业务 API 的输入、权限和响应。
4. 使用固定参数直接调用 Tool，确认 Agent 与业务 API 的连接。
5. 验证工具选择、参数提取和工具结果回传。
6. 最后测试完整多轮对话、越界问题、失败流程和人工转接。

这种顺序能把模型加载、端口配置、协议兼容、工具执行和对话逻辑的问题分开定位。

### 8. 建立端到端评估集

评估集至少覆盖：

- 正确选择订单、物流、退款或库存工具。
- 缺少订单号或身份信息时先追问。
- 参数错误时不调用工具或请求修正。
- 工具超时、无结果和异常时不编造。
- RAG 回答能够引用检索到的文档事实。
- 非业务问题能够稳定拒答。
- 用户要求人工时能够进入转接流程。
- 最终回复与工具结果一致，不泄露敏感数据。

客服语气只是其中一个指标，还应记录工具选择准确率、参数正确率、任务完成率、事实忠实度、拒答准确率和人工转接成功率。

## 实践任务

**建议产出：**

- 搭建一个可独立调试的本地客服最小系统，包含模型 HTTP 服务、模拟业务 API 和 Agent / Workflow。

**完成标准：**

- [ ] 三层服务可以分别启动、测试和查看日志。
- [ ] 至少一个订单或物流工具完成真实的结构化调用闭环。
- [ ] 能证明工具调用来自模型、适配层或确定性路由中的哪一层。
- [ ] 模型不会把未执行的查询描述成已完成。
- [ ] 覆盖缺少参数、工具失败、越界问题和人工转接测试。
- [ ] 日志不记录完整手机号、订单凭证等敏感信息。

## 复习检查

- [ ] 为什么微调模型会说“正在查询”，却不代表系统真的查询了订单？
- [ ] QLoRA、RAG、Tool 和 Workflow 分别应保存或控制什么？
- [ ] 正则路由在什么情况下是合理方案，为什么它不等于模型 Tool Calling？
- [ ] 调试完整客服系统时，为什么要先分层验证？
