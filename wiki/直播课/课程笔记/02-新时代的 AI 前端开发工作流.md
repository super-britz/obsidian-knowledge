# 02 新时代的 AI 前端开发工作流

> [!abstract] 核心问题
> 怎样让 AI 参与完整的前端交付，而不是只生成一段代码或一张页面？

## 本节结论

- 一个可复现的 AI 前端工作流应覆盖想法、需求、设计、实现、验证、测试和部署。
- PRD 是产品意图与自动化验收之间的桥梁；需求不清，后续生成再快也会偏航。
- Figma、代码工具和浏览器工具分别负责设计表达、工程实现和运行验证，不能互相替代。
- MCP 的价值是为模型提供受控的上下文与工具入口，而不是安装得越多越好。
- 交付物必须包含运行结果和验收证据，截图相似不等于功能完成。

## 知识框架

### 1. AI 前端交付闭环

```text
产品想法
  -> PRD / 用户流程 / 验收标准
  -> Figma 或参考界面
  -> 项目约束与任务拆解
  -> 生成和修改代码
  -> 浏览器中运行、调试和比对
  -> E2E / UI 测试
  -> 部署与复盘
```

闭环的关键不是每一步都由同一个 AI 完成，而是每一步都有明确输入、输出和验证方式。

### 2. PRD 决定“做什么”和“怎样算完成”

一份可执行的 PRD 至少要描述：

- 用户是谁，要解决什么问题。
- 页面与功能有哪些。
- 用户如何在页面之间流转。
- 关键状态、异常和权限边界。
- 每个功能的验收条件。

自动化测试可以从这些验收条件生成操作路径和断言。没有验收标准时，AI 往往只完成“看起来像”的部分。

### 3. 设计稿和代码是两种不同表达

Figma 负责视觉结构、组件、间距、状态和协作；代码还要处理数据、路由、交互、错误和响应式。

从设计到代码时要重点核对：

- 页面层级和组件边界。
- 字体、颜色、间距和响应式规则。
- loading、empty、error、disabled 等状态。
- 交互是否与需求一致。
- 生成结果是否符合项目已有技术约束。

### 4. 浏览器是最终事实来源

代码编译成功只说明语法和构建链路基本通过。真正的验证发生在运行环境：

- 页面是否能打开。
- 交互是否可用。
- 控制台和网络请求是否报错。
- 不同尺寸下是否正确。
- 实际结果是否满足 PRD 和设计稿。

### 5. MCP 应按任务和权限选择

选择 MCP 或其他工具连接时，应先问：

1. 它提供了什么必要上下文或操作能力？
2. 当前任务是否真的需要？
3. 它能读取哪些数据、执行哪些操作？
4. 出错后怎样撤销、审计和隔离？

## 实践任务

**建议产出：**

- 用一个小型 Web 产品走完“PRD -> 设计 -> 代码 -> 浏览器验证 -> 测试 -> 部署”。

**完成标准：**

- [ ] PRD 包含用户流程和可测试的验收标准。
- [ ] 设计与代码的主要差异有记录和修正。
- [ ] 至少有一条自动化测试或结构化验收记录。
- [ ] 能解释每个 AI 工具在流程中的职责。

## 复习检查

- [ ] 为什么 PRD 能提高代码生成和自动化测试质量？
- [ ] 为什么 Figma 转代码不能代替工程设计？
- [ ] 编译通过、页面相似和真正交付分别差在哪里？
