# 13 企业 AIGC 工程提效第二季

> [!abstract] 核心问题
> 如何把零散的 AI 编程工具组织成可触发、可观察、可评审、可恢复的企业研发流程？

## 本节结论

- 企业提效的单位不是一次对话，而是从需求到验证的完整工作流。
- 长任务必须主动管理上下文，把稳定约束写入项目文件，把临时过程留在任务记录中。
- 浏览器、桌面和远程入口只是执行通道，权限、登录态和失败恢复决定它们能否进入真实流程。
- 需求、设计、实现和评审可以由不同角色或模型承担，降低单一上下文自我确认的风险。
- 合并、部署、资金和数据删除等高风险节点必须保留人工审批。

## 知识框架

### 1. 从工具调用升级为工作流

```text
需求输入
  -> 澄清与规格
  -> 技术设计
  -> 任务拆分
  -> 实现
  -> Review 与修复
  -> 自动化验证
  -> 人工批准
  -> 合并或部署
```

每个节点都应有明确输入、输出、失败状态和责任人。

### 2. 上下文按寿命分层

| 上下文 | 适合保存的内容 |
| --- | --- |
| 仓库级 | 架构、命令、规范、安全边界 |
| 功能级 | Requirements、Design、验收条件 |
| 任务级 | 当前步骤、Todo、测试结果和阻塞 |
| 会话级 | 临时推理、工具输出和中间讨论 |

会话过长时可以压缩或重开，但必须从持久文件恢复事实与进度。

### 3. 外部系统通过受控工具接入

浏览器协议、MCP、CLI 或桌面控制都可以让 Agent 执行外部动作。接入时要限制：

- 可访问的站点、应用和目录。
- 能否使用真实登录态。
- 哪些动作必须确认。
- 超时、中断和重试方式。
- 操作日志与审计记录。

### 4. 生成者与评审者分离

同一个 Agent 容易沿用自己的错误假设。让独立角色评审 Requirements、Design 或代码，可以从另一套检查清单重新审视边界，但评审结果仍需测试和人工判断。

### 5. 自动化程度由风险决定

低风险读取、分析和测试可以高度自动化；写代码、创建分支可自动但应可回滚；合并、发布、生产数据操作和费用变更需要明确审批。

## 实践任务

**建议产出：**

- 一条从需求输入到浏览器验证的最小 AI 研发工作流。

**完成标准：**

- [ ] 每个阶段有持久化输入与输出。
- [ ] 实现者和评审者使用不同上下文或角色。
- [ ] 浏览器验证留下报告或截图。
- [ ] 高风险动作有人工确认点和审计记录。

## 复习检查

- [ ] 为什么“能远程控制电脑”不等于企业工作流已经成立？
- [ ] 哪些上下文应写入仓库，哪些只属于当前任务？
- [ ] 哪些动作可以自动化，哪些必须审批？
