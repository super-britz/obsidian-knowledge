# 36 Serverless 增强课（终）

> [!abstract] 核心问题
> Cloudflare 边缘平台与 AWS Serverless 生态应如何选型、部署和验证？

## 本节结论

- Cloudflare 与 AWS 都能承载 Serverless 应用，但运行时、服务组合和组织集成方式不同。
- 边缘运行时强调靠近用户与 Web 标准 API，AWS Lambda 更容易与完整云服务生态组合。
- SSR Streaming 是否有效取决于渲染接口、运行时、网关和客户端整条链路。
- 冷启动应拆成运行环境、代码加载、依赖初始化和业务执行分析，不能只比较平台名称。
- 部署完成后还要验证环境变量、日志、指标、Trace、费用和回滚，才算交付完成。

## 知识框架

### 1. 两类平台的能力组合

| 方向 | Cloudflare 侧 | AWS 侧 |
| --- | --- | --- |
| 入口与防护 | CDN、WAF、边缘网络 | CloudFront、WAF、API Gateway、ALB |
| 计算 | Workers | Lambda |
| 存储与数据 | R2、D1、KV 等 | S3、数据库、缓存等 |
| 异步与事件 | 平台队列与事件能力 | SQS、事件服务、流服务等 |
| 观测 | 日志、指标与平台分析 | CloudWatch 等服务 |

具体能力和限制具有时效性，项目应以实际验证为准。

### 2. 选型看约束，不看口号

Cloudflare 更适合评估：

- Web 标准 API 是否足够。
- 边缘延迟是否是核心收益。
- 应用是否轻量、无复杂原生依赖。

AWS 更适合评估：

- 公司是否已有 AWS 网络、权限和数据服务。
- 是否需要复杂事件、队列和企业系统集成。
- 团队是否具备云资源治理与运维能力。

### 3. Streaming 是端到端能力

```text
React / 框架产生 Stream
  -> 运行时持续输出
  -> 网关不缓冲
  -> CDN 正确转发
  -> 浏览器逐步解析
```

任何一层缓冲或不支持持续响应，都会让 Streaming 退化成完整响应后一次返回。

### 4. 冷启动需要拆分测量

```text
调度执行环境
  -> 初始化运行时
  -> 加载代码和依赖
  -> 创建连接与全局对象
  -> 执行业务函数
```

减少依赖、延迟初始化、复用连接与控制包体积，往往比抽象比较平台更有价值。

### 5. 框架适配取决于运行时

Hono 等面向 Web 标准的框架更容易适配边缘运行时；依赖 Node.js 特定 API 的框架可能需要兼容层。采用适配器前要验证请求、响应、中间件、流式输出和第三方依赖。

### 6. 部署必须可追踪和可回退

- 环境与账号隔离。
- 敏感变量安全注入。
- 部署版本和变更记录。
- 实时日志、指标与 Trace。
- 费用预算与异常告警。
- 灰度、回滚与配置恢复。

控制台临时修改也应进入配置治理，避免下一次部署覆盖。

**完成标准：**
