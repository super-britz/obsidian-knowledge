# 48 AI 开发面试与工程经验

> [!abstract] 核心问题
> 如何把本地模型、RAG、Agent 和智能客服项目中的真实实践，整理成可信的面试回答，并补齐记忆、路由、测试与责任治理等工程能力？

## 本节结论

- AI 面试的区分度来自真实项目证据：能说明问题、方案、取舍、失败和验证，比罗列模型、框架或硬件名称更有说服力。
- 客服记忆应分为当前会话、结构化工作状态和跨会话语义召回三层；不同记忆的内容、存储、过期与隐私规则不能混在一起。
- RAG 调优不能只回答“TopK 设多少”，而要解释分片、查询表达、候选召回、重排、上下文预算和评估集之间的关系。
- Tool Calling 应先处理确定性强或风险高的意图，再使用语义路由覆盖开放表达，并在执行前完成参数、权限和业务状态校验。
- AI 生成代码仍需项目规则、自动化测试、提交前检查、人工 Code Review 和明确责任人，AI 不能承担上线后的业务责任。
- 企业选择 AI 工具时应优先考虑稳定性、安全、数据边界、团队连续性和退出方案，价格或模型榜单不应成为唯一判断标准。

## 知识框架

### 1. 面试回答从项目证据出发

一段可信的项目回答可以按以下顺序组织：

```text
业务问题
  -> 约束与失败风险
  -> 方案选择
  -> 为什么不选其他方案
  -> 实现与调试过程
  -> 测试或指标证据
  -> 当前限制与下一步
```

讲智能客服时，不要只说“使用了 QLoRA、RAG 和 Agent”，而应说明：

- QLoRA 调整了什么稳定行为。
- RAG 保存了哪些文档知识，如何证明召回有效。
- Tool 访问了哪些实时业务事实，如何校验参数和权限。
- Agent / Workflow 如何路由、回退和转人工。
- 遇到过什么错误路由、上下文过长或工具调用失败。
- 用什么日志、测试集或运行结果证明修复有效。

面试不是复述课程结论，而是展示自己能否把技术放进一个受约束的系统里。

### 2. 客服 Memory 的三层结构

| 层级 | 保存内容 | 主要作用 | 主要风险 |
| --- | --- | --- | --- |
| 当前会话记忆 | 最近若干轮消息、当前目标 | 保持本轮对话连续 | 上下文过长、旧信息干扰 |
| 工作记忆 | 订单号、已验证身份、当前处理阶段等结构化状态 | 支撑客服流程与参数补全 | 状态过期、字段冲突、越权复用 |
| 长期语义记忆 | 经过筛选的历史偏好、稳定事实或历史问题摘要 | 跨会话召回相关经历 | 隐私泄露、错误记忆、无限保存 |

本节计划同时实现工作记忆和跨会话语义召回。工程上仍应分别验收三层能力，避免把“同时开发”误解为“无需分层测试”。

#### 当前会话记忆

- 保留有限窗口，而不是无限拼接全部消息。
- 超出窗口时可生成摘要，但要保留关键实体和未完成任务。
- 新消息与旧状态冲突时，应以可验证的最新信息为准。

#### 工作记忆

适合使用结构化状态，例如：

```text
customer_verified: true
order_id: "mock-001"
intent: "refund_status"
workflow_step: "waiting_for_tool"
```

结构化字段更便于校验、更新、过期和审计，不应只依赖自然语言历史。

#### 长期语义记忆

写入前要判断内容是否跨会话有用、是否敏感、来源是否可靠、何时过期，以及用户能否查看、纠正或删除。长期记忆不是把全部聊天记录再做一个向量库，而是有选择地保存必要且有生命周期的数据。

### 3. RAG 面试题要回答完整调优链路

“TopK 设为多少”只是表面问题。更完整的回答应包括：

1. 用评估集确认答案片段是否能被召回。
2. 检查分片是否切断条件、例外或结论。
3. 必要时改写查询或增加意图、品类等过滤条件。
4. 扩大候选召回范围，提高正确片段进入候选集的机会。
5. 使用 Rerank 重新排序，再控制最终送入模型的片段数量。
6. 检查最终回答是否忠实于检索证据，并记录无答案情况。

```text
候选召回数量：为召回率服务
最终上下文数量：为排序质量、噪音和上下文预算服务
```

第 47 节演示了初召回 20 条、重排后保留 4 条；本节继续强调客服场景最终上下文不宜堆入过多片段。面试时应说明这是项目实验结果，而不是通用于所有知识库的固定答案。

### 4. Tool Calling 使用“确定性优先 + 语义补充”

```text
输入请求
  -> 高确定性 / 高风险规则优先判断
  -> 语义路由处理开放表达
  -> 参数与权限校验
  -> 执行 Tool 或进入 RAG
  -> 根据结果更新状态并生成回复
```

适合优先拦截的情况包括用户明确要求人工、涉及退款或身份验证等高风险动作，以及已经包含清晰订单或物流意图的请求。

语义模型适合处理措辞多样、边界不清的普通问题，但执行前仍需校验：

- 工具名称是否在允许列表中。
- 必填参数是否完整且格式正确。
- 当前用户是否有权访问目标数据。
- 当前工作流状态是否允许执行该动作。

确定性规则不是为了替代模型，而是为风险边界和明确业务路径提供可测试的控制点。

### 5. AI 工作流必须保留工程治理

```text
项目规则 / Skills
  -> AI 生成或修改代码
  -> 静态检查与自动化测试
  -> AI Review 辅助发现问题
  -> 人工 Code Review
  -> 合并与发布
```

关键原则：

- 规则应放在项目可版本化的位置，而不是只存在于聊天记录。
- 测试应覆盖模块、接口和关键用户流程，不能只验证“页面能打开”。
- Git Hook 可以阻止明显不合规的提交，但不能代替 CI 和代码评审。
- AI Review 可以扩大检查范围，但核心业务逻辑仍需责任人确认。
- 高权限浏览器、远程控制和生产操作必须使用最小权限，并保留人工确认点。

AI 能完成大量实现工作，不等于可以取消责任归属。上线代码、数据访问和生产变更必须有明确的人类责任主体。

### 6. 把过往经验固化为可复用测试能力

自动化工具本身不是重点，重点是把团队经验转成可重复执行的规则：

- 哪些模块完成后必须执行单元测试。
- 哪些接口需要正常、异常、超时和权限用例。
- 哪些用户流程需要浏览器或 E2E 验证。
- 哪些失败必须阻止合并或触发人工检查。
- 测试失败时需要保存哪些截图、日志和网络请求。

这些规则可以整理成 Skills、测试清单或流水线配置，让 AI 根据固定输入执行，但测试结论仍要有可查看的证据。

### 7. 四类核心面试题的回答骨架

#### 问题一：为什么为较大本地模型选择 QLoRA？

- 目标是调整客服语气、格式或稳定行为，而不是更新实时知识。
- 全量微调资源成本高，普通 LoRA 仍需加载较高精度基座模型。
- QLoRA 通过量化基座模型并训练 Adapter，降低训练显存压力。
- 需要用训练前后评估集证明行为变化，不能只以训练成功作为结论。

#### 问题二：RAG 召回不准如何排查？

- 先区分未召回、排序错误和生成未使用证据三类问题。
- 检查文档质量、分片、元数据、Embedding 和查询表达。
- 使用宽召回加 Rerank，提高候选覆盖并压缩最终上下文。
- 用固定评估集记录召回命中、答案忠实度和延迟变化。

#### 问题三：多轮客服记忆如何设计？

- 当前会话消息用于连续对话。
- 结构化工作记忆保存订单号、验证状态和流程阶段。
- 长期语义记忆只保存经过筛选的跨会话稳定信息。
- 说明更新、冲突、过期、隐私和删除机制。

#### 问题四：多个客服能力如何路由？

- 明确 RAG、业务 Tool、拒答和人工转接的边界。
- 确定性强或高风险意图优先走规则控制。
- 其他问题交给语义路由，并在执行前校验参数与权限。
- 通过混淆意图、缺少参数和工具失败用例验证路由。

### 8. 企业工具选型回答要体现边界感

面试中评价工具不应只按“模型强不强”排序，也不应贬低面试团队正在使用的方案。更专业的评估维度包括：

- 稳定性与服务连续性。
- 数据是否进入第三方系统，是否满足公司安全要求。
- 权限、审计、团队账号和密钥管理能力。
- 与现有 IDE、代码仓库、CI 和知识库的集成成本。
- 供应商退出、服务中断或模型切换时的迁移方案。
- 总成本是否低于节省的人力与故障成本。

平台价格、套餐、返现、账号注册和模型榜单具有强时效性，不作为长期课程结论；实际采用前需要重新核实公司政策和当地合规要求。

### 9. 简历只写能够展示和解释的能力

适合写入简历的是自己确实完成并能展示的内容：

- 可运行的本地模型服务和资源配置记录。
- 有来源、分片、召回、重排和评估的 RAG 系统。
- 有参数校验、失败回退和人工转接的客服 Agent。
- 自动化测试、AI Code Review 与人工评审组成的交付流程。
- 一次真实失败、定位过程、修复证据和限制说明。

不应声称未实际使用的模型规模、硬件吞吐、生产用户量或业务收益。项目表达越具体，越能验证经验真实性。

## 实践任务

**建议产出：**

- 为本地智能客服项目制作一份“项目证据包”，并完成一次围绕 QLoRA、RAG、Memory 和 Tool 路由的模拟面试。

**完成标准：**

- [ ] 有一页系统架构图，能区分模型、RAG、Memory、Tool 与 Workflow。
- [ ] 有一组 RAG 召回与重排对比结果，不只展示成功回答。
- [ ] 有三层 Memory 的字段、生命周期、隐私与冲突处理说明。
- [ ] 有路由、缺少参数、越权、工具失败和人工转接测试。
- [ ] 四道核心问题都能在两分钟内说明问题、方案、取舍和证据。
- [ ] 简历中的每项技术都能对应到代码、日志、测试或演示结果。

## 复习检查

- [ ] 为什么只保存最近若干条消息不足以构成完整的客服 Memory？
- [ ] 如何区分 RAG 的召回问题、排序问题和生成忠实度问题？
- [ ] 为什么确定性规则与语义路由应该组合，而不是二选一？
- [ ] Git Hook、AI Review、自动化测试和人工 Code Review 分别解决什么问题？
- [ ] 如何把一个项目回答从“技术名词列表”改造成可验证的工程叙述？
