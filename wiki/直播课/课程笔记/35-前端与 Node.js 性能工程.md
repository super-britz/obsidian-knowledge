# 35 前端与 Node.js 性能工程

> [!abstract] 核心问题
> 如何从架构、网络、渲染、监控和运行时建立可验证的性能优化方法？

## 本节结论

- 性能问题应先定位发生在哪一层，再选择优化手段，不能把压缩、缓存或框架升级当成通用答案。
- 用户体验需要同时观察加载、交互和视觉稳定性，单一指标不能代表完整体验。
- 浏览器性能优化的核心是减少主线程工作、布局与绘制范围，以及不必要的资源传输。
- 性能监控应关联页面、设备、网络、版本、用户操作和错误上下文，同时保护隐私。
- Node.js 性能需要结合吞吐、延迟、内存、GC 和事件循环分析，压测结果不能只看 QPS。

## 知识框架

### 1. 性能优化从架构假设开始

先确认应用是 CSR、SSR、MPA、边缘渲染还是混合架构，并回答：

- 内容在何处生成？
- 静态资源如何缓存与分发？
- 数据请求是否阻塞首屏？
- 服务端和客户端分别承担多少计算？
- 用户位于什么网络与设备环境？

架构不同，瓶颈位置也会不同。

### 2. 交付层减少字节与等待

- 对文件使用内容哈希和长期缓存。
- 使用 CDN 缩短静态资源路径。
- 压缩文本资源并删除无用代码。
- 拆分关键与非关键资源。
- 预加载真正影响关键路径的资源。
- 避免缓存策略与发布版本不一致。

协议和压缩格式不是目标，实际传输时间与兼容性才是验证依据。

### 3. 浏览器渲染是一条流水线

```text
JavaScript
  -> Style
  -> Layout
  -> Paint
  -> Composite
```

频繁读取布局后再写样式、扩大重绘区域或执行长任务，都会增加主线程压力。使用合成层也有内存成本，不应无条件提升元素。

### 4. 指标要映射到用户问题

| 体验维度 | 常见指标 |
| --- | --- |
| 服务响应 | TTFB |
| 内容出现 | FP、FCP、LCP |
| 交互响应 | INP、长任务、TBT |
| 视觉稳定 | CLS |

指标阈值会随标准和业务变化，项目应保存采集版本与统计口径。

### 5. 性能监控需要上下文

```text
PerformanceObserver / Performance API
  + 资源与导航计时
  + 错误和请求
  + 页面与发布版本
  + 脱敏后的操作上下文
  -> 聚合、分位数、告警与回归分析
```

不能采集密码、完整表单、令牌或其他敏感信息。

### 6. Node.js 性能看完整画像

- 压测：吞吐、平均延迟与尾延迟。
- 事件循环：是否存在长时间同步任务。
- 内存：堆、外部内存、Buffer 和泄漏趋势。
- GC：回收频率、停顿和对象存活情况。
- I/O：是否可以通过 Stream 和背压减少峰值内存。

手动触发 GC 只适合诊断实验，不能代替内存问题修复。

## 实践任务

**建议产出：**

- 为一个前端与 Node.js 应用完成性能基线、监控和优化报告。

**完成标准：**

- [ ] 使用真实设备或受控环境记录优化前后数据。
- [ ] 前端指标能关联到页面、版本和网络环境。
- [ ] Node 压测同时记录延迟、内存与 GC。
- [ ] 每项优化都能说明瓶颈证据与收益。
