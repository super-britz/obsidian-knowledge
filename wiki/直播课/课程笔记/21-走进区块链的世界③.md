# 21 走进区块链的世界③

> [!abstract] 核心问题
> 前端开发者需要怎样理解 Solidity 合约、部署结果和调用上下文？

## 本节结论

- 智能合约是部署到链上执行环境的程序，状态写入和调用都受网络规则约束。
- 合约部署会产生地址，ABI 描述其外部接口，前端通过二者构造调用。
- `msg.sender` 和 `msg.value` 来自当前调用上下文，是权限和付款逻辑的重要输入。
- `payable` 只表示允许接收原生资产，不代表函数已经具备正确的账务与提款规则。
- 教学合约只能用于理解流程，不能未经测试、审计和权限设计就承载真实资产。

## 知识框架

### 1. Solidity 文件的基本结构

```solidity
// SPDX-License-Identifier: ...
pragma solidity ...;

contract Example {
    // state, constructor, functions, events
}
```

版本范围影响编译行为；合约接口和状态模型应在实现前明确。

### 2. 状态与执行存在成本

状态变量保存在链上环境中，写状态通常比读取更昂贵。设计时应减少不必要的存储、循环和重复写入，同时避免为了省成本牺牲正确性。

### 3. 调用上下文

| 值 | 含义 |
| --- | --- |
| `msg.sender` | 当前直接调用者 |
| `msg.value` | 本次调用携带的原生资产数量 |
| `address(this)` | 当前合约地址 |
| `block.*` | 当前区块相关上下文 |

通过其他合约转发调用时，`msg.sender` 可能是中间合约，而不是最初用户。

### 4. 部署与调用链路

```text
Solidity 源码
  -> 编译
  -> Bytecode + ABI
  -> 部署交易
  -> 合约地址
  -> 前端用 ABI + 地址调用
```

地址必须与当前网络匹配，ABI 必须与该地址上的代码版本匹配。

### 5. 收款与提款需要完整账务

一个存取款合约至少要明确谁的余额如何记录、谁能提款、能提多少、外部调用失败如何处理，以及重入等安全风险。

## 实践任务

**建议产出：**

- 在本地或测试环境部署一个最小合约并从前端读取状态。

**完成标准：**

- [ ] 能解释编译产物中的 ABI 与 Bytecode。
- [ ] 记录网络、部署交易哈希和合约地址。
- [ ] 前端能读取状态并处理网络错误。
- [ ] 不将简单收付款 Demo 用于真实资金。

## 复习检查

- [ ] `msg.sender` 在合约间调用时可能是谁？
