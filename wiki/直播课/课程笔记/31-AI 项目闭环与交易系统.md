# 31 AI 项目闭环与交易系统

> [!abstract] 核心问题
> 如何用一个复杂业务项目证明 AI 开发工作流，而不是只展示生成页面的 Demo？

## 本节结论

- AI 工作流的价值要由真实需求、可运行代码、测试、部署和问题处理共同证明。
- 从图片或设计稿生成页面只是交付链路的一环，仍需检查视觉一致性、交互、响应式与可维护性。
- 交易系统前端的复杂度集中在实时数据、K 线、盘口、订单状态和性能，而不是普通表单。
- 高频更新应先分析数据量、刷新频率和渲染范围，再决定使用虚拟列表、Worker 或其他优化。
- 项目表达应展示真实职责、设计取舍和验证证据，不能用代码量或夸大经历代替理解。

## 知识框架

### 1. 项目证明是一条证据链

```text
需求与约束
  -> 设计与任务拆分
  -> 代码实现
  -> 自动化测试
  -> 浏览器验证
  -> 部署与监控
  -> 问题复盘
```

面试或复盘时，应能解释每一环的输入、产出和人工判断。

### 2. 视觉生成需要工程验收

从截图或图片生成页面后，至少检查：

- 字体、间距、层级、颜色与关键视觉资产。
- 不同视口下的布局和文字溢出。
- Hover、弹窗、导航和表单等交互状态。
- 资源体积、加载失败和无障碍语义。
- 组件边界与重复样式是否可维护。

“看起来相似”不能代替可用性和代码质量。

### 3. 交易界面的数据链路

```text
行情源 / Mock
  -> WebSocket 消息
  -> 解析、校验与聚合
  -> 状态模型
  -> K 线 / 盘口 / 成交列表
  -> 下单与订单状态反馈
```

系统必须处理断线重连、乱序、重复消息、快照与增量同步。

### 4. 盘口性能先减少无效工作

可依次考虑：

1. 合并高频更新，控制提交频率。
2. 只更新发生变化的价位。
3. 对长列表使用窗口化渲染。
4. 将重计算移出主线程。
5. 用性能记录验证优化是否有效。

Worker 适合计算和数据处理，不能直接操作 DOM；WASM 也只有在明确的计算瓶颈下才值得引入。

### 5. 交易状态需要明确语义

限价、市价、开仓、平仓、撤单和清算等概念会改变界面状态。前端应以服务端或链上确认结果为准，避免只根据按钮点击进行乐观推断。

## 实践任务

**建议产出：**

- 实现一个不接触真实资金的交易界面 Demo，并附完整交付记录。

**完成标准：**

- [ ] 包含 K 线、盘口、实时数据与订单状态。
- [ ] 能模拟断线、重连、重复消息和异常响应。
- [ ] 用性能数据说明是否需要虚拟列表或 Worker。
- [ ] 保留需求、测试、部署和问题复盘证据。

## 复习检查

- [ ] 什么证据能证明项目不是一次性生成的 Demo？
- [ ] 盘口高频更新应按什么顺序优化？
- [ ] 为什么前端不能自行推断交易最终状态？
