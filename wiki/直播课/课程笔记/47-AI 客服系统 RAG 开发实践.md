# 47 AI 客服系统 RAG 开发实践

> [!abstract] 核心问题
> 如何为电商售后客服接入可调试、可评估的 RAG 知识层，并通过分片、召回、重排和资源隔离提高回答准确性与系统稳定性？

## 本节结论

- RAG 负责商品说明、保修政策、退换货规则和故障排查等文档知识；订单、物流和库存等实时事实仍应由 Tool / API 提供。
- 一条完整 RAG 链路包括文档清洗与分片、Embedding、向量写入、查询召回、可选重排、上下文压缩和答案生成，不能只验证向量数据库是否返回结果。
- TopK 不是越大越好：候选过少可能漏掉答案，候选过多会增加噪音和上下文成本；本节采用“宽召回、重排、少量送入模型”的优化思路。
- Embedding 与生成模型应按硬件资源分开调度，并限制检索结果长度，避免多个模型争抢显存或长上下文拖垮服务。
- RAG 命中内容不等于最终回答正确，还要验证路由、结果转换、上下文注入和生成答案是否忠实于检索证据。
- AI 可以协助生成知识文档、业务代码和部署脚本，但核心链路仍需代码评审、测试用例、日志和失败回退共同验收。

## 知识框架

### 1. 先明确客服系统中的职责边界

```text
用户问题
  -> Agent / Workflow：识别意图、选择知识或业务工具
      -> RAG：查询相对稳定的文档知识
      -> Tool / API：查询订单、物流、库存等实时事实
  -> 本地模型：结合可信上下文组织客服回复
```

RAG 适合承载商品使用说明、故障排查、售后政策与可以独立更新的 FAQ；它不应替代需要身份校验的订单查询、持续变化的业务状态或具有副作用的业务动作。

课堂演示中的本地模型会参与意图判断与回复生成，但实际执行权仍应放在 Agent / Workflow 和受控 Tool 中。模型表现出客服语气，也不能证明它已经正确完成路由或业务调用。

### 2. 文档写入链路

```text
Markdown 知识文档
  -> 清洗与递归分片
  -> Embedding 模型生成向量
  -> 附加来源、品类、标题等元数据
  -> Upsert 到 Qdrant
```

本节选择 Qdrant 作为本地向量数据库，并使用框架已有的 RAG 能力完成写入与读取。课程中的部署方式是直接运行本地二进制文件；这是演示环境选择，不代表所有项目都应排斥容器或托管服务。

写入阶段至少要验证：

- 文档格式、编码和读取结果是否正常。
- 分片是否保留标题、条件与必要上下文。
- 每个 Chunk 是否带有可追溯的来源元数据。
- 重复写入是否会产生不可控的重复数据。
- 写入数量、失败数量和目标索引是否有日志。

### 3. 查询与生成链路

```text
用户问题
  -> 意图路由
  -> Query Embedding
  -> 向量召回候选片段
  -> 过滤 / Rerank
  -> 提炼为短上下文
  -> 交给模型生成回答
  -> 返回答案与来源
```

调试时要逐段保存证据：

1. 路由器是否把文档问题送入 RAG，而不是错误地要求订单号。
2. 向量数据库是否召回了真正相关的片段。
3. Rerank 是否把包含关键条件的片段排到前面。
4. 传入模型的上下文是否完整、简短且格式可读。
5. 最终回答是否只使用检索结果中的事实。

如果数据库已经命中，但回答仍然错误，问题可能出在结果序列化、上下文过长、Prompt 结构或后续模型调用，而不一定是向量检索本身。

### 4. Chunking 决定检索的基本单位

本节沿用递归分片：优先按较大的自然边界切分，片段过长时再按更小的分隔符继续切割。

| 分片情况 | 主要风险 |
| --- | --- |
| 片段过大 | 同一向量混入多个主题，召回后上下文过长 |
| 片段过小 | 条件、例外和结论被拆散，单个片段无法独立回答 |

不能只看 Chunk 数量，还要用真实问题检查召回片段是否同时包含适用条件、规则正文和限制条件。标题、品类与来源等元数据也应保留，便于过滤和引用。

### 5. 区分候选 TopK 与最终上下文数量

TopK 控制检索阶段返回多少候选。调参时至少考虑召回率、排序质量、噪音量与上下文成本。

本节提出的优化方案是：

```text
初始向量召回 TopK = 20
  -> Rerank 二次排序
  -> 最终保留 4 条上下文
```

这里的 20 与 4 属于不同阶段，不能混成一个固定经验值。实际项目应通过评估集决定候选数量和最终保留数量，而不是直接复制课堂参数。

### 6. Rerank 解决“相似但不够准确”的排序问题

向量召回擅长找到语义相近内容，但相近不等于满足全部业务条件。Rerank 在候选集合上进行第二次相关性判断，适合处理：

- 多篇售后政策措辞相近，但适用品类不同。
- 用户问题包含多个限制条件，向量距离未能正确排序。
- 需要先扩大召回范围，再压缩最终上下文。

课堂计划优先复用现有框架中的重排能力，因为对当前售后文档改动较小。只有普通向量检索与重排仍无法满足复杂关系或多步问题时，才值得增加更复杂的检索架构。

### 7. 资源隔离与上下文控制

演示中将轻量 Embedding 模型放到 CPU，将主要 GPU 资源留给生成模型，同时限制 RAG 返回长度。核心原则是让不同组件的资源需求可观测、可控制：

- 分别记录 Embedding、向量查询和生成阶段耗时。
- 监控 CPU、内存、GPU 显存和上下文长度。
- 不把完整检索 JSON 原样塞入 Prompt，只提取必要文本与来源。
- 为超时、空结果、模型服务不可用和上下文溢出设计回退。

“迁移到 CPU”是本节硬件条件下的取舍，不是普遍性能结论。真正的验收标准是资源不会互相挤占，关键请求能稳定完成。

### 8. 路由、兜底和失败回退

课堂调试中出现了非物流问题被错误路由到物流工具、反复要求订单号的情况。路由规则需要区分：

- 明确的订单或物流请求：进入对应 Tool，并校验必要参数。
- 商品说明或售后政策问题：进入 RAG。
- 意图不明确：先澄清，而不是默认调用高频工具。
- 工具或检索失败：说明失败状态，允许重试或转人工。

兜底不是无限重试。它应包含最大重试次数、错误分类、用户指引、日志记录和人工接管条件，避免系统在同一路径中循环。

### 9. 用评估集验收 RAG

评估集至少覆盖：

- 能直接命中的商品说明问题。
- 需要同时满足品类、时间或政策条件的问题。
- 表述不同但语义相同的问题。
- 知识库中不存在答案的问题。
- 应调用 Tool 而不应进入 RAG 的实时业务问题。
- 检索命中但答案可能被长上下文干扰的问题。

建议分别记录候选召回是否命中、重排后是否进入前列、最终答案是否忠实、来源是否正确，以及端到端耗时。这样才能判断问题发生在检索、排序还是生成阶段。

## 实践任务

**建议产出：**

- 为本地智能客服增加一个可评估的售后知识库 RAG 模块，完成文档写入、查询、重排和答案引用链路。

**完成标准：**

- [ ] 至少准备两类商品或政策文档，并保留来源元数据。
- [ ] 能展示文档分片、向量写入和重复写入处理结果。
- [ ] 能对比“直接取前 4 条”与“宽召回后重排取 4 条”的结果。
- [ ] 能证明实时订单问题进入 Tool，而不是被 RAG 直接回答。
- [ ] 覆盖无结果、错误路由、上下文过长和模型服务失败场景。
- [ ] 有包含召回、排序、答案忠实度和耗时的评估记录。

## 复习检查

- [ ] 为什么向量数据库已经返回结果，最终回答仍可能不正确？
- [ ] 候选 TopK 与最终传入模型的片段数量有什么区别？
- [ ] 什么情况下应该先优化分片和重排，而不是立即引入更复杂的 RAG 架构？
- [ ] 为什么 Embedding 模型放在 CPU 只是资源取舍，而不是固定最佳实践？
- [ ] 如何证明一个问题应走 RAG、Tool，还是先向用户澄清？
