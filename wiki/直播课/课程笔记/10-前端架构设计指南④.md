# 10 前端架构设计指南④

> [!abstract] 核心问题
> 如何把 AI 生成的页面和接口真正接入现有工程，而不破坏架构、类型和业务约束？

## 本节结论

- AI 开始修改项目之前，应先读取并记录目录、依赖、约定和禁止事项。
- 生成页面需要归位到既有组件、样式和资源体系，而不是作为一大块孤立代码落地。
- tRPC、oRPC 等方案通过共享契约减少前后端类型漂移，但不能替代业务校验和权限控制。
- 接口设计要显式处理幂等、重复提交、失败重试和状态一致性。
- AI 生成代码必须经过清理、测试和人工评审，最终责任不能交给生成工具。

## 知识框架

### 1. 先建立项目上下文

项目上下文应包含：

- 应用与共享包的职责。
- 技术栈和关键依赖。
- 组件、样式、图片和配置的存放规则。
- 测试、构建和部署命令。
- 安全边界与不可自动执行的操作。

上下文文件的具体名字不重要，重要的是内容可维护，并且能随代码一起更新。

### 2. 让生成代码服从现有架构

```text
生成页面
  -> 识别现有 UI 组件
  -> 抽取业务组件
  -> 复用设计令牌
  -> 归档真实素材
  -> 接入路由、状态和接口
  -> 测试与视觉验收
```

不要让 AI 为同一个按钮、通知或表单重复引入组件库，也不要保留无用演示代码。

### 3. 类型安全 API 共享的是契约

tRPC、oRPC 一类工具让客户端从服务端契约推导输入和输出类型，减少手写 DTO 的重复。它们解决的是开发期契约一致性；运行时仍需验证外部输入、鉴权和业务规则。

区块链场景中的 JSON-RPC 也属于远程调用，但调用对象、传输约定和使用场景不同。

### 4. 接口要以状态变化为中心设计

以“提交生成任务”为例，需要明确：

- 同一个请求能否安全重试。
- 如何生成和保存幂等键。
- 重复请求返回旧结果还是拒绝。
- 状态写入与异步任务如何保持一致。
- 客户端超时后怎样查询最终结果。

Redis 可以保存短期幂等状态，但事实状态仍应由可靠的数据存储维护。

### 5. 评审覆盖代码之外

AI Review 至少检查：架构归属、依赖变化、类型、错误处理、权限、敏感信息、资源引用、测试和部署影响。

## 实践任务

**建议产出：**

- 在既有项目中完成一个页面和一个类型安全接口。

**完成标准：**

- [ ] 项目上下文能指导 AI 找到正确目录和复用规则。
- [ ] 页面复用现有组件和设计令牌。
- [ ] 接口具有运行时校验与幂等策略。
- [ ] 变更通过测试并完成一次人工 Review。

## 复习检查

- [ ] 类型安全 API 解决了什么，又没有解决什么？
- [ ] 为什么项目上下文应随代码维护？
- [ ] 如何判断一个提交接口是否支持安全重试？
