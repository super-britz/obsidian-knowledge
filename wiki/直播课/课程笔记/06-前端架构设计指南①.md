# 06 前端架构设计指南①

> [!abstract] 核心问题
> 当前端开始承担 BFF 和全栈职责时，怎样理解 Serverless、云网络和数据服务？

## 本节结论

- BFF 的价值是按前端场景聚合和裁剪数据，同时也把稳定性与安全责任带给前端团队。
- Serverless 把服务器运维交给平台，但开发者仍需设计状态、冷启动、权限、网络和观测。
- AWS 部署不是单个 Lambda，而是入口、函数、权限、网络和数据服务共同组成的资源图。
- VPC、Subnet、Security Group 和出网方案共同决定服务之间能否通信。
- S3、关系型数据库、缓存和 CDN 解决不同问题，不能因为都“存数据”就混用。

## 知识框架

### 1. BFF 让接口围绕页面组织

```text
浏览器
  -> BFF
  -> 聚合多个后端接口
  -> 裁剪和转换数据
  -> 返回页面需要的模型
```

BFF 可以降低页面对后端内部结构的耦合，但也需要处理鉴权、超时、重试、限流、缓存和故障降级。

### 2. Serverless 管理的是运行资源，不是业务责任

平台可以负责分配机器和扩缩容，应用仍要处理：

- 函数无状态，持久数据必须放到外部服务。
- 初始化依赖可能产生冷启动。
- 调用链跨越多个托管服务，排错依赖日志和追踪。
- 权限通常由角色和策略控制。
- 流量、运行时间和外部服务共同决定成本。

### 3. AWS 请求链路

```text
互联网
  -> API Gateway
  -> Lambda / Node 服务
  -> VPC 内的数据或缓存服务
```

部署通常还会涉及：

- CloudFormation 或其他 IaC 描述资源。
- IAM Role 授予服务访问权限。
- VPC、Subnet 与 Security Group 控制网络。
- 日志和指标记录运行状态。

### 4. 云网络先回答“谁能访问谁”

| 概念 | 作用 |
| --- | --- |
| VPC | 云上的私有网络边界 |
| Subnet | 在 VPC 内按用途和路由进一步分区 |
| Security Group | 资源级访问控制 |
| Internet Gateway | 为合适的公网资源提供互联网连接 |
| NAT Gateway | 让私有子网主动访问公网 |
| VPC Endpoint | 在私网访问特定云服务 |

排查连通性时，要同时检查地址、路由、端口、安全组、身份权限和目标服务状态。

### 5. 数据服务按数据形态分工

| 服务类型 | 适合保存或处理 |
| --- | --- |
| S3 / 对象存储 | 图片、音视频、文件、构建产物 |
| RDS / Aurora | 有关系和事务要求的结构化业务数据 |
| ElastiCache / Redis | 热数据、会话、计数和临时加速 |
| CloudFront / CDN | 在靠近用户的位置缓存和分发内容 |

对象存储不是数据库，缓存也不是事实来源，CDN 更不是原始存储。

## 实践任务

**建议产出：**

- 画出并实现一个“浏览器 -> API Gateway -> Lambda -> 数据服务”的最小系统。

**完成标准：**

- [ ] 能解释 BFF 为什么存在以及新增了哪些责任。
- [ ] 能说明函数放入 VPC 后如何访问数据库与公网。
- [ ] 能为文件、业务数据和缓存选择不同服务。
- [ ] 能通过日志定位一次接口失败。

## 复习检查

- [ ] BFF 与直接调用后端接口的主要权衡是什么？
- [ ] Lambda 进入私有子网后为什么可能无法访问公网？
- [ ] S3、数据库、Redis 和 CDN 分别解决什么问题？
