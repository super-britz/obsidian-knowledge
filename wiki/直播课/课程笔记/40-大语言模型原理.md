# 40 大语言模型原理

> [!abstract] 核心问题
> Transformer 如何利用 Token、向量与 Attention 生成下一个 Token，工程上又受哪些资源约束？

## 本节结论

- 大语言模型将输入转换为 Token 与向量表示，并根据上下文预测下一个 Token。
- Self-Attention 让每个位置根据相关性聚合其他位置的信息，Q、K、V 是其中的三类投影。
- 上下文变长会增加计算、显存和延迟压力，标称窗口不等于所有任务都能有效利用。
- 模型选择需要同时比较任务效果、延迟、成本、隐私、部署和维护条件。
- 动态事实应优先通过 RAG 或工具获取，不能期待模型参数持续记住最新业务状态。

## 知识框架

### 1. 语言生成的基本链路

```text
文本
  -> Tokenizer
  -> Token ID
  -> Embedding
  -> 多层 Transformer
  -> 下一个 Token 的概率分布
  -> 采样或选择
  -> 重复生成
```

模型生成的是概率结果，不是从数据库直接取出一段确定答案。

### 2. Attention 处理上下文关系

输入向量经过线性投影得到：

- Query：当前位置正在寻找什么信息。
- Key：每个位置可用于匹配的特征。
- Value：匹配后要聚合的内容。

Query 与 Key 计算相关性，再用权重汇总 Value。多头机制让模型从不同表示子空间建立关系。

### 3. Transformer Block 的核心组成

一个简化 Block 通常包含：

```text
Self-Attention
  -> 残差连接与归一化
  -> 前馈网络
  -> 残差连接与归一化
```

层数、隐藏维度、注意力结构和训练方法共同影响模型能力与成本。

### 4. 上下文窗口不是免费容量

输入越长：

- Attention 与缓存需要更多计算和内存。
- 重要信息可能被大量无关内容稀释。
- 首次响应时间与推理成本可能增加。
- 不同位置的信息利用效果可能不同。

应先检索、压缩和组织上下文，而不是无条件塞入全部资料。

### 5. 推理资源受多项因素影响

- 参数规模与数值精度。
- KV Cache 和上下文长度。
- 显存容量与带宽。
- 批大小和并发。
- 模型架构与推理框架。
- 数据在设备之间的传输。

单看显卡名称或理论算力无法判断实际业务性能。

### 6. 大模型技术选型

| 需求 | 优先考虑 |
| --- | --- |
| 通用能力与快速接入 | 托管模型 API |
| 数据不可外发 | 本地或私有化模型 |
| 私有文档知识 | RAG |
| 实时业务状态 | API / Tool |
| 稳定语气与输出行为 | Prompt 或微调 |
| 多步骤任务执行 | Agent / Workflow |

这些能力可以组合，不是互斥选项。
