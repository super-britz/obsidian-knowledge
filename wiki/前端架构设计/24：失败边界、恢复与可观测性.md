# 失败边界、恢复与可观测性

> [!abstract] 先用一句话说清楚
> 失败无法被彻底消灭，架构能做的是限制一次失败最多破坏多少有用能力，把系统恢复到语义明确的状态，并留下足够证据判断发生了什么、恢复是否有效。失败边界不是一个万能 catch，可观测性也不是“多打日志”。

## 从“失败不可消灭”推导完整闭环

前端同时依赖用户输入、浏览器资源、网络、服务端、缓存、第三方脚本和持续变化的代码。有限测试无法穷尽所有输入，有限资源也无法保证所有依赖永远及时响应。因此“系统永不失败”不是可实现目标，真正可以设计的是：

    一个局部故障发生
    → 先保留它的失败语义
    → 在最小仍有意义的边界内停止传播
    → 选择不会制造更大风险的恢复动作
    → 向权威来源验证结果
    → 用相关联的证据判断故障和恢复
    → 再调整边界、预算或实现

如果缺少其中任一步，局部错误就可能放大：

    一个组件或依赖失败
    → 共享状态、资源或无界重试把影响传给其他能力
    → 整页、整会话或下游服务一起退化
    → 只剩“用户说不能用”，没有版本、路径和操作证据
    → 团队只能猜测、刷新或回滚，恢复慢且可能再次伤害用户

所以可靠性不等于失败数量为零，而是同时控制四件事：**爆炸半径、失败持续时间、恢复的正确性、诊断所需时间。**

## 失败边界按“独立有用且能独立恢复”划分

失败边界回答的是：**这个位置出错时，最多允许哪些状态、资源和用户能力一起失效？** 它不等于代码目录，也不等于每个组件都放一个 Error Boundary。

边界粒度可以从两个问题反推：

1. 边界外是否还存在值得保留的独立用户能力？
2. 边界内是否有明确所有者，能在不重置外部正确状态的前提下恢复？

| 失败位置 | 合理的隔离与处理范围 | 不应被一起破坏的能力 |
| --- | --- | --- |
| 表单输入无效 | 字段或表单状态 | 页面导航、已加载数据 |
| 订单冲突或权限拒绝 | 当前业务流程 | 其他 Feature 与应用壳 |
| 消息列表渲染缺陷 | 消息列表或单条消息 | 编辑器、导航和其他会话 |
| 推荐服务不可用 | 推荐 Feature 或依赖调用预算 | 搜索、结算等核心路径 |
| 某个租户或缓存分区异常 | 对应租户、键空间或会话 | 其他主体的数据与资源 |

边界过粗时，一个头像组件就可能让整页白屏；边界过细时，每个小组件都维护 fallback、重置和告警，页面被碎片化，系统性事故也被大量局部提示掩盖。正确粒度不是越小越好，而是尽量贴合**独立有用能力、状态所有权、共享资源和恢复责任**。

[[23：运行时 Schema 与错误模型|错误模型]]与失败边界承担不同责任：前者说明“发生的失败意味着什么”，后者说明“这个失败最多传播到哪里，由谁接管”。没有分类，Boundary 不知道该重试还是停止；没有边界，分类正确的错误仍可能拖垮整页。

## 预期失败进入状态，意外缺陷才兜底

输入错误、业务拒绝、登录过期、冲突、限流和结果未知，都是系统明确预期且调用方能够处理的结果。它们应进入 [[21：状态机与异步流程|合法状态转换]]，让用户修改、登录、等待、查询或协调，而不是先抛成异常再由顶层统一显示“出错了”。

真正超出局部代码处理能力的内部不变量破坏、未知判别分支和渲染缺陷，才交给上层失败边界：

    可预期失败
    → 结构化 Result / 事件
    → 当前用例或状态所有者决定

    意外缺陷
    → 终止当前不可信执行路径
    → 最近且有能力提供安全 fallback 的边界接管
    → 记录诊断证据

React Error Boundary 是这条原则在渲染树中的一种实现。官方文档说明它可以捕获后代组件的渲染错误并显示 fallback，但不捕获事件处理器、服务端渲染、Boundary 自身错误和通常的异步回调错误。因此它不能代替请求错误模型、事件处理中的显式转换、全局未处理异常采集或服务端隔离。

Boundary 也应放在用户能理解的恢复单元周围，例如路由、会话列表、编辑器或独立插件，而不是机械包围每个按钮。Fallback 至少要说明受影响能力、仍可使用的能力、用户能做什么，并提供可关联的错误编号；不能把内部堆栈直接交给用户。

## 恢复是受约束的状态转换，不是重新执行

catch 只说明异常没有继续冒泡，fallback 只说明替代界面被显示；二者都没有证明系统恢复。恢复必须回答：

    当前已知事实是什么？
    → 目标状态仍然安全吗？
    → 哪个动作可以到达目标状态？
    → 动作会不会重复副作用或扩大负载？
    → 谁能证明恢复后的状态成立？

| 恢复动作 | 必要前提 | 不能假装保证 |
| --- | --- | --- |
| 让用户修正或重新认证 | 错误责任确实在输入或身份 | 原操作一定尚未发生 |
| 重取并合并权威数据 | 有明确权威来源和冲突规则 | 本地草稿自动安全 |
| 查询 Operation ID | 服务端保存可查询的操作身份 | 查询失败等于原操作失败 |
| 自动重试 | 暂时失败、仍有意义、预算内、重复效果安全 | 每次失败最终都会成功 |
| 使用缓存或默认值 | 陈旧度和缺失能力可接受 | 数据仍然新鲜或适合写入 |
| 禁用非核心功能 | 核心旅程不依赖该能力 | 用户不会感知降级 |
| 重建组件或刷新页面 | 重建条件已改变，外部状态可协调 | 清空内存就是修复根因 |
| 回滚版本 | 新版本与故障有可验证关联 | 已写入的数据和外部副作用自动回滚 |

重置 Boundary 前还要改变导致错误的条件，例如切换路由、刷新数据、撤销问题配置或发布修复。若只反复卸载再挂载同一输入，系统会进入“崩溃 → fallback → 重试 → 再崩溃”的循环。关键写操作则必须保留 Operation ID 并查询权威结果，不能靠刷新把 `outcomeUnknown` 擦掉。

**恢复完成的判据必须来自权威状态和用户能力，而不是“异常消失”。** 例如结算恢复应证明订单结果可查且用户能继续，不能只看页面重新渲染成功。

## 重试、熔断与降级都在控制失败放大

重试会增加一次成功机会，也会额外消耗浏览器、网络和下游资源。依赖已经过载时，无界或同步重试会形成正反馈；多层各自重试还会让尝试次数相乘。因此自动重试至少需要：

- 错误被证明是暂时性的，永久错误和非法请求不重试；
- 操作仍有业务意义，旧查询和过期动作直接淘汰；
- 重复效果由幂等语义或稳定 Operation ID 保证安全；
- 只有一个明确层级拥有重试责任，并限制次数、总时长与整体预算；
- 遵守服务端等待提示，使用指数退避与随机抖动分散重试波峰。

Circuit Breaker 解决另一问题：当某个共享依赖近期很可能继续失败时，与其让每个调用都等到超时，不如用共享状态快速拒绝并保护资源。Closed 正常放行，失败达到阈值后 Open，恢复窗口后 Half-Open 只允许少量探测；成功后再逐步恢复。

熔断器因此不是“更高级的重试”，而是一个会产生误判的新状态系统。阈值太敏感会误伤健康请求，粒度太粗会把健康分片一起阻断，探测过快会再次压垮恢复中的依赖，过慢又延长降级时间。简单本地操作、低调用量或已有平台统一治理时，不应为了模式完整额外引入它。

浏览器内的熔断状态通常只代表当前会话观察到的近期失败，不能据此裁决全局服务健康；需要跨用户保护共享依赖时，责任通常应放在 BFF、网关或服务平台等能观察整体负载的位置。

当资源已饱和，限制并发、队列长度或主动拒绝非关键工作，可以让系统保留核心能力。降级结果必须显式标记：缓存数据有多旧、哪个功能暂不可用、哪些操作被禁止。尤其不能用陈旧权限、库存或价格继续高风险写入。

## 可观测性从“需要区分哪些解释”反推

可观测性不是收集得越多越好，而是能否依据系统输出区分关键假设：

    是单个用户输入错误，还是某版本普遍回归？
    是前端渲染缺陷，还是响应契约变化？
    是一次 Attempt 超时，还是同一 Operation 最终结果未知？
    是依赖本身失败，还是重试正在放大过载？
    fallback 被显示后，核心用户旅程是否真的恢复？

不同信号回答不同尺度的问题：

| 信号            | 主要回答             | 适合记录                        | 单独使用的盲区           |
| ------------- | ---------------- | --------------------------- | ----------------- |
| Metrics       | 发生多少、分布怎样、是否越过阈值 | 成功率、错误分类占比、延迟、重试率、熔断状态、恢复时间 | 聚合后看不到单次因果路径      |
| Logs / Events | 某个时刻发生了什么离散事实    | 状态转换、边界接管、恢复动作和结果           | 没有关联字段时只是零散文本     |
| Traces        | 一次执行经过哪些组件与依赖    | 前端导航、请求、服务端 Span、等待和失败位置    | 采样可能遗漏，且不直接说明总体影响 |

一条可诊断事件通常至少需要：时间、环境、应用与发布版本、路由或 Feature、失败类别、Boundary、流程阶段、恢复动作与结果。具体执行再用身份关联，而不是把所有信息塞进一段 message。

## 不同 ID 回答不同问题

| 身份 | 回答的问题 | 生命周期 |
| --- | --- | --- |
| Operation ID | 这是哪一次逻辑业务意图？ | 同一意图的安全重放保持不变 |
| Attempt ID | 这是该意图的哪一次具体尝试？ | 每次网络或执行尝试更新 |
| Trace ID / Span ID | 这次执行经过了哪条调用路径？ | 随一次执行上下文传播 |
| Error Event ID | 用户和支持人员指的是哪次错误呈现？ | 每次边界接管或错误事件生成 |

Trace Context 解决跨组件传播执行上下文，不承担业务去重。因此 Trace ID 不能替代 Operation ID：同一业务意图的多次尝试可能是同一 Trace 内的多个 Span，也可能在跨轮次恢复时形成多条 Trace；一条 Trace 也可能包含多个业务步骤。指标适合聚合稳定低维度，例如版本、路由和错误类别；Operation ID、Trace ID 等高基数精确身份更适合保留在日志或追踪中，再通过关联字段下钻。

## 客户端证据天然不完整

浏览器可能在上报前关闭、离线、被扩展拦截或发生崩溃；遥测 SDK 和采集端本身也可能失败，采样还会主动丢弃部分事件。因此“没有收到客户端错误”不能证明没有错误，成功率也应尽可能结合服务端回执、关键业务结果和合成测试交叉验证。

可诊断性还受安全边界约束：

- 不记录 Token、密码、完整表单、原始非法载荷和不必要的个人信息；
- Trace Context 只用于关联，不把用户身份或业务秘密编码进 Header；
- Source Map、发布版本和错误详情按环境控制访问；
- 先定义必要字段、采样和保留期限，再计算上报流量与存储成本；
- 遥测失败不得阻塞结算、保存等主路径，也不能递归触发无界上报。

证据不足时应诚实标记“未知”，而不是从浏览器暴露的模糊网络异常推断具体根因。

## 何时值得使用，代价是什么

最小实现可以从关键旅程开始：明确错误分类，在路由或独立 Feature 放置失败边界，为暂时性读取设置有界重试，并贯穿发布版本、Operation ID、Attempt ID 与 Trace ID。只有真实证据表明共享依赖反复失败并消耗资源时，再引入熔断、负载卸载或更复杂的采样与告警。

每个新增边界都带来 fallback、重置协议、状态协调和测试成本；每种自动恢复都增加新的失败路径；每个遥测字段都消耗网络、存储、查询和隐私预算。Boundary 还可能让应用表面“仍能用”，却隐藏一个持续扩大或影响核心路径的系统事故。局部隔离不能替代按用户影响聚合告警，也不能替代 [[16：组织所有权与系统边界|明确的运行所有者]]。

## 可观察的错误信号

| 现象 | 可能缺失或错误的机制 |
| --- | --- |
| 一个小部件错误导致整页白屏 | 失败边界过粗或不存在 |
| 每个小组件都显示独立错误卡片 | 边界过细，恢复单元被碎片化 |
| 业务拒绝统一进入顶层 Error Boundary | 预期失败没有进入合法状态 |
| 点击“重试”立即再次崩溃 | 重置前置条件没有改变 |
| 写操作超时后刷新并重新提交 | 结果未知和 Operation ID 被擦除 |
| 故障期间请求量反而上升 | 多层、同步或无预算重试正在放大失败 |
| 熔断一个分片却阻断全部数据 | 熔断状态的资源粒度过粗 |
| fallback 展示缓存但不说明时间 | 降级结果丢失新鲜度语义 |
| 日志只有 message 和堆栈 | 缺少版本、边界、状态、身份和恢复结果 |
| Trace ID 被当作幂等键 | 执行身份与业务身份混淆 |
| 没有客户端错误就判定发布成功 | 忽略客户端证据缺失与采样偏差 |

## 做项目时怎么验证

1. 选一条关键用户旅程，标出独立有用能力、共享状态、外部依赖、资源预算和运行所有者。
2. 把 [[23：运行时 Schema 与错误模型|错误类别]]映射到局部状态、最近失败边界和用户动作；预期错误不得全部抛给顶层。
3. 为每个 Boundary 写清隔离范围、fallback、重置条件、仍可用能力和升级告警条件。
4. 为重试记录拥有层级、适用错误、重复安全证明、Operation ID、Attempt ID、退避方式和总预算。
5. 若引入熔断或降级，测试阈值、资源粒度、Half-Open 探测、缓存新鲜度和恢复后的逐步放量。
6. 定义能回答真实诊断问题的 Metrics、Logs 和 Traces，用版本、Feature、错误类别和关联 ID 连接，而不是先全量采集。
7. 注入渲染异常、非法成功响应、离线、超时、429/503、迟到回执、响应丢失、队列饱和和遥测上报失败。
8. 验证故障没有越过预定爆炸半径，重试没有超预算，用户动作与失败语义一致，并能从权威来源证明恢复完成。

## 别误解

- **Error Boundary 能捕获所有错误。** 它只覆盖特定 React 渲染错误；事件、异步、请求和业务失败各有自己的处理边界。
- **捕获异常就完成恢复。** 捕获只是停止传播；恢复还需要安全目标、有效动作、权威验证和防循环条件。
- **重试能提高可靠性，所以越多越好。** 重试同时消耗资源；错误不可恢复、操作不安全或依赖过载时，它会扩大事故。
- **有日志就有可观测性。** 没有结构、身份、版本和信号关联的日志，很难区分根因假设或验证恢复。
- **降级就是返回任何旧数据。** 降级必须保持对当前任务仍正确的最小语义，并向用户暴露缺失能力与新鲜度。

## 复习

1. 为什么“减少失败数量”不能替代爆炸半径、恢复时间和诊断时间？
2. 错误模型与失败边界分别决定什么？
3. 为什么显示 fallback 或页面重新渲染不等于系统恢复？
4. 重试在什么条件下提高可靠性，又怎样形成级联失败？
5. Operation ID、Attempt ID、Trace ID 和 Error Event ID 为什么不能复用成一个？
6. 如何证明一次降级既保住了核心能力，又没有用陈旧事实制造新错误？

## 来源与下一步

- **来源事实：** React 官方文档说明 Error Boundary 可为后代渲染错误显示 fallback，并列出事件处理器、服务端渲染、Boundary 自身和通常异步回调等捕获边界；Google SRE 说明重试可能放大过载，并建议随机指数退避、单请求限制、整体预算和避免多层重试；Azure Architecture Center 将 Circuit Breaker 建模为 Closed、Open、Half-Open 状态，并记录阈值、资源粒度和恢复探测代价；OpenTelemetry 区分 Traces、Metrics、Logs 等信号，并用 TraceId、SpanId 关联日志与执行上下文；W3C Trace Context 规定 `traceparent`、`tracestate` 的跨系统传播与隐私边界；RFC 9110 用预期服务端效果定义幂等。
- **机制推导：** 从失败不可消灭推导“分类 → 隔离 → 恢复 → 权威验证 → 留证 → 调整”的控制闭环；以独立有用能力、状态所有权、共享资源和恢复责任决定失败边界，并区分业务身份、执行身份与错误呈现身份。
- **工程建议：** 先为关键旅程建立最小失败边界、有界恢复和关联证据；仅当观测到共享依赖故障放大时再增加熔断或负载卸载，并用故障注入验证爆炸半径、重试预算、降级语义和恢复判据。
- **待项目验证：** Boundary 粒度、重试责任与预算、熔断阈值、降级数据新鲜度、证据字段和留存周期，都必须根据真实用户旅程、依赖故障、资源上限、隐私要求和恢复目标确定。
