# 组织所有权与系统边界

> [!abstract] 先用一句话说清楚
> 系统边界只有在现实中有人能够理解、决定、修改、发布并根据运行反馈修正时才成立。组织所有权的目标不是让代码复制组织架构，而是让一类高频变化尽量由一个拥有必要上下文、权限和反馈的稳定团队闭环完成。

## 从“系统由人持续改变”推导

代码不会自己演进。一次变化真正经过的是：

    用户或业务信号
    → 理解规则与现状
    → 做出取舍
    → 修改代码、契约或数据
    → 验证并发布
    → 观察结果、恢复失败
    → 把新知识带回下一次决策

这个闭环需要三种东西：

- **上下文：** 知道目标、规则、历史和风险；
- **权力：** 能修改、审批、发布或推动必要改变；
- **反馈：** 能看到用户结果、运行指标和故障。

只有责任而没有权限，所有者只能排队等待；只有权限而不承担反馈，局部优化可能把成本推给别人；多人都能改但没人必须对结果负责，问题会在团队之间漂移。因此，所有权不是联系人标签，而是**决策权、执行能力与结果责任形成的闭环**。

## 协作为什么会重新塑造代码

Conway 的原始论述指出：组织会受到自身沟通结构约束，系统结构因而倾向于映射这种沟通结构。原因不神秘：两个模块要正确协作，设计和维护它们的人就必须围绕接口持续交换信息。

    一个高频变化
    → 必须经过多个团队
    → 产生排期、解释、审批和交接
    → 团队建立临时接口、共享状态或绕行路径
    → 这些协作方式逐渐固化为系统结构

即使代码图看起来已经分层，只要每次改变仍必须跨团队同步，系统在交付层面就是耦合的。可以用一个定性模型检查这种负担：

    协调负担
    ≈ 变化频率 × 必经交接数量 × 每次等待、误解与返工成本

这不是精确公式，而是提醒：低频、高风险的跨团队评审可能合理；高频日常变化若长期依赖多次交接，边界就值得重新检查。

## 系统存在多种边界

“这个模块属于谁”不能只看目录：

| 边界 | 回答的问题 |
| --- | --- |
| 业务边界 | 哪组规则和用户结果共同变化？ |
| 代码边界 | 哪些实现能被外部导入和修改？ |
| 契约边界 | 团队之间承诺什么输入、输出与兼容性？ |
| 数据边界 | 谁裁决事实、Schema、迁移与删除？ |
| 发布边界 | 哪些变化可以独立验证、部署和回退？ |
| 运行边界 | 什么会一起失败，谁接收告警并恢复？ |
| 所有权边界 | 谁拥有上述决策所需的上下文、权限与责任？ |

这些边界不必完全重合，但映射必须明确。一个团队拥有组件源码，却不能改变接口、发布应用或查看线上错误，它并没有真正拥有该用户能力。

## 好边界是“可独立改变的责任单元”

对同一变化流中的大多数日常需求，一个主要负责团队应当能够：

1. 理解目标和业务规则；
2. 决定边界内部怎样实现；
3. 修改并验证代码和契约；
4. 在必要控制下发布与回退；
5. 观察用户结果并处理运行故障。

这里的“独立”不是不与任何人沟通，而是**不把持续同步审批当作每次交付的正常路径**。安全、合规、设计系统和基础设施仍可提供约束，但应尽量通过稳定契约、自助平台和自动检查服务日常变化。

所有者也应优先是稳定团队而非某个个人。个人可以是联系人，团队才能通过文档、评审、轮值和能力冗余承接长期责任，避免关键知识随人员离开而消失。

## 一个前端结算场景

假设结算功能按技术层分给页面团队、接口团队、数据团队和发布团队。修改一个优惠提示也可能需要：前端排期、后端改字段、数据确认埋点、运维授权发布。模块各自“很专业”，但用户价值流被四次交接切断。

更接近闭环的方式可能是：

    结算团队拥有页面、用例编排、客户端契约和运行指标
    + 服务端团队拥有价格事实、授权与交易一致性
    + 平台团队自助提供构建、发布、观测和设计系统能力

关键不是强行把所有代码塞给同一团队。价格权威和安全校验仍应留在可信服务端边界；但团队之间通过清楚契约协作后，展示类变化不必等待交易核心修改，交易规则变化也不必暴露内部状态给页面。

## 平台与共享代码什么时候有价值

把通用能力集中给专门团队，可以减少每个业务团队重复理解构建、权限、设计系统或观测细节。但只有满足以下条件时，它才降低认知负担：

- 消费方通过稳定 API、文档和自助流程使用；
- 平台方对兼容性、可靠性和支持反馈负责；
- 临时协作完成后能够转为清楚的服务关系；
- 平台边界没有要求每次使用都提交工单和等待人工配置。

否则“平台团队”只是新的审批队列，“共享包”只是所有人都依赖、却无人能安全改变的公共耦合点。共享能力应像内部产品一样拥有用户、契约、版本和退出策略。

## 原则与后续机制

| 原则层要解决的问题 | 可选机制 | 机制不能替代什么 |
| --- | --- | --- |
| 明确谁对代码变化负责 | `CODEOWNERS`、强制评审 | 业务结果和运行责任 |
| 限制跨边界依赖 | 包公共 API、依赖规则 | 正确的业务划分 |
| 允许独立演进 | 版本、弃用期、兼容测试 | 双方对契约的承诺 |
| 形成交付闭环 | 独立流水线、权限与回退 | 生产观测和故障响应 |
| 共享通用复杂度 | 自助平台、设计系统 | 平台产品质量与支持责任 |

GitLab 的 `CODEOWNERS` 可以把路径映射给评审团队并配合规则要求审批，但在文件里写下名字不会自动赋予维护上下文、发布权限或线上反馈。自动化只能执行已经被定义清楚的责任。

## 可观察的错误信号

| 现象 | 可能的所有权问题 |
| --- | --- |
| 一个普通功能每次都要协调三四个团队 | 变化流被技术层或审批层切碎 |
| 合并请求长时间找不到真正能判断的人 | 代码路径与知识所有权不一致 |
| 团队能改代码却不能发布或看监控 | 执行与反馈闭环断裂 |
| 事故在多个群之间反复转发 | 运行边界没有主要责任团队 |
| 共享包变更必须召集所有调用方开会 | 契约不稳定或共享边界过大 |
| 平台能力必须通过人工工单获得 | 平台没有形成自助服务边界 |
| 微前端仍共享全局状态和统一发布窗口 | 运行与发布没有真正自治 |
| 组织一调整就必须搬动大量代码 | 系统机械复制了汇报关系 |

## 做项目时怎么验证

1. 选取最近三次需求或事故，画出从提出到上线、恢复的完整路径。
2. 标出每次必经的团队交接、等待时间、重复解释和返工位置。
3. 按真实变化流识别候选边界，而不是先按前端、后端或岗位名称分组。
4. 为每个边界写明主要团队、决策范围、公共契约、数据责任、发布权限和故障入口。
5. 将高频重复交接改为稳定契约、自助能力或同一团队内的端到端责任。
6. 用交付前置时间、交接次数、等待占比、变更失败和恢复时间观察是否改善。
7. 当业务流、认知负荷或团队能力改变时重新划界，不把当前组织图永久固化进系统。

## 别误解

- **一个模块只能由一个团队修改。** 主要所有权用于明确最终决策与结果责任，不排斥受控贡献和协作。
- **系统必须完全复制组织架构。** Conway 描述的是现实约束；工程目标是让沟通结构支持期望的系统与变化流，而非机械照搬汇报线。
- **跨职能团队应该拥有所有技术。** 超出团队认知负荷的通用或高度专门能力可以由平台、赋能或专门团队提供。
- **使用微前端就获得团队自治。** 如果状态、契约、流水线和故障仍共同耦合，页面切分只增加了集成成本。
- **写了 `CODEOWNERS` 就完成治理。** 路径评审只是所有权闭环中的一个执行点。

## 复习

1. 为什么代码已经分层，交付过程仍可能是高度耦合的？
2. 所有权为什么必须同时包含上下文、决策权和反馈责任？
3. 什么情况下平台团队降低认知负担，什么情况下它只是新队列？
4. 为什么“与团队边界对齐”不等于“复制当前组织架构”？
