# 可信边界与副作用隔离

> [!abstract] 先用一句话说清楚
> 程序内部可以依赖已经建立的不变量，外部输入和外部操作却不受当前程序控制。可信边界负责把未知输入解析为内部可信命令；副作用边界负责把业务决定转成受控的网络、存储、导航等真实操作，并用回执确认实际结果。

## 从外部不确定性推导

浏览器中的用户输入、URL、网络响应、localStorage、跨窗口消息、时间和第三方脚本都有共同性质：当前模块无法保证它们的形状、语义、权限和新鲜度。

如果外部对象直接进入内部状态：

    外部 unknown
    → 被类型断言为内部模型
    → 业务代码默认不变量成立
    → 脏数据、越权请求或错误状态向内部扩散

如果业务判断直接执行网络或存储：

    判断规则 + 外部操作混在一起
    → 结果依赖网络、时间和执行顺序
    → 难以独立测试、取消、安全重试或解释失败

因此需要两道不同的边界：

1. **输入信任边界：** 外部数据在这里被解析、校验和转换。
2. **副作用执行边界：** 内部决定在这里变成真实外部操作，并返回可验证回执。

## “可信”不是来源看起来可靠

自己维护的后端也可能出现版本错位、旧缓存、部分部署和错误数据；客户端代码还可以被用户绕过。因此可信不是“我相信发送者”，而是：

    当前值
    → 已通过当前边界要求的检查
    → 被转换为内部明确语义
    → 只在对应生命周期和权限范围内使用

信任是一次有范围、有时效的判断，不是给某个来源永久贴上“安全”标签。

## 类型安全不等于运行时可信

TypeScript 在编译后会擦除类型，类型断言不会产生运行时检查：

    const user = response as User

这句话只要求编译器相信开发者，没有证明 response 真的是 User。类型安全 API 可以减少受控客户端与服务端之间的开发期契约漂移，但不能阻止恶意请求、旧客户端、部署版本不一致或损坏缓存。

更可靠的边界是：

    unknown
    → 运行时解析与结构校验
    → 语义转换
    → 内部可信模型

校验成功后不应继续把原始外部对象四处传递，否则内部代码仍可能绕过边界。

## 校验有多个层次

| 层次 | 回答的问题 | 示例 |
| --- | --- | --- |
| 解析 | 输入能否被读取？ | 是否为合法 JSON |
| 结构与语法 | 字段和格式是否正确？ | amount 是有限正数 |
| 业务语义 | 当前上下文是否允许这个值？ | 折扣不能超过订单金额 |
| 身份认证 | 请求者是谁？ | 会话或 Token 是否有效 |
| 授权 | 该主体能否对该对象执行该动作？ | 用户只能取消自己的订单 |
| 时间与并发 | 这次操作是否仍然有效？ | 版本、过期时间、幂等键 |
| 资源限制 | 输入会否耗尽资源？ | 长度、数量、文件大小 |

结构正确不代表业务合法，已经登录也不代表有权操作目标资源。前端校验可以改善即时反馈，但承担安全责任的校验和授权必须在服务端、网关或受信任执行边界完成。

## 副作用为什么需要隔离

副作用是读取或改变当前计算之外世界的操作，例如网络、存储、DOM、导航、日志、时间和随机数。它们通常具有以下性质：

- 可能失败、超时或只完成一部分；
- 相同调用不一定产生相同结果；
- 有些操作不可撤销或重复执行；
- 结果到达顺序不由调用者控制。

可以把业务决定与执行分开理解：

    decide(可信命令, 当前状态)
    → 新状态意图 + 待执行操作

    execute(待执行操作)
    → 成功、拒绝、未知或失败回执

简单页面不必把每次点击都实现成正式命令系统，但业务规则不应依赖“请求刚好成功”；副作用应集中在可识别的位置，并把结果重新作为事件交还状态系统。

## 失败回执不等于“没有发生”

提交订单后连接超时，可能是：

1. 请求根本没有到达；
2. 服务端已完成，但响应丢失；
3. 服务端只完成了部分步骤；
4. 服务端明确拒绝。

把这些情况都表示成 error，然后无条件重试，可能重复创建订单或扣款。高风险副作用至少要明确：

- 操作身份：这次尝试是否有稳定 ID？
- 超时与取消：调用方放弃后，执行方会怎样？
- 重试语义：重复执行是否安全？
- 最终查询：结果未知时怎样获得权威状态？
- 补偿与人工处理：无法自动恢复时由谁负责？

幂等键、超时、重试库只是后续机制，不能替代对副作用业务语义的定义。

## Adapter、可信边界和副作用边界的关系

| 边界 | 主要责任 |
| --- | --- |
| Adapter | 转换内部契约与外部协议或 SDK |
| 可信边界 | 判断外部输入能否进入内部模型 |
| 副作用边界 | 控制何时、以什么身份和语义改变外部世界 |
| 失败边界 | 限制一次失败影响哪些用户和功能 |

它们可以由同一段入口代码协作完成，但责任不能混淆。Adapter 把字段改名，不代表输入已经授权；Schema 校验通过，也不代表操作可以安全重试。

## 一个提交生成任务的流程

    客户端校验表单，提供即时反馈
    → 服务端重新解析并校验结构
    → 认证身份并检查该项目的操作权限
    → 校验额度、任务状态和业务不变量
    → 转换为内部 SubmitJob 命令
    → 决定状态变化和待执行任务
    → 持久化或投递外部任务
    → 返回带任务 ID 的回执
    → 客户端根据权威任务状态展示结果

每一步失败的含义不同，应进入不同错误模型，而不是统一变成“请求失败，请重试”。

## 可观察的错误信号

| 现象 | 可能的问题 |
| --- | --- |
| 网络响应直接使用 as 强转 | 只有静态声明，没有运行时信任转换 |
| 隐藏按钮就认为用户无权操作 | 把体验控制误当成服务端授权 |
| Schema 通过后直接执行高风险操作 | 缺少业务语义或对象级权限检查 |
| 业务计算内部直接 fetch 或写存储 | 判断与副作用无法独立验证 |
| 所有异常都变成同一个 error | 失败语义和恢复策略被抹平 |
| 写操作超时后自动无限重试 | 未定义幂等与结果未知状态 |
| 第三方响应结构遍布组件 | 外部模型越过 Adapter 和可信边界 |

## 做项目时怎么验证

1. 枚举所有输入边界和副作用，不只检查 HTTP。
2. 将边界输入默认标为 unknown，定义结构、语义、身份、权限和资源检查。
3. 把外部模型转换为内部命令，不让原始对象继续传播。
4. 将业务决定和外部执行分开，记录操作身份和结构化回执。
5. 对写操作模拟超时、重复请求、响应丢失、部分完成和越权访问。
6. 确认客户端检查只负责体验，服务端会独立拒绝非法或越权请求。
7. 最后再选择 Schema、请求、重试和日志工具。

## 别误解

- **前后端共用 TypeScript 类型就不需要校验。** 静态类型不验证运行时数据。
- **数据格式正确就可以执行。** 结构、业务语义、身份和授权是不同检查。
- **客户端禁用按钮就完成权限控制。** 客户端可被绕过，不能成为安全裁决者。
- **把 fetch 放进 Service 就完成副作用隔离。** 只有规则能够独立决定、外部执行有明确回执时，边界才有实质作用。

- **来源事实：** TypeScript 官方文档说明编译后类型被擦除；OWASP 要求尽早校验外部输入，并明确客户端检查不能承担服务端授权。课程材料指出类型安全 API 不替代运行时校验、权限和业务规则，写接口还需处理幂等、重试与状态一致性。
