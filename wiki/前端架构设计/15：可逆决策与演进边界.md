# 可逆决策与演进边界

> [!abstract] 先用一句话说清楚
> 未来需求、团队和技术无法被准确预测。架构不应试图预先实现所有未来，而应根据决策出错后的修正成本，决定何时快速试验、何时延后承诺，以及在哪里保留可渐进迁移和退出的边界。

## 从未来不可预测推导

任何架构选择都基于当前信息，但信息会变化：

    当前约束与证据
    → 做出一个技术判断
    → 业务、规模、团队或生态发生变化
    → 原判断可能不再合适

问题不是能否永远选对，而是选错后要付出多大代价。可以用一个简化模型思考：

    长期预期成本
    ≈ 当前实现成本
    + 持续维护成本
    + 未来改变概率 ×（迁移或退出成本 + 决策失效期间的影响）

这是用于比较方案的定性模型，不是可直接精算的公式。可逆性降低的是未来改变发生后的成本，但为可逆性建立接口、兼容和迁移能力也会增加当前实现与持续维护成本。因此既不能完全忽略未来，也不能为所有想象中的未来提前抽象。

## 什么使一个决定难以撤销

难改通常不是因为代码行数多，而是决定已经进入更多外部状态和责任：

| 放大因素 | 为什么难以撤销 |
| --- | --- |
| 持久化数据 | 新旧结构需要迁移、校验和恢复 |
| 公共契约 | 无法同时控制所有调用方升级 |
| 已发布客户端 | 不同版本会长期同时访问服务 |
| 外部副作用 | 通知、扣款和删除不能靠代码回滚撤销 |
| 供应商专有模型 | 数据、协议和能力难以迁出 |
| 团队技能与流程 | 培训、招聘、值班和发布方式已经绑定 |
| 跨模块共享 | 一个决定被越多模块依赖，改变半径越大 |

修改局部函数通常高度可逆；改变公共 URL、数据格式、认证模型或组织发布边界则更难逆转。

## 可逆性是一种有成本的选择权

保留两个可行方向，相当于购买未来选择权。它适合：

- 当前不确定性高，近期能够获得更多证据；
- 错误判断会影响大量数据、用户或团队；
- 用很小边界就能隔离易变部分；
- 迁移可以分批进行并测量结果。

它不适合：

- 局部实现替换非常便宜；
- 为假想替代方案维护两套系统的成本更高；
- 兼容路径扩大了安全或正确性风险；
- 旧路径没有退出期限，已经成为永久负担。

“以后可能更换数据库”不足以证明要为每个对象建立复杂抽象；“供应商类型已进入核心模型并持久化”才是值得处理的具体证据。

## 什么是演进边界

演进边界是在新旧实现之间建立的临时或稳定接缝，使变化可以被分批引入：

    旧实现继续服务
    → 新实现接入同一稳定入口
    → 一部分流量、功能或数据迁移
    → 比较行为与指标
    → 继续扩大、回退或修正
    → 迁移完成后移除旧路径和临时接缝

一个有效的演进边界至少包含：

1. 新旧实现可以在有限时间内共存；
2. 迁移单位和影响范围可控制；
3. 两条路径具有可比较的结果证据；
4. 数据、配置和外部副作用有独立恢复方案；
5. 旧路径有明确所有者和删除条件。

如果只能一次性切换，或者切换后无法知道结果是否变差，就没有真正的演进能力。

## 代码回滚不等于系统回滚

一次变更可能同时改变多个层面：

| 层面 | 需要回答 |
| --- | --- |
| 代码 | 旧版本能否重新部署？ |
| 配置 | 新旧版本能否读取相同配置？ |
| 数据 | 新写入的数据能否被旧代码理解？ |
| 契约 | 旧客户端和第三方调用者是否兼容？ |
| 缓存 | 旧副本和新键怎样失效？ |
| 外部副作用 | 已发生的操作怎样补偿或人工处理？ |

数据库已经写入新格式时，回滚前端代码并不会恢复旧世界。高风险决策要分别设计代码、数据、契约和副作用的退出路径。

## 为什么大爆炸式重写风险高

一次性重写同时改变边界、状态、工具和运行方式：

    同时变化的假设增多
    → 失败时难以归因
    → 验证只能推迟到集成末期
    → 回退范围接近整个系统

渐进迁移不是永远并行维护两套系统，而是缩小每次变化的假设数量和故障半径。它仍有双轨运行、数据同步和临时适配成本，所以必须给兼容窗口设置期限。

## 原则与后续机制

| 原则层决定 | 后续可选机制 |
| --- | --- |
| 哪些决定需要保留选择权 | Port、Adapter、Facade |
| 怎样限制首次影响范围 | Feature Flag、灰度发布 |
| 新旧契约怎样短期共存 | 版本兼容、扩展再收缩 |
| 数据怎样逐步迁移 | 双读、回填、分批校验 |
| 怎样替换大型旧系统 | Strangler 式渐进迁移 |
| 怎样知道可以继续或回退 | 指标、对照、结构化错误和回执 |

机制不能反过来证明原则成立。没有退出条件的 Feature Flag 只是新的永久分支；没有真实替换风险的 Adapter 只是多余间接层。

## 一个前端框架迁移场景

假设旧应用需要迁移到新渲染框架。先确认真正目标可能是构建速度、首屏性能或团队维护性，而不是“新框架更现代”。

更可逆的路径是：

    保持 URL、接口和设计系统契约稳定
    → 选择一个依赖较少的路由作为迁移单位
    → 新旧页面短期并存
    → 比较用户行为、错误和性能
    → 修正边界后扩大范围
    → 清理旧运行时与兼容代码

如果两个框架共享了不可分割的全局状态和 DOM 控制权，先解决边界问题可能比立即迁移更重要。

## 可观察的错误信号

| 现象 | 可能缺失的可逆性 |
| --- | --- |
| 发布要求所有客户端同一时间升级 | 公共契约没有兼容窗口 |
| 代码回滚后系统仍无法运行 | 数据或配置已经不可逆变化 |
| 供应商类型遍布核心和持久化数据 | 缺少隔离与迁出边界 |
| 新旧系统只能到最后一起验收 | 迁移单位过大，反馈过晚 |
| Feature Flag 数量只增不减 | 临时演进机制没有退出责任 |
| 双写长期存在且结果经常不一致 | 兼容成本已变成永久复杂度 |
| ADR 只写为什么采用，不写何时放弃 | 决策没有复审和退出条件 |

## 做项目时怎么验证

1. 列出决策会写入的数据、公开契约、客户端、团队流程和外部副作用。
2. 分别估算代码、数据、契约和运营层面的撤销成本。
3. 高不确定且高撤销成本的决定，优先寻找最小演进边界。
4. 写清迁移单位、兼容期限、继续指标、回退条件和旧路径所有者。
5. 先迁移影响较小但具有代表性的一段，验证真实收益。
6. 每扩大一次范围都重新检查新增状态和失败路径。
7. 迁移完成后删除 Flag、Adapter、双写和旧文档，回收选择权成本。

## 别误解

- **可逆就是永远不做决定。** 可逆性允许更快试验，但仍需要完成条件和截止时间。
- **抽象越多越容易替换。** 没有真实变化轴的抽象只增加维护成本。
- **能重新部署旧代码就能回滚。** 数据、契约和外部副作用可能已经改变。
- **渐进迁移一定比重写便宜。** 双轨成本过高或旧系统无法切分时，需要重新比较方案。
