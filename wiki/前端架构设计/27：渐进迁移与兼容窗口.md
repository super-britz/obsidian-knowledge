# 渐进迁移与兼容窗口

> [!abstract] 先用一句话说清楚
> 线上系统不能在同一瞬间把全部代码、数据、客户端与缓存原子替换，所以迁移期间必然存在新旧组合。渐进迁移不是“慢慢发版”，而是主动建立一个有期限的兼容窗口：先让每个可达中间状态都安全，再用小迁移单元、稳定分组和可归因证据逐步切换；越过不可逆边界后改用前向修复或补偿，最后删除旧路径，避免临时复杂度永久化。

## 为什么这一篇排在“可逆原则”之后

[[15：可逆决策与演进边界|可逆决策与演进边界]]属于 L3，回答的是：

> 面对不确定未来，哪些决策值得为可逆性付出成本？

本页属于 L4，回答的是：

> 已决定保留退出路径后，怎样用兼容、Flag、分批迁移和证据把它实现出来？

两层不能混为一谈。若任何改动都永久保留双版本、双写和 Flag，兼容成本会持续累积；若高风险变更又没有兼容窗口，一次错误判断就只能全量承受。正确关系是：

    先判断错误代价、未知程度与恢复价值
    → 决定是否值得建立演进边界
    → 选择足够小的迁移机制
    → 达到退出证据后删除临时机制

因此 Flag、双读、双格式和 Canary 不是“架构越成熟越多”，而是为特定不确定性临时购买信息与可逆性。

## 第一性原理：线上替换不是一个瞬间

一次本地赋值可以让旧值瞬间变成新值，线上系统却由多个独立更新的参与者组成：

- 服务实例滚动部署，旧进程与新进程会同时接收流量；
- 浏览器旧标签页可能运行数小时，移动端和小程序客户端可能长期不升级；
- 数据库、消息、LocalStorage、IndexedDB 与 Cache API 保存跨版本状态；
- CDN、Service Worker 和配置服务按各自生命周期传播；
- 第三方消费者和人工流程不受当前团队统一调度。

于是迁移期间真正运行的不是“旧系统或新系统”二选一，而是：

    可达运行组合
    = {旧代码, 新代码}
      × {旧数据, 新数据}
      × {旧客户端, 新客户端}
      × {旧配置或缓存, 新配置或缓存}

组合数量不是为了数学精确，而是揭示不可约约束：**只要这些参与者不能共享一个全局事务，就无法假设它们同时切换。**

因此迁移的研究对象不是代码 Diff，而是一个分布式状态转换：

    旧系统
    → 新旧安全共存
    → 小范围启用新行为
    → 扩大并迁移持久状态
    → 新系统成为唯一权威
    → 删除旧机制

兼容窗口就是其中“新旧安全共存”的有限时间区间。它不追求所有版本永远兼容，只保证迁移真实可经过的状态有效，并为观察、暂停和纠错留出时间。

## 先区分四件常被混用的事

| 层次 | 改变了什么 | 主要控制对象 | 不能单独证明 |
| --- | --- | --- | --- |
| 部署 Deployment | 哪些机器或客户端已经拥有新代码 | 实例、产物、版本 | 用户正在执行新路径 |
| 发布 Release | 哪些请求或用户获得新行为 | 流量、用户、环境、Flag | 持久数据可以安全回退 |
| 迁移 Migration | 事实格式、所有权或依赖关系怎样转移 | Schema、数据、协议、路由 | 新方案产生了产品价值 |
| 实验 Experiment | 一个产品假设如何被因果比较 | 随机分组、指标、样本 | 新版本具备生产安全性 |

它们可以组合：先部署新代码，用 Flag 向 Canary Cohort 发布，同时迁移一部分数据，并在另一个独立实验中验证产品假设。但它们的判断标准不同。

把灰度发布直接叫 A/B 实验，会把“没有报错”误当成“产品更好”；把代码部署成功叫迁移完成，又会忽略旧数据、旧客户端和旧缓存仍在运行。

## 把迁移写成状态机，而不是操作清单

一条可控制的迁移链可以抽象为：

    Prepare
    → Verify readiness
    → Activate a small cohort
    → Expand
    → Cut over authority
    → Bake
    → Retire

    任一可逆阶段
    → Pause / Roll back to a compatible state

每个状态都要声明：

| 契约项 | 必须回答 |
| --- | --- |
| 不变量 | 当前阶段无论成功或失败，什么都不能被破坏？ |
| 迁移单元 | 按用户、租户、记录、地域、实例还是能力切换？ |
| 权威 | 冲突时旧系统还是新系统最终裁决？ |
| 进入证据 | 什么证明可以开始当前阶段？ |
| 继续条件 | 哪些结果允许扩大？ |
| 停止条件 | 哪些错误、差异或预算消耗要求暂停？ |
| 恢复动作 | 关闭新路径、退回兼容版本、前向修复还是业务补偿？ |
| 退出条件 | 什么证明旧路径可以删除？ |
| 所有者与期限 | 谁判断、谁处置、临时机制何时清理？ |

这正是 [[21：状态机与异步流程|状态机]]思想在系统演进中的应用：重点不是步骤名称，而是只允许证据充分的合法转换。没有状态和门槛的“先发一点看看”，遇到异常时没人知道应该等待、继续、回滚还是修数据。

## 兼容性必须落到“谁写、谁读”

“向后兼容”“向前兼容”容易因观察视角不同而歧义。更可靠的做法是直接画 Reader / Writer 矩阵：

| Reader \ Writer | 旧格式 | 新格式 |
| --- | --- | --- |
| 旧 Reader | 必须可读 | 共存期间必须可读，或路由保证永远遇不到 |
| 新 Reader | 必须可读 | 必须可读 |

若旧 Reader 无法理解新 Writer 的输出，就必须先让所有可能读取共享状态的版本获得双格式能力，再允许任何 Writer 产生新格式。AWS 的 Rollback Safety 文章将其概括为 Prepare 与 Activate 两阶段：

1. **Expand / Prepare：** 增加新字段、新格式解析器或新端点，但仍按旧格式写入；
2. **部署 Reader：** 让服务、队列消费者和可控客户端同时理解旧、新两种输入；
3. **验证覆盖：** 用版本指标和兼容样本证明实际 Reader 已就绪；
4. **Activate：** 只对小迁移单元启用新 Writer 或新消费者；
5. **Migrate：** 对历史状态幂等回填，并处理迁移期间的并发写；
6. **Cut over：** 比较语义结果后，让新路径成为唯一权威；
7. **Bake：** 保留兼容版本经过足够观察期；
8. **Contract / Retire：** 没有旧读取、旧写入和回滚依赖后，再删除旧字段、代码与配置。

顺序背后的因果很朴素：

    先升级 Reader，后升级 Writer
    → 新输出始终有人能读

    回退时先停止新 Writer，后考虑缩减 Reader
    → 仍存在的新数据不会被旧代码误读

“新增一个可选字段一定兼容”也不成立。GitHub 的 REST 文档把新增可选字段定义为其契约内的非破坏性变更，但前提是消费者允许未知字段。严格反序列化、封闭枚举、穷举分支、默认值变化和权限语义都可能让语法上的增量变成行为破坏。兼容性不是生产者单方面宣布的属性，而是：

    生产者可能输出的集合
    ⊆ 消费者承诺接受的集合

所以应给 API、序列化状态和本地数据显式记录 Schema / Data Version，并用真实消费者样本验证，不能只比较应用 Build Number。

## Feature Flag 分离“代码存在”与“行为生效”

Feature Flag 的最小模型不是一个散落的 `if`，而是一次可解释求值：

    Variant
    = f(
        Flag Key,
        Environment,
        Context Identity 与属性,
        Flag Configuration Version
      )

它让新代码可以先部署但不立刻暴露，并可按环境、用户、租户或迁移状态逐步启用。OpenFeature 进一步要求调用方提供类型化默认值，详细结果可记录 Variant、Reason 和 Error；提供方异常时返回默认值而不是让业务路径直接抛错。

这仍不代表 `false` 天生安全。若数据库已经只保存新格式，Flag 关闭后走旧 Reader 反而可能崩溃。安全默认值必须同时满足当前数据版本、业务不变量和权限边界。

一个可治理 Flag 至少需要：

- **单一目的：** Release、Experiment、Interoperability、Entitlement 或 Operational，不复用一个 Flag 表达多个决定；
- **稳定分组：** 同一身份在扩量过程中保持 Variant，避免结算或编辑流程走到一半切换；
- **身份转换规则：** 匿名用户登录后是保持原 Cohort、重新分配还是重启流程；
- **服务端权威：** 客户端 Flag 只改变界面和调用路径，授权与业务校验仍由可信服务执行；
- **故障默认值：** 提供方未就绪、超时、类型错误和旧配置时各走哪条安全路径；
- **可归因证据：** 记录 Flag、Variant、Reason、配置版本和 Cohort，但不泄露敏感上下文；
- **Owner、期限与清理单：** 何时删除输家分支、求值代码和服务端配置。

Flag 每增加一个独立布尔分支，理论组合就翻倍；相互依赖的 Flag 还会产生无法测试或根本不该到达的状态。因此应缩小作用域、限制依赖，只测试并观测真实可达组合。LaunchDarkly 的治理指南也强调：100% 放量不是完成，临时 Flag 应先删除旧代码与求值调用，再归档配置。

Kill Switch 同样只是在未来请求上停止某条路径。它不能撤销已经写入的数据、已经发送的通知和已完成的支付；把关闭开关叫“回滚”，会掩盖真正的不可逆边界。

## Canary 的价值是限制未知影响范围

全量发布只产生一个巨大样本，发现问题时所有用户已经暴露；Canary 用较小 Cohort 先获取生产证据：

    小范围启用
    → 与 Control 比较
    → 同时检查绝对 SLO 与业务不变量
    → 满足样本量、持续时间和停止条件
    → 再逐级扩大

Google SRE 指出，Canary 需要“可选择子集 + 可评价结果 + 接入发布流程”三部分。小流量降低总体 Error Budget 消耗，但不会降低一个不可逆错误对单个用户的伤害。因此资金、删除、消息发送等高风险动作还要有审批、额度、Dry Run、影子执行或补偿，不应直接拿真实用户试错。

有效 Canary 还要求：

- Cohort 能代表关键地域、设备、租户、权限和数据规模；
- 指标能归因到版本或 Variant，而不是只看全站平均值；
- 既比较 Control，也检查 Canary 自身是否超过错误率、延迟和任务失败上限；
- 观察时间覆盖缓存冷热、定时任务、长会话和低频错误；
- 同一 Cohort 不同时叠加多个无法拆分归因的变化；
- 放量按固定台阶进行，每一阶都有自动或人工 Stop Gate。

Rolling / Canary Deployment 控制哪些实例承载新二进制；Percentage Rollout 控制哪些上下文执行新行为；Experiment 验证产品因果；Shadow Execution 只比较新路径结果而不把它返回给用户。它们目的不同，不能用同一个“灰度”词替代设计。

## 数据迁移的核心是权威与并发

持久数据一旦改变，迁移就不能只靠关闭前端入口。首先要声明：

> 在每个阶段，发生冲突时哪一份数据是事实来源？

### 回填必须允许中断和重来

历史回填可能运行数小时或数天，期间线上写入仍在继续。可恢复回填需要：

- 以稳定主键或游标分片，记录 Checkpoint 与进度；
- 对同一记录重复执行得到相同结果，即具备幂等性；
- 携带源版本或更新时间，避免旧回填覆盖迁移期间的新写；
- 对失败分片重试，对永久错误进入隔离与人工处置；
- 记录已迁移量、剩余量、Lag、错误量与最后成功位置；
- 完成后按业务语义校验，而不是只比较记录总数。

若回填读取 A 后，线上请求又更新 A，简单脚本可能把旧快照写回新库。解决方式可能是版本条件写、Change Data Capture、增量重放或暂停局部写入，具体选择取决于数据量、停机预算和一致性要求。

### 双读要暴露差异，不能掩盖差异

常见过渡方式有：

- **Shadow Read：** 同时读取旧、新系统，规范化后比较语义结果，但仍只返回权威旧结果；
- **New-first + Old-fallback：** 优先读新系统，缺失或失败时退回旧系统；
- **按迁移标记路由：** 已迁移单元只读新系统，未迁移单元只读旧系统。

Shadow Read 适合在不改变用户结果的前提下验证新系统；Fallback 能提高可用性，却可能长期遮住回填不完整。因此必须记录 `read_source`、Fallback Rate、差异类型与对应迁移单元，并设置退出阈值。

比较也不能机械按字节。字段顺序、时间戳、默认值和最终一致延迟可能不同，应先定义“用户与业务认为相同”的规范化结果和不变量。

### 双写最容易制造两个事实来源

若一次操作独立写旧库和新库：

    写旧库成功
    → 写新库超时
    → 无法知道新库未执行、已执行还是稍后执行

更换顺序不能消除这个窗口。双写需要 Operation ID、幂等、重试、对账、补偿和明确权威；否则只是把迁移风险变成长期数据分叉。

当业务数据与事件能落在同一数据库事务中时，[[raw/links/2026-08-24-AWS Transactional Outbox Pattern|Transactional Outbox]]可以先原子保存业务变更与待发送事件，再异步中继；Relay 仍可能重复发送，所以消费者必须幂等。其他场景可按边界评估事务、CDC 或单写权威加异步复制。原则不是“一律禁止双写”，而是不能把两个独立成功当成原子事实。

## 先标出 Rollback Frontier

迁移前期若新代码尚未产生旧路径无法理解的持久输出，关闭 Flag 或回滚代码通常仍安全。新 Writer 一旦写出不兼容数据，就跨过了 Rollback Frontier：

    Frontier 之前
    → 可以关闭新行为或回滚代码

    Frontier 之后
    → 只能退到仍能读取新旧格式的兼容版本
      或暂停写入、前向修复、迁回数据、执行业务补偿

这就是“代码回滚不等于系统回滚”。数据库记录、消息、邮件、付款和第三方调用不会因为 Git 版本下降而自动消失。高风险迁移必须预先写明：

- 最后一个安全回滚版本是什么；
- 哪个事件会越过 Frontier；
- 过线后是暂停、Forward Fix、反向数据迁移还是补偿；
- 数据恢复耗时是否仍在业务 RTO 内；
- 谁有权限触发以及如何确认恢复完成。

所谓 Blue/Green 也只复制了应用环境。若两套环境共享同一数据库、队列或客户端协议，Schema 与持久状态仍然决定能否安全切回。

## 前端的兼容窗口通常比部署任务更长

前端不能把“服务端实例已全部升级”当成所有 Reader 已升级：

- 旧标签页仍持有旧 JavaScript 和内存状态；
- HTML 与 Chunk 可能来自不同发布版本；
- 浏览器、App 和小程序版本由用户决定何时更新；
- LocalStorage 与 IndexedDB 会跨页面和跨版本持久化；
- Service Worker 和 Cache API 有独立生命周期。

W3C Service Worker 规范明确说明，Cache API 条目不会自动更新或自动过期，Service Worker 脚本升级也不会自动清除旧 Cache。因此前端迁移还要设计：

- **静态资源：** 带内容 Hash 的旧 Chunk 在活跃会话窗口内仍可访问，或加载失败时提供有界安全刷新；
- **HTML / JS：** 记录 Build Version，发现不可兼容组合时停止 Hydration 或操作并取得一致版本；
- **本地数据：** 给 LocalStorage / IndexedDB 记录 Schema Version，迁移可重复执行，避免旧标签页再次按旧格式覆盖；
- **多标签页：** 用版本事件或锁协调切换，无法协调时至少检测并提示刷新；
- **Service Worker：** Cache Name 版本化，明确 Activate、清理、回退与离线时的旧资源策略；
- **API：** 兼容窗口覆盖真实旧客户端生命周期，或明确最低支持版本和可理解的升级失败响应；
- **Feature 路由：** URL、权限、埋点和业务语义保持稳定，新旧页面只是背后的实现不同。

若新旧页面仍直接共享全局可变状态、DOM 约定和私有模块，表面按路由切开，真实变化仍会互相传播。Strangler 的关键不是同时保留两套 UI，而是建立稳定入口和可独立替换的所有权边界。

## 用证据决定扩大与清理

渐进迁移需要把 [[24：失败边界、恢复与可观测性|可观测性]]放进控制回路，而不是发版后才看 Dashboard：

| 证据 | 回答的问题 |
| --- | --- |
| App / Schema / Data Version | 当前代码实际在读写哪种格式？ |
| Phase 与 Cohort | 请求处于迁移哪一步、属于哪一组？ |
| Flag Variant / Reason / Config Version | 为什么走了这条路径，依据哪版配置？ |
| `read_source` 与 Fallback Rate | 新系统是否真的成为读取来源？ |
| Divergence Rate 与差异类型 | 新旧结果在哪些业务语义上不同？ |
| Backfill Progress / Lag / Error | 历史状态是否追上线上变化？ |
| 旧客户端与旧格式使用率 | 是否仍有人依赖兼容路径？ |
| Error、Latency、Task Success | 技术健康和用户结果是否同时成立？ |
| Rollback / Recovery Duration | 退出路径是否在真实时间预算内可用？ |

测试也应覆盖迁移过程，而不只覆盖旧终态和新终态：

1. 旧 Reader 读取新旧数据，新 Reader 读取新旧数据；
2. 先升级再降级时，兼容版本能否处理已经产生的新状态；
3. Flag Provider 超时、未就绪、类型错误和配置陈旧时默认路径是否安全；
4. 用户在流程中途切组、匿名转登录或多标签页并存时是否破坏状态；
5. 回填中断、重复、乱序以及与实时写入竞争时是否覆盖新值；
6. 双写任一侧成功、超时、重试和重复投递时能否对账；
7. 旧 HTML、旧 Chunk、旧 LocalStorage 和旧 Service Worker 组合能否恢复；
8. 越过 Rollback Frontier 后，暂停、前向修复或补偿是否真的可执行。

清理不是按日期盲删，而是证明在规定观察窗口内：

    旧 Reader 使用量 = 0
    且旧 Writer 使用量 = 0
    且回填与对账完成
    且不存在仍需旧路径的支持版本
    且回滚方案不再依赖旧代码

然后按依赖顺序移除旧分支、旧 Schema、迁移任务、观测项与 Flag 配置。若条件长期不成立，应重新评估支持策略，而不是让“临时兼容”无限期成为第二套系统。

## 做项目时怎么设计

1. **列参与者：** 写出所有代码版本、Reader、Writer、数据库、消息、本地状态、缓存、客户端与第三方消费者。
2. **枚举可达组合：** 不追求全排列，只找部署与真实生命周期中确实可能同时存在的组合。
3. **声明不变量和权威：** 哪些数据不能丢、不能重复、不能越权，冲突由谁裁决。
4. **选择最小迁移单元：** 优先能独立暂停和核对的用户、租户、记录、路由、地域或实例。
5. **画 Reader / Writer 矩阵：** 先补读取兼容，再启用新写入；不兼容组合必须被路由阻断并可验证。
6. **标记 Rollback Frontier：** 分别写清过线前后的恢复动作，不用“可回滚”一词掩盖差异。
7. **设计证据与 Gate：** 每一阶段都有进入、继续、停止和退出阈值，并能归因到版本与 Cohort。
8. **绑定清理责任：** 临时 Flag、旧代码、旧字段、旧 Cache 和迁移指标都有 Owner、截止时间与删除顺序。

若变更完全局部、无持久状态、瞬间可替换且失败影响很小，直接发布可能比建立整套兼容机制更合理。机制复杂度必须小于它要控制的未知风险。

## 可观察的错误信号

| 现象 | 更可能缺少的机制 |
| --- | --- |
| Flag 已 100% 开启半年，旧分支仍在 | 没有退出条件、Owner 和代码清理阶段 |
| 关闭 Flag 后页面反而崩溃 | 新数据已越过 Rollback Frontier，默认旧路径不再兼容 |
| 同一用户刷新后随机进入不同版本 | Cohort 身份或分桶不稳定 |
| 客户端隐藏按钮，但直接请求仍能操作 | 把 Feature Flag 当成服务端授权 |
| 回填显示 100%，Fallback 仍很高 | 只统计搬运数量，没有记录真实读取来源 |
| 新旧系统数据偶发分叉 | 独立双写没有原子交接、幂等和对账 |
| 代码回滚后错误继续增加 | 共享数据、消息或缓存已经写成旧版本无法理解的格式 |
| 新版发布后仍有用户运行旧页面 | 忽略旧标签页、客户端升级与 Service Worker 生命周期 |
| 全站平均正常，某地区或大租户失败 | Canary 样本和指标没有覆盖关键分群 |
| 兼容逻辑越来越多但没人敢删 | 没有为临时机制定义期限和删除证据 |

## 别误解

- **渐进迁移就是把发布速度调慢。** 慢而没有兼容状态、停止门槛和恢复动作，只会把故障拖得更久。
- **Feature Flag 就是一个 `if`。** `if` 只实现分支，完整机制还包括稳定求值、故障默认、证据、权限边界和生命周期。
- **增加可选字段永远不破坏客户端。** 只有消费者契约允许未知字段和新值时才兼容，业务语义也可能改变。
- **代码能回滚，系统就能回滚。** 持久数据与外部副作用不会随代码自动撤销。
- **双写能让新旧系统更一致。** 跨边界的两个独立写入反而新增部分成功状态，必须有权威、幂等和对账。
- **Canary 成功就证明产品实验成功。** 它主要证明生产安全性；产品因果需要另一套实验设计。
- **兼容保留越久越安全。** 时间越长，分支、攻击面、测试组合和理解成本越高；兼容窗口必须有期限。
- **旧路径留着总能应急。** 未持续验证的旧路径会腐化，并可能已无法读取新数据，只制造虚假的安全感。

## 复习

1. 为什么线上迁移无法被建模成“旧版本瞬间替换为新版本”？
2. 兼容窗口为什么必须有限，而不是永久支持所有历史状态？
3. 部署、发布、迁移和实验分别改变什么，为什么不能混用证据？
4. 为什么应先升级 Reader，再允许 Writer 产生新格式？
5. Feature Flag 的安全默认值为什么不能机械设为 `false`？
6. Shadow Read、Fallback Read 和 Dual Write 分别会隐藏或新增什么风险？
7. 什么是 Rollback Frontier，越过它以后为什么代码回滚可能不再安全？
8. 前端为何要把旧标签页、本地存储与 Service Worker 纳入兼容矩阵？
9. 哪些证据足以证明旧路径可以真正删除？

## 来源与下一步

- **来源事实：** AWS Rollback Safety 文章说明分布式部署会让新旧版本共存，并用 Prepare / Activate 两阶段保证先升级 Reader、后启用 Writer；Google SRE 把 Canary 定义为部分、限时、带 Control 与评价门槛的发布；OpenFeature 规定类型化默认值及 Variant、Reason、Error 等求值结果；LaunchDarkly 指南区分临时与永久 Flag，并要求稳定后删除代码再归档配置；GitHub 文档给出其 REST API 的 Breaking / Non-breaking 分类；AWS Transactional Outbox 说明独立双写的部分失败问题与本地事务加异步中继；W3C 说明 Cache API 条目和旧 Cache 不会随 Service Worker 升级自动更新或删除。
- **机制推导：** 由独立更新参与者推出“迁移是分布式状态转换”；用可达组合、Reader / Writer 矩阵和 Rollback Frontier 定义兼容边界；把渐进迁移统一为 Prepare、验证、局部启用、扩大、权威切换、观察与清理的有限状态机；将 Flag、Canary、双读、回填和 Outbox 放回各自负责的控制对象。
- **工程建议：** 先列参与者、不变量、权威和可达组合，再选择最小迁移单元；每个阶段绑定版本、Cohort、进入与停止证据，越过 Frontier 前后采用不同恢复动作；用旧路径零使用、回填对账完成和支持版本退出证明可以 Contract，而不是长期保留临时兼容。
- **待项目验证：** 兼容多久、哪些版本组合必须支持、Cohort 怎样分层、何时越过 Rollback Frontier、哪些证据允许扩量或删除旧路径，都必须结合真实客户端生命周期、数据副作用和事故风险决定。
