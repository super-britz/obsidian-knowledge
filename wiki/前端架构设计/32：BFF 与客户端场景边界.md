# BFF 与客户端场景边界

> [!abstract] 先用一句话说清楚
> 用户任务按页面和交互组织，后端能力却按业务事实与所有权组织，两种边界天然不会总是一致。BFF 在可信服务端为一类客户端体验聚合、裁剪和适配后端能力，减少公网往返与客户端对后端拓扑的耦合；它没有消灭复杂度，而是用额外网络层、部署、安全、容量和故障责任换取更低的客户端协调成本。

## 为什么 BFF 属于 L5

[[22：Adapter、Repository 与依赖注入|Adapter]]已经说明怎样在一份应用代码内翻译外部协议，[[23：运行时 Schema 与错误模型|运行时 Schema]]和[[24：失败边界、恢复与可观测性|失败控制]]也分别提供了边界机制。BFF 属于 L5，是因为它把多种机制组合成一个**可独立部署、承接真实流量的客户端场景边界**：

- 对外拥有客户端可依赖的接口契约；
- 对内连接多个领域服务或平台能力；
- 执行身份、授权、数据裁剪和协议适配；
- 管理并发、超时、部分失败、缓存和追踪；
- 拥有容量、发布、兼容、值班和恢复责任。

因此，一段封装 `fetch` 的函数不是 BFF；把 Node.js 放在浏览器与后端之间也不自动得到 BFF。只有当这层对一类用户体验形成了稳定责任闭环，它才是一种系统形态。

## 第一性原理：页面边界与领域边界不一致

一个商品详情或结算页面可能需要商品、价格、库存、会员权益和推荐数据；这些事实不应该因为恰好显示在同一屏，就由同一个领域服务拥有。领域服务更适合围绕业务不变量、数据权威和组织所有权划分，客户端则围绕一次用户任务组织信息：

```text
客户端场景：完成一个用户任务
领域服务：维护一组长期成立的业务事实
```

若浏览器直接组合所有领域服务：

```text
客户端
├→ 商品服务
├→ 价格服务
├→ 库存服务
├→ 会员服务
└→ 推荐服务
```

客户端就必须知道服务拓扑、认证方式、字段差异、调用顺序和每种失败语义。每增加一个依赖，都会增加公网连接、版本组合和失败组合；移动网络、高延迟环境和不能即时更新的客户端会把这些成本进一步放大。

BFF 把场景组合移到更靠近后端、也更可信的执行边界：

```text
客户端 → 场景契约（BFF）
                  ├→ 商品服务
                  ├→ 价格服务
                  ├→ 库存服务
                  ├→ 会员服务
                  └→ 推荐服务
```

核心交换是：

```text
没有 BFF 的成本
≈ 客户端编排 + 公网往返 + 后端拓扑泄漏 + 客户端版本协调

使用 BFF 的成本
≈ 额外网络跳转 + 聚合运行时 + 容量与发布 + 安全与故障责任
```

只有前一组被节省的成本持续大于后一组新增成本，BFF 才有净价值。

## BFF 真正执行的是一次“场景翻译”

一条典型读取链路是：

```text
用户请求 + 会话 + 客户端上下文
→ 解析并校验输入
→ 认证主体并授权动作
→ 选择场景所需下游能力
→ 按依赖关系并发或顺序调用
→ 校验并翻译下游响应
→ 应用超时、降级和新鲜度规则
→ 组装稳定的页面 ViewModel
→ 返回结果、完整性与诊断关联信息
```

这里真正稳定的是**场景契约**，不是某个下游 JSON 的镜像。BFF 可以把后端迁移和字段变化挡在客户端之外，但前提是它把下游 DTO 转成自己的输出模型，而不是原样透传。

复杂度并未消失：原来散落在多个客户端的编排、转换和恢复逻辑，现在集中成了一个服务端责任。集中之后更容易统一修复和观察，也意味着这层故障会同时影响整类用户任务。

## 先分清 BFF 与相邻概念

| 概念 | 主要回答的问题 | 不自动负责什么 |
| --- | --- | --- |
| BFF | 某类客户端体验需要怎样的服务端场景契约？ | 领域事实的最终裁决 |
| API Gateway | 外部流量怎样统一进入、路由、限流和执行通用策略？ | 每个体验的复杂业务组合 |
| Reverse Proxy | 请求怎样转发到目标服务？ | 语义裁剪、场景所有权 |
| Gateway Aggregation | 怎样把一次客户端操作所需的多个调用聚合起来？ | 是否应按客户端拆分及由谁拥有 |
| SSR | HTML 在何时、何处生成？ | API 所有权、授权和数据权威 |
| GraphQL | 客户端怎样按 Schema 表达字段需求？ | 服务边界、成本控制、失败与部署责任 |
| Domain Service | 哪个服务维护业务不变量和权威事实？ | 某个页面的展示形状 |
| 本地 Adapter | 应用内部怎样隔离外部协议或 SDK？ | 独立运行时、容量和服务级目标 |

这些概念可以组合：API Gateway 先执行通用入口策略，再路由到不同 BFF；BFF 可以提供 REST 或 GraphQL，可以给 CSR 客户端返回 JSON，也可以被 SSR 层调用。组合关系不能反过来证明它们是同一个概念。

GraphQL 能让客户端按字段取数，确实可能消除一部分固定接口的过度获取；但 Resolver 在哪里运行、谁拥有 Schema、怎样授权字段、限制查询成本、处理跨服务失败，仍然是架构问题。协议灵活性不能替代责任边界。

## 场景边界不是“一个设备一个服务”

“每个前端一个 BFF”容易被机械理解。更稳妥的拆分依据是：一组请求是否因**同一类体验变化**而共同变化，并能否由一个团队端到端负责。

可以同时检查四件事：

1. 数据形状、交互流程和性能约束是否实质不同？
2. 发布节奏与兼容窗口是否不同？
3. 可靠性、权限或地域要求是否不同？
4. 是否有团队能同时修改客户端和 BFF，并处理线上故障？

手机和桌面端若请求相同、同团队维护、同节奏交付，共用一个场景服务可能最简单；同为“手机”，iOS 与 Android 若由不同团队、生命周期和能力差异长期驱动，也可能需要分开。边界应跟随稳定的变化原因，不跟随设备标签。

两个极端都要避免：

```text
每个页面一个 BFF
→ 服务数量、重复代码和运维负担爆炸

所有客户端共用一个通用 BFF
→ clientType 条件不断增长
→ 重新形成中心团队和共享发布瓶颈
```

## 聚合性能由关键路径决定

“客户端只发一个请求”不等于“页面一定更快”。端到端时间更接近：

```text
总时间
≈ 客户端 ↔ BFF
  + 内部依赖图的最长关键路径
  + 排队与组装
```

互不依赖的请求可以并行；必须先拿到用户区域才能查询价格时，后一个调用仍在前一个调用的关键路径上。把五个请求写进 `Promise.all` 只改变等待方式，不会消除最慢依赖，也可能瞬间耗尽下游连接池。

还要观察请求放大：

```text
内部调用量
≈ 客户端请求量 × 每次 Fan-out × 每层尝试次数
```

如果客户端、BFF 和下游 SDK 都各自重试，底层流量会相乘。更可靠的约束是：

- 为整次用户操作设置 Deadline，再向下游传播剩余预算；
- 客户端已离开且结果不再有用时，传播取消并释放资源；
- 只在明确可重试、重复安全且仍有预算时重试；
- 一个调用链只指定一个主要重试责任层；
- 限制单请求 Fan-out、并发、响应大小和下游连接池；
- 用负载测试验证 BFF 不会成为瓶颈或级联失败放大器。

BFF 的性能收益应由公网请求数、传输字节、关键路径和真实任务时间证明，而不是由接口数量看起来变少证明。

## 先定义完整结果，才能处理部分失败

聚合请求把多个下游命运绑定到一次用户操作。设计前要按任务语义分类：

| 数据角色 | 失败时的行为 | 示例 |
| --- | --- | --- |
| 必需事实 | 整个动作失败或进入明确不可继续状态 | 结算价格、可售库存 |
| 可选增强 | 返回部分结果并明确缺失能力 | 推荐列表、营销装饰 |
| 可接受旧值 | 返回带时间和来源的降级副本 | 非关键统计、说明信息 |
| 可延后内容 | 拆成后续请求或流式区域 | 首屏之外的评论 |

部分成功必须是契约的一部分。若推荐服务失败，页面可以隐藏推荐区；若价格失败，却返回 `200` 并让金额默认为 `0`，就是把关键失败伪装成成功。

输出至少应让客户端知道：

- 哪些必需事实已经验证；
- 哪些可选区域缺失或降级；
- 数据截至什么时间、来自缓存还是权威源；
- 用户可以继续、重试、刷新还是必须停止。

具体字段可以不同，但“完整性、新鲜度和恢复动作”不能只存在于日志里。每个下游输入仍需经运行时 Schema 解析，并映射到[[23：运行时 Schema 与错误模型|稳定错误模型]]。

## BFF 可以编排用例，不能篡夺事实所有权

判断一条逻辑属于哪里，可以问：

> 如果去掉当前客户端，这条规则是否仍必须对所有渠道成立？

- 若答案是“是”，它通常属于领域服务：价格计算、库存扣减、额度、对象权限和订单状态不变量都必须由权威服务执行。
- 若答案是“否”，且它只随该体验变化，BFF 可以拥有：字段裁剪、展示分组、分页适配、可选模块组合和客户端专属工作流映射。

对写操作，一条安全链路更接近：

```text
客户端提交命令与幂等标识
→ BFF 校验场景契约和身份上下文
→ 领域服务重新授权并验证业务不变量
→ 权威服务执行状态转换
→ BFF 把结构化回执映射给客户端
```

BFF 可以协调一次用户用例，却不能仅凭自己算出的价格或权限直接写库。跨多个服务的写入也不是因为有了 BFF 就变成原子事务；它仍需要状态机、幂等、补偿、结果查询或消息一致性机制。

一旦多个 BFF 各自复制核心业务规则，它们会形成多个事实版本。短期看客户端更自主，长期会出现“Web 能下单、App 被拒绝”之类渠道分叉。

## 聚合缓存同时继承所有数据约束

一个聚合响应可能同时包含公开商品说明、用户权益、实时价格和推荐。它能否复用，不由最容易缓存的字段决定，而受所有组成数据中最严格的身份、权限和新鲜度要求约束。

```text
聚合 Cache Key
至少覆盖各组成数据 Key 所需的身份、租户、权限、查询、语言和版本维度
```

漏掉其中一个维度，可能把用户 A 的权益返回给用户 B；统一使用最短有效期虽然更安全，却可能让稳定公共内容也频繁回源。常见改进不是不断堆缓存规则，而是重新拆分：

```text
稳定公开数据 → 可共享缓存
私有或高频变化数据 → 用户隔离、短时或不缓存
可选增强数据 → 独立失败与独立新鲜度
```

BFF Cache 仍是[[25：缓存与数据一致性|受控副本]]：必须声明 Key、权威来源、新鲜度、失效、删除、观测和回源责任。聚合不会绕过缓存一致性，只会把多个副本协议叠在一起。

## 进入可信服务端，也进入新的安全边界

BFF 可以把不应暴露于浏览器的服务凭据和一部分令牌职责留在服务端。RFC 10017（BCP 212）描述的 OAuth BFF 会作为机密 Client 保存 Token，并让浏览器只持有会话 Cookie；这能降低 Token 直接暴露给浏览器脚本的风险。但该规范描述的是浏览器 OAuth 安全架构，不等于所有数据聚合 BFF 都必须采用这种实现。

服务端拥有更强网络和凭据能力，也使 BFF 可能成为 **Confused Deputy**：攻击者让一个有权限的 BFF 代替自己调用本无权访问的资源。安全边界至少包括：

- 所有入站值按 `unknown` 解析，限制长度、数量、方法和内容类型；
- 每次请求都按主体、租户、对象和动作重新授权，不能相信隐藏按钮；
- 下游凭据采用最小权限，并保留最终用户身份或可审计上下文；
- 只允许调用显式配置的协议、主机、端口和路径，不能把用户 URL 直接变成通用代理；
- 不盲目转发全部 Header、Cookie、Token、PII 或下游错误；
- Cookie 会话必须单独设计 CSRF、Secure、HttpOnly、SameSite、Origin 和会话生命周期；
- 设置限流、请求体上限、Deadline 和审计日志。

`HttpOnly` 能阻止脚本直接读取 Cookie，却不能阻止已在页面执行的恶意代码借当前会话发起请求。BFF 缩小一种凭据暴露面，不会自动消除 XSS、CSRF 和对象级越权。

## 新增一层，就新增一套运行责任

BFF 处在关键用户路径上，必须有人对以下闭环负责：

```text
需求 → 契约 → 实现 → 部署 → 监控 → 值班 → 恢复 → 清理
```

较自然的分工是：体验团队拥有客户端及其 BFF；领域团队拥有权威服务和业务不变量；平台团队提供通用入口、身份、运行时、部署和观测能力。若 BFF 由另一个中心团队统一接单，它很容易重现原本要消除的等待队列。

关键证据不能只有一个总接口耗时。一次请求至少要能关联：

- BFF 自身排队与处理时间；
- 每个下游的调用次数、耗时、状态和尝试次数；
- 关键路径、Fan-out 与连接池状态；
- 完整成功、部分结果、缓存降级和超时比例；
- Client Version、Contract Version、Trace ID 与脱敏后的错误类别。

全链路 Trace 可以把一次客户端操作与下游 Span 连接起来；Metric 用来发现比例和趋势；Log 保存离散决策证据。三者仍要围绕“用户为什么没有完成任务”设计，而不是只证明服务器返回了响应。

## 同团队交付也不是原子切换

前端和 BFF 由同团队维护，可以同时设计契约，却不代表它们同时到达用户：

```text
BFF 新版本已部署
≠ CDN 中旧资源已消失
≠ 用户旧标签页已刷新
≠ App / 小程序已经审核并升级
≠ 回滚后旧 BFF 一定理解新客户端
```

因此仍要按[[27：渐进迁移与兼容窗口|Reader / Writer 兼容窗口]]设计：

- 明确旧客户端的支持期限和可识别版本；
- 先让 BFF 同时接受新旧请求，再发布新客户端；
- 下游变更先兼容 BFF 的旧读写方式，再切换流量；
- 回滚时同时检查客户端契约、缓存、数据和下游副作用；
- 迁移结束后删除临时字段、分支和翻译层。

BFF 可以保护客户端免受一次后端迁移影响，但如果临时适配器永不清理，它会变成记录所有历史版本的“协议考古层”。

## 一个商品结算场景

假设页面需要以下数据：

| 数据 | 权威方 | 场景要求 |
| --- | --- | --- |
| 商品标题与说明 | 商品服务 | 公开、变化慢，可共享缓存 |
| 当前价格 | 定价服务 | 必需、用户与区域相关，需明确时间 |
| 可售库存 | 库存服务 | 必需、变化快，提交时仍须重新验证 |
| 会员权益 | 会员服务 | 私有、按用户授权 |
| 推荐商品 | 推荐服务 | 可选，失败不阻止购买 |

BFF 可以并行读取互不依赖的数据，给价格与库存设置严格 Deadline，让推荐失败只影响推荐区，并向客户端返回场景 ViewModel。页面从五个公网接口变成一个场景接口，但内部仍保留五种事实所有权。

用户点击购买时，BFF 只负责把身份、商品、数量和幂等标识转换成下单命令；订单或交易领域服务必须重新校验价格、库存和权限。若 BFF 自己缓存价格、计算优惠并直接写订单表，它就越过了场景边界，成为没有清楚所有权的第二套交易系统。

## 什么时候采用，什么时候保持简单

更值得采用 BFF 的信号：

- 一个关键任务长期需要组合多个领域服务；
- 不同客户端的交互、数据形状、网络或发布约束确实不同；
- 公网瀑布请求、传输量或后端拓扑耦合已有可测成本；
- 需要在服务端保护 Token、会话或第三方凭据；
- 体验团队能拥有部署、容量、安全、值班和兼容窗口。

优先保持直接调用、任务型 API 或较轻聚合的信号：

- 只有一个简单客户端，后端已经按用户任务提供稳定接口；
- 多个客户端实际请求相同，只是技术栈或屏幕尺寸不同；
- 需求只是隐藏 CORS、改几个字段名或把所有接口换个域名；
- 团队没有服务端运行与事故响应能力；
- 方案会把核心业务规则复制进多个 BFF；
- 一个通用 BFF 已开始靠大量 `clientType` 分支平衡所有人。

可以用定性公式约束讨论：

```text
BFF 净收益
≈ 节省的公网通信、客户端编排和跨团队等待
  - 新增的延迟、服务数量、运维、故障与安全成本
```

不要先建立“统一 BFF 平台”再寻找用途。选一条高价值、高调用扇出的用户旅程做 Pilot，证据成立后再扩展边界。

## 可观察的错误信号

| 现象 | 更可能的边界问题 |
| --- | --- |
| BFF 只是透明转发所有后端 DTO | 新增跳转，却没有形成场景契约 |
| 一个 BFF 充满客户端类型条件 | 边界过粗，变化原因没有分开 |
| 每个页面都部署独立服务 | 边界过细，运维和重复代码超过收益 |
| BFF 直接查多个领域数据库 | 绕过权威服务，数据所有权模糊 |
| 价格、权限等规则在多个 BFF 复制 | 渠道产生不同业务事实 |
| 所有下游都放进一次 `Promise.all` | 没区分依赖、必需数据与可选数据 |
| 每层都自动重试 | Fan-out 与重试相乘，放大故障 |
| 下游失败后仍返回无标记的 `200` | 部分结果被伪装成完整成功 |
| BFF 用高权限服务账号代表所有用户 | 形成 Confused Deputy 和越权面 |
| 只有总耗时，没有下游关联信息 | 无法定位关键路径和故障责任 |
| 体验团队改接口仍要向中心团队排期 | 名称是 BFF，所有权闭环没有改变 |

## 做项目时怎么验证

1. **先画现状：** 选一条关键用户旅程，记录客户端请求数、字节、依赖图、P75 / P95 任务时间、失败率和跨团队等待。
2. **声明边界：** 写清 BFF 服务哪类体验、谁拥有、哪些是场景逻辑、哪些规则必须留在领域服务。
3. **定义契约：** 标出必需、可选、可旧和可延后数据，以及完整性、新鲜度、错误和恢复动作。
4. **设资源预算：** 限制 Deadline、Fan-out、并发、尝试次数、响应大小、连接池和缓存范围。
5. **做故障注入：** 让每个下游分别慢、错、返回坏 Schema 或未授权，验证整体失败、部分结果、取消与追踪。
6. **做安全验证：** 直接调用隐藏端点，测试跨用户/租户访问、CSRF、Header 注入、任意目标代理、限流和敏感数据日志。
7. **做容量验证：** 压测聚合层和下游，观察排队、连接池、缓存击穿、重试放大与级联失败。
8. **做版本验证：** 组合旧客户端、新 BFF、旧 BFF、新下游和回滚路径，验证兼容窗口而非只测最新版本。
9. **比较净收益：** 上线后重新测任务时间、请求量、故障归因、交付等待和事故负担；没有持续收益就合并或移除这一层。

## 来源与认识边界

- **来源事实：** 课程材料将 BFF 概括为前端通过 Node.js 编排、裁剪后端接口，并提醒前端团队会同时承担服务器运行责任；Azure BFF 模式说明了客户端定制、服务拆分成本和不适用条件；Azure Gateway Aggregation 说明了公网往返收益、单点与瓶颈、部分结果、容量和追踪责任；Sam Newman 的原始文章说明了用户体验与团队自治；RFC 10017、OWASP 和 GraphQL 官方资料分别支撑 OAuth BFF、授权与代理安全、查询机制的能力边界。
- **机制推导：** 本页用“客户端任务边界与领域事实边界天然不一致”推导场景翻译层，再由一次请求的内部依赖图推导关键路径、Fan-out、部分失败、缓存和可观测性责任。
- **工程建议：** 按稳定体验变化和责任闭环划分 BFF；领域服务保留业务不变量；明确必需与可选数据；设置 Deadline、重试与容量预算；用最小权限、逐请求授权、目标允许列表和全链路证据保护边界。
- **待项目验证：** 是否需要 BFF、拆几个、采用 REST 还是 GraphQL、是否承接 OAuth 会话、哪些内容可部分返回，都必须由具体用户旅程、网络、客户端生命周期、团队能力和故障数据验证。
