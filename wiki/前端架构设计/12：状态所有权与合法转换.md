# 状态所有权与合法转换

> [!abstract] 先用一句话说清楚
> 状态是系统为了决定当前输出和下一步行为而必须保留的最小历史信息。状态设计先回答“哪个事实由谁裁决、谁能修改、怎样合法变化”，再决定放在组件、URL、查询缓存还是状态库；共享范围大不等于应该全局化。

## 从状态空间增长推导

前端输出不仅取决于当前输入，还取决于过去发生过什么，因此必须保存状态：

    当前输出 = 当前输入 + 必要历史状态

但每增加一个独立状态，系统需要处理的组合都会增加。两个布尔值有 4 种组合，三个有 8 种；如果其中一些组合不合法，代码就要不断补充条件。

同一个事实保存多份会进一步产生矛盾：

    items = [A, B]
    itemCount = 3

此时系统无法从数据本身判断哪个值是真的。底层目标因此是：

1. 只保存无法从其他事实推导出的最小状态；
2. 一个事实只有一个权威裁决者；
3. 状态只能通过保持业务不变量的合法转换变化。

## 所有者不是“拿到值的组件”

状态所有者是有权裁决该事实、定义合法写入并负责其生命周期的一方。判断所有权至少要回答：

| 问题 | 含义 |
| --- | --- |
| 谁创建它？ | 初始事实从哪里产生？ |
| 谁能修改？ | 哪些事件具有写权限？ |
| 谁保证不变量？ | 什么组合永远不能出现？ |
| 活多久？ | 一次渲染、页面、会话还是长期持久化？ |
| 失败后怎样恢复？ | 丢失、超时或冲突时以谁为准？ |

组件读取服务端用户资料，不代表组件拥有资料；Context 转发某个值，也不自动成为该值的权威来源。

## 先区分状态的语义身份

| 状态语义 | 常见权威来源 | 关键问题 |
| --- | --- | --- |
| 局部交互 | 当前组件或局部流程 | 离开界面后是否仍需存在？ |
| 导航与筛选 | URL / Router | 刷新、分享和前进后退是否应保留？ |
| 服务端事实 | 服务端数据存储 | 本地只是缓存、草稿还是乐观副本？ |
| 用户草稿 | 当前编辑流程 | 何时提交、放弃或与服务端合并？ |
| 会话身份 | 认证会话 | 过期、切换用户和多标签页如何处理？ |
| 外部环境 | 浏览器、设备或系统 API | 怎样订阅变化并清理？ |
| 派生结果 | 不单独拥有 | 能否每次从现有事实计算？ |

“服务端资料”和“尚未提交的编辑草稿”即使字段完全相同，也是两个语义不同的状态；前者由服务端裁决，后者由当前编辑流程拥有。复制是否合理取决于语义，不取决于对象长得是否相同。

## 单一事实来源不等于单一 Store

单一事实来源的含义是：发生冲突时，存在唯一裁决规则。它不要求把整个应用放进一个全局对象。

一个事实可以有缓存和副本，但必须显式说明：

    权威来源
    → 副本何时创建
    → 允许旧多久
    → 谁使它失效
    → 冲突时覆盖、合并还是拒绝

如果这些规则不存在，副本就会悄悄变成第二个写入源。查询缓存、localStorage、IndexedDB 和 Service Worker 都不会自动解决权威与一致性问题。

## 合法转换比任意赋值更重要

状态变化可以统一理解为：

    当前状态 + 事件
    → 检查前置条件和业务不变量
    → 新状态 + 需要执行的副作用

例如订单不能从“已取消”直接进入“已支付”。如果任何组件都能直接写任意字段，规则只能散落在调用者中，系统就无法保证转换合法。

简单局部状态可以直接更新；当流程包含多个阶段、失败、取消、重试或并发时，应先写清合法状态和事件，再选择 Reducer 或状态机等机制。

## 异步意味着同时存在多条时间线

用户操作和网络响应独立推进：

    搜索 A 发出
    → 搜索 B 发出
    → B 先返回并展示
    → A 后返回，错误覆盖 B

仅有 loading、data、error 三个变量不足以说明响应属于哪次请求。异步状态还需要请求身份、版本、取消或“只接受最新结果”等裁决规则。

乐观更新同样不是把本地值直接当成事实，而是：

    本地暂时预测
    → 服务端确认或拒绝
    → 提交、回滚或重新协调

## 一个编辑资料的例子

编辑页面至少包含三类状态：

    serverProfile：服务端已确认事实
    draftProfile：用户尚未提交的草稿
    saveProcess：idle / submitting / success / failure

它们不能合成一个含糊的 profile：

- 服务端刷新不应无条件覆盖未提交草稿；
- 提交成功后才能用响应更新服务端事实；
- 失败只改变保存流程，不应让草稿消失；
- 放弃编辑时，草稿才重置为已确认事实。

先区分语义身份和转换规则，之后才能合理选择组件状态、查询缓存或状态机。

## 可观察的错误信号

| 现象 | 可能的状态设计问题 |
| --- | --- |
| 用 Effect 在两个状态之间持续同步 | 同一事实可能被保存了两份 |
| 组件状态和全局 Store 都能修改同一对象 | 权威来源和写权限不明确 |
| 多个布尔值能组成 loading 且 success | 合法状态没有显式建模 |
| 页面刷新或返回后状态意外丢失 | 生命周期或 URL 归属选择错误 |
| 旧请求覆盖新结果 | 缺少异步身份和冲突裁决 |
| 切换用户后看到上一用户数据 | 会话边界、缓存键或清理责任错误 |
| 全局状态变化导致大量无关渲染 | 状态范围、订阅粒度或数据模型过大 |

## 做项目时怎么验证

1. 用业务语言列出事实，不先列 Store 字段。
2. 为每个事实标记权威来源、允许的写入入口、生命周期和使用范围。
3. 删除能从其他事实稳定计算出的派生状态。
4. 对副本写清新鲜度、失效、冲突和恢复规则。
5. 列出允许的事件与转换，尝试构造非法组合。
6. 模拟乱序响应、重复操作、切换用户、刷新和卸载。
7. 最后才根据范围、更新频率和流程复杂度选择状态机制。

## 别误解

- **共享状态就应该放进全局 Store。** 共享描述读取范围，所有权描述谁裁决，两者不是一回事。
- **不可变更新解决状态设计。** 它让变化更容易观察，但不能消除重复事实或错误所有权。
- **缓存就是状态权威。** 缓存是副本；除非系统明确把它设计为可离线写入的事实来源。
- **状态库能够统一状态。** 它统一的是存储和订阅方式，不会自动定义语义、生命周期和合法转换。

## 复习

1. 为什么单一事实来源不等于只能有一份数据？
2. 服务端资料和表单草稿字段相同，为什么仍是两个状态？
3. 只有 loading、data、error 为什么不足以处理乱序请求？
4. 选择状态库之前必须先回答哪些所有权问题？
