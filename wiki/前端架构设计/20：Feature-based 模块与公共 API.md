# Feature-based 模块与公共 API

> [!abstract] 先用一句话说清楚
> Feature-based 模块把完成同一用户能力、因同一原因变化的代码放在一起；公共 API 只暴露其他模块真正需要依赖的稳定能力；依赖规则阻止调用方绕过入口。目录只能告诉人“代码在哪里”，三者合起来才能让逻辑边界成为可持续的代码边界。

## 从“源码导入就是依赖”推导

[[10：按变化原因建立边界|变化边界]]首先是一个逻辑判断，但代码最终通过导入关系连接。假设优惠功能的组件、状态、接口和规则分别放进全局 `components/`、`stores/`、`services/` 和 `utils/`：

    修改一次“使用优惠券”能力
    → 在多个技术目录寻找上下文
    → 同一变化分散，不同功能在公共目录中碰撞
    → 理解、测试和回滚范围扩大

把这些文件移入 `features/coupon/` 能让共同变化靠近，却还没有完成封装。如果结算、订单和营销模块都能导入 `coupon/store`、`coupon/queryKey` 或内部 DTO，那么这些实现细节事实上已经成为外部契约：

    任意内部路径都可被导入
    → 外部依赖内部结构和临时决策
    → 移动文件或更换状态实现也会破坏调用方
    → 目录边界退化为视觉分类

因此需要一条完整机制链：

    真实变化流
    → Feature 内聚共同变化
    → 公共 API 缩小跨边界承诺
    → 依赖规则禁止绕过入口
    → 内部重构主要停留在模块内部

## Feature 不是页面或文件类型

Feature 是一组能够用用户或业务语言命名、共同完成某项能力的规则、状态转换和界面，例如“使用优惠券”“提交结算”或“修改收货地址”。它不是以下任一概念的同义词：

- **不是页面：** 一个页面可以组合多个 Feature，一个 Feature 也可能出现在多个路由。
- **不是组件：** 组件只是它可能拥有的一种表现形式，Feature 还可能包含用例、状态和外部适配。
- **不是固定层级：** 小 Feature 可以先保持扁平；只有内部出现独立变化原因时，再拆 `ui`、`domain`、`api` 等子边界。
- **不是所有代码：** 路由装配、运行时配置、设计系统和通用平台能力有自己的变化原因，不必伪装成业务 Feature。

判断依据仍然是：这些代码是否在多数真实需求中一起变化、共享业务不变量，并由同一责任主体维护，而不是目录模板是否对称。

## 三道机制怎样配合

### 1. 共同变化的代码就近放置

先建立能独立说清职责的 Feature 目录，把组件、测试、状态、用例和适配器放回它们服务的能力附近。就近放置降低寻找上下文和跨目录修改的成本，但模块内部仍可自由重构。

### 2. 只承诺有意设计的公共 API

公共 API 不是专指 HTTP 接口，而是其他模块被允许依赖的全部导出：组件、命令、查询、事件和必要类型。它应表达稳定能力，例如“应用优惠券”，而不是暴露 `couponStore`、缓存键、Reducer、原始服务端 DTO 等内部实现。

`index.ts` 可以集中声明入口，但它本身只是约定；`export *` 若把所有内部符号重新暴露，只是把深层导入换了写法。一个大入口造成循环或让不同消费者承担无关依赖时，可以设计少量明确的子路径 API，重点是**有意选择承诺面**，而不是强求只有一个文件。

### 3. 把允许的依赖方向变成规则

调用方只从目标模块的公共入口导入；应用装配层负责组合多个平级 Feature；稳定的共享能力不反向依赖具体业务。若两个 Feature 互相导入，应先检查用例编排是否属于上层，或某项规则是否有真正的独立所有者，不能只为消除循环就把代码扔进 `shared/`。

对独立包可用包入口限制未声明子路径；对同一源码树可用 lint、依赖图和 CI 检查深层导入、禁止方向与循环依赖。自动化出现的原因是：规则若只能靠评审者记忆，交付压力下就会持续失效。

## 一个最小结算示例

    src/
      app/                         # 路由和跨 Feature 装配
      features/
        coupon/
          index.ts                 # 对外承诺
          CouponSelector.tsx       # 内部实现
          applyCoupon.ts
          events.ts
          couponStore.ts
          couponApi.ts

`coupon/index.ts` 可以有意导出：

```ts
export { CouponSelector } from './CouponSelector';
export { applyCoupon } from './applyCoupon';
export type { CouponApplied } from './events';
```

结算模块通过 `features/coupon` 使用这些能力，不直接读取优惠券 Store 或请求结构。这样，优惠券模块可以更换缓存库、调整目录或修改接口映射，而调用方只在公共语义确实改变时才需要同步修改。

这不是要求一开始就创建大量子目录。最小做法是先把相关文件放在一起、写出有意导出，并禁止外部深层导入；只有边界数量和违规频率上升后，才增加标签、依赖图或专门工具。

## 新增成本与可观察信号

公共 API 会增加命名、兼容和例外治理成本；过小会迫使调用方不断申请新入口，过大又把内部变化传播出去。Feature 拆得太细时，一次简单交互会穿过大量模块；单个总入口也可能扩大静态依赖图或暴露循环，实际构建影响必须用产物分析验证。

| 可观察现象 | 可能的问题 |
| --- | --- |
| 一个需求同时修改多个全局技术目录 | 同一 Feature 的上下文被分散 |
| 调用方大量使用 `feature/internal/path` | 公共能力不足，或规则没有执行 |
| `index.ts` 对内部目录全部 `export *` | 入口存在，但承诺面没有收缩 |
| 移动内部文件会修改许多调用方 | 外部依赖了目录结构而非能力 |
| 两个 Feature 循环导入 | 编排层、状态或规则所有权不清 |
| `shared/` 充满业务分支和特殊参数 | 为消除重复而制造了公共耦合点 |
| 每个 Feature 都复制多层空目录 | 从模板而非真实复杂度出发 |

目录划分也不自动带来运行时隔离、独立部署、按需加载或团队自治；这些是后续系统形态和交付机制要单独承担的责任。

## 做项目时怎么验证

1. 从最近三次需求出发，按用户能力重新标记共同变化的文件，不先套目录模板。
2. 为候选 Feature 写一句职责，并列出它拥有的状态、规则、外部适配和主要团队。
3. 先把共同变化的代码就近放置；规模小时保持扁平。
4. 记录真实调用方需要的能力，只显式导出这些组件、操作、事件和类型。
5. 画出依赖图，消除意外循环，并逐步禁止跨模块深层导入和错误方向。
6. 做“内部搬家测试”：移动、重命名或替换一个内部实现，调用方不应随之修改。
7. 用下一次同类需求观察触及的模块数、外部调用方修改数和测试范围；若协调成本上升，就合并或重新划界。

小型原型只有少量文件、变化证据尚未出现时，不需要包、标签和复杂规则；先保持命名清楚即可。边界反复被多人依赖、开始独立发布，或越界问题已进入评审与故障记录时，再提升执行强度。

## 别误解

- **按 Feature 组织就不能分层。** 先按业务变化建立外边界，内部复杂到需要隔离时仍可再分层。
- **公共 API 越少越好。** 目标是最小且足够的稳定承诺；过窄同样会制造传话层和绕行依赖。
- **所有跨 Feature 依赖都错误。** 稳定的单向依赖可以存在；平级流程的协调通常应上移到装配或用例边界。
- **建一个 `shared/` 就能复用。** 只有语义、变化和所有权确实共享时才应抽取，否则少量重复更可逆。
- **`index.ts` 会自动隐藏内部文件。** 它只聚合导出；没有解析或 lint 约束时，调用方仍可深层导入。

## 复习

1. 为什么把文件移入 Feature 目录后，边界仍可能只是视觉分类？
2. 公共 API 为什么应暴露业务能力，而不是 Store、缓存键和原始 DTO？
3. 两个 Feature 循环依赖时，为什么不能直接把相关代码移入 `shared/`？
4. 怎样用“内部搬家测试”验证信息隐藏是否真实存在？

## 来源与下一步

- **来源事实：** Angular 官方风格指南建议按功能区域组织应用代码而非按组件、指令、服务等代码类型划分；Node.js 文档说明包 `exports` 可声明公共入口并限制未声明子路径，同时提醒新增它可能造成破坏性变更且不构成绝对封装；Nx 文档说明可用标签与 lint 或依赖图规则自动检查项目依赖；课程材料强调应用与共享包职责、依赖方向及项目目录约定需要明确。
- **本页推论：** 将 Feature 就近放置、公共 API 和依赖规则组合为一条“逻辑边界 → 依赖边界”的实现链，并用“内部重构是否迫使调用方改变”检验信息隐藏。
- **工程建议：** 从真实变更记录发现 Feature，先采用扁平目录和显式导出，再按越界频率逐步增加自动约束；不要从固定模板、全量 Barrel 或消除重复的冲动反推边界。
