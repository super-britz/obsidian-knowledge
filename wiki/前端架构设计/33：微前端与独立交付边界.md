# 微前端与独立交付边界

> [!abstract] 先用一句话说清楚
> 微前端不是把页面切成很多远程组件，而是让多个团队拥有的前端业务能力能够独立构建、发布、回滚和处理故障，再通过显式契约组合成一个连贯产品。它用运行时版本组合、加载、性能、安全、状态和体验治理成本换取团队交付自治；如果普通模块边界和独立流水线已经足够，就不需要把边界升级到浏览器运行时。

## 为什么微前端属于 L5

[[20：Feature-based 模块与公共 API|Feature-based 模块]]可以在一份应用内局部化代码变化，[[31：Monorepo 与代码协作边界|Monorepo]]可以降低跨项目源码协作成本，[[27：渐进迁移与兼容窗口|兼容窗口]]则控制新旧版本共存。微前端属于 L5，是因为它把这些机制进一步组合成真实的交付与运行系统：

- 多个业务切片和稳定团队所有权；
- 独立 Build、Artifact、Pipeline、Deployment 与 Rollback；
- Shell、Router、Manifest 或 Module Loader；
- 运行时生命周期、版本兼容和共享依赖；
- DOM、CSS、状态、消息和安全边界；
- 性能预算、失败降级、观测与一致体验。

因此，配置一次 Module Federation、注册一个 Custom Element 或嵌入 iframe，都只是在选择集成机制。只有独立交付收益和上述责任共同成立，才形成微前端架构。

## 第一性原理：多个交付者，只有一个用户产品

大型前端存在两个同时成立、又彼此拉扯的事实：

```text
事实一：多个团队需要并行改变不同业务能力
事实二：用户只看到一个页面、一条任务链和一套产品体验
```

单体前端把所有代码放进同一 Build 与 Release：

```text
任一团队修改
→ 全应用集成与验证
→ 等待共同发布窗口
→ 一个局部故障可能阻塞所有团队
```

当团队和变化流增多，主要成本可能不再是写代码，而是排队、协调、全量回归和共同回滚。微前端尝试把这条链改成：

```text
团队独立修改业务切片
→ 独立构建与验证 Artifact
→ 在兼容契约内独立发布
→ 运行时与其他切片组合
→ 用户仍完成一条连贯任务
```

它优化的是**组织吞吐与变化爆炸半径**，不是天然优化代码量或页面速度。可以用定性模型约束讨论：

```text
微前端净收益
≈ 减少的等待、交接、全量验证与共同发布成本
  - 新增的契约、平台、版本组合、运行时、性能、安全与体验成本
```

如果只有一个小团队，或每次需求仍必须同时修改所有区域，第一项收益接近零，后面的成本却仍然存在。

## “独立”必须拆成不同维度

把代码放到不同仓库，只证明文件和 Git 历史分开。真正的独立至少包含：

| 维度 | 要回答的问题 |
| --- | --- |
| Source | 能否在不直接修改别人内部代码的情况下开发？ |
| Build | 一个切片能否不重新编译所有应用就产生 Artifact？ |
| Deploy | 能否独立上传、保留和回滚自己的 Artifact？ |
| Release | 能否不等待其他团队同时上线就向用户启用？ |
| Contract | 新旧生产者和消费者能否在兼容窗口内共存？ |
| Runtime | 加载、挂载和卸载是否有清楚生命周期？ |
| Failure | 一个切片失败时，其他任务能否继续有用？ |
| Ownership | 团队是否拥有代码、流水线、指标、告警和恢复权限？ |

其中最容易被偷换的是 Deploy 与 Release：团队可以把文件上传到 CDN，却仍要等中心 Shell 改版本、全站回归和统一发布；这只是独立产出 Artifact，不是独立把价值交付给用户。

独立也不等于“毫无协调”。微前端把每次发布前的人肉同步，转换为预先约定的契约、兼容窗口、平台规则和自动验证。若没有这些机制，协调不会消失，只会在生产环境以版本不兼容的形式出现。

## 先按业务变化切，不按页面零件切

候选边界应同时满足：

```text
一组业务能力高频共同变化
∧ 跨边界共同变化相对少
∧ 有稳定团队能端到端负责
∧ 用户在边界失效时仍有可定义行为
```

订单查询、商品管理、账户中心这类垂直能力，通常比 Header、表格、表单、样式这样的水平技术关注点更接近独立交付边界。后者更适合作为有版本的设计系统、组件库或平台能力。

路由往往是安全的第一候选，因为切换路由时本来就会重建大量局部 UI State，也容易声明独立加载、错误页和性能预算。同一个路由内拆出许多远程“小部件”，会增加挂载顺序、通信、布局和部分失败组合，必须由更强的同屏独立发布需求证明。

边界过粗会形成一个新的前端单体；边界过细则会出现：

```text
一个用户动作
→ 同时调用多个微前端公共接口
→ 共享大量状态和事件
→ 每次变更仍要协调所有团队
```

这时切开的只是代码包，真正的变化和任务边界仍然耦合，应合并或重新确定上层编排者。

## 集成时机决定你购买哪种复杂度

微前端不等于客户端运行时加载。常见组合方式位于不同阶段：

| 集成方式 | 独立发布能力 | 主要收益 | 主要代价 |
| --- | --- | --- | --- |
| Build-time Package | 弱，Host 通常需重建发布 | 类型、优化和本地调试简单 | Release 重新锁步，更像模块化单体 |
| Route / MPA | 强，按 URL 进入独立应用 | 边界粗、生命周期和故障清楚 | 完整导航、共享 Shell 和状态衔接 |
| Server / Edge Composition | 可强，服务端组合 HTML 或 Fragment | 首屏与服务端策略集中 | 服务端关键路径、缓存和 Hydration 协议 |
| Runtime JS / Import Maps / Module Federation | 强，浏览器动态解析 Remote | 同页组合灵活、可独立替换 | 加载瀑布、版本协商、弱隔离与远程代码风险 |
| Web Components | 取决于资产交付方式 | 浏览器原生元素与生命周期契约 | Registry、Attributes / Events、样式和框架桥接 |
| iframe | 强，可独立 Origin 与 Document | DOM、CSS、Global 和权限隔离更强 | 路由、焦点、尺寸、无障碍、通信与性能成本 |

Build-time Package 本身通常不能满足严格的独立 Release，但可以先把业务边界理清；未来确有必要时，再把加载点升级为运行时边界。反过来，为了“看起来先进”直接选择最动态的组合方式，会提前支付最大版本和故障成本。

一个稳健顺序是：

> 优先选择能满足真实自治需求的最粗边界、最少动态性和最简单运行模型。

## Shell 是组合控制面，不是新的业务单体

Runtime Composition 通常需要 Shell 或 Root Config。它至少要声明：

```text
Route / Slot
→ 解析哪一个已批准 Artifact
→ 检查兼容和发布策略
→ Load
→ Bootstrap
→ Mount
→ Observe
→ Unmount 或 Fallback
```

Shell 适合拥有：

- 顶层路由、全局导航和页面骨架；
- Route / Module 到不可变 Artifact 的映射；
- 公共生命周期、超时、错误兜底和紧急停用；
- 会话存在性、Locale、Theme 等最小上下文传递；
- Trace、Client Version、Remote Version 与发布 Cohort；
- CSP、允许来源、能力策略和全局性能护栏。

Shell 不应拥有：

- 每个领域的业务规则和页面流程；
- 所有应用共同读写的全局 Store；
- Remote 的内部路由、DOM 和私有类型；
- 每次业务发布都必须修改的巨大注册逻辑；
- 只能由中心团队人工处理的上线工单。

如果每个 Feature 都要先改 Shell，Shell 就成为新的中心协调瓶颈。可扩展的控制面应通过稳定 Schema、自助注册和自动策略承接日常交付，同时由明确平台团队维护其可靠性和兼容性。

## 跨边界通信先定义契约，再选 Event Bus

每一种共享都是一条变化传播边：

| 契约 | 适合表达什么 | 主要风险 |
| --- | --- | --- |
| URL / Route / Query | 导航、可分享状态、跨路由目标标识 | 参数兼容与历史语义 |
| Lifecycle | Bootstrap、Mount、Unmount、Cleanup | 重复挂载、资源泄漏 |
| Props / Attributes | 父级提供的稳定输入 | 把整个内部模型暴露出去 |
| Domain Event | 已经发生的跨切片事实 | 隐藏消费者、顺序与重复 |
| Command API | 请求某个所有者执行动作 | 超时、拒绝、幂等与授权 |
| Service / BFF API | 权威数据和业务状态转换 | 网络失败与版本兼容 |
| Design Token | 颜色、间距、字体等视觉语言 | 全局升级与主题兼容 |
| Telemetry Context | Trace、版本和 Cohort | 隐私与字段不一致 |

Event Bus 只能让发送者不知道接收者，不能让双方没有契约。事件需要稳定名称、版本、Runtime Schema、重复和顺序语义；消费者还要能在生产者缺失时安全运行。

优先传递业务含义，而不是内部数据结构：

```text
不推荐：setGlobalState({ cart: 整个 Redux State })
更清楚：请求购物车所有者 addItem(command)
         → 返回明确回执
         → 发布 cart:item-added 事实供摘要区域刷新
```

如果两个区域持续同步输入框、弹窗开关和临时选择，它们本质上在共同拥有一个 UI 状态机。继续增加事件只会隐藏耦合，合并为一个微前端通常更诚实。

## 状态所有权不能被全局 Store 抹平

可以按语义放置状态：

```text
组件临时交互 → 所属微前端本地状态
导航与可分享选择 → URL
领域事实 → 领域服务 / 对应 BFF 的权威状态
跨切片长期流程 → 明确的领域流程或上层用例状态机
一次发生通知 → 带 Schema 的事件
```

共享一个全局 Store 看似最容易，却要求所有独立应用理解相同 State Shape、Action 和更新时序。任一团队修改结构，都必须同时考虑所有消费者的前向、后向兼容，发布再次锁步。

认证上下文也要分层：Shell 可以告诉 Remote 当前存在何种会话和显示信息，但客户端对象不是授权事实。每个服务端请求仍须按主体、对象和动作重新授权，不能因为代码由“已登录 Shell”加载就信任它。

## 独立发布会扩大运行版本组合

单体 Build 在编译时固定一组依赖；微前端允许用户实时遇到：

```text
Shell h
× Orders a
× Catalog b
× Account c
× Shared Runtime d
× Backend APIs e
```

每个部分保留多个活跃版本时，理论组合数会相乘，无法靠完整 E2E 穷举。架构必须主动压缩组合空间：

- Artifact 使用不可变版本 URL，不覆盖已发布内容；
- Manifest / Import Map 作为发布控制面，拥有原子更新、缓存和回滚策略；
- 一次页面会话尽量使用一致的版本快照，避免导航中途随机换 Remote；
- 公共契约保留明确的 N / N-1 或时间型兼容窗口；
- Consumer Contract 验证公开入口、事件和 Schema；
- 先向稳定 Cohort 发布，并保证一次用户旅程命中一致版本；
- 遥测记录 Shell、Remote、共享依赖和后端版本组合；
- 临时兼容分支到期删除，防止永久协议考古。

“无需同步上线”不等于“可以随意 Breaking Change”。真正的独立发布，是一方发布新版本时无需知道另一方正在运行哪个**兼容版本**。

回滚也只能恢复代码选择，不能撤销已写入的数据、事件或外部副作用；仍要使用[[27：渐进迁移与兼容窗口|Rollback Frontier]]检查完整恢复路径。

## 共享依赖是在字节与自治之间交换

每个微前端自带依赖：

```text
优点：版本由自己控制，升级局部
代价：重复下载、解析、执行和内存
```

多个微前端共享依赖：

```text
优点：大依赖可能只加载一次
代价：共享版本、初始化顺序和兼容性成为跨团队运行契约
```

webpack Module Federation 的 `shared`、`requiredVersion`、`singleton` 和 `strictVersion` 正是在表达这个交换。React 等需要单实例的 Runtime 可能必须共享，但这意味着框架大版本升级不再完全自治；不兼容时要么拒绝加载，要么提供受控 Fallback，不能只忽略 Console Warning。

更稳妥的判断是：

- 只共享体积大、确有单实例约束或语义必须统一的依赖；
- 小型库可允许重复，以保留独立升级；
- Design Token 和无领域规则的基础组件可以版本化共享；
- 不共享跨领域 Model、业务规则和可变全局对象；
- 同时测首个路由与后续跨路由导航，而不是只看总 Bundle 大小。

共享不是越少越先进，也不是越多越高效；它把成本从网络侧移动到协调和兼容侧。

## 隔离是分层能力，不是一个开关

| 组合方式 | DOM / CSS | JavaScript 与权限 | 通信 | 主要边界性质 |
| --- | --- | --- | --- | --- |
| 同 Document Remote | 默认共享；需 Namespace、CSS Modules 等约束 | 通常共享 `window`、Origin 和页面能力 | 函数、Event、Module Import 很灵活 | 主要依赖契约和团队纪律 |
| Shadow DOM / Custom Element | 可封装内部 DOM 与样式选择 | 执行代码仍在宿主页信任范围 | Attributes、Properties、Events | 组件封装，不是安全沙箱 |
| cross-origin iframe + Sandbox | 独立 Document，样式和 Global 隔开 | Same-Origin Policy 与 Sandbox 可限制能力 | `postMessage`、URL、服务端 | 隔离更强，集成成本也更高 |
| Route / 独立 Document | 页面生命周期天然分开 | Origin 与部署可分别设计 | URL、服务端状态 | 粗粒度、清楚但导航接缝明显 |

Shadow DOM 可以减少样式和 DOM 结构泄漏，却不会阻止同页脚本读取被允许的数据、发起请求或占用主线程。React Error Boundary 也只捕获特定渲染树错误，不能隔离无限循环、全局事件、副作用和 CSS 污染。

iframe 的隔离能力取决于 Origin 与 Sandbox Token。WHATWG 明确提醒，同源内容同时启用 `allow-scripts` 与 `allow-same-origin` 时可能逃逸 Sandbox；因此不能复制一串 `allow-*` 后宣称“已经安全”。跨 Document 使用 `postMessage` 时，要固定 `targetOrigin`，校验 `event.origin` 与消息 Schema，并限制消息可触发的能力和频率。

即使脚本权限分开，所有区域仍共享用户设备、网络带宽和整页体验。一个 iframe 或 Remote 制造 Long Task、请求风暴或布局抖动，用户仍会感到整个产品卡顿。

## Remote Code 也是供应链边界

同 Document 动态加载的 Remote 会在宿主页上下文执行。独立团队的源码、依赖、CI 凭据或 CDN 任何一处被攻陷，都可能把恶意代码带入拥有用户会话的页面；“公司内部代码”不是浏览器安全边界。

运行时加载至少需要：

- 仅允许批准的 Origin、Module Name 和不可变 Artifact；
- 在加载链支持时使用内容完整性校验，并限制 CSP `script-src`；
- 保留 Build Provenance、依赖扫描、发布审计与紧急禁用能力；
- 不把原始 Token、全量用户对象和高权限函数直接交给 Remote；
- 用最小 Capability 接口代替“整个 `window` 都可用”的隐式授权；
- 记录实际加载的 URL、Hash、版本和发布者，便于事故定位。

安全机制也有交付代价：固定 Hash 与“随时把稳定名称指向最新版”天然冲突。正确方案不是取消校验，而是把不可变 Artifact、受控 Manifest、Cohort、缓存与回滚作为一套发布协议设计。

## 失败隔离必须对用户可见

Runtime Composition 新增了独有失败：Manifest 不可用、Remote 404、Chunk 超时、共享依赖不兼容、Bootstrap 抛错、Mount 超时、Unmount 泄漏和跨版本事件不识别。

Shell 需要为每个边界定义：

| 问题 | 要提前决定什么 |
| --- | --- |
| 加载失败 | 重试一次、使用已验证旧版、显示局部 Fallback 还是整路由失败？ |
| 挂载失败 | 谁清理半完成 DOM、Event Listener、Timer 和请求？ |
| 运行异常 | 哪类错误可由 Boundary 捕获，哪类需要刷新或停用 Remote？ |
| 版本不兼容 | 拒绝加载、回退版本还是阻止本次 Release？ |
| 关键能力缺失 | 用户能否继续其他任务，还是必须进入明确不可用状态？ |
| 恢复完成 | 怎样确认权威数据和用户流程仍一致？ |

失败边界应和有用能力一致。推荐区坏了可以隐藏；结算区坏了不能显示一个空白矩形并让用户猜测订单是否提交。局部 Fallback 也要保留错误编号、恢复动作和可访问状态。

观测必须能从一次用户任务关联到 Shell、Remote、API 与版本组合。只记录“页面报错”无法判断是加载、兼容、业务、后端还是某个 Cohort 的问题。

## 性能关键路径不会因团队拆分而消失

客户端运行时组合可能产生新的依赖链：

```text
HTML / Shell
→ Manifest 或 Import Map
→ Remote Entry
→ Shared Dependencies
→ Remote Chunks
→ Data
→ Render / Hydrate
→ User Task Ready
```

任何一步串行等待都会进入关键路径。将一个 Bundle 拆成十个 Remote，可能减少首路由无关代码，也可能增加 DNS、连接、请求、解析、执行和缓存失配。

因此要为每个 Route / Slot 声明：

- 首次与后续导航的传输、请求和缓存预算；
- Shell 到 Remote Ready 的 P75 / P95 时间；
- JavaScript 解析执行、Long Task 和 Hydration 成本；
- Remote 加载失败与 Fallback 比例；
- Feature Ready、Task Success 和 Core Web Vitals；
- 每个微前端对整页预算的责任份额和超限处置。

Lazy Loading、Code Splitting 和 CDN 在单体应用里同样可以实现，不能把它们的收益都归因于微前端。是否更快只能由真实用户路径和目标设备数据证明。

## 团队自治不能牺牲产品一致性

用户不关心某个区域属于哪个仓库。以下能力必须形成跨团队产品契约：

- URL、导航、返回和 Deep Link；
- 语义化 HTML、键盘、焦点、读屏与对比度；
- Design Token、基础组件和响应式断点；
- Locale、时区、数字、货币和错误语言；
- 会话过期、权限拒绝、加载与空状态；
- Analytics、隐私同意和任务成功口径。

一致性不要求所有团队复制相同框架实现。平台可以提供版本化设计系统、自动无障碍检查、统一观测 SDK 和自助发布护栏；业务团队仍拥有自己的垂直切片。

若“自治”被理解成每个团队任意选择框架、交互和监控，用户会替组织支付碎片化成本。技术多样性可以用于渐进迁移或特殊约束，但它是附加成本，不是微前端的目标。

## 一个后台系统的渐进拆分

假设商品、订单、结算和账户由四个稳定团队维护，但都在一个 SPA 中：任何局部改动都要等待全量流水线和每周共同 Release。最近需求显示，订单域变化频繁，却很少需要同时改商品与账户。

可以先选择 `/orders/*` 做 Route-level Pilot：

```text
现有 Shell 保留导航和会话入口
→ Route Manifest 将 /orders/* 指向不可变 Orders Artifact
→ Orders 团队拥有页面、必要时的场景 BFF、Pipeline、SLO 和回滚
→ 其他 Route 继续由旧单体处理
```

边界契约只包含 Route、最小会话上下文、Design Token、Trace Context 和 Orders API。订单列表状态留在 Orders 应用；账户事实来自权威服务；Shell 不建立全局 Redux Store。

若全局 Header 要显示“待处理订单数”，它通过订单所有者提供的稳定摘要 API 读取，并在 `order:status-changed` 事实发生后定向失效；它不直接读取 Orders 内部 Store。

先验证 Orders 能在不重建 Shell 和其他应用的情况下发布与回滚，旧 Shell 与新 Orders 能共存，Remote 不可用时只有订单路由失败，真实用户性能没有越界。只有这些证据成立，再迁移下一个稳定业务切片。

## 什么时候采用，什么时候保持模块化单体

更值得采用微前端的信号：

- 多个稳定、面向产品能力的团队长期修改同一大型前端；
- 真实数据表明共同 Build、全量验证或统一 Release 已形成主要等待；
- 业务边界较粗，跨边界 UI State 和同步交互较少；
- 团队能拥有 Pipeline、运行指标、值班、兼容和回滚；
- 需要用 Strangler 方式逐步迁移难以整体替换的旧系统；
- 独立发布和局部故障收益大于额外用户性能与平台成本。

优先保持 Feature-based 模块化单体的信号：

- 只有一个或少数紧密协作团队，发布等待并不明显；
- 大多数需求跨多个候选切片共同变化；
- 目标只是复用组件、拆 Bundle、使用不同框架或改善目录；
- 所有区域依赖一个全局 Store、同一业务事务或共同 Release Train；
- 缺少契约测试、灰度、观测、紧急停用和运行所有者；
- 当前最主要问题是慢接口、图片、主线程或代码质量，而非组织交付。

Monorepo 与微前端不是二选一：Monorepo 可以管理源码和 Affected CI，独立 Pipeline 再发布多个 Runtime Artifact。[[32：BFF 与客户端场景边界|BFF]]也不是每个微前端的标配；只有该客户端切片与领域服务边界不一致、聚合收益成立时才增加 BFF。

## 可观察的错误信号

| 现象 | 更可能的问题 |
| --- | --- |
| 配置了 Module Federation 就宣布完成 | 工具存在，独立交付与责任闭环不存在 |
| 一个团队维护十几个微前端 | 没有组织并行收益，只有运行复杂度 |
| 每个按钮、表格都是 Remote | 边界按 UI 零件而非变化流切得过细 |
| 所有应用共享一个全局 Store | 状态契约把 Release 重新锁在一起 |
| 每次发布仍要全站回归和共同上线 | 独立 Deploy 没转化为独立 Release |
| Shell 包含大量业务分支 | 控制面变成新的前端单体和中心队列 |
| 共享所有依赖以追求零重复 | 依赖版本升级成为全局运行契约 |
| Remote 版本覆盖同一个 CDN URL | 缓存与回滚无法确定用户实际代码 |
| 只靠 React Error Boundary 隔离故障 | 主线程、CSS、事件和副作用仍会传播 |
| 用 `postMessage('*', data)` 传敏感信息 | 消息没有目标、来源和 Schema 边界 |
| 每个团队任意选择交互与监控 | 组织自治由用户体验和事故响应买单 |
| 为了性能采用微前端，却没有 RUM | 把 Code Splitting 收益误归因于架构名称 |

## 做项目时怎么验证

1. **量化现状：** 记录最近需求的交付前置时间、流水线时长、共同发布次数、跨团队等待、变更失败和恢复时间。
2. **选择边界：** 从高频独立变化的垂直业务能力选择一个粗粒度 Route，不先按组件或技术栈拆分。
3. **声明独立维度：** 明确 Source、Build、Deploy、Release、Contract、Runtime、Failure 与 Ownership 哪些必须独立。
4. **选择最小机制：** 先比较 Package、Route / MPA、Server Composition、Runtime JS、Web Component 和 iframe，选择满足目标的最低复杂度。
5. **定义契约：** 固定 Route、Lifecycle、Input、Event、API、Design Token、Telemetry、版本和弃用期，并做 Runtime Schema 校验。
6. **证明独立交付：** 一个团队不修改、不重建其他应用即可发布、灰度、停用和回滚自己的 Artifact。
7. **验证版本组合：** 测当前与相邻版本、旧 Shell、新 Remote、旧 Remote、新后端和 Manifest 回滚，不追求穷举全部组合。
8. **注入失败：** 模拟 Manifest、Remote、Chunk、共享依赖、Mount、API 和 Unmount 失败，检查局部有用能力与证据链。
9. **验证安全与体验：** 检查 Remote 来源、CSP / Integrity、消息 Origin、Token 暴露、键盘、焦点、读屏、Locale 和错误一致性。
10. **比较净收益：** 上线后同时比较交付等待与用户性能、故障、平台维护成本；自治没有改善时合并或退回模块化单体。

## 来源与认识边界

- **来源事实：** Martin Fowler 站点文章提供“可独立交付应用组合”定义、垂直团队、集成方式和成本；single-spa 官方资料说明路由优先、公共入口、Import Maps、依赖共享与全局状态约束；webpack 文档说明 Remote、异步加载和 Shared Scope；WHATWG、CSSWG 与 OWASP 分别支撑 Import Maps、Custom Elements、Shadow DOM 样式封装、iframe Sandbox、跨 Document 消息和远程脚本安全边界。课程原文仅零散提及 Module Federation，本页没有把这些提及扩写成课程原有结论。
- **机制推导：** 本页从“多个交付者与一个用户产品”的矛盾推导独立交付，再由浏览器同页组合推导契约、版本组合、状态、隔离、性能和体验责任。
- **工程建议：** 优先粗粒度 Route 和最低复杂度集成；Shell 保持通用；Artifact 不可变；Manifest 受控；共享状态最小；Remote 执行按供应链边界治理；用兼容窗口和真实用户证据验证收益。
- **待项目验证：** 是否需要微前端、切几个、选择 Runtime JS 还是 iframe、哪些依赖共享、兼容多久和由谁运行平台，都必须基于真实组织等待、业务变化流、威胁模型、目标设备和生产数据决定。
