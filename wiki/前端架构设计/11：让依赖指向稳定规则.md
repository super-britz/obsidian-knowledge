# 让依赖指向稳定规则

> [!abstract] 先用一句话说清楚
> 划出边界还不够：如果核心业务直接依赖数据库、支付 SDK、浏览器 API 或框架类型，外部技术变化仍会沿依赖传入核心。依赖方向设计的目的，是让表达长期业务意图的代码只依赖自身需要的稳定契约，由易变实现去适配这个契约。

## 从变化传播推导依赖方向

依赖不只是代码里出现一条 import。只要 A 的编译、测试、行为或理解方式会被 B 的变化迫使改变，A 就依赖 B。

假设结算用例直接调用某支付 SDK：

    结算规则
    → 支付 SDK 的类、参数和错误类型
    → 某一家支付平台

支付平台升级时，原本稳定的结算规则也必须修改。[[10：按变化原因建立边界|逻辑边界]]虽然存在，变化仍沿源码依赖穿透边界。

底层因果链是：

    核心规则寿命长、被更多功能依赖
    + 外部技术变化快、可替换
    → 核心若依赖外部细节，变化会从外围传向中心
    → 核心只声明自己需要的能力
    → 外部实现反过来满足该能力

这里的“稳定”不是永远不改，而是**变化频率较低、承载业务意义更多、修改影响更大**。

## 先区分四种“依赖”

| 维度 | 问题 |
| --- | --- |
| 业务依赖 | 完成用例真正需要什么能力？ |
| 源码依赖 | 哪个模块 import、引用了哪个类型？ |
| 运行时调用 | 执行时谁调用谁？ |
| 创建依赖 | 谁选择具体实现并管理生命周期？ |

依赖倒置主要改变的是**源码依赖和创建责任**，不是否认运行时调用：

    运行时：CheckoutUseCase → StripeAdapter

    源码：
    CheckoutUseCase → PaymentPort
    StripeAdapter   → PaymentPort
    CompositionRoot → CheckoutUseCase + StripeAdapter

业务仍然会在运行时请求支付，但它不需要知道 Stripe 的类名、字段和错误结构。

## 稳定契约应该表达调用方的需要

契约不是把第三方 SDK 的全部方法重新抄一遍，而是表达业务用例真正需要的最小能力：

    PaymentPort
      charge(orderId, amount)
      → Paid | Declined | Unknown

外部适配器负责：

- 把内部金额、订单和身份转换为供应商参数；
- 把供应商响应转换为内部结果；
- 隔离 SDK 异常、版本和重试细节。

因此契约通常由需要该能力的稳定一侧拥有。如果契约由供应商模型决定，外部细节仍然会借接口泄漏进核心。

## 原则、机制和工具不要混在一起

| 层级 | 概念 | 作用 |
| --- | --- | --- |
| 设计原则 | 依赖指向稳定规则、依赖倒置 | 决定源码依赖的方向 |
| 边界契约 | Port / Interface | 表达核心真正需要的能力 |
| 适配机制 | Adapter / Repository | 把外部实现转换为内部契约 |
| 创建机制 | 依赖注入（DI） | 从外部把具体对象交给使用者 |
| 运行控制 | 控制反转（IoC） | 把创建或流程控制交给外部协调者 |
| 可选工具 | DI Container | 自动注册、解析并管理对象生命周期 |

有接口不等于依赖已经倒置；使用 DI 容器也不等于架构自动合理。若核心接口仍暴露具体 SDK 类型，或者核心自己去容器查找实现，依赖只是换了一种隐藏方式。

## Composition Root 是允许知道细节的地方

系统最终必须选择真实实现。应把这种选择集中在靠近应用启动的位置：

    创建 StripeAdapter
    → 创建 CheckoutUseCase(adapter)
    → 创建 Controller(useCase)
    → 启动应用

这个位置称为 Composition Root。它可以同时知道抽象和具体实现，因为它的职责就是组装对象；业务模块则不负责选择供应商、读取全局容器或决定对象生命周期。

## 什么时候值得倒置

更值得建立契约和 Adapter：

- 外部服务、浏览器 API、存储或框架变化频率明显高于业务规则；
- 核心规则需要脱离网络、数据库或 UI 独立测试；
- 外部数据结构不应成为内部业务模型；
- 多个实现确实存在，或失败、安全和生命周期需要独立控制；
- 一次供应商升级已经影响多个业务模块。

不必为了形式给每个类创建一对一接口。稳定的小型工具函数、语言标准能力，或者只在局部使用且替换成本很低的库，可以直接依赖。抽象本身会增加命名、跳转、映射和维护成本。

## 可观察的错误信号

| 现象 | 依赖问题 |
| --- | --- |
| 测试优惠规则必须启动数据库或网络 | 核心规则依赖了外部运行环境 |
| 供应商 SDK 类型遍布业务模块 | 外部数据模型越过了边界 |
| 更换请求库需要修改多个 Feature | 易变实现没有被局部适配 |
| 业务代码到处读取全局容器 | 真实依赖和创建责任被隐藏 |
| 接口与实现方法完全一一对应 | 可能只有形式抽象，没有隔离变化 |
| 单例对象携带用户状态 | 生命周期选择造成跨请求状态串扰 |

## 做项目时怎么验证

1. 从一个核心用例列出它直接引用的外部类型、全局对象和具体实现。
2. 逐项判断谁更稳定、谁拥有业务语义、变化会向哪里传播。
3. 只为真实易变边界定义调用方需要的最小契约。
4. 在 Adapter 中完成外部类型、错误和协议的转换。
5. 在 Composition Root 选择实现并明确单例、请求级或临时生命周期。
6. 用替身实现独立测试核心，再模拟一次 SDK 或存储替换；核心无须修改才说明隔离有效。

## 别误解

- **依赖倒置就是多写 Interface。** 接口若复制具体实现，依赖方向没有实质改变。
- **依赖注入必须使用容器。** 构造函数参数和普通工厂函数已经可以完成显式注入。
- **所有依赖都应该抽象。** 只有变化传播成本超过间接层成本时，抽象才有净收益。
- **调用方向就是依赖方向。** 运行时可以由核心调用 Adapter，源码却由 Adapter 依赖核心契约。
