# 按变化原因建立边界

> [!abstract] 先用一句话说清楚
> 边界的作用不是把代码切成更多文件，而是让一种变化尽量只影响一个可独立理解的区域。经常因为同一原因一起变化的代码应靠近；由不同角色、规则或生命周期驱动的代码应避免互相暴露内部细节。

## 从底层约束推导

人的认知有限，而业务、界面、接口和基础设施会分别变化。假设一个模块同时包含价格规则、页面布局、接口调用和埋点：

    设计改布局 ─┐
    产品改规则 ─┼→ 都修改同一个模块
    后端改接口 ─┤
    数据改埋点 ─┘

这些变化来源相互独立，却在代码中汇合，于是产生两类成本：

- 修改任何一项都要理解其他无关细节；
- 不同需求容易修改同一位置，引发冲突和意外回归。

目标因此不是“代码更整齐”，而是 [[01：第一性原理——前端架构为何存在#L2：约束先推导质量目标|变化局部性]]：

    某种变化发生
    → 找到负责该变化的边界
    → 只通过稳定入口影响其他边界
    → 修改、测试和回滚主要停留在局部

## 什么叫“变化原因”

变化原因不是“这段代码用了 TypeScript”或“它也是一个组件”，而是谁会因为什么决策要求它改变。常见变化轴包括：

| 变化轴 | 例子 |
| --- | --- |
| 业务规则 | 优惠计算、权限、订单状态约束 |
| 用户体验 | 布局、交互、无障碍和文案 |
| 外部契约 | 后端字段、支付渠道、浏览器 API |
| 数据生命周期 | 草稿、服务端事实、缓存和持久化 |
| 安全与失败 | 鉴权、重试、降级和审计 |
| 团队所有权 | 不同团队独立发布和维护 |

“单一职责”更准确的理解不是一个函数只能做一个动作，而是一个边界尽量只有一组高度相关的变化原因。

## 相关概念各自回答什么

这些术语不是互相独立的口号，而是观察同一个边界问题的不同角度：

| 概念 | 回答的问题 |
| --- | --- |
| 关注点分离 | 哪些变化维度不应混在一起？ |
| 单一职责 | 当前边界主要对哪一组变化负责？ |
| 高内聚 | 边界内部的代码是否经常一起变化？ |
| 低耦合 | 一个边界变化时，外部是否很少被迫修改？ |
| 信息隐藏 | 外部是否依赖了本可留在边界内的易变决策？ |
| 封装 | 是否存在真正限制外部访问的入口？ |

它们共同指向一个可验证标准：

> 好边界内部共同变化多，跨边界被迫共同变化少。

## 边界过粗与过细都会增加成本

边界过粗时，一个模块包含太多变化原因；边界过细时，一个简单需求必须协调大量接口和中间层。

    总成本
    = 边界内部的理解成本
    + 跨边界的协调与转换成本

因此不能根据文件行数机械拆分。出现以下证据时更值得拆：

- 两部分由不同规则或角色反复独立修改；
- 修改一部分经常导致另一部分意外回归；
- 两部分可以拥有独立测试、生命周期或发布节奏；
- 内部细节已被许多调用者依赖，重构经常扩散。

如果只是暂时看起来相似、变化模式尚未出现，保留少量重复往往比提前制造通用抽象更便宜。

## 用一个场景发现边界

一个结算面板同时包含：

    价格与优惠规则
    + 提交订单流程
    + 页面展示
    + 后端字段转换
    + 埋点

不要先问“应该建几个文件夹”，先依次问：

1. 哪些决策由产品规则改变，哪些由设计或外部接口改变？
2. 哪些状态必须始终保持同一个业务不变量？
3. 哪些细节是其他部分真正需要知道的？
4. 如果只改优惠规则，理想情况下哪些代码和测试应该变化？

由此可以先得到价格规则、结算用例、展示和外部适配等**逻辑边界**。至于它们最终是函数、组件、模块还是包，属于后续实现机制，不在原则层预先决定。

## 实际项目中的诊断信号

| 可观察现象 | 可能的问题 |
| --- | --- |
| 一个小需求要修改许多不相关目录 | 同一变化被分散，内聚不足 |
| 一个文件经常因完全不同的需求修改 | 边界过粗，职责发散 |
| 参数不断增加特殊开关 | 不同语义被强行塞进同一抽象 |
| 调用方深度导入内部文件 | 信息隐藏失效，目录不是真边界 |
| 模块之间循环依赖 | 双方同时拥有对方需要的决策或状态 |
| 每层只把参数原样传给下一层 | 边界过细，没有独立责任 |

这些信号不是自动重构命令，而是进一步调查真实变化原因的证据。

## 做项目时怎么验证

1. 选取最近两三个真实需求，列出各自修改了哪些代码。
2. 标记每次变化的发起者、规则、数据所有者和失败责任。
3. 检查同一原因的修改是否分散，不同原因的修改是否频繁碰撞。
4. 为候选边界写出一句职责和最小公开能力；无法写清时先不要拆。
5. 用下一次同类需求验证修改范围、测试范围和协作冲突是否减少。
6. 如果跨边界转换和协调成本反而更高，合并或重新划界。

## 别误解

- **文件更小就更符合单一职责。** 行数衡量体积，不衡量变化原因。
- **视觉相同就应该复用。** 外观相同但业务语义和变化方向不同，强行复用会产生大量条件参数。
- **消灭重复永远优先。** 重复是可见成本，错误抽象会把原本独立的变化永久绑定。
- **建了目录就是建立边界。** 如果调用方仍能任意深度导入内部实现，目录只提供位置，没有提供封装。

## 复习

1. 为什么边界应该由变化原因而不是代码类型决定？
2. 如果一次修改只涉及一个文件，是否足以证明边界正确？
3. 两段相似代码在什么条件下不应该立即抽象复用？
4. 怎样用下一次真实需求验证一次拆分是否有效？
