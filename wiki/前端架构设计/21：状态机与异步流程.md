# 状态机与异步流程

> [!abstract] 先用一句话说清楚
> 状态机不是一种状态库，而是把流程写成“当前状态 + 已发生事件 → 合法新状态 + 待执行命令”。它存在的原因是外部结果可能迟到、丢失、重复或乱序；只有同时记录流程阶段和操作身份，系统才能判断某个结果现在是否仍有资格改变状态。

## 从“异步是多条时间线”推导

JavaScript 一次只执行一段代码，不代表业务没有并发。用户可以继续操作，网络和定时器也在独立推进：

    搜索 A 发出
    → 用户改成搜索 B
    → B 先返回并展示
    → A 后返回并覆盖 B

`await` 只让当前函数的写法看起来顺序化，不能控制其他操作和外部响应的先后。若收到 `REQUEST_SUCCEEDED` 就无条件写入数据，系统实际采用的是“最后到达者获胜”，而不是“最新用户意图获胜”。

因此 [[12：状态所有权与合法转换|合法转换]] 在异步场景还必须加入两个条件：

1. 当前流程阶段允许这个事件发生；
2. 事件属于当前仍有效的查询或业务操作。

完整控制链是：

    当前状态 + 带身份的事件
    → 守卫检查阶段、身份和业务条件
    → 新状态 + 待执行命令
    → 外部世界执行
    → 成功、拒绝、超时或取消回执再次成为事件

状态机负责决定，副作用执行器负责与外部世界交互；这延续了 [[13：可信边界与副作用隔离|副作用隔离]]，也让转换逻辑能够用普通输入输出测试。

## 最小模型包含什么

| 元素 | 回答的问题 | 示例 |
| --- | --- | --- |
| State | 系统现在能合法做什么？ | `idle`、`submitting`、`succeeded` |
| Event | 已经发生了什么？ | `SUBMIT_REQUESTED`、`WAIT_TIMED_OUT` |
| Guard | 此刻是否允许转换？ | 操作身份匹配、仍在重试预算内 |
| Transition | 接下来进入什么状态？ | `submitting → succeeded` |
| Command / Effect | 需要外部做什么？ | 发送请求、查询状态、写日志 |
| Receipt | 外部实际回了什么？ | 成功、业务拒绝、连接丢失 |

状态最好互斥，而不是由多个布尔值拼装：

```ts
type SubmitState =
  | { status: 'idle' }
  | { status: 'submitting'; operationId: string; attempt: number }
  | { status: 'succeeded'; orderId: string }
  | { status: 'rejected'; reason: string }
  | { status: 'retryableFailure'; operationId: string; attempt: number }
  | { status: 'outcomeUnknown'; operationId: string };
```

这样流程不会同时表示成功和失败，`succeeded` 也必然携带 `orderId`。但类型只排除了结构上的非法组合；操作身份是否正确、服务端是否去重，仍要由运行时规则保证。

## 三种身份不能混成一个 ID

“给请求加 ID”仍然太含糊，不同身份回答不同问题：

| 身份 | 表示什么 | 重试或新意图时怎样变化 |
| --- | --- | --- |
| Query Version | 当前用户想看的第几版结果 | 新搜索递增；只接收当前版本 |
| Operation ID | 一次逻辑业务意图，如“创建这一个订单” | 同一意图重试时保持不变 |
| Attempt ID | 某次具体网络尝试 | 每次发送重新生成，用于关联与观测 |

搜索 A 被搜索 B 取代时，应使 A 的版本失效；创建订单超时后重试，却应复用原来的 Operation ID，让服务端识别这仍是同一次下单。若每次重试都生成新的幂等身份，客户端实际上是在发起多个新业务操作。

身份还必须有作用域和生命周期：用户切换、参数改变或流程重置后，旧身份不能继续写入新会话；服务端去重记录也需要明确保存多久以及如何返回原结果。

## 查询与写命令需要不同裁决

### 查询：新意图可以淘汰旧结果

读请求通常可以采用“最新意图获胜”：新查询产生新版本，旧响应即使成功也被忽略。中止旧请求可能节省部分资源，但正确性不能只依赖中止，因为中止信号可能与完成竞态，或底层 API 根本不支持中止。

### 写命令：没收到响应不等于没执行

下单、支付或删除请求在服务端产生副作用。连接断开或客户端超时只能证明“当前没有拿到结果”，无法证明服务端未执行。因此应区分：

- **业务拒绝：** 服务端明确说明没有接受该操作；
- **可安全重试的失败：** 错误是暂时性的，并且契约能证明重复发送不会新增业务效果，例如明确未执行，或同一 Operation ID 的重放会返回既有结果；
- **结果未知：** 请求可能已执行但回执丢失，应先用 Operation ID 查询或按契约协调最终状态；这个事实本身不能单独决定重放是否安全。

把结果未知直接显示成“失败”并创建新的操作，可能产生重复订单。禁用提交按钮只能减少单页面中的连续点击，挡不住超时重试、多标签页或其他客户端；真正的重复安全需要服务端按同一 Operation ID 去重并返回既有结果，之后客户端才能选择查询，或按契约安全重放同一操作。

## 取消、超时与重试各自保证什么

- **取消：** `AbortSignal` 是协作信号。它能让支持该协议的 API 停止或拒绝未完成工作，但不能倒放已经发生的远端副作用。若业务需要取消订单，必须有独立的领域命令和确认状态。
- **超时：** 表示调用方不再等待，不是服务端结论。读请求可以废弃旧版本；写请求通常进入 `outcomeUnknown`，优先查询最终结果；若契约保证同一 Operation ID 可安全重放，也可以把重放作为协调手段。
- **重试：** 只在操作仍有意义、错误可恢复、预算未耗尽且重复效果安全时发生。同一业务意图复用 Operation ID，每次网络尝试更新 Attempt ID。

一个简化的提交转换表可以是：

| 当前状态 | 事件与守卫 | 新状态 | 命令 |
| --- | --- | --- | --- |
| `idle` | `SUBMIT_REQUESTED` | `submitting(op, 1)` | `SendOrder(op)` |
| `submitting` | 匹配身份的 `SUCCEEDED` | `succeeded` | 无 |
| `submitting` | 明确 `BUSINESS_REJECTED` | `rejected` | 无 |
| `submitting` | 暂时失败，且重复效果已被契约保证安全 | `retryableFailure` | 无 |
| `submitting` | `WAIT_TIMED_OUT` | `outcomeUnknown` | `CheckStatus(op)` |
| `submitting` | 重复 `SUBMIT_REQUESTED` | 不变 | 无 |
| `retryableFailure` | `RETRY_REQUESTED` 且预算允许 | `submitting(op, n+1)` | `SendOrder(op)` |
| `outcomeUnknown` | 权威回执确认完成或明确拒绝 | `succeeded` 或 `rejected` | 无 |

未列出的状态—事件组合应被明确忽略、拒绝或记录，而不是落入一个万能更新分支。

表中选择“先查询”是保守默认，不是禁止安全重放。若状态查询暂时不可用，而服务端保证同一 Operation ID 的重复请求只返回既有结果，可以增加从 `outcomeUnknown` 到下一次同身份 Attempt 的协调转换；不能生成新的 Operation ID 冒充重试。

## 何时值得使用，代价是什么

简单输入框或一次性开关没有有意义的非法转换，直接使用局部状态更便宜。当流程出现多个阶段、迟到回执、取消、重试、超时、并发操作或审计要求时，显式状态机才开始偿还成本。

状态和事件越多，转换矩阵也越大。多个相互独立的生命周期不应全部展开成一个巨型状态名，例如 `editingAndUploadingAndSaving`；应拆成可以独立推理的子流程，只在真实不变量要求时协调。实现也可渐进升级：

    可辨识联合 + Reducer
    → 显式转换表与测试
    → 需要层级、并行、定时和可视化时再引入状态机库

工具能够执行模型，不能替团队找出正确状态，也不能替服务端完成幂等和最终事实裁决。

## 可观察的错误信号

| 现象 | 可能缺失的机制 |
| --- | --- |
| `loading`、`success`、`error` 可以同时为真 | 状态没有互斥建模 |
| 任意成功回调都能覆盖当前结果 | 缺少当前阶段或 Query Version 守卫 |
| 超时后直接显示“操作失败”并新建请求 | 没有表达 `outcomeUnknown` |
| 调用 `abort()` 后就显示“订单已取消” | 把本地中止误当成领域撤销 |
| 每次重试生成新的幂等键 | Operation ID 与 Attempt ID 混淆 |
| 只靠按钮禁用阻止重复下单 | 正确性边界停留在 UI |
| 一个状态名组合大量平行流程 | 独立生命周期没有拆分 |
| 线上无法关联原操作和各次尝试 | 身份没有贯穿日志与服务端回执 |

## 做项目时怎么验证

1. 选一个真实关键流程，先分开服务端领域事实与客户端等待状态。
2. 用互斥名词列状态，用已发生的事实列事件，并为每个转换写出守卫。
3. 定义 Query Version、Operation ID 和 Attempt ID 中实际需要的身份及生命周期。
4. 把请求、计时和取消写成命令，让回执带身份重新进入转换函数。
5. 用表驱动测试覆盖合法转换和非法状态—事件组合。
6. 模拟旧查询迟到、连续点击、中止与成功竞态、服务端已提交但响应丢失、同一操作多次重试。
7. 在日志和接口回执中贯穿 Operation ID 与 Attempt ID，确认能查到最终权威结果。

## 别误解

- **用了状态机就没有竞态。** 只有事件携带身份且转换检查身份时，迟到结果才会被正确拒绝。
- **`await` 会让整个流程串行。** 它只暂停当前异步函数，用户、其他任务和外部系统仍独立推进。
- **取消等于回滚。** 中止观察和撤销业务是两个协议，后者需要权威方确认。
- **所有失败都应该重试。** 业务拒绝、权限错误和不安全的写操作不能靠重复发送解决。
- **状态越详细越严谨。** 不影响合法行为的状态只会扩大转换矩阵；细分必须服务于不同决策。

## 来源与下一步

- **来源事实：** Redux 官方指南建议让当前状态与事件共同决定转换，并用有限状态减少非法组合；DOM Standard 将 `AbortController` 定义为由 API 协作响应的中止信号机制；RFC 9110 用重复请求的预期服务端效果定义幂等，并限制非幂等请求的自动重试；课程材料要求显式处理状态流程、幂等、重复提交和失败重试。
- **本页推论：** 将异步流程建模为“带身份的事件 → 状态与身份守卫 → 新状态与命令 → 外部回执”，并区分查询版本、逻辑操作和网络尝试三种身份；进一步从不可观测的远端执行状态推导出 `outcomeUnknown`。
- **工程建议：** 先用联合类型和 Reducer 显式表达关键流程，再按复杂度升级工具；查询用版本拒绝迟到结果，写操作用稳定 Operation ID、服务端去重和结果查询保证重复安全。
