# 按数据生命周期分配资源

> [!abstract] 先用一句话说清楚
> 网络、CPU、内存、存储、服务端成本和用户等待时间都有限。架构应先消除重复传输、无效计算等人为浪费，再根据数据从产生到删除的生命周期，决定剩余成本在何时、何地、由谁承担，并用可验证预算约束这种交换。

## 从资源下界与成本交换推导

一个页面结果通常要经历：

    等待与排队
    → 网络往返
    → 服务端读取或计算
    → 序列化与传输
    → 浏览器解析、计算和渲染

算法改进、删除重复请求或减少无效渲染，可以直接消除人为浪费；但产生正确结果仍有不可避免的读取、计算、传输或保存工作。缩短这些必要步骤中的一步，常常会增加另一步：

- 预先计算减少请求时延，但增加构建时间和存储；
- 缓存减少网络和计算，但增加旧数据、失效和空间成本；
- 把计算移到浏览器减少服务端负载，但占用用户设备和主线程；
- 把数据复制到靠近用户的位置降低延迟，但增加一致性和删除成本。

所以性能设计的第一步是消除不必要工作；剩余工作的第一性原理不是“所有地方尽可能快”，而是：

> 围绕关键用户结果，在有限总成本内分配时间、计算、传输、存储和复杂度。

## 为什么以数据生命周期为主线

大多数资源消耗都围绕数据发生。先描述数据怎样流动：

    产生
    → 校验并写入权威来源
    → 复制、索引或缓存
    → 读取与计算
    → 更新并使旧副本失效
    → 过期、归档或删除

每类数据都应回答：

| 问题 | 影响的决策 |
| --- | --- |
| 谁是权威来源？ | 失败或冲突时向哪里回源 |
| 多久变化一次？ | 是否适合预计算或长期缓存 |
| 多久读取一次、从哪里读取？ | 是否值得复制到消费者附近 |
| 数据和计算有多大？ | 传输、存储与计算哪项更昂贵 |
| 允许旧多久？ | 新鲜度和失效策略 |
| 是否按用户隔离？ | 能否共享缓存、怎样设计键 |
| 丢失后能否重建？ | 持久化、备份和恢复成本 |
| 何时必须删除？ | 副本、日志和缓存的清理责任 |

不知道生命周期时讨论 CDN、localStorage 或 SSR，只是在先选工具后猜问题。

## 先定义用户结果，再分配预算

用户不关心某个函数执行了多少毫秒，而关心能否及时看到内容、开始操作和确认任务完成。因此预算应该从关键旅程向下分配：

    用户动作与完成证据
    → 关键路径上必须完成的工作
    → 网络、服务端、主线程和渲染预算
    → 非关键工作延后、分批或取消

预算不一定先写成行业通用数字，但必须说明：

- 测量哪个用户结果，而不是只测技术步骤；
- 在什么设备、网络、数据量和负载下验证；
- 正常范围和退化范围分别是什么；
- 哪项资源超限时由哪个边界负责调整。

只看开发机、平均值或单次实验，容易隐藏低端设备、弱网和长尾请求。

## 数据位置是一组条件判断

| 数据特征 | 更可能采用的方向 | 主要代价 |
| --- | --- | --- |
| 内容不可变且带版本 | 提前生成并靠近用户复制 | 发布和版本管理 |
| 服务端事实变化频繁 | 从权威来源读取或使用短期副本 | 网络延迟与服务端负载 |
| 计算昂贵但结果稳定 | 预计算或缓存结果 | 失效、空间和重建 |
| 仅当前交互需要 | 留在局部内存 | 页面结束后丢失 |
| 弱网或离线仍需使用 | 保存可恢复的本地副本 | 同步、冲突和隐私 |
| 大型静态文件 | 对象存储并分发到近端 | 存储、流量和版本 |
| 用户敏感数据 | 减少副本并缩短保留时间 | 可能增加回源延迟 |

这些不是固定答案。价格和库存即使与商品描述来自同一个接口，也可能因为新鲜度要求不同而采用不同缓存策略。

## 缓存是成本交换，不是免费加速

缓存复制已有结果，用空间和一致性复杂度换取时间：

    缓存收益
    = 减少的网络 + 计算 + 等待

    缓存成本
    = 旧数据风险 + 失效逻辑 + 存储
      + 隔离与隐私 + 调试和运维复杂度

只有在目标场景中收益大于成本时才值得缓存。任何缓存都必须声明：

- 缓存什么语义的数据；
- 键是否包含用户、权限、版本和查询条件；
- 允许旧多久；
- 谁使它失效；
- 未命中或损坏时如何回源；
- 权威数据删除后怎样清理副本。

HTTP Cache、查询缓存、IndexedDB、Service Worker 和 CDN 是不同位置的后续机制，不是可互换的“缓存开关”。

## 计算放在哪里

| 计算时机或位置 | 换取的收益 | 适用约束 |
| --- | --- | --- |
| 构建时预计算 | 请求时几乎不计算 | 输入集合有限、变化较慢 |
| 服务端请求时计算 | 接近权威数据和安全边界 | 个性化或必须实时 |
| 靠近用户的分布节点 | 减少网络距离 | 数据可复制且失效可管理 |
| 浏览器计算 | 交互即时、减少服务端工作 | 设备能力足够且数据可下发 |
| 后台或空闲时计算 | 不阻塞关键交互 | 结果不要求立即可见 |

计算位置还受权限、数据体积、运行环境和失败恢复约束，不能仅按 CPU 时间选择。

## 一个商品列表场景

同一页面的数据不应采用一套统一策略：

    商品图片：版本化静态文件，可长期近端复制
    商品描述：变化较慢，可接受短期旧值
    实时价格与库存：服务端权威，新鲜度要求高
    当前筛选条件：属于导航，可进入 URL
    用户收藏状态：按用户隔离，不能共享公共副本

这里不是因为使用了五种技术才复杂，而是五类数据的权威来源、变化频率、共享范围和失败代价本来就不同。

## 可观察的错误信号

| 现象 | 可能的资源或生命周期问题 |
| --- | --- |
| 首次交互前加载所有功能 | 没有区分关键路径和非关键工作 |
| 同一数据在短时间内重复请求 | 副本复用或请求协调不足 |
| 发布后用户长期看到旧页面 | 版本与失效责任不明确 |
| 不同用户读到同一私有结果 | 缓存键和隔离范围错误 |
| 内存、存储只增不减 | 没有淘汰和删除阶段 |
| 为“性能”保存大量派生状态 | 把计算成本换成了一致性成本 |
| 服务端省下资源但低端设备卡顿 | 成本只是转移给了用户设备 |

## 做项目时怎么验证

1. 选择一个关键用户旅程，写出完成证据和可接受退化。
2. 画出关键路径上的数据、计算、网络和渲染步骤。
3. 为每类数据标记权威来源、变化频率、新鲜度、读取范围和删除条件。
4. 找到真实瓶颈，再决定预计算、延迟、复制、缓存或回源。
5. 为新增副本定义版本、失效、隔离、降级和清理责任。
6. 在代表性设备、网络、数据量和负载下测量完整旅程。
7. 同时记录性能收益、正确性风险、基础设施成本和维护复杂度。

## 别误解

- **加缓存一定会更快。** 命中率低或失效复杂时，缓存可能只增加分支和错误。
- **数据越新越好。** 新鲜度需要网络与计算成本，应由业务允许的旧值范围决定。
- **把工作移到客户端就是降本。** 服务端成本可能下降，但用户等待、电量和设备负担会上升。
- **所有数据都适合放进同一种存储。** 文件、事务事实、热副本和分发副本拥有不同生命周期。

## 复习

1. 为什么性能优化既要消除人为浪费，又要管理必要成本的转移？
2. 为什么同一商品接口里的描述、价格和库存可能需要不同策略？
3. 缓存除了空间，还引入了哪些正确性成本？
4. 怎样从用户完成证据反向分配技术预算？
