# 渲染架构与交付形态

> [!abstract] 先用一句话说清楚
> 渲染架构不是给整个网站贴上 CSR、SSR 或 SSG 标签，而是针对每类用户旅程建立“工作放置契约”：哪些内容在构建时、请求时或交互时产生，计算靠近用户还是权威数据，哪些副本可以共享，哪些区域需要 JavaScript，失败时保留什么，以及这些选择要求怎样的部署与运行责任。只有不同路由或区域的约束确实不同，组合方案的收益才值得额外边界成本。

## 为什么到 L5 才讨论“渲染架构”

[[26：渲染机制与性能预算|渲染机制与性能预算]]属于 L4，已经回答：

- CSR、SSR、SSG、Streaming 分别把工作移到哪里；
- SPA / MPA 与 HTML 生成时机为什么是两个维度；
- Hydration、拆包、预取和 CDN 改变了哪些等待；
- 怎样用用户结果和性能预算验证单个机制。

本页属于 L5，不再重复这些机制，而是回答：

> 一个真实应用拥有多种页面、数据、身份和失败代价时，怎样把机制组合成可以部署、运行和演进的整体？

所以两层关系是：

    L4：理解零件的能力、约束与代价
    ↓
    L5：按真实问题组合零件，并承担组合后的接缝

若还没有理解缓存、可信边界、失败恢复和渐进迁移，直接讨论“上某某全栈框架”，就会把工具默认值误当成架构结论。反过来，若每个组件都单独选择一套模式，系统又会被接缝淹没。L5 的任务正是找到最小、稳定的组合规则。

## 第一性原理：必要工作不会因架构名称消失

一个页面要产生有用结果，至少要完成其中一部分工作：

    识别 URL、身份与环境
    → 读取并校验数据
    → 计算内容与界面
    → 传输 HTML、数据、样式和代码
    → 浏览器解析、绘制并激活交互
    → 用户发起操作
    → 可信系统授权、执行并确认结果

优化可以删除重复取数、无用 JavaScript 和错误串行等浪费；剩余必要工作只能改变：

- **何时做：** 构建时、请求时、导航时、交互时或后台；
- **在哪里做：** CI、源站、边缘、浏览器、Worker 或数据服务旁；
- **做几次：** 每次请求、每个版本、每个用户，还是命中副本时不再做；
- **以谁为准：** 构建快照、请求时事实、客户端副本还是服务端权威；
- **失败由谁承担：** 整页、局部区域、当前操作还是后台更新。

因此渲染架构本质上是**必要工作的时空与责任分配**。它不能同时免费获得：

    构建时的低请求成本
    ∧ 请求时的个性化与最新事实
    ∧ 浏览器中的即时交互
    ∧ 零客户端 JavaScript
    ∧ 零服务端运行责任
    ∧ 永不失效的共享缓存

每取得一项能力，都会在其他时间、位置或团队边界支付成本。第一性问题不是“哪种模式最好”，而是“哪个用户结果最重要，哪种成本由谁承担最合理”。

## 架构不是标签，而是一张工作放置契约

对一个路由或独立页面区域，可以用以下契约描述：

    RenderingArchitecture(Unit)
    = ⟨
        用户结果,
        导航与 Document 生命周期,
        HTML 生成时机与位置,
        数据权威与取数时机,
        Cache Key、共享范围与新鲜度,
        客户端激活范围,
        Mutation 与授权路径,
        失败和降级行为,
        部署拓扑与版本协议
      ⟩

这张契约比“这是 SSR 页面”多回答了几个关键问题：

| 维度 | 必须回答 |
| --- | --- |
| 用户结果 | 先阅读、立即编辑、完成交易，还是持续实时操作？ |
| 导航 | 获取新 Document，还是复用当前 Document 做客户端导航？ |
| HTML | 构建时预先生成、请求时生成，还是浏览器收到数据后生成？ |
| 数据 | 何时可得、谁是权威、允许旧多久、是否按身份变化？ |
| 缓存 | 哪一层保存什么副本，Key 包含什么，谁触发失效？ |
| 激活 | 哪些内容只需 HTML，哪些必须下载代码并拥有客户端状态？ |
| 写入 | 谁校验、授权、去重和确认副作用，乐观结果如何纠正？ |
| 失败 | 哪个区域还能保持有用，返回旧值、Fallback 还是明确失败？ |
| 交付 | 只需静态文件，还是需要请求时 Runtime、流式代理、共享缓存与密钥？ |
| 演进 | HTML、Chunk、接口和持久数据跨版本时怎样兼容与回退？ |

框架可以自动实现其中一些选择，却无法替项目回答数据是否私有、库存允许旧多久、支付是否可重复、哪些用户必须在弱网完成任务。

## 先按用户旅程和数据约束切分

整个应用通常不是一个有效决策单元。公开文档、商品详情、搜索、个人中心和支付即使使用同一组件框架，也可能拥有完全不同的约束。

先为每条关键旅程回答：

| 约束 | 它怎样影响组合 |
| --- | --- |
| 内容必须在 JavaScript 前可读吗？ | 倾向在 HTML 中交付关键内容 |
| 是否需要公开发现、分享或机器消费？ | URL、HTTP Status、Metadata 与可解析内容进入协议 |
| 数据在构建时已知吗？ | 已知且稳定才适合提前生成 |
| 是否按用户、权限或请求变化？ | 请求时可信读取，避免公共副本串用户 |
| 允许旧多久？ | 决定静态生成、TTL、校验和实时回源 |
| 交互有多密集、多长？ | 决定客户端状态与 JavaScript 激活范围 |
| 写入失败代价多大？ | 决定服务端授权、幂等、确认与恢复 |
| 用户设备与网络怎样？ | 决定可承担的客户端计算、字节和往返 |
| 流量与路径规模怎样？ | 决定构建、请求时计算和缓存是否经济 |
| 团队能否运行服务端？ | 决定可承担的容量、密钥、监控和值班责任 |

只有某个页面区域在数据生命周期、交互、失败和团队所有权上能独立变化，才值得继续细分。为了技术炫技把每个组件分别放在服务端、边缘和客户端，会让调用、序列化、缓存与调试边界远多于收益。

## 从约束自然长出的五种组合

下面不是五个新“架构流派”，而是约束相近时常出现的稳定组合：

| 系统形态 | 典型约束 | 机制组合 | 主要新增责任 |
| --- | --- | --- | --- |
| 静态内容交付 | 公开、可共享、构建时已知、变化较慢、交互少 | 构建时 HTML + 版本化资源 + CDN + 最小客户端增强 | 路径规模、构建时间、发布与失效 |
| 缓存的动态文档 | 公开或分群内容、请求时才能确定、可接受短期旧值 | 请求时渲染 + 共享或分群 Cache + 条件校验 | Cache Key、源站容量、失效与击穿 |
| 服务端快照加客户端增强 | 首屏内容重要，之后交互密集或数据继续变化 | SSR / Streaming + 一致初始快照 + 局部 Hydration + 客户端再验证 | 双环境一致、激活间隙、重复数据与版本 |
| 客户端应用 | 登录后长会话、公开内容价值低、交互状态复杂 | 静态 App Shell + CSR + API + Query Cache + 路由拆包 | 首次代码与取数、低端设备、API 可用性 |
| 实时或离线应用 | 网络可能中断、状态持续变化、需要本地即时反馈 | 初始快照 + 增量事件 + 本地副本或操作日志 + 重连同步 | 顺序、冲突、幂等、积压、隐私与清理 |

同一站点可以使用多种组合，但每增加一种就新增构建产物、缓存规则、故障路径、测试矩阵和认知成本。默认从最简单的主形态开始，只在一类旅程的证据长期不满足时引入第二种。

## HTML、数据和交互代码不必共享生命周期

“一个页面采用什么模式”常常太粗。页面至少包含三类产物：

1. **HTML 与内容结构：** 决定没有客户端代码时能看到什么；
2. **数据快照与后续数据：** 决定内容依据哪个时间点和身份；
3. **交互代码：** 决定哪些区域何时拥有客户端行为。

它们可以组合：

    稳定 Shell
    → 构建时生成并长期缓存

    公开内容
    → 短期缓存或请求时生成

    私有账户状态
    → 请求时读取，不进入公共 Cache

    低优先级推荐
    → 独立 Streaming Boundary

    搜索筛选与购物车
    → 局部客户端下载并激活

拆分的收益来自生命周期差异，而不是“组件级渲染”这个名词本身。若这些区域共享同一必须同步变化的状态、必须一起成功，或必须反复跨边界传递大对象，拆开反而制造瀑布和不一致。

一个实用判据是：

> 该区域能否独立说明数据权威、新鲜度、可用结果、失败恢复和发布版本？

不能独立回答时，它很可能不是一个真实架构边界。

## 数据获取位置决定等待、信任与重复

### 在服务端取数

服务端取数可以接近权威数据库和内部服务，隐藏密钥，在返回 HTML 前完成身份、Schema 与权限校验，也能减少浏览器先下载代码再请求数据的串行往返。

代价是：

- 取数进入 TTFB 或流式区域等待；
- 服务端 Runtime 要承担连接、超时、容量和故障；
- 私有结果不能误入共享缓存；
- 服务端与浏览器都要使用的数据可能被再次序列化和传输；
- 数据服务很远时，所谓“边缘渲染”仍可能反复跨区。

### 在客户端取数

客户端适合读取只在交互后需要、变化很快、依赖浏览器环境或需要持续轮询/订阅的数据。长会话可以只更新局部状态，不必重新取得整个 Document。

代价是内容依赖 JavaScript、公开 API 和额外往返；网络失败、取消、乱序、旧缓存与权限错误都成为可见状态。浏览器传来的身份、参数和“已经校验”声明仍不可信。

### 组合时只保留一个事实来源

常见组合是服务端交付初始快照，客户端从相同版本继续：

    服务端读取权威事实 version = 42
    → HTML 与可序列化快照携带 version = 42
    → 客户端 Hydrate
    → 按新鲜度规则从 version = 42 再验证

若客户端启动后不识别初始快照，又立刻请求同一数据，会造成重复工作和界面跳变；若永不再验证，又会把请求时快照误当成长期事实。初始数据的来源、版本、Freshness 与客户端接管规则必须连成一个协议。

所有 Mutation 仍应进入 [[13：可信边界与副作用隔离|可信执行边界]]。OWASP 要求每个请求都执行授权检查；SSR、隐藏按钮或客户端路由都不能代替服务端对主体、对象和动作的裁决。乐观 UI 只能表示“客户端预计会成功”，最终仍以服务端回执和权威重读为准。

## 缓存策略决定“静态”能维持多久

构建产物、HTML Cache、CDN、浏览器 HTTP Cache、Service Worker 与 Query Cache 都是副本。渲染架构只要使用其中一层，就必须继承 [[25：缓存与数据一致性|缓存协议]]：

    语义 Key
    + 共享范围
    + Fresh / Stale 规则
    + Validator 或版本
    + 失效与回源
    + 删除和容量

尤其要区分：

- **公共内容：** 多个用户在正确情况下应得到相同结果，才可能进入 Shared Cache；
- **分群内容：** 语言、地域、设备能力、实验 Variant 等必须进入 Key 或由明确路由隔离；
- **私有内容：** 身份、租户、权限和敏感字段不能因 URL 相同而被公共复用；
- **实时事实：** 价格、库存和权限即使与静态描述同页，也可能需要更短窗口或权威确认。

RFC 9111 规定 HTTP Cache Key、`Vary`、Freshness 和 `private` 等协议语义，但不知道业务上“修改商品会影响哪些列表”。失效依赖图仍由应用维护。

所谓增量生成、按需重建或静态再验证，本质都是：

    复用旧 HTML 副本
    → 判断何时不再信任
    → 触发重建
    → 重建期间返回旧值、等待还是失败
    → 新版本怎样传播到所有缓存层

名称可以变化，状态问题不会消失。多实例 Runtime 若各自保存页面 Cache，还要定义共享、同步或容忍分叉；否则同一 URL 会随命中实例不同而返回不同代际。

## 交付形态由运行时依赖反推

渲染选择最终必须落到真实可运行的拓扑：

| 交付形态 | 必需组成 | 运行时主要风险 |
| --- | --- | --- |
| 纯静态托管 | 构建流水线、对象存储或静态服务器、CDN | 构建失败、旧产物、失效和大规模路径生成 |
| 客户端应用 | 静态 Shell 与 Chunk、独立 API、浏览器 Runtime | 首屏依赖脚本、Chunk 版本、API 故障和设备性能 |
| 请求时服务端渲染 | Web Runtime、数据访问、密钥、容量、超时与监控 | TTFB、冷启动、连接耗尽、级联失败和成本 |
| 流式服务端渲染 | SSR 全部条件，加可流式代理、Boundary 与客户端恢复 | 中间层缓冲、响应提交后状态码、局部失败与版本 |
| 边缘执行 | 可用的边缘 Runtime、部署分发、数据或服务访问路径 | Runtime 限制、跨区回源、复制一致性和排查复杂度 |

“代码部署在边缘”不等于请求自动更快。端到端等待更接近：

    用户 → 计算节点
    + 计算节点 → 每个依赖的数据位置
    + 串行依赖次数
    + 计算、排队与传输

AWS Well-Architected 指南同时要求考虑用户位置、数据位置与安全合规。若边缘函数要连续五次访问远端单区数据库，缩短第一段距离可能被后面的跨区往返抵消。适合放在边缘的通常是可独立完成、状态已就近复制或只需一次远端交接的工作；靠近权威数据的聚合计算则可能更合理地留在 Region 内。

交付形态还改变团队责任。静态站并非“没有后端”，只是不在页面请求时运行渲染服务；请求时 SSR 则让前端团队直接拥有容量、密钥、补丁、日志和事故响应。[[16：组织所有权与系统边界|所有权]]必须覆盖真实 Runtime，而不是只覆盖组件仓库。

## SEO 是消费者约束，不是 SSR 的别名

公开发现需要搜索引擎、社交机器人和其他机器消费者能够：

- 找到稳定、可链接的 URL；
- 收到有意义的 HTTP Status；
- 取得主要内容、标题、描述和 Canonical；
- 跟随真实链接发现后续页面；
- 在资源失败或 JavaScript 能力受限时仍理解结果。

Google Search 可以执行 JavaScript，但其文档仍说明 Crawling、Rendering、Indexing 是不同阶段，渲染可能排队，且并非所有机器人都能执行 JavaScript。服务端或构建时输出关键内容通常能缩短机器取得信息的依赖链，但这不等于“SSR 会提升排名”。

因此 SEO 决策应从内容消费者推导：

    公开内容需要可靠发现
    → 关键内容与协议语义尽量直接可得
    → 用 Search Console、抓取日志和实际 Rendered HTML 验证

登录后控制台没有公开索引目标，就不应只为 SEO 引入 SSR；公开页面即使 SSR，也可能因错误 Status、Canonical、权限或缓存而无法正确索引。

## 组合架构最大的成本在接缝

Hybrid Rendering 可以让不同工作采用更合适的位置，也会新增这些边界：

- 构建时数据与请求时数据之间的新鲜度；
- 服务端输出与客户端首次输出之间的一致性；
- 静态 Shell 与动态区域之间的布局和失败；
- 公共 Cache 与私有状态之间的隔离；
- 旧 HTML 与新 Chunk、旧客户端与新 API 之间的版本；
- Edge、Origin、数据服务与浏览器之间的 Trace；
- MPA 全页导航与 SPA 客户端导航之间的状态清理。

接缝成本可粗略表示为：

    组合净价值
    = 某些旅程减少的等待、计算与失败影响
      - 新增边界的开发、运行、验证与演进成本

如果团队无法回答某次请求到底由哪层生成、命中了哪层 Cache、使用哪版数据、为何需要 Hydrate，组合已经超过当前可管理复杂度。

[[27：渐进迁移与兼容窗口|渐进迁移]]也必须覆盖交付接缝。新旧 HTML、Chunk、Schema 和 Service Worker 无法原子更新；W3C 规范还说明 Cache API 不会随 Service Worker 升级自动清空。发布协议要保留旧 Hash 资源、关联 Build Version，并在不兼容时安全刷新或回到仍能读新旧状态的版本。

## 一个商品详情页怎样推导

不要先说“商品页应该 SSR”。先拆用户结果和数据：

| 页面部分 | 约束 | 推导出的形态 |
| --- | --- | --- |
| URL、标题、商品描述 | 公开、可分享、需要机器发现、变化较慢 | 构建或缓存的 HTML，稳定 URL、Metadata 与 Status |
| 图片与样式 | 内容带版本、跨用户共享 | Hash 资源 + CDN 长期复用 |
| 价格与库存 | 变化快，购买前必须接近权威事实 | 请求时短期副本或客户端再验证；提交时服务端重新确认 |
| 推荐 | 个性化、非关键、失败不应阻塞主体 | 独立请求或 Streaming Boundary，可超时降级 |
| 收藏与购物车 | 用户私有、长会话交互 | 局部客户端状态 + 私有服务端事实 + 写后协调 |
| 立即购买 | 高风险副作用 | 服务端授权、幂等、库存与价格复核、明确结果未知状态 |

可能得到的组合是：

    CDN 提供版本化 Shell、描述与资源
    → 请求时或客户端取得价格库存
    → 非关键推荐独立揭示
    → 购物车局部激活
    → 购买始终进入服务端可信状态机

这套架构不能被一个“SSR”标签完整描述。它真正的价值在于每类数据按生命周期分配资源，并让关键购买链不依赖推荐、Hydration 或陈旧公共 Cache。

## 何时保持简单，何时允许混合

优先保持单一主形态，当：

- 页面目标和数据生命周期高度相似；
- 首次等待、SEO、设备性能和服务端成本都已满足预算；
- 团队没有运行多种 Runtime 和缓存协议的能力；
- 额外边界无法产生可测量收益。

考虑引入混合，当：

- 公开内容与登录后应用拥有持续、显著不同的约束；
- 某个独立区域长期主导关键路径或故障半径；
- 数据确实在不同时间才可得，且拥有清晰权威与新鲜度；
- 静态共享能显著节省请求成本，而少量内容必须个性化；
- 已经具备版本、缓存、Trace、失败恢复和迁移能力。

选择顺序应是：

    用户旅程与完成证据
    → 数据权威、生命周期和信任边界
    → 性能、可靠性、安全与成本预算
    → 最小机制组合
    → 所需交付拓扑和团队责任
    → 具体框架与平台

若顺序反过来，团队会为了使用工具功能而发明需求。

## 做项目时怎么验证

1. 列出公开入口、登录后入口和关键 Mutation，分别写明内容可见、Feature Ready 与 Task Success。
2. 为每个路由或真实独立区域填写工作放置契约，标出 HTML、数据、代码、权威、Cache 和 Runtime。
3. 画冷访问与热访问两条完整依赖链，包含 DNS、CDN、Origin、数据服务、浏览器主线程与 Hydration。
4. 检查所有 Cache Key 的身份、租户、语言、权限、版本和查询条件，验证私有响应不会进入 Shared Cache。
5. 在 JavaScript 禁用、脚本延迟、低端设备、弱网、冷 Cache 与长会话下，确认关键内容和操作的退化行为。
6. 模拟构建失败、Origin 超时、慢数据、流式中断、旧 Chunk、Service Worker 旧 Cache 和版本错配。
7. 对公开页面验证真实 HTTP Status、Metadata、Canonical、链接与搜索引擎看到的 Rendered HTML，不从框架模式直接推断 SEO。
8. 对写操作绕过页面直接请求接口，确认每次都有服务端 Schema、授权、幂等和权威回执。
9. 按 Route、Render Mode、Cache Status、Build Version 与 Cohort 关联 TTFB、LCP、INP、Feature Ready、Task Success 和成本。
10. 若混合方案没有在目标分群改善结果，或接缝故障与维护成本超过收益，退回更简单形态。

## 可观察的错误信号

| 现象 | 更可能缺少的架构判断 |
| --- | --- |
| 团队只能说“项目是 Next SSR” | 只有工具标签，没有工作放置契约 |
| 全站统一 SSR，静态文档也消耗请求时计算 | 没按数据可得时间和共享范围拆旅程 |
| 所有内容静态化，用户却长期看到旧库存 | 把不同生命周期数据绑定到同一副本 |
| CDN 命中很高但出现串用户 | Cache Key 或 Public / Private 边界错误 |
| Edge 函数离用户很近，页面仍慢 | 计算与远端权威数据之间存在多次往返 |
| HTML 很快出现，核心控件很晚才可用 | 只优化内容交付，没有控制激活范围 |
| 服务端和客户端各请求一次相同数据 | 初始快照与客户端接管协议缺失 |
| 搜索结果出现大量 Soft 404 | 客户端路由没有真实 HTTP Status |
| 局部 Streaming 后排查更困难 | Boundary 没有版本、Trace 和独立失败语义 |
| 更新后偶发 Hydration 或 Chunk 错误 | HTML、资源、数据与 Service Worker 缺少版本兼容 |
| 为一个简单后台维护三套渲染路径 | 组合复杂度超过用户收益 |

## 别误解

- **渲染架构就是在 CSR、SSR、SSG 中三选一。** 它还包括导航、取数、缓存、激活、写入、失败、部署和版本。
- **整个应用应该统一一种渲染模式。** 应统一决策规则；不同旅程约束显著不同时，结果可以不同。
- **Hybrid 一定比单一模式先进。** 它提高局部适配能力，也增加接缝和状态空间；没有证据时保持简单更好。
- **SSR 自动解决性能与 SEO。** 它可能提前内容，但会增加 TTFB、Runtime 和 Hydration；SEO 还依赖 URL、Status、Metadata 与实际可抓取结果。
- **静态页面不需要后端设计。** 页面请求时可以无渲染服务，但构建数据、Mutation、权限、失效和发布仍可能依赖后端。
- **Edge 一定比 Region 快。** 只有完整依赖链缩短才更快；远端数据往返可能抵消用户侧距离收益。
- **服务端取数天然安全。** 它提供可信执行位置，但每个请求仍需输入校验与授权。
- **部分 Hydration 只会减少 JavaScript。** 它也新增区域边界、加载顺序、共享状态与测试组合。
- **框架自动缓存就不用设计缓存。** 框架不知道业务 Key、新鲜度、权限、删除和冲突语义。
