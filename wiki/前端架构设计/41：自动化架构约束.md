# 自动化架构约束

> [!abstract] 先用一句话说清楚
> 自动化架构约束，是把已经说明“为什么要保护”的架构意图，翻译成带适用范围、证据输入、判定规则、执行动作、例外、Owner 和退役条件的反馈闭环。它降低违规被发现的时间和随机性，却不能替团队发现正确边界，也不能证明用户结果已经改善。

## 为什么它属于 L7

[[40：架构决策记录与验证|ADR]] 保存“为什么这样决定”，但文档本身不会阻止代码偏离。根本原因不是开发者不认真，而是三个不可消除的事实：

1. 系统每天都在变化，规则却只在少数时刻被讨论；
2. 人的注意力有限，Review 不可能稳定重算完整依赖图、版本组合和性能分位数；
3. 越界依赖或不兼容接口传播越久，修复时要协调的代码、版本和团队越多。

因此，只靠记忆会形成一条放大链：

```text
架构意图写进文档
→ 变化发生时没人及时核对
→ 偏离进入共享分支或生产
→ 更多代码依赖这个偏离
→ 修复成本与争议同时增加
```

L7 要做的，是让证据在最接近变化且足够可信的位置返回：

```text
决定 → 可观察约束 → 自动反馈 → 人或系统响应
  ↑                                  ↓
  └────── 结果、副作用与新证据复审 ──────┘
```

## 第一性原理：自动化购买的是更短反馈延迟

一条规则是否值得自动化，不能由“能不能写脚本”决定，而要比较两组成本：

```text
不自动化的预期成本
≈ 违规概率 × 发现延迟 × 传播范围 × 修复与事故代价

自动化的总成本
≈ 建设 + 运行等待 + 维护 + 误报漏报 + 例外治理
```

公式不是用来精确打分，而是解释三个结论：

- **高频、可重复、可观察且违规代价高**的规则，最值得自动化；
- 一次性、主观且上下文快速变化的判断，更适合 ADR、Design Review 或限时实验；
- 反馈越早通常修复越便宜，但只有证据足够可信时才应阻断，不能用一个脆弱代理换来大量误阻。

自动化的目标不是“规则越多越成熟”，而是以更低总成本保护少数关键质量。

## 一条可执行约束需要完整控制回路

“禁止跨层调用”还不是可执行规则。至少要展开为：

```text
架构意图 Why
→ 适用对象 Scope
→ 可取得证据 Input / Sensor
→ 判定规则 Policy
→ 执行位置 Enforcement Point
→ 通过、提醒、阻断或回退 Action
→ 决策证据 Evidence
→ Owner、例外与生命周期
```

其中三件事不能混在一起：

| 层次 | 回答的问题 | 例子 |
| --- | --- | --- |
| Policy | 什么关系在什么范围内允许？ | `feature` 只能经目标模块 Public API 导入 |
| Check / Fitness Function | 用什么证据判断是否符合？ | 从 Project Graph 和 Import AST 找越界边 |
| Enforcement | 违反后发生什么？ | 本地提示、PR 阻断或受控 Bypass |

OPA 把策略决策与执行点分开的实现，说明这两个责任可以独立变化；但普通前端仓库不必因此引入 OPA。简单 Import Rule、类型检查或测试已经足够时，应选择更小机制。

## 在最早且可信的边界执行

约束对象不同，可靠证据出现的时间也不同：

| 执行位置 | 适合保护什么 | 局限 |
| --- | --- | --- |
| 编辑器、本地 Lint | 导入方向、命名、禁用 API | 快但可被跳过，环境可能不一致 |
| 编译、静态分析、单元测试 | 类型、Schema、状态不变量、源码依赖 | 看不到真实部署组合和用户环境 |
| PR / CI | 全仓依赖、Contract、测试、Bundle 与许可证护栏 | 会增加排队；错误 Gate 阻断所有人 |
| Artifact / Deploy | 产物签名、配置、迁移前置、版本兼容、Canary | 反馈较晚，回退与权限责任更重 |
| Runtime | RUM、错误率、SLO、Error Budget、故障隔离 | 能看到真实结果，但用户可能已经承担代价 |

选择原则是：**把规则放到最早能够获得可信证据的边界，并为高风险质量保留生产结果反馈。** 例如源码依赖不应等线上事故才发现；性能也不能只看构建时 Bundle，因为真实设备、缓存、第三方脚本和数据等待只会在运行环境出现。

常见约束可以这样组合：

| 架构意图 | 早期反馈 | 交付或运行反馈 |
| --- | --- | --- |
| Feature 不穿透另一个模块内部 | Module Boundary / Import Rule | 受影响 Project 与交付数据复审 |
| Consumer 依赖的 API 保持兼容 | 类型、Schema、Consumer Contract | 实际版本组合、错误率与任务成功率 |
| 关键路由不超性能预算 | Bundle / Lab Budget | 分 Cohort 的 RUM 与业务任务护栏 |
| 发布不能扩大可靠性风险 | 测试、配置与回滚检查 | Canary、SLO / Error Budget 与自动回退 |

## 先观察，再决定是否阻断

“能检测”不等于“适合做硬 Gate”。阻断前至少确认：

- 规则对应已接受的意图，而不是某个人的偏好；
- 输入稳定，判定具有足够精度，失败信息能指向修复动作；
- 违规损失高于等待和误阻损失；
- 有 Owner 能处理误报、基础设施故障和紧急例外；
- 现有遗留问题有 Baseline 或迁移计划，不会要求一次清零。

规则可以渐进进入系统：

```text
Draft → Observe → Warn → Enforce → Deprecated → Retired
```

先在 Observe 阶段记录“如果启用会阻断什么”，测量命中率和修复成本；成熟后只阻止新增违规，逐步降低 Baseline。GitHub Rulesets 的 Evaluate 与 Active 是这一迁移思路的产品实例，不是所有系统都必须采用的状态名。

生产约束也不一定立即回滚。可以先暂停放量、请求人工确认或冻结高风险变更；Google SRE 的 Error Budget Policy 进一步说明，运行指标必须连到事先认可的动作和责任人，才不只是 Dashboard 上的数字。

## 例外不是关掉规则，而是有期限的风险合同

真实系统会遇到安全修复、第三方故障或迁移窗口。完全禁止例外会诱导人绕过系统；无限 Allowlist 又会掏空规则。一次受控例外至少记录：

```text
规则 ID、理由、精确范围、风险
Owner、审批者、补偿控制
开始与到期时间、清理条件、审计证据
```

紧急 Bypass 应最小授权并留下路径，过期后自动失败或进入升级队列。反复出现同类例外时，不应继续续期，而应判断是边界设计错误、规则表达不准，还是架构决定已经改变。

规则本身也有生命周期。每条长期规则都应回链 ADR 或 Policy，声明 Owner、适用范围、故障默认和复审触发器；决定被 Supersede、迁移结束或指标失去预测力时，规则必须同步修改或退役。

## 示例：禁止 Feature Deep Import

假设订单 Feature 经常直接导入支付 Feature 的内部文件，导致支付重构要同时修改多个调用方。自动化过程应是：

1. **先证实问题：** 用依赖图和变更记录确认 Deep Import 确实扩大受影响范围；
2. **记录意图：** 订单只能通过支付模块 Public API 依赖稳定承诺；
3. **定义 Scope：** 只限制跨 Feature 导入，不限制 Feature 内部组织；
4. **建立 Sensor：** 解析 Import 与 Project Tag，输出完整依赖路径；
5. **先 Observe：** 记录既有违规为 Baseline，验证别名、测试和生成代码的误报；
6. **再 Enforce：** 阻止新增违规，并给出正确 Public API 和修复说明；
7. **管理例外：** 迁移例外限定文件、Owner 与到期日；
8. **复审结果：** 观察跨 Feature 修改数量、支付变更 Lead Time 和规则维护成本。

最后一步很关键：Lint 通过只证明源码符合当前边界，不证明边界真的降低了交付成本。如果真实结果没有改善，应复审因果假设，而不是继续增加规则数量。

## 可观察的错误信号

| 现象 | 缺失的环节 |
| --- | --- |
| Wiki 写着禁止，但代码长期违反 | 没有执行点或 Owner |
| CI 有几十个红灯却没人处理 | 反馈没有连接责任与动作 |
| 所有指标超限都阻断合并 | 代理可靠性和违规代价未分级 |
| Rule 失败只显示退出码 | 反馈不能支持局部修复 |
| 新规则第一天要求清空多年债务 | 没有 Observe、Baseline 与迁移窗口 |
| `skip-check` 没有理由和期限 | 例外已经变成永久旁路 |
| 规则经常因平台故障卡住发布 | 执行点自身没有可靠性与故障默认 |
| ADR 已替代，旧 Gate 仍阻断 | 决策与规则生命周期失联 |
| 检查全绿，但用户任务持续退化 | 只验证符合性，没有结果护栏 |
| 团队只追求零违规数量 | 代理指标替代了真实质量目标 |

## 做项目时怎么执行

1. **从风险开始：** 选一个反复发生、代价可见的架构偏离，不从工具清单开始。
2. **回链决定：** 写清它保护的质量场景、适用范围和不适用范围。
3. **选择最小证据：** 依赖图、AST、类型、Contract、Artifact 或生产 SLI，只取判定所需输入。
4. **选择最早可信执行点：** 同时记录等待、可绕过性和执行点故障时的默认行为。
5. **Shadow 运行：** 统计命中、误报、修复时间和既有 Baseline，再决定 Warn 或 Enforce。
6. **设计可修复输出：** 返回 Rule ID、依赖路径、原因、Owner、修复入口和例外流程。
7. **限制例外：** 最小范围、审批、补偿控制、到期与审计缺一不可。
8. **连接真实结果：** 同时观察用户、交付、可靠性和规则运行成本，按新证据调整或退役。

## 复习

1. 为什么一份写得很清楚的 ADR 仍不能阻止架构漂移？
2. 为什么反馈越早通常越便宜，却不代表所有检查都应阻断提交？
3. Policy、Check 与 Enforcement 各自回答什么问题？
4. 静态 Import Rule 为什么不能证明模块边界真的改善了交付结果？
5. 一个合格例外为什么必须有精确范围、Owner 和到期日？
6. 什么时候应退役规则，而不是不断增加 Allowlist？

## 来源与认识边界

- **来源事实：** Thoughtworks 资料把 Fitness Function 描述为持续衡量架构特征的反馈机制；Nx 展示基于标签和依赖图执行模块方向；OPA 展示策略决策与执行点分离；Pact 展示 Consumer Contract 与 Provider Verification；GitHub Rulesets 展示 Evaluate、Active、Required Check 与受控 Bypass；Google SRE 说明 SLO 和 Error Budget 只有连接书面动作与责任人才成为决策机制。
- **机制推导：** 本页从变化持续发生、人的注意力有限和违规成本随传播扩大，推导“架构意图 → 可观察证据 → 判定 → 执行动作 → 结果复审”的控制回路，并将 Policy、Check 和 Enforcement 分开。
- **工程建议：** 优先自动化高频、可重复、可观察且违规代价高的规则；在最早可信边界反馈；先 Observe 再阻断；对例外和规则本身实施 Owner、期限与退役治理。
- **待项目验证：** 哪些规则值得阻断、阈值、Baseline、误报容忍、执行点故障默认、审批权限和观察窗口，必须依据项目风险、团队能力、交付链和真实生产证据确定。
- **下一步：** 当前专题的第一性原理主干已从 L0 闭合到 L7。后续不按编号机械扩页；优先用真实项目练习“现象 → 决策 → 自动约束 → 结果复审”，只有反复出现新的稳定问题时再拆独立页。
