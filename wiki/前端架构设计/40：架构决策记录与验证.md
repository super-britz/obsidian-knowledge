# 架构决策记录与验证

> [!abstract] 先用一句话说清楚
> 架构决策不是宣布采用某个工具，而是在信息不完整、质量目标互相竞争的条件下，依据当前证据选择一组边界与机制，并提前声明代价、验证方法和退出条件。ADR 保存“当时为什么这样选”，检查保证“实现没有偏离”，生产证据再回答“这个选择是否真的改善了结果”。

## 为什么它属于 L7

前面的页面已经建立了不同层次：

```text
不可约约束
→ 质量目标
→ 设计原则
→ 实现机制
→ 复合系统形态
→ 具体工具
```

但从下层推导出一个方案，只能说明“在当前认识下值得尝试”。真实系统投入运行后，用户、流量、团队和依赖会提供新证据。若没有反馈返回决策层，整套架构会退化成一次性设计：

```text
做出选择
→ 实现并长期保留
→ 原始背景逐渐被遗忘
→ 新成员只能盲目接受或盲目推翻
```

L7 在链条末端增加回路：

```text
问题证据 → 决策 → 实现 → 运行结果
    ↑                         ↓
    └── 保留、修正、替代或撤销 ──┘
```

所以 ADR 不是额外文档工作，而是决策状态的持久化；验证也不是项目末尾的验收，而是让架构能够纠错的反馈机制。

## 第一性原理：架构决策是受约束的假设

做架构决定时有四个无法消除的事实：

1. **未来信息不完整。** 需求、流量、组织和供应商都会变化。
2. **质量目标会冲突。** 更强隔离可能增加延迟，更高自治可能增加运行复杂度。
3. **团队记忆会衰减。** 人员变动后，代码只能显示“现在是什么”，不能完整说明“为什么成为这样”。
4. **方案只有进入真实环境才暴露全部后果。** 设计评审无法穷举设备、流量、版本和人的行为。

因此，架构决策更接近：

```text
在上下文 C、约束 K 和证据 E 下
我们选择方案 A
期望改善质量结果 Q
接受已知代价 T
并用验证 V 判断是否保留
```

它不是永恒真理，而是带适用范围和置信度的工程假设。一个决定即使当时合理，也可能因为上下文变化而需要被新决定替代；这不表示旧决定“失败”，而表示系统正确使用了新信息。

## 什么值得成为架构决策

不是每个代码选择都需要 ADR。一个选择越容易产生以下影响，越值得记录：

- 改变模块、部署、数据、权限或团队边界；
- 建立跨团队依赖、公开接口或长期兼容责任；
- 显著影响性能、可靠性、安全、成本或可修改性；
- 失败会扩大到大量用户、数据或多个系统；
- 回退需要迁移数据、协调多个版本或中断业务；
- 预计持续较久，未来成员无法从代码恢复其完整理由。

可以用一个定性模型判断记录力度：

```text
架构重要性
≈ 变化爆炸半径 × 撤销成本 × 预期寿命 × 不确定性 × 协作者数量
```

这不是计算分数，而是提醒团队：局部、短命、容易撤销的实现细节可以留在 Pull Request；改变公共契约、状态权威、部署边界或安全模型的选择，则需要独立决策记录。

常见误区有两个极端：

- 什么都不记录，理由只存在于会议和某个人脑中；
- 每个依赖小版本和变量命名都写 ADR，真正重要的决定淹没在噪声里。

## 决策必须从问题证据开始

一条可复核的决策链应区分不同认识层：

| 层次 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 现象 | 真实观察到了什么？ | 发布经常等待、某路由 P75 变慢 |
| 证据 | 观察来自哪里，口径是什么？ | 发布记录、RUM、事故、代码依赖图 |
| 解释 | 哪条因果假设解释现象？ | 共享 Release Train 形成排队 |
| 约束 | 哪些条件不能随意改变？ | 法规、旧客户端、团队、预算、截止时间 |
| 质量场景 | 哪个主体在什么条件下应得到什么结果？ | 峰值流量下结算仍在预算内完成 |
| 原则 | 应调整什么关系？ | 缩小变化传播和故障半径 |
| 机制 | 用什么可复用办法改变关系？ | 兼容窗口、缓存、Adapter、独立流水线 |
| 系统形态 | 多个机制如何协同？ | BFF、微前端、混合渲染 |
| 工具 | 哪个实现满足这些条件？ | 某框架、Bundler、平台产品 |
| 验证 | 用什么证据判断有效？ | Contract Test、Canary、RUM、恢复演练 |

若从“想用 Module Federation”“要上 SSR”或“统一成 Monorepo”开始，方案已经偷偷替代了问题定义。工具只能在最后一段被选择；前面的证据、约束或目标变化时，工具选择也应允许变化。

还要分清事实和解释：

```text
事实：最近 12 次订单改动有 8 次等待共同发布窗口
解释：等待主要由共享 Release 决策造成
```

第二句仍是假设。它可能被更深的证据推翻，例如真正瓶颈其实是人工验收环境不足，而不是仓库或运行时结构。

## 把“更好”改写成质量场景

“高性能、稳定、可扩展、易维护”没有环境、刺激和衡量方法，无法比较方案。SEI 的 Quality Attribute Scenario 可以把愿望还原为六个部分：

```text
刺激来源 Source
→ 在环境 Environment 下产生刺激 Stimulus
→ 作用于对象 Artifact
→ 系统产生响应 Response
→ 用 Response Measure 判断
```

例如，“页面要快”可以改写为：

```text
一名使用目标低端设备的回访用户
→ 在普通移动网络下进入 /orders
→ 浏览器加载订单路由及首屏数据
→ 展示可识别内容并允许主要操作
→ P75 LCP 与 Feature Ready 满足上限，任务成功率满足下限
```

这里没有给出通用毫秒数，因为阈值必须来自当前基线、用户环境和业务风险。对可修改性也一样：

```text
一个熟悉项目的开发者
→ 在正常迭代中新增一种订单筛选条件
→ 修改订单 Feature
→ 不改无关领域即可完成、验证和发布
→ 受影响 Project、修改文件、交接次数和 Lead Time 在目标范围内
```

质量场景的价值是让方案面对相同问题。它不能保证测量绝对客观，也不能把用户信任、认知负担等复杂结果压缩成一个漂亮数字。

## 比较方案是在相同约束下交换代价

至少保留三类候选：

1. **保持现状：** 说明不改变的真实代价，作为基线而非稻草人。
2. **最小改变：** 先修复主要因果环节，例如优化流水线而不拆运行时。
3. **结构改变：** 当最小机制不能满足目标时，再比较新的系统形态。

比较时先使用不可违反的约束淘汰方案，再比较剩余方案如何影响高优先级质量场景：

| 候选 | 目标收益 | 新增代价 | 关键未知 | 失败与退出 |
| --- | --- | --- | --- | --- |
| A | 改善什么场景 | 牺牲哪些质量 | 哪个假设未证实 | 怎样停用或回退 |
| B | 改善什么场景 | 牺牲哪些质量 | 哪个假设未证实 | 怎样停用或回退 |

不要为了显得科学，把主观权重包装成精确总分。评分矩阵适合暴露参与者重视什么，不会自动产生正确答案。对于高影响决定，可以借用 ATAM 的思想：用 Stakeholder 排序后的场景识别 Risk、Sensitivity Point 和 Tradeoff Point，而不是只累计优点。

## 证据投入应与错误代价匹配

决策前不可能消除所有不确定性，继续分析本身也有机会成本。合理的证据预算近似满足：

```text
所需证据强度
∝ 撤销难度 × 失败爆炸半径 × 不确定性 × 决策寿命
```

| 决策类型 | 典型处理 |
| --- | --- |
| 局部且可逆 | 短 ADR 或 PR 说明、小实验、自动测试 |
| 跨模块但可灰度 | ADR、候选比较、Spike、兼容与回滚方案、有限 Cohort |
| 数据、安全或组织边界难逆 | 多类 Stakeholder、质量场景、Threat Model、迁移演练、分阶段批准 |

Spike 的产物不是“代码跑起来了”，而是降低某个关键未知，例如浏览器兼容、缓存命中、迁移吞吐或供应商限制。超过 Timebox 仍无法降低关键不确定性，也是应记录的证据。

[[15：可逆决策与演进边界|可逆性]]可以主动设计：Facade、Adapter、版本化契约、双读、Shadow Traffic、Feature Flag 和小 Cohort 都是在购买退出能力。但这些机制也有实现与清理成本，不应永久保留未使用的“未来可能性”。

## ADR 保存的是决定时刻，不是所有项目文档

Nygard 风格的最小 ADR 只有 Title、Context、Decision、Status 和 Consequences。为了让决策能够验证，可以在不失去轻量性的前提下补充：

```text
ID 与标题
状态、日期、Owner、Decision Makers / Consulted / Informed
上下文与基线证据
约束、Decision Drivers 与质量场景
考虑过的方案及未选原因
明确的 Decision
正面、负面和中性 Consequences
风险、关键假设与未知
Confirmation：怎样检查实现符合决定
Outcome：怎样判断目标改善且护栏未越界
Rollback / Exit 与复审触发条件
关联 ADR、代码、仪表盘、Runbook 和迁移计划
```

一份 ADR 只记录一个能够被明确陈述的重要决定。完整接口 Schema、任务拆解和操作步骤应链接出去，不应把 ADR 变成永远无法读完的总设计文档。

| Artifact | 它主要回答什么 |
| --- | --- |
| RFC / Design Proposal | 我们正在讨论哪些方案？ |
| ADR | 当时为什么决定做什么，并接受什么后果？ |
| Implementation Plan / Issue | 谁在什么时候完成哪些步骤？ |
| Contract / Test / Fitness Function | 当前实现必须满足什么？ |
| Architecture Diagram | 系统目前怎样连接？ |
| Runbook | 运行失败时怎样判断与恢复？ |
| Dashboard / Experiment Report | 决定产生了什么结果？ |
| Standard / Policy | 现在普遍生效的规则是什么？ |

ADR 可以从 RFC 的结论产生，但不能用一份历史记录代替持续更新的当前事实。

## 决策、交付和证据是三条状态轴

把所有状态只写成 `Accepted` 会制造错觉。至少应区分：

```text
Decision：Proposed → Accepted / Rejected → Superseded
Delivery：Not Started → In Progress → Shipped / Rolled Back
Evidence：Unverified → Observing → Supported / Refuted / Inconclusive
```

- Accepted：团队同意按此方向承担代价；不代表已经实现。
- Shipped：代码已进入目标环境；不代表目标结果已经出现。
- Supported：限定时间、环境和指标内的证据支持当前假设；不代表永远正确。
- Superseded：新决定替代旧决定；旧记录仍保留其历史上下文。

因此，不应直接改写已接受 ADR 的理由来配合现状。上下文或选择实质改变时创建新记录，并从新旧 ADR 双向链接；这样历史不会被事后合理化。

## 验证要覆盖从因果假设到生产结果

一项架构决定至少经过六类验证：

| 层次 | 核心问题 | 常见证据 |
| --- | --- | --- |
| 问题验证 | 现象真实且值得解决吗？ | Baseline、事故、用户任务、交付数据 |
| 机制验证 | 候选机制能影响推测的原因吗？ | Prototype、模型、Benchmark、Threat Model |
| 实现符合性 | 代码和部署遵守决定吗？ | Review、Contract Test、依赖规则、配置检查 |
| 结果验证 | 用户或团队结果改善了吗？ | RUM、Task Success、Lead Time、恢复时间 |
| 副作用验证 | 其他重要质量是否退化？ | 性能、安全、成本、错误率和运维护栏 |
| 保留验证 | 上下文仍成立，收益仍高于成本吗？ | 触发式复审、事故和趋势数据 |

“测试通过”通常只回答局部实现正确；“指标变好”也不自动证明由该决定导致。能做受控 Cohort、前后对照或逐步放量时，应固定版本、用户群、观察窗口和终止条件，减少同时变化造成的归因混乱。

验证失败也要保留语义：

- **Refuted：** 关键假设被证据反驳，应回退或提出替代 ADR；
- **Inconclusive：** 样本不足、指标噪声或实现偏离，不能伪装为成功；
- **Guardrail Breach：** 主目标改善但安全、性能或成本越界，仍不能继续放量；
- **Context Changed：** 原问题或约束已经变化，需要重新决策。

## Fitness Function 是反馈传感器，不是决策本身

当 ADR 中某个重要特征可以持续观察时，可以将其变成 Architecture Fitness Function：

| 架构意图 | 可用反馈 |
| --- | --- |
| Feature 不得反向依赖页面内部 | Dependency Graph / Import Rule |
| 公共契约保持兼容 | Consumer Contract / Schema Compatibility |
| 关键路由不超性能预算 | Bundle、Lab、RUM 与 Long Task 护栏 |
| Remote 失败不拖垮整页 | 故障注入与局部任务成功率 |
| 服务具备可诊断性 | Trace Context、结构化日志与 Runbook 检查 |
| 发布可以安全恢复 | Canary、Rollback Drill 与恢复时间 |

关系应保持清楚：

```text
ADR 说明为何保护某项质量
→ Quality Scenario 定义什么叫满足
→ Fitness Function 持续提供局部反馈
→ 生产结果验证是否创造真实价值
```

不是所有质量都能自动化，也不是所有可测指标都重要。覆盖率、Bundle 大小或告警数量只是代理；若它们不再预测用户和业务结果，就应修改或删除。[[41：自动化架构约束|自动化架构约束]]继续说明怎样选择执行点、严重级别、例外和所有者。

## 复审应由证据触发，而不是篡改历史

ADR 可以声明复审日期，但更重要的是声明 Trigger：

- 关键质量场景连续越过阈值；
- 真实流量、用户设备或业务规模跨过原假设范围；
- 发生与该决定相关的重大事故或安全事件；
- 上游 API、浏览器、框架或供应商进入不兼容或停止支持状态；
- 团队所有权、合规或预算约束发生变化；
- 迁移阶段完成，临时兼容机制应该收缩；
- 实际维护成本长期高于记录的收益。

复审可能得到四类结果：继续保持、调整执行、创建替代 ADR、撤销并清理。若决定已经失效却没有删除实现和自动约束，系统会同时服从新旧意图；若只删除旧约束却不留下替代记录，团队又失去历史。

## 示例：是否把订单路由拆成微前端

> [!note] 示例边界
> 下列数字仅用于展示 ADR 怎样连接证据与验证，不是任何项目的推荐阈值。

### 1. Context 与证据

某后台系统由四个团队共同维护一个 SPA。样本期内，订单需求多数只修改订单域，但仍要等待共同 Build、全量回归和固定 Release Window。订单团队没有独立回滚入口。

基线同时记录：

- 订单变更从完成到上线的 P50 / P90 等待时间；
- 全站 Pipeline 与回归耗时；
- 跨团队共同修改比例；
- `/orders` 的 LCP、Feature Ready、错误率和任务成功率；
- 当前事故恢复时间与共同回滚次数。

### 2. 约束与质量场景

- 必须沿用统一登录、导航、Design Token 和审计链；
- 目标设备不能因拆分增加不可接受的主线程和网络成本；
- 旧 Shell 与新订单 Artifact 必须在兼容窗口内共存；
- Remote 失效时只允许订单任务不可用，其他路由仍可使用。

目标不是“采用微前端”，而是：订单团队在不重建其他业务的前提下完成灰度、发布和回滚，同时整页用户性能与安全护栏不退化。

### 3. 候选方案

| 方案 | 预期收益 | 主要代价或未知 |
| --- | --- | --- |
| 保持现状 | 无迁移成本 | 共同发布等待继续存在 |
| 只优化 Monorepo Affected CI | 缩短 Build 与回归 | 仍可能共享 Release 和回滚 |
| Route-level 独立 Document | 发布、生命周期和失败边界清楚 | 导航与共享体验接缝 |
| 同页 Runtime Remote | 同页体验连续、独立 Artifact | 版本组合、弱隔离、性能与供应链风险 |

### 4. Decision

假设证据表明主要瓶颈确实是 Release 耦合，可以先选择 `/orders/*` 的 Route-level Pilot；具体采用独立 Document 还是 Runtime Remote，由目标体验和测得的性能、隔离约束决定，而不是预先绑定 Module Federation。

决定同时接受：需要 Manifest / Route、兼容窗口、独立 Pipeline、版本遥测、Fallback 和平台维护成本。其他路由暂不拆分。

### 5. Confirmation 与 Outcome

实现符合性：

- Orders 可不修改、不重建其他应用产生和发布不可变 Artifact；
- Shell / Orders N 与 N-1 Contract Test 通过；
- 路由、Session Context、Telemetry 和 Design Token 契约符合 Schema；
- 失败注入证明订单边界可以停用和回退。

结果验证：

- 订单变更等待和共同发布次数相对基线下降；
- 订单任务成功率、RUM 与错误率没有越过 Guardrail；
- 独立回滚在目标时间内完成，并能确认权威状态；
- 平台维护、版本事故和跨团队协调成本没有抵消收益。

退出条件：若经过约定样本和窗口后交付等待没有改善，或性能、可靠性、安全成本持续越界，则停止迁移下一个路由，回退 Pilot 或改用更简单的模块化与流水线优化方案，并用新 ADR 记录替代决定。

## 可观察的错误信号

| 现象 | 决策链中缺失了什么 |
| --- | --- |
| ADR 标题是“采用 React” | 没有问题、约束和期望结果 |
| 只列最终方案的优点 | 没有真实权衡与负面后果 |
| 用“大家都在用”作为证据 | 流行度没有映射到本项目质量场景 |
| 所有方案都打一个总分 | 主观权重被伪装成客观精度 |
| Accepted 后再也不看 | 没有交付、结果和复审状态 |
| 修改旧 ADR 让它符合现状 | 历史上下文被事后重写 |
| 测试通过就宣布架构成功 | 只验证实现，没验证结果和副作用 |
| 指标改善却没有 Baseline / Cohort | 无法判断变化来自何处 |
| 每项指标都变成阻塞 Gate | 反馈成本和误报阻断正常演进 |
| ADR 只有架构师能创建 | 决策与实际实现、运行责任脱节 |
| 决定失效但规则仍在 CI 阻塞 | 决策生命周期和约束生命周期失联 |

## 做项目时怎么执行

1. **收集 Baseline：** 先记录用户、交付、故障或成本现象及口径，不从工具名称开始。
2. **指定 Owner 与 Stakeholder：** 找到承担实现、运行和结果的人，而不是只邀请技术职位最高者。
3. **写约束和质量场景：** 把抽象 `-ility` 写成 Source、Stimulus、Environment、Artifact、Response 和 Measure。
4. **列真实方案：** 至少包括保持现状、最小变化和结构变化，记录淘汰条件与未知。
5. **匹配证据预算：** 根据可逆性、爆炸半径、寿命和不确定性选择讨论、Spike、模型、Threat Model 或正式评估。
6. **写一项明确 Decision：** 说明做什么、不做什么、适用范围、承担的后果和关键假设。
7. **分开两类验证：** Confirmation 检查实现符合性；Outcome 与 Guardrail 检查真实结果和副作用。
8. **设计渐进交付：** 明确兼容窗口、Cohort、停止条件、Rollback Frontier 和证据关联字段。
9. **连接执行入口：** 从代码、PR、测试、仪表盘和 Runbook 回链 ADR；重要约束再转成 Fitness Function。
10. **用新证据复审：** Supported、Refuted 或 Context Changed 都留下记录；改变方向时创建替代 ADR 并清理旧机制。

## 来源与认识边界

- **来源事实：** Michael Nygard 提供轻量 ADR 的 Context、Decision、Status 与 Consequences 结构及 Superseded 历史；AWS 资料补充 Owner、Review、Decision Log 和接受后不可变流程；MADR 提供 Options、Drivers 与 Confirmation 等扩展字段；CMU SEI 的质量场景与 ATAM 支撑场景化质量表达、风险和权衡分析；Thoughtworks 资料支撑 Fitness Function 作为持续架构反馈机制。
- **机制推导：** 本页从未来信息不完整、质量目标冲突、组织记忆衰减和生产环境不可穷举，推导“决策是假设 → ADR 保存上下文 → 分层验证 → 证据回流 → 替代或退出”的闭环。
- **工程建议：** 使用架构重要性和错误代价匹配 ADR 与证据投入；分开 Decision、Delivery、Evidence 状态；同时记录 Outcome、Guardrail、Rollback 和 Trigger；只把重要且可观察的特征变成 Fitness Function。
- **待项目验证：** 哪些决定需要 ADR、使用何种状态、谁批准、质量阈值、观察窗口和哪些检查阻断发布，必须结合团队规模、监管、风险、系统寿命和现有交付能力决定。
