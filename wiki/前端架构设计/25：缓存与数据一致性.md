# 缓存与数据一致性

> [!abstract] 先用一句话说清楚
> 缓存是为了少做一次昂贵工作而保留的可复用副本；副本一旦离开权威来源，就必然可能因时间、身份或并发变化而失真。因此缓存设计不是“存多久”一个参数，而是同时定义身份、新鲜度、失效、回源、冲突、隔离和删除的副本协议。

## 从“复用旧结果必然产生副本”推导

不使用缓存时，每次读取都向权威来源重新计算或传输，正确性路径短，但等待和资源成本可能重复发生。缓存把某次结果留在离消费者更近的位置：

    一次请求与上下文
    → 权威来源产生结果 R0
    → 以 Key K 保存副本
    → 后续等价请求复用 R0
    → 节省网络、计算和等待

收益来自“没有重新确认就复用过去结果”，风险也来自同一件事。副本建立后，权威事实、权限、查询条件或代码版本都可能改变：

    t0：权威值 A，缓存副本 A
    → t1：权威值改成 B
    → 更新尚未传播或缓存仍在有效窗口
    → 权威值 B，缓存副本 A 同时存在

只要允许复制并减少协调，就不能同时免费获得瞬时全局一致。架构真正能决定的是：**哪些读取允许看到多旧的值，哪些动作必须重新确认，差异怎样被发现和收敛。**

完整读取协议应是：

    请求 + 身份与查询上下文
    → 构造语义唯一的 Key
    → 找到候选副本
    → 判断 fresh、可容忍 stale、必须校验、不可用或 miss
    → 复用、条件校验、回源或安全失败
    → 更新或淘汰副本
    → 暴露来源、版本和新鲜度证据

所以 Cache Hit 只表示“找到了可复用对象”，不自动表示 Key 正确、用户隔离正确或值足够新。

## 每个缓存先写出副本契约

[[14：按数据生命周期分配资源|数据生命周期]]决定是否值得复制；本页继续定义副本建立后的协调责任：

| 契约问题 | 必须明确的内容 |
| --- | --- |
| 缓存什么 | 原始响应、规范化实体、查询结果、渲染产物还是失败结果 |
| 谁是权威 | 冲突或恢复时由哪个服务、版本或领域规则裁决 |
| Key 是什么 | 哪些输入、身份、权限、语言、版本会改变正确结果 |
| 允许旧多久 | 无需校验窗口、可降级旧值窗口和绝对不可用条件 |
| 怎样更新 | 时间过期、写后失效、事件推送、版本换 Key 或按需校验 |
| 冲突怎么办 | 覆盖、合并、拒绝、回滚还是重新读取 |
| 谁能共享 | 私有会话、租户、区域或公共内容的隔离范围 |
| 怎样退出 | 未命中、损坏、源站失败、登出、删除和版本升级时的行为 |

这些规则不存在时，缓存会从“受控副本”变成第二个事实来源。库可以管理存储和订阅，不能替业务决定旧价格能否结算、旧权限能否继续访问。

## Key 是数据语义身份，不只是 URL

若两个请求在正确情况下可能得到不同结果，它们就不能无条件共享同一个 Key。一个查询身份可能受到这些因素影响：

    资源与接口版本
    + tenant / account / permission scope
    + locale / currency
    + filter / sort / page
    + feature or schema version

HTTP Cache 至少按方法和目标 URI 选择响应；当 Header 会改变表示时，源站用 `Vary` 声明选择维度。应用查询缓存则需要把 Query Function 所依赖且会改变结果的变量纳入 Query Key。身份或权限由隐式会话提供时，也必须把缓存隔离在不可混淆的会话命名空间中，并在切换主体时清理，而不是把 Token 原文写入 Key。

Key 过少会把不同语义碰撞在一起，造成串用户、错语言或错筛选；Key 过多又会让本可复用的请求全部 Miss，增加存储和回源。判断标准不是字符串长短，而是：

> 相同 Key 是否意味着这些消费者可以在同一新鲜度和权限规则下安全复用同一结果？

多层缓存还可能使用不同 Key。CDN 只看 URL 与部分 Header，Query Cache 却还包含页面参数；任何一层遗漏真实变化维度，都可能在更上层已经正确分 Key 时仍返回错误副本。

## 新鲜度是允许不协调的时间窗口

缓存至少要区分五种状态：

| 状态 | 已知事实 | 合理动作 |
| --- | --- | --- |
| Fresh | 仍在允许免校验复用的窗口 | 直接使用 |
| Stale but usable | 超出新鲜窗口，但当前任务允许短期旧值 | 标明旧值，同时后台校验 |
| Stale and must validate | 不得未经确认继续使用 | 条件校验或完整回源 |
| Missing / evicted | 没有可用副本 | 回源，或进入明确离线状态 |
| Corrupt / incompatible | 结构或版本不能被当前代码解释 | 删除副本并安全重建 |

要避免把四个不同的时间混成一个 TTL：

| 时间 | 回答的问题 |
| --- | --- |
| Freshness Window | 多久内可以不联系权威来源直接复用？ |
| Stale Serving Window | 过期后还能否为降级短暂展示？ |
| Retention / GC Time | 无人使用的副本在本地保存多久？ |
| Business Expiration | 这项事实在领域上何时失去效力？ |

HTTP 的 `max-age` 定义 Freshness Lifetime，不保证源站在窗口内绝对没变，也不保证缓存一定保留到该时刻。`no-cache` 是“可以存，但复用前必须校验”；`no-store` 才是“不要存”。中文语境中的“强缓存”和“协商缓存”更适合看成同一副本生命周期的两个路径：Fresh 时直接复用，Stale 时携带 Validator 重新确认。

## 校验减少传输，不等于没有请求

服务端返回 ETag 后，客户端可在后续 GET 中发送 `If-None-Match`：

    本地持有 representation + ETag v1
    → If-None-Match: "v1"
    → 源站当前仍是 v1：返回 304，继续复用本地 Body
    → 源站已经是 v2：返回 200 + 新 Body + 新 Validator

304 通常减少响应体传输，但请求、网络往返和服务端比较仍然存在。若目标是完全隐藏等待，需要在可容忍窗口内先显示旧值并后台校验；`stale-while-revalidate` 正是在显式扩大旧值窗口来换取低延迟。

Validator 还可保护写入。客户端携带 `If-Match: "v1"` 修改资源时，若服务端已经变成 v2，可以拒绝这次基于旧版本的覆盖，让流程进入 [[23：运行时 Schema 与错误模型|conflict]]，而不是静默丢失他人的更新。ETag 因而是表示版本证据，不是业务幂等键或 Operation ID。

不同用户动作需要的保证也不同：

| 用户语义 | 更有用的一致性要求 |
| --- | --- |
| 版本化静态资源 | URL 版本不变时内容不变 |
| 新闻或商品列表 | 在明确窗口内允许旧值，最终收敛 |
| 用户刚保存的资料 | Read-your-writes：成功后不能立刻读回旧值 |
| 连续查看同一流程 | Monotonic reads：不能先看到新版又退回旧版 |
| 权限、价格、库存、支付 | 执行动作时由权威方重新验证关键不变量 |

只说“最终一致”或“强一致”仍太粗；工程契约应写成用户能观察到的顺序与最长旧值窗口。

## 失效是撤销信任，不是更新已经完成

缓存更新有四种基本触发：

- **时间：** 超过窗口后要求校验或回源；
- **写事件：** 已知某次 Mutation 影响哪些副本，将它们标记为 Stale；
- **版本换 Key：** 内容变化产生新 URL、Hash 或 Schema Version，旧副本不再被新请求选中；
- **读取时校验：** 用 ETag、版本号或服务端查询判断现有副本是否仍可用。

失效的本质是“不能再把这个副本当作当前可信答案”，实现可以删除，也可以保留并强制校验。以 TanStack Query v5 为例，`invalidateQueries` 会把匹配 Query 标为 Stale，当前使用中的 Query 还可能后台 Refetch；它并没有让远端事实或其他缓存层同时更新。

一次商品修改可能影响详情、列表、搜索结果、购物车摘要和统计聚合。这个反向依赖图不会由 HTTP 或 Query Library 自动推断。常见策略是：

| 已知程度 | 更新策略 | 主要代价 |
| --- | --- | --- |
| Mutation 返回完整权威实体 | 精确替换对应实体副本 | 仍需处理列表和聚合投影 |
| 知道受影响的 Query 家族 | 定向失效并重取 | 增加请求，但规则清晰 |
| 结果可由客户端可靠计算 | 同步修改相关副本 | 容易遗漏或复制服务端规则 |
| 依赖关系不明确 | 扩大失效或直接不缓存 | 命中率和性能下降 |

HTTP 规范要求成功的不安全请求使其经过的缓存中的目标 URI 失效，但这不代表所有相关 URI、CDN 节点、Service Worker 和 Query Cache 已在全局更新。发布或写入流程必须逐层说明传播与兜底。

## 多层缓存会相乘状态空间

| 层次 | 典型所有者 | 关键特点 |
| --- | --- | --- |
| CDN / Reverse Proxy | 平台或服务团队 | 跨用户共享，隔离和 Purge 风险高 |
| Browser HTTP Cache | 浏览器与响应协议 | 服从 Freshness、Validator、`Vary` 等 HTTP 语义 |
| Service Worker Cache API | 前端脚本 | 与 HTTP Cache 独立，不自动更新或过期 |
| Query Cache | 应用运行时 | 按业务 Query Key 管理服务端事实副本 |
| IndexedDB / 持久化副本 | 应用与设备 | 跨会话存在，需要迁移、配额和删除治理 |

一项数据同时经过三层缓存时，不是只有“新/旧”两个状态，而是每层都可能 Hit、Miss、Stale 或持有不同版本。加层之前要说明：

    哪层有权直接回答
    → 哪层负责校验
    → 写入如何逐层失效
    → 出错时怎样绕过
    → 版本升级和删除怎样遍历全部副本

Service Worker 的 Cache API 不会因为脚本升级自动清理，也不会自动遵守 HTTP Cache 的过期过程；需要版本化 Cache Name，并在新 Worker 能安全接管时迁移或删除旧内容。若本地还允许离线写入，它就不再只是缓存，而是一个需要 Operation ID、同步队列、冲突规则、Tombstone 和重新授权的复制系统。

## Mutation 与乐观更新必须回到权威事实

服务端事实的本地副本可以用三种强度更新：

1. **使用成功响应：** 服务端返回规范化后的最终实体，直接更新精确 Query；
2. **失效并重取：** 客户端无法可靠推导所有结果时，撤销相关副本信任并从权威来源重建；
3. **乐观更新：** 提交前先显示预测结果，同时保留 Pending 身份、旧快照或逆操作，失败时回滚，完成后再协调权威结果。

乐观更新不是“先宣布成功”。它适合失败概率低、反馈收益高、结果可逆且冲突可解释的动作；支付、下单和不可逆删除通常应展示“处理中”，等待权威回执。

并发会让简单快照回滚失效：

    Mutation A 乐观写入
    → Mutation B 基于新状态继续写入
    → A 失败后恢复 A 之前的整份快照
    → B 的较新结果也被抹掉

因此需要按 Operation 或版本应用逆变更，或在失败后重新获取权威版本。Mutation 前发出的旧 Refetch 也可能迟到并覆盖新结果；取消请求只能节约资源，正确性仍要靠 [[21：状态机与异步流程|Query Version、流程守卫或资源版本]]拒绝陈旧写入。

## 缓存失败也需要隔离与观测

缓存可以降低源站负载，也可能在同一时刻制造更大负载：

    热 Key 同时过期
    → 大量消费者一起 Miss
    → 同时回源
    → 源站变慢或失败
    → 重试继续放大

可以用同 Key 在途请求合并、随机化过期时间、后台刷新、并发预算和 [[24：失败边界、恢复与可观测性|有界重试]]控制惊群。`stale-if-error` 可以在明确窗口内用旧值换可用性，但必须排除不能安全陈旧的权限和交易事实。

缓存观测至少要区分：

- 哪一层 Hit、Miss、Bypass、Stale、Revalidated 或 Error；
- 实际 Key 家族、数据版本、`cachedAt`、Age 与剩余新鲜时间；
- Miss 是真正不存在、`Vary` 不匹配、被主动失效还是版本不兼容；
- Mutation 后多久完成所有必要副本的收敛；
- 304 比例、回源量、合并请求数、旧值展示率和 Read-your-writes 违例；
- 登录切换、数据删除和发布后是否仍有旧副本被读取。

RFC 9211 的 `Cache-Status` 可以解释 HTTP Cache 链路中的 Hit、转发原因、TTL、存储和请求合并，但不能观察 Query Cache 或 Service Worker。Hit Ratio 也不是最终质量指标：一个漏掉 Tenant 的错误 Key 可能拥有极高命中率。必须把延迟与用户看到错误、越权或回退旧版本的证据一起判断。

## 何时值得缓存，代价是什么

缓存值得使用的必要条件是：在允许的旧值窗口内，确实存在足够多语义相同的重复读取，而且节省的等待、计算或传输超过副本协调成本。若请求几乎不重复、结果变化快且错误代价高、Key 难以安全隔离，或源操作本身很便宜，不缓存通常更简单可靠。

同一时刻到达的重复请求可以先做 In-flight Deduplication：让它们等待同一次正在进行的工作，但完成后不长期保留结果。这能消除并发重复，又不承担长期新鲜度；它与缓存不是同一机制。

渐进顺序可以是：

    测量真实重复成本
    → 先消除重复调用或合并在途请求
    → 为一种数据定义副本契约
    → 只增加一层缓存
    → 验证性能收益和一致性风险
    → 证据足够再扩大范围或持久化

每增加一层都会新增 Key、时钟、容量、失效、迁移、安全和诊断责任。TTL 不应来自习惯数字，而应来自“业务最多能承受多旧，以及到期回源会造成多大峰值”。

## 可观察的错误信号

| 现象 | 可能缺失的机制 |
| --- | --- |
| 不同用户看到相同私有数据 | Key 或共享范围缺少身份隔离 |
| 切换语言后仍显示旧语言 | 影响表示的变量未进入 Key 或 `Vary` |
| 用户保存成功后立即读到旧值 | 缺少 Read-your-writes 协调 |
| 页面先显示新版又退回旧版 | 迟到 Refetch 没有版本守卫 |
| `invalidate` 后仍断言缓存已更新 | 把撤销信任误当成权威重建 |
| Service Worker 更新后长期运行旧页面 | Cache 版本和清理责任缺失 |
| 同一时刻大量请求击穿源站 | 热 Key 过期未做合并、抖动或预算 |
| 缓存损坏后每次启动都崩溃 | 缺少 Schema 版本、淘汰和重建路径 |
| 命中率很高但投诉数据错误 | 指标只衡量复用，没有衡量正确性 |
| 登出或数据删除后设备仍有副本 | 删除生命周期没有覆盖持久化缓存 |

## 做项目时怎么验证

1. 选一项真实服务端事实，写出权威来源、消费者和可接受旧值窗口。
2. 画出 CDN、HTTP Cache、Service Worker、Query Cache 与持久化存储的真实读取链；不存在的层不要为了完整而添加。
3. 为每层写 Key、共享范围、Fresh/Stale 规则、Validator、Retention、容量和绕过方式。
4. 从所有会改变正确结果的输入生成测试矩阵：Tenant、Account、权限、语言、筛选、分页和版本。
5. 模拟 Fresh、Stale、Miss、损坏、离线、源站失败与多层持有不同版本，检查用户看到的来源和新鲜度是否明确。
6. 测试写成功后的详情、列表和聚合更新，以及旧 Refetch 迟到、连续 Mutation、乐观失败和版本冲突。
7. 模拟热 Key 同时过期，验证请求合并、回源峰值、重试预算和 Stale Fallback。
8. 测试登出、切换用户、Service Worker 升级、Schema 迁移、服务端删除和清除敏感数据。
9. 同时比较用户延迟、字节与源站节省，以及旧值率、错误复用、收敛时间和维护复杂度；收益不足就移除该层。

## 别误解

- **缓存命中就是正确结果。** 命中只证明找到了候选副本；Key、隔离与新鲜度仍可能错误。
- **TTL 到期会自动拿到新数据。** 到期只撤销免校验资格；是否回源、何时回源、失败时怎么办仍由读取协议决定。
- **`no-cache` 表示完全不缓存。** HTTP 中它允许存储，但要求复用前校验；禁止存储使用 `no-store`。
- **调用 Invalidate 就完成同步。** 它通常只是标记 Stale 或删除本地副本，权威重取和其他层传播尚未完成。
- **离线写入只是多加一层 Cache。** 一旦副本可以独立接受写入，就需要完整同步、冲突、身份和删除协议。
- **乐观更新让系统更快。** 它缩短感知等待，却增加 Pending、回滚、并发和权威协调状态。

## 来源与下一步

- **来源事实：** RFC 9111 定义 HTTP Cache Key、`Vary`、Freshness、Validation、Cache-Control 与局部失效语义；RFC 9110 定义 ETag、条件读写、304 和前置条件失败；RFC 5861 定义 `stale-while-revalidate` 与 `stale-if-error`；TanStack Query v5 文档说明 Query Key、Invalidation 和乐观更新行为；Service Workers 规范说明 Cache API 与 HTTP Cache 独立且不会自动更新或过期；RFC 9211 定义可解释 HTTP Cache 处理路径的 `Cache-Status`；课程材料区分 HTTP、本地存储与 Service Worker 等缓存位置。
- **机制推导：** 将缓存统一建模为“语义 Key → 副本状态判断 → 复用或协调 → 更新与淘汰 → 证据”的协议，并从复制必然产生时间差推导身份、新鲜度、失效、冲突、隔离和删除责任。
- **工程建议：** 先用用户可观察语义定义最长旧值窗口和写后保证，再只为有实测重复成本的数据增加一层缓存；以版本与权威重取处理 Mutation 和并发，以多层故障注入同时验证性能收益与错误复用风险。
- **待项目验证：** 哪些数据值得复制、Cache Key 包含哪些身份与版本维度、每层允许旧多久、写后怎样收敛、敏感数据何时删除，都必须由业务正确性、真实流量、权限模型和故障成本决定。
