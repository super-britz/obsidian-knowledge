# 渲染机制与性能预算

> [!abstract] 先用一句话说清楚
> 页面变得有用不是一个“加载完成”事件，而是内容出现、布局稳定、交互响应和任务完成逐步成立。CSR、SSR、SSG、流式渲染、拆包与 CDN 只是把必要工作移到不同时间、位置和设备；应先定义用户结果，再按关键依赖链分配预算，用真实设备上的分位数和任务证据判断这次交换是否值得。

## 从“用户到底在等什么”开始

用户打开页面后，系统至少可能经过：

    导航、身份与缓存上下文
    → DNS、连接、请求与服务端取数
    → HTML 开始到达
    → 发现并下载 CSS、字体、图片与 JavaScript
    → 构建 DOM、CSSOM 与 Render Tree
    → Style、Layout、Paint 与 Composite
    → 下载、解析、编译并执行交互代码
    → Hydration、事件处理器和 Feature 就绪
    → 用户动作得到反馈
    → 权威系统确认任务完成

这条链上有多个不同结果：

| 结果 | 用户观察 | 不能由它证明 |
| --- | --- | --- |
| 内容出现 | 不再白屏，能读到主要信息 | 布局不会跳、按钮可用 |
| 布局稳定 | 内容不会意外移动 | 点击能及时响应 |
| 交互可响应 | 输入后很快出现视觉反馈 | 业务操作已经成功 |
| Feature 就绪 | 当前功能所需代码、状态与数据可用 | 服务端副作用已提交 |
| 任务完成 | 用户得到可验证的业务结果 | 其他旅程也同样快 |

因此“页面加载用了 2 秒”缺少终点语义。若服务端 HTML 在 500 毫秒出现，但 JavaScript 8 秒后才附着事件，用户看到的按钮可能只是不能工作的图片；反过来，内部工具即使首屏没有营销内容，只要核心表单很快可操作，也可能已经满足目标。

性能的第一性问题不是“哪个框架跑分高”，而是：

> 对哪个用户、在哪种环境中，哪个有价值结果必须在多久内成立，慢下来时又是哪段依赖链在消耗预算？

## 关键路径是依赖图，不是资源清单

产生正确结果需要一些不可省略的读取、计算、传输与呈现工作。优化可以删除重复请求、无用代码和强制同步布局等浪费；剩余工作则只能改变：

- **何时做：** 构建时、请求时、首次交互前或空闲时；
- **在哪里做：** 源站、边缘、浏览器主线程、Worker 或 GPU；
- **做几次：** 每次请求、每个版本、每个用户或命中副本时不再做；
- **谁承担：** 平台、服务端、网络还是用户设备；
- **等待关系：** 串行阻塞、并行进行还是晚于关键结果。

如果 A、B 可以并行，用户不会等待 `A + B`；如果 C 必须等 A 完成，A→C 就构成依赖链。某个目标的完成时间主要受最长前置链控制：

    目标可用时间
    ≈ max（所有必要依赖链的完成时间）

所以仅把所有文件压小 10%，不一定改变最长链；把非关键第三方脚本从链上移走，反而可能显著改善结果。浏览器的 Critical Rendering Path 只解释首次像素依赖哪些 HTML、CSS、JavaScript 和渲染步骤，**不是完整用户任务的全部关键路径**。

这也解释了为什么渲染机制不会凭空创造性能。它们只是重新安排上述工作；若没有先找到目标和最长链，就只能把成本从一个指标移到另一个指标。

本页把“渲染机制”和“性能预算”放在一起，是因为它们构成一个最小决策闭环：机制是改变工作位置与依赖关系的手段，预算是判断改变是否改善用户结果的验收条件。这里只有选择机制所必需的局部预算；跨应用的自动卡口、发布治理和持续反馈属于后续 L7，不与本页的实现机制混在一起。L5 的 [[30：渲染架构与交付形态|渲染架构]]则负责组合数据、缓存、部署和运行责任，也不是本页要提前解决的问题。

## 先把两个维度分开

课程材料把 SPA、MPA、CSR、SSR、SSG 与同构放在同一段讨论，适合建立技术地图，但做架构决策时需要拆成两个正交问题：

| 维度 | 回答的问题 | 常见选择 |
| --- | --- | --- |
| 导航与文档生命周期 | 切换 URL 时复用当前 Document，还是向服务端获取新 Document？ | SPA、MPA、两者混合 |
| 初始 HTML 产生时机 | 当前路由的内容由谁、在什么时候变成 HTML？ | CSR、请求时 SSR、构建时 SSG、流式 SSR |

一个应用可以首次请求用 SSR，Hydration 后再用 SPA 式客户端导航；MPA 的每个页面也可以由请求时模板生成或由静态文件直接返回。于是：

- SPA 不等于只能 CSR；
- SSR 不等于每次导航都刷新整个 Document；
- SSG 不等于页面没有客户端状态；
- “同构”只说明部分代码可在服务端和浏览器运行，不自动证明两边环境、数据与输出一致。

不先拆维度，就容易把“切页方式”“HTML 来源”“数据新鲜度”和“客户端交互”绑定成一个套餐。

## 四种机制分别移动了什么工作

| 机制 | HTML 何时产生 | 主要换取 | 新增成本与约束 |
| --- | --- | --- | --- |
| CSR | 请求后由浏览器运行 JavaScript 产生主要内容 | 静态部署简单；复杂登录态交互集中在客户端；后续局部导航自然 | 首次内容依赖脚本、设备 CPU 和客户端取数；弱网低端机更敏感 |
| 请求时 SSR | 每次请求在服务端取数并生成 HTML | 请求特定内容可在客户端代码就绪前出现；服务端接近私有数据和可信边界 | TTFB 加入服务端计算；需要运行容量、缓存、双环境兼容、失败恢复和 Hydration |
| SSG | 构建或再生成阶段预先产生 HTML | 请求时几乎不做渲染计算，产物容易由 CDN 共享 | 构建时间、路径数量、新鲜度、发布与失效成为主要成本 |
| 流式 SSR | 请求时先生成 Shell，再按 Boundary 逐段发送 | 独立快速区域不必等待慢区域，用户可更早看到有意义骨架和内容 | Boundary、Fallback、顺序、状态码、代理缓冲、客户端恢复与 Hydration 更复杂 |

### CSR：把首屏工作交给每台用户设备

典型 CSR 链路是：

    极小 HTML Shell
    → 下载入口脚本和依赖 Chunk
    → 解析、编译、执行
    → 获取页面数据
    → 生成 DOM
    → 浏览器布局与绘制

它的优势不是“浏览器一定更快”，而是静态文件易部署、服务端无需为每次请求渲染，且复杂登录态应用的交互状态本来就要留在客户端。代价是每台设备都要重复承担代码执行，主要内容可能被脚本和数据串行阻塞。

因此后台系统、离线应用或打开后长时间操作的工具可能合理使用 CSR；公开内容页、弱网入口或低端设备占比高的旅程，则要证明用户可以接受这段前置工作。不能从一次开发机白屏时间推断所有用户体验。

### SSR：把 HTML 生成移到请求路径

请求时 SSR 把取数与初始组件执行移到服务端：

    请求
    → 服务端鉴权、取数和渲染
    → 返回已有内容的 HTML
    → 浏览器绘制
    → 下载客户端代码并 Hydrate

它可能缩短“主要内容出现”的链，却会增加服务端 TTFB、计算容量、冷启动、部署和监控成本；服务端数据慢时，整份 HTML 也可能更晚开始。HTML 更早出现，也没有删除浏览器为了完整交互仍需执行的 JavaScript。

SSR 更适合请求特定、需要在脚本就绪前可读或需要服务端可信数据的页面。若内容完全静态、无需个性化，每次请求重新渲染通常是在重复工作；若页面只有登录后重交互且公开内容价值很低，SSR 的运维成本也可能没有对应收益。

### SSG：用构建与新鲜度换请求时成本

SSG 将多次重复的请求时渲染折叠为一次预计算：

    构建时确定路径与数据
    → 生成带版本的 HTML 和资源
    → 发布到分发节点
    → 多个请求复用同一产物

当路径集合有限、内容可共享、变化慢且允许按发布更新时，它能缩短请求关键链并降低运行容量。路径数量巨大、数据频繁变化或每个用户输出不同，则会把请求成本变成超长构建、陈旧页面和失效风暴。

所谓增量或按需再生成，本质是在 SSG 产物之上增加“何时判旧、谁触发重建、重建期间返回什么、失败后是否继续用旧值”的 [[25：缓存与数据一致性|副本更新协议]]。它改变静态产物的新鲜度，不是浏览器中的第五套渲染管线。

### 流式 SSR：解开独立区域的等待

假设页面 Shell、账户摘要和推荐列表互不依赖，而推荐接口最慢。非流式 SSR 可能等待全部区域后才响应；流式 SSR 可以先发送 Shell 与摘要，用 Fallback 占位，推荐完成后再发送其 HTML。

它优化的是：

    所有区域取最大完成时间后一起出现
    ↓
    最小可用 Shell 先出现，各独立区域按完成顺序揭示

慢推荐仍然慢，客户端交互代码仍然要加载。过早发送一个只有 Spinner 的 Shell 也未必有用户价值。Boundary 应贴合独立可理解、可失败和可恢复的区域，而不是为了“流式”机械切碎组件树。

流一旦开始，HTTP Header 与状态码通常已经提交；Shell 失败、后续区域失败和客户端恢复需要不同策略。代理或平台还可能缓冲 Chunk，所以必须从真实客户端验证“何时收到并绘制”，不能只看服务端已经 `write`。

## Hydration 暴露“可见但不可用”的间隙

服务端或静态生成只产生 HTML 快照。对于需要客户端状态与事件的页面，还要经历：

    服务端 HTML 已可见
    → 客户端脚本下载、解析和执行
    → 用相同初始数据重建组件结果
    → 将逻辑和事件附着到现有 DOM
    → 交互真正可用

这段时间是 Hydration Gap。用户可能已经看到按钮并点击，却没有任何反馈。解决方向不是隐藏所有内容直到 Hydration 完成，而是按用户价值减少必须激活的范围：

- 纯内容和原生链接尽量依赖 HTML 自身语义；
- 只给需要交互的区域发送客户端代码；
- 按路由、Feature 或用户动作延迟非关键激活；
- 对激活前可能发生的操作提供禁用、排队或明确反馈；
- 用 `feature_ready`、第一次有效操作等事件测量真实可用时间。

React 要求 Hydration 的客户端首次输出与服务端 HTML 一致。服务端和客户端使用不同数据、时区、随机数、浏览器 API 或不同发布版本，都可能产生不匹配。隐藏警告不能恢复正确性；应让两边共享同一份经过 [[23：运行时 Schema 与错误模型|校验且可序列化的初始状态]]，并为版本错配建立重新获取或安全刷新路径。

“岛屿”、选择性 Hydration 和渐进增强都在缩小客户端激活范围，但会增加服务端/客户端边界、跨岛状态、加载顺序和测试组合。它们也不是零成本默认答案。

## 拆包、预取与 CDN 只优化特定阶段

### 拆包是在等待与调度之间做交换

一个巨大的入口 Bundle 会让首次旅程下载和执行从未用到的功能；按路由或 Feature 拆包，可以把非关键代码移出首屏链：

    首次真正需要的代码
    → 首屏前加载

    低概率或后续动作代码
    → 路由进入或用户意图出现后加载

但 Chunk 不是越碎越好。每个 Chunk 都可能增加请求调度、优先级竞争、模块初始化、版本映射和失败分支；若关键 Chunk 在运行时才被发现，还会形成新的串行瀑布。判断标准是“是否切断了一段非关键工作”，而不是文件数量或某个 Bundle 插件的绿色提示。

字节数也只是代理指标。相同压缩体积的图片和 JavaScript，对主线程的解析执行成本不同；相同总字节在依赖链、缓存命中和设备 CPU 不同时，结果也不同。预算至少同时观察关键资源发现时间、传输量、主线程工作和用户结果。

### 预取是在概率与资源竞争之间做交换

预取可能提前支付下一步成本，用户真正进入时便少等待；若预测错误，它会浪费流量、电量、服务端容量，并与当前关键资源竞争。可用一个朴素判断：

    预取价值
    ≈ 下一步发生概率 × 可节省等待
      - 误取流量、CPU、新鲜度与隐私成本

因此应在用户意图增强时预取高概率路径，并让低速网络、流量节省模式和当前关键请求拥有更高优先级。把所有路由都预加载，只是把“以后可能发生的成本”重新塞回首次关键路径。

### CDN 缩短传输，不执行浏览器工作

CDN 通过在近端复用可缓存的 HTML、JavaScript、CSS、图片等副本，减少网络距离、源站传输和重复计算。它不能：

- 替浏览器解析和执行 JavaScript；
- 自动缩短 Hydration 与主线程 Long Task；
- 让不可共享的个性化 HTML 变成公共内容；
- 自动修复错误 Cache Key、旧版本或失效传播；
- 让缓存未命中的慢接口变快。

所以 CDN 是否有效取决于资源可共享性、Key、命中率、版本和回源路径；这些属于 [[25：缓存与数据一致性|缓存协议]]。把页面放上 CDN 后仍卡顿，通常不是 CDN “没生效”，而是瓶颈根本不在它负责的阶段。

## 性能预算是用户结果的资源契约

“尽量快”无法判断一次改动能否上线，也无法在团队间分配责任。一个可执行预算至少声明：

| 契约项 | 必须回答 |
| --- | --- |
| 用户结果 | 内容出现、Feature 可用还是任务完成？ |
| 场景 | 哪个路由、身份、数据规模、设备、网络、地域与缓存状态？ |
| 分布 | P75、P95、失败率还是最坏可接受范围？ |
| 端到端上限 | 用户从什么动作开始，到什么证据结束？ |
| 阶段护栏 | 服务端、关键资源、脚本、主线程、渲染和第三方各能消耗多少？ |
| 处置 | 谁在超限时阻止回归、降级、回退或重新分配预算？ |

预算从用户结果反推，而不是从一个行业数字正推：

    关键旅程与完成证据
    → 找出所有必要前置依赖
    → 为最长链保留端到端预算
    → 给服务端、网络、主线程与渲染设置护栏
    → 非关键工作延后、取消或按需加载
    → 用实验和真实用户分布校正

阶段预算不能机械相加，因为工作可能并行；它们的作用是定位哪个所有者正在侵占端到端目标。Bundle 大小、请求数和 Long Task 数量也是护栏，不是用户价值本身。

截至 2026-08-24，Core Web Vitals 的官方 “Good” 基线是在 P75 上满足：

| 指标 | 当前基线 | 主要观察 |
| --- | --- | --- |
| LCP | ≤ 2.5 秒 | 主要内容何时呈现 |
| INP | ≤ 200 毫秒 | 一次交互到下一帧反馈的响应 |
| CLS | ≤ 0.1 | 可见内容的意外位移 |

它们覆盖加载、响应和稳定三个通用维度，但不能替代业务预算：

| 信号 | 能帮助判断 | 单独使用的盲区 |
| --- | --- | --- |
| TTFB | HTML 响应开始前的网络与服务端等待 | 后续内容、脚本和交互 |
| FCP / LCP | 首批与主要内容呈现 | 内容是否正确、是否可操作 |
| CLS | 视觉稳定 | 响应速度与任务结果 |
| INP | 页面生命周期内的交互响应 | 接口最终完成和业务成功 |
| Long Task | UI Thread 被长时间独占的风险 | 网络等待和多个短任务累积 |
| `feature_ready` | 某个功能何时真正可用 | 用户是否完成目标 |
| `task_success` / `task_latency` | 关键旅程的结果与总耗时 | 具体慢在哪个技术阶段 |

最小指标集应同时保留“通用体验信号 + 产品完成证据 + 分阶段诊断证据”。只追 Lighthouse 总分，会让团队优化容易得分的代理指标，却可能错过登录后页面、低端设备、长会话交互和真实失败。

## 实验室与真实用户各回答一半问题

实验室测试能固定设备、网络、数据和代码版本，适合重复比较并定位因果；但一次模拟不能代表真实用户分布。真实用户监测（RUM）能看到设备、地域、缓存、长会话和第三方差异，却会受到样本量、版本混合、测量支持和业务流量变化影响。

合理闭环是：

    Field 发现哪个人群、旅程和分位数退化
    → Lab 在可控条件下复现最长依赖链
    → 改变一个机制并比较因果
    → 灰度到 Field 验证真实分布和任务结果

平均值会让大量快速访问掩盖弱网与低端设备。P75 适合通用达标判断，关键高风险旅程还应查看 P95、失败率和特定人群；分位数选择来自业务后果，而不是越高越“专业”。

## 渲染也是失败与一致性问题

渲染链跨越构建产物、缓存、服务端、浏览器和数据版本，会产生特有失败：

| 失败 | 用户表现 | 需要的边界与恢复 |
| --- | --- | --- |
| SSR 在 Shell 前失败 | 没有可用文档或直接 5xx | 返回最小独立 HTML、静态兜底或安全 CSR Shell |
| 流式区域后续失败 | 部分页面可见，某区长期 Fallback | 保留其他能力，由区域 Boundary 重试或降级 |
| HTML 与客户端版本错配 | Hydration 警告、闪烁、错误事件绑定 | 版本关联、停止不可信激活、获取一致资源或刷新 |
| JavaScript Chunk 加载失败 | 页面可见但导航或按钮失效 | Chunk 版本重取、有界刷新、清晰说明受影响能力 |
| 服务端与客户端数据不同 | 先显示 A，激活后跳成 B | 共享初始快照与版本，按新鲜度协议再验证 |
| 个性化 HTML 被公共缓存 | 串用户或泄露私有内容 | 正确 Cache Key、私有响应和身份隔离 |
| 第三方脚本占满主线程 | 核心交互迟钝 | 延迟、隔离、超时和移出关键路径 |

流式响应开始后，某个后续区域失败不一定还能把 HTTP 状态改成错误；客户端“看到了 200”也不证明所有区域成功。因此需要把 Shell、Boundary、Hydration、Feature Ready 与业务结果作为不同事件，并用版本、路由和 Trace 关联到 [[24：失败边界、恢复与可观测性|恢复证据]]。

SSR 还会把浏览器代码带入服务端运行环境。模块初始化时直接读取 `window`、使用只存在于某个 Runtime 的 API，或把未经转义的外部数据序列化进 HTML，都会越过 [[13：可信边界与副作用隔离|环境与信任边界]]。同构降低代码重复，也扩大了需要同时成立的约束集合。

## 做项目时怎么选择

不要给整个应用先贴一个渲染标签。按路由甚至页面区域回答：

1. **关键结果是什么？** 先读内容、立即编辑、完成支付，还是长时间操作？
2. **哪些内容必须在客户端代码前出现？** 搜索抓取、分享预览、弱网可读和用户首屏是否真正依赖它？
3. **数据何时才能确定？** 构建时已知、请求时按用户确定，还是只能在浏览器取得？
4. **能否安全共享副本？** 内容按版本公共复用，还是包含身份、权限和实时事实？
5. **成本落在哪里？** 服务端容量、构建时间、网络距离、用户设备 CPU 和主线程哪个更稀缺？
6. **失败后保留什么？** Shell、只读内容、局部 Feature 或旧副本是否仍有明确价值？
7. **用什么证据退出？** 哪个分位数、任务指标或运行成本证明应保持、回退或升级？

常见结果会是混合，而不是胜者通吃：

- 营销和文档内容用 SSG 与 CDN，搜索或个性化区域客户端增强；
- 商品详情主体静态或服务端生成，价格库存按新鲜度单独读取；
- 登录后应用 Shell 服务端输出，低频复杂功能按路由拆包；
- 慢而独立的推荐区域流式揭示，结算核心路径不等待它；
- 纯展示区域不 Hydrate，需要交互的局部区域才发送客户端代码。

这仍只是 L4 的机制选择；[[30：渲染架构与交付形态|渲染架构]]还要把数据获取、缓存、部署、路由、失败恢复和团队运行责任组合成完整系统。

## 做项目时怎么验证

1. 选一条关键用户旅程，写出内容可见、布局稳定、Feature 可用和任务完成四个时间点。
2. 画出从导航到完成证据的依赖图，标记服务端、网络、浏览器主线程、渲染、第三方和缓存命中。
3. 用 Network Waterfall、Performance Timeline、服务端 Trace 和业务事件找到最长依赖链，不从 Bundle 大小直接猜根因。
4. 为目标人群建立端到端预算与阶段护栏，记录设备、网络、数据量、身份、地域、冷/热缓存和分位数。
5. 分别在 CSR、SSR、SSG 或流式候选中只改变必要机制，比较用户结果、正确性、基础设施成本和开发复杂度。
6. 测试低端设备、弱网、冷缓存、慢数据、超大数据、第三方阻塞、JavaScript 延迟或失败以及快速重复导航。
7. 对 SSR/SSG 验证服务端与客户端输出一致、发布版本兼容、私有数据不被共享缓存；对 Streaming 验证中间层没有缓冲。
8. 用 RUM 查看 P75/P95、失败率和任务成功率；若收益只存在于实验室或代价越过其他预算，则回退或缩小使用范围。

## 可观察的错误信号

| 现象 | 更可能缺少的判断 |
| --- | --- |
| HTML 很快出现，按钮长时间无反应 | 把可见时间当成交互就绪，忽略 Hydration Gap |
| SSR 后 LCP 变快但 TTFB 与服务成本暴涨 | 只优化一个阶段，没有端到端与成本预算 |
| SSG 发布越来越慢且页面仍陈旧 | 路径规模、新鲜度与再生成协议不匹配 |
| 开启 Streaming 后用户仍同时看到全部内容 | Boundary 没解开依赖，或代理正在缓冲 |
| 拆包后请求瀑布更长 | 关键 Chunk 被运行时串行发现，粒度过碎 |
| 预取占满弱网，当前页面反而更慢 | 没有按概率和当前资源竞争分配优先级 |
| CDN 命中很高但低端机仍卡 | 瓶颈在脚本执行、布局或第三方主线程工作 |
| Lighthouse 分数很好，核心任务仍失败 | 代理指标没有连接业务完成证据 |
| 平均值正常但用户持续投诉 | 长尾设备、人群或失败样本被平均值隐藏 |
| Hydration 偶发跳变或错误绑定 | 初始数据、环境或发布版本不一致 |

## 别误解

- **SSR 一定比 CSR 快。** SSR 可能提前内容，也可能因服务端取数、冷启动和 Hydration 增加更长链；必须比较目标结果。
- **SSG 既最快又永远最新。** 它用预计算和可共享性换请求速度，新鲜度取决于重建与失效协议。
- **页面已经有 HTML 就能交互。** 依赖客户端逻辑的控件要到 Hydration 或局部激活完成后才可用。
- **代码拆得越细越快。** 拆包只有把非关键工作移出最长链时才有收益，过碎会产生请求和调度瀑布。
- **Bundle 更小就等于体验更好。** 字节只是一种成本；执行、布局、数据等待和第三方阻塞也可能主导结果。
- **CDN 能解决前端性能。** 它主要优化可缓存内容的传输与回源，不能代替客户端计算和正确的缓存协议。
- **Core Web Vitals 达标就代表产品快。** 它们是通用体验基线，不知道登录、保存或支付何时真正完成。
- **一种渲染模式应统一全站。** 路由和区域的数据时机、共享范围、用户目标与失败代价不同，合理结果通常是组合。

## 复习

1. 为什么“页面加载完成”不足以描述用户真正等待的结果？
2. 为什么渲染模式改变的是工作位置与依赖关系，而不是让必要工作凭空消失？
3. SPA / MPA 与 CSR / SSR / SSG 分别属于哪两个维度？
4. SSR 为什么可能让内容更早出现，却仍留下不可交互间隙？
5. Streaming 解开了哪种等待，又新增了哪些状态与失败边界？
6. 为什么拆包、预取和 CDN 都只能优化特定阶段？
7. 性能预算为什么必须同时写清用户结果、环境、分位数和超限处置？
8. Core Web Vitals、Feature Ready 与 Task Success 分别能证明什么？
