# 第一性原理：前端架构为何存在

> [!abstract] 先用一句话说清楚
> 前端架构存在，不是因为项目需要一种漂亮目录，而是因为有限的人必须持续修改一个包含大量状态、外部不确定性和资源约束的系统。架构通过控制变化、状态、依赖和失败的传播范围，降低长期理解与修改成本。

## L0：先确定研究对象

前端首先是一个与外部世界交互的状态系统：

    用户事件 + 服务端数据 + 浏览器环境 + 时间
    → 根据规则改变内部状态
    → 产生界面、请求、存储、导航等输出与副作用

组件、Hooks、框架和构建工具都是这个系统的实现手段。架构研究的不是某个手段是否流行，而是输入、状态、规则、副作用之间怎样建立边界。

## L1：不可约的系统约束

这些约束不能靠更换框架消失：

| 底层约束    | 为什么不可约                    | 可观察表现                |
| ------- | ------------------------- | -------------------- |
| 人的认知有限  | 人无法同时稳定推理大量隐式关系           | 改一个需求前必须阅读许多不相关代码    |
| 状态组合会增长 | 多个独立状态会形成更多可能组合，异步还会产生乱序  | 界面出现互相矛盾的状态，旧请求覆盖新结果 |
| 外部世界不可靠 | 网络、服务、缓存、URL 和第三方数据不受前端控制 | 超时、重复提交、脏数据和局部失败     |
| 变化不可避免  | 业务、设计、接口、团队和技术会以不同速度变化    | 局部变化迫使无关模块一起修改       |
| 资源与协作有限 | 网络、CPU、主线程、开发时间和沟通能力都有上限  | 首屏变慢、构建变慢、多人修改互相阻塞   |

因此，复杂度无法全部消灭。架构只能消除人为制造的复杂度，并把必要复杂度限制在能够独立理解和处理的范围内。

## L2：约束先推导质量目标

质量目标描述“系统希望保持什么性质”，还不是实现方案：

| 从什么约束出发 | 推导出的质量目标 | 判断问题 |
| --- | --- | --- |
| 认知有限 + 持续变化 | **局部性** | 一个需求能否主要在一个边界内完成？ |
| 状态增长 + 异步乱序 | **可预测性** | 能否指出当前状态的权威来源与合法转换？ |
| 外部不可靠 | **可靠性与可诊断性** | 局部失败能否被隔离、解释和恢复？ |
| 运行资源有限 | **效率** | 是否把资源花在用户真正等待的路径上？ |
| 未来变化不可预测 | **可演进性与可逆性** | 判断错误后能否局部替换，而不是整体重写？ |
| 多人协作有限 | **自治与一致性** | 团队能否独立交付，同时遵守必要契约？ |

性能、可维护性、可靠性之间可能冲突，不能同时无限最大化。架构决策本质上是在当前约束下选择优先级。

## L3：质量目标再推导设计原则

原则说明“应该怎样组织系统”，但不绑定某个库：

1. **为了局部性：** 按变化原因分离关注点，让共同变化的代码高内聚；隐藏实现，只暴露稳定接口；让稳定规则不依赖易变细节。
2. **为了可预测性：** 明确状态所有者和唯一权威来源；能派生的值不重复保存；让事件和状态转换单向、显式。
3. **为了可靠性：** 把外部输入视为不可信；在边界建立契约和运行时校验；隔离副作用和失败域；留下可诊断证据。
4. **为了效率：** 先定义用户目标和资源预算，再测量瓶颈；根据数据生命周期决定计算、传输、存储和缓存位置。
5. **为了可演进性：** 优先采用能够解决当前问题的最小机制；隔离易变技术；为高风险决策保留回退与替换路径。
6. **为了团队自治：** 让代码所有权、发布边界和系统契约对应真实组织责任；把重要约束自动化，而不是只靠口头约定。

这些原则回答“为什么这样设计”。如果直接从问题跳到工具，就无法判断工具是否真的解决了对应约束。

## L4：原则落地为可复用机制

机制是原则在特定场景中的实现，不具有普遍优先级：

| 设计原则 | 可选机制 | 需要付出的新成本 |
| --- | --- | --- |
| 按变化原因建立边界 | Feature-based 模块、公共 API、分层 | 边界设计和层间转换 |
| 明确状态所有权 | Reducer、状态机、服务端查询缓存 | 状态建模和同步规则 |
| 隔离易变细节 | Adapter、Repository、依赖注入 | 接口和适配代码 |
| 守住系统边界 | Runtime Schema、错误分类、幂等键 | 校验、版本和恢复逻辑 |
| 在预算内改善体验 | 缓存、拆包、SSR、CDN、懒加载 | 一致性、构建和运行复杂度 |

状态机、Adapter、缓存和 SSR 都不是第一性原理。只有先指出它们服务哪个质量目标，才能判断是否值得采用。

## L5：多个机制组合成系统形态

系统形态同时回应多种约束，不能由单一原则直接推出：

| 系统形态 | 组合的主要机制 | 成立前提 |
| --- | --- | --- |
| BFF | 契约、聚合、Adapter、鉴权、超时与缓存 | 客户端场景确实需要独立的数据编排边界 |
| Monorepo | 包边界、公共 API、依赖规则和统一构建 | 多应用或共享包存在高频协作需求 |
| 微前端 | 运行时隔离、发布边界、跨应用契约和故障隔离 | 多团队独立交付收益超过集成成本 |
| CSR / SSR / SSG 组合 | 渲染策略、缓存、数据获取和部署机制 | 首屏、SEO、交互与运行成本目标已明确 |

系统形态不是原则的同义词，而是多个原则和机制在一组具体约束下的组合结果。

## L6：最后才选择工具

React、Vue、Zustand、Redux、XState、Zod、TanStack Query、Next.js 等工具只是机制的具体载体。选择顺序应该是：

    观察到的问题
    → 找到不可满足的质量目标
    → 选择相应设计原则
    → 选择最小可行机制
    → 再比较工具

同一个原则可以由不同工具实现；同一个工具也可能被错误使用。工具选型不能替代状态归属、依赖方向和失败语义的设计。

## L7：用反馈闭环检验架构

架构不是一次性画图，而是一组需要证据支持、可以被修正的假设：

    记录可观察问题
    → 定位约束与传播路径
    → 选择质量目标和最小机制
    → 写清新增成本与退出条件
    → 用测试、性能数据、故障记录或交付周期验证
    → 保留、调整或撤销

如果无法说明一个机制修复了什么现象、如何验证以及何时撤销，它更可能是技术偏好，而不是架构决策。

## 别误解

- **先分层等于先写 UI 层、Service 层、Repository 层。** 本页的“分层”先区分抽象层次；代码是否需要技术分层，仍要由变化原因决定。
- **概念被分层后彼此就没有关系。** 分层是明确因果与依赖方向，不是切断关系；下层约束解释上层方案为什么存在。
- **最底层原则永远直接对应一个工具。** 原则通常经过多个机制才能落地，跳层选工具会隐藏取舍。

## 复习

1. 为什么“外部不确定性”“可诊断性”“契约优先”和“Zod”不能放在同一抽象层？
2. 如果一次需求变化会影响许多无关模块，底层违反了哪个质量目标？
3. 看到“项目应该使用微前端”时，怎样沿着层级反向检查它是否成立？

## 来源与下一步

- **来源事实：** 现有课程提供了 BFF、Serverless、缓存、Monorepo、类型安全 API、幂等、分层、依赖注入和状态管理等场景。
- **本页推论：** 将这些场景按“研究对象 → 不可约约束 → 质量目标 → 设计原则 → 可复用机制 → 复合系统形态 → 工具 → 验证”重组；这是本页建立的学习模型，不是课程原文结构。
- **工程建议：** 遇到任何架构名词时，先沿层级向下追问它回应了什么约束，再向上检查其成本和验证方式。
- **下一步：** 从 L3 的第一个原则开始，学习“按变化原因建立边界”，而不是先背具体目录结构。
