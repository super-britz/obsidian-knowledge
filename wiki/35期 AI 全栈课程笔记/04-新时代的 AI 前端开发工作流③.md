# 04 新时代的 AI 前端开发工作流③

> [!abstract] 核心问题
> 怎样把 AI 的执行能力组织成可远程触发、可分工、可验证的开发系统？

## 本节结论

- 远程开发的核心不是“远程桌面”，而是让代码、依赖、身份和执行入口处于可控环境。
- 浏览器控制要区分无登录的公开页面与携带登录态的业务页面，后者风险更高。
- App 和 IDE 控制缺少稳定结构时，需要更细的步骤、状态检查和失败恢复。
- 多 Agent 的价值来自职责分离，而不是角色数量：规划、实现、测试和审查应有不同输出。
- 提示词应逐步变成任务规范，明确目标、上下文、步骤、约束、验收和停止条件。

## 知识框架

### 1. 远程执行环境的四个组成

```text
可访问的计算环境
  + 可复现的项目依赖
  + 受控的账号与密钥
  + 可触发、可观察的任务入口
```

环境可以是本地独立账号、虚拟机、云主机或容器。选择标准是能否隔离风险、复现问题和保留日志。

### 2. 浏览器控制分成两类

| 类型 | 特点 | 适合场景 | 主要风险 |
| --- | --- | --- | --- |
| 无状态浏览器 | 没有个人登录信息 | 公开网页、爬取、基础测试 | 页面变化、反自动化 |
| 有状态浏览器 | 带 Cookie、会话和账号 | 后台操作、真实业务流程 | 数据泄露、越权、误提交 |

真实业务操作必须设置明确的人工确认点，尤其是发布、删除、支付和权限变更。

### 3. 控制 App 比调用 API 更脆弱

屏幕控制依赖当前窗口、布局、焦点和渲染状态。要提高稳定性，需要：

- 一次只执行一个可观察动作。
- 每步之后检查界面是否进入预期状态。
- 对弹窗、加载和失败设置分支。
- 对不可逆操作要求人工确认。
- 保存截图、日志或其他执行证据。

### 4. 专用 Agent 应围绕产出分工

```text
Planner: 拆解任务和定义验收
Implementer: 修改代码或执行操作
Tester: 运行测试并记录结果
Reviewer: 检查风险、偏差和遗漏
```

这些角色可以由不同模型、不同会话或同一个系统的不同阶段承担。关键是输出契约清晰，避免互相默认“对方已经处理”。

### 5. 任务规范是自动化的控制面

一份可执行任务至少要包含：

- 目标与非目标。
- 可读取的上下文。
- 允许使用的工具和权限。
- 必须遵守的约束。
- 验收标准和验证命令。
- 失败、超时与停止条件。

## 实践任务

**建议产出：**

- 在隔离环境中实现一条“远程触发 -> 修改小功能 -> 浏览器验证 -> 输出报告”的流水线。

**完成标准：**

- [ ] 任务规范包含目标、权限和验收标准。
- [ ] 规划、实现和验证有独立输出。
- [ ] 关键操作保留日志或截图。
- [ ] 不使用个人主浏览器和高价值账号。
