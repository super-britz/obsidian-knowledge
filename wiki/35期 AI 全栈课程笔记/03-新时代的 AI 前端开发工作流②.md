# 03 新时代的 AI 前端开发工作流②

> [!abstract] 核心问题
> 怎样把设计、代码、测试和 AI 执行环境连接成可持续迭代的系统？

## 本节结论

- 设计稿、代码和运行页面必须形成反馈回路，而不是单向生成。
- PRD 不只用于开发前沟通，也可以补齐测试路径和验收报告。
- AI 可以整理录音和资料，但最终笔记必须由人校正、压缩并连接到已有知识。
- 电脑控制类 Agent 扩大了 AI 的执行范围，也同步扩大了账号、隐私和误操作风险。
- 自动化环境要使用最小权限和独立身份，不应直接承载高价值账号。

## 知识框架

### 1. 设计与代码的一致性需要反复验证

```text
设计稿
  -> 生成代码
  -> 浏览器渲染
  -> 截图或结构比对
  -> 定位差异
  -> 修改代码或设计
```

重点不是追求像素数字本身，而是建立稳定的差异发现机制。常见差异包括组件层级、字体、间距、状态、内容长度和响应式行为。

### 2. PRD 可以驱动验收

PRD 中的用户故事可以转成测试：

```text
用户目标
  -> 前置条件
  -> 操作步骤
  -> 预期结果
  -> 异常分支
```

测试报告反过来又能暴露 PRD 中缺失的状态和边界，因此需求与测试是双向校正关系。

### 3. AI 学习的价值在于“编译知识”

把录音交给 AI 生成摘要只是第一步。可长期复用的笔记还需要：

- 删除片头、闲聊和重复表达。
- 校正术语和明显转写错误。
- 把内容改写成因果、流程、对比或模型。
- 连接到已有页面，而不是重复建孤岛。
- 留下可以实践和自测的产出。

这正是 [[wiki/LLM Wiki 模式|LLM Wiki 模式]] 与普通会议纪要的区别。

### 4. 电脑控制让 Agent 从“回答”进入“执行”

电脑或浏览器控制通常通过截图、可访问性树、浏览器协议或系统自动化来执行动作。它适合重复操作和跨应用流程，但稳定性通常低于结构化 API。

风险来自三类能力叠加：

- 看见屏幕和本地数据。
- 使用已经登录的身份。
- 点击、输入、下载、删除或发送。

因此执行环境必须与个人主环境隔离。

## 实践任务

**建议产出：**

- 为 02 的小项目增加设计差异检查、需求驱动测试和一份人工校正后的学习笔记。

**完成标准：**

- [ ] 能展示一次设计稿与运行页面的差异修正。
- [ ] 至少把一个用户故事转成自动化或手工验收步骤。
- [ ] 自动化工具使用独立浏览器 Profile 或测试账号。
- [ ] 笔记中不保留无意义的转写错误和课堂噪音。

## 复习检查

- [ ] 为什么 PRD 与测试应该互相校正？
- [ ] AI 生成的会议摘要为什么还不是知识页？
- [ ] 电脑控制与 API 工具调用的稳定性和风险有何不同？
