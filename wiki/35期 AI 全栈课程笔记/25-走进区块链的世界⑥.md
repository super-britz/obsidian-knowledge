# 25 走进区块链的世界⑥

> [!abstract] 核心问题
> ERC20 的授权机制如何支撑商品购买，又会引入哪些安全风险？

## 本节结论

- ERC20 的直接转账与授权转账解决不同问题：前者由持有人主动付款，后者允许指定合约在额度内代扣。
- `approve` 只设置授权额度，真正移动代币通常由 `transferFrom` 完成。
- 商品购买 DApp 应把商品状态、支付代币、授权额度、购买交易和购买记录组织为完整流程。
- ERC20 表示可互换的数量，ERC721 表示不可互换的 Token ID，业务建模方式不同。
- 复用 OpenZeppelin 可以减少标准接口的重复实现，但不能代替业务权限、安全检查和测试。

## 知识框架

### 1. ERC20 的两条转账路径

```text
直接转账：
持有人 -> transfer -> 收款人

授权转账：
持有人 -> approve(spender, amount)
spender -> transferFrom(owner, recipient, amount)
```

第二条路径适合商城、订阅和托管等“合约代表用户扣款”的场景。

### 2. allowance 是剩余授权额度

`allowance(owner, spender)` 表示 `spender` 还能从 `owner` 账户使用多少代币。购买前端可以先读取额度：

```text
allowance < 商品价格 -> 请求 approve
allowance >= 商品价格 -> 请求 buy
```

前端显示只能帮助用户理解状态，最终约束仍必须由合约执行。

### 3. 授权不是付款完成

用户完成 `approve` 后，资产通常还在原账户中。DApp 必须明确区分：

- 授权交易是否成功。
- 授权对象是否为正确合约。
- 授权额度是否足够。
- 购买交易是否成功。
- 购买记录是否已经更新。

把授权成功显示成购买成功，会造成严重的状态误导。

### 4. ERC20 与 ERC721 的建模差异

| 标准 | 核心单位 | 常见问题 |
| --- | --- | --- |
| ERC20 | 可互换的数量 | 余额、转账、授权和供应量 |
| ERC721 | 唯一 Token ID | 所有权、授权、元数据和转移 |

商品支付通常使用 ERC20；唯一商品凭证或收藏品可以使用 ERC721，但是否上链取决于业务需求。

### 5. 商品购买 DApp 的最小闭环

```text
管理员创建商品
  -> 用户读取商品与价格
  -> 连接钱包并确认网络
  -> 检查余额与 allowance
  -> approve（需要时）
  -> buy
  -> 查询交易结果与购买记录
```

每一步都应处理拒签、余额不足、额度不足、网络错误和交易失败。

## 实践任务

**建议产出：**

- 设计并实现一个使用 ERC20 支付的商品购买 DApp。

**完成标准：**

- [ ] 管理员可以创建商品并设置价格。
- [ ] 前端能区分余额、授权额度和购买状态。
- [ ] 合约在购买时校验商品、价格、调用者和授权额度。
- [ ] 测试覆盖拒签、余额不足、额度不足与购买成功。
- [ ] 不使用真实资产或无限授权完成练习。
