# 33 跨境金融系统架构

> [!abstract] 核心问题
> 如何拆解一个同时连接身份合规、链上钱包与外部支付通道的金融系统？

## 本节结论

- 跨境金融系统应拆分身份、企业、交易监测、账本、钱包、外部支付和运营审核等边界。
- KYC、KYB、KYT 与 AML 解决不同的合规问题，不能用一次身份认证替代持续交易监测。
- 链上交易、外部支付与 Webhook 都具有异步性，业务状态需要幂等、重试、对账和人工兜底。
- 用户余额不能仅通过扫描钱包临时计算，应有可审计的业务账本并与外部系统对账。
- 资金、身份和跨境业务必须先满足法律、牌照、隐私和安全要求，技术方案不能绕开这些约束。

## 知识框架

### 1. 系统按责任分层

```text
用户端 / 企业端
  -> 身份与企业认证
  -> 业务订单与内部账本
  -> 钱包与链上交易
  -> 外部支付或结算服务
  -> Webhook / 队列 / 对账
  -> 运营、风控与审计后台
```

每一层都要明确数据所有者、权限和失败处理。

### 2. 合规能力不能混为一谈

| 能力 | 关注对象 |
| --- | --- |
| KYC | 个人身份与风险 |
| KYB | 企业主体与受益所有人 |
| KYT | 交易与资金路径风险 |
| AML | 反洗钱制度、规则、调查与报告 |

认证通过也不代表后续所有交易自动可信。

### 3. 钱包架构要隔离职责

可从概念上区分用户地址、业务归集地址和平台资金地址。关键问题包括：

- 私钥由谁控制，能否单人操作。
- 归集和转出需要哪些审批。
- 如何设置限额、白名单和异常暂停。
- 链上记录如何映射到内部用户与订单。
- 热钱包故障或外部服务异常如何恢复。

这些设计应交由合规与安全团队共同审查。

### 4. 账本是业务事实来源

内部账本应记录每笔余额变化的原因、关联订单、外部交易标识和状态。链上余额或支付服务余额是对账来源，不能替代业务账本。

```text
业务事件
  -> 账本分录
  -> 发起外部操作
  -> 接收回调或查询结果
  -> 更新状态
  -> 定期对账
```

### 5. 异步流程必须设计失败状态

队列和 Webhook 处理需要：

- 幂等键与重复消息处理。
- 超时、退避重试和死信队列。
- 回调签名与来源验证。
- 长时间未完成状态的巡检。
- 自动对账与人工处理入口。

Serverless 函数适合短时处理，长流程应由状态机、队列或任务系统编排。

## 实践任务

**建议产出：**

- 绘制不包含真实资金操作的跨境金融系统架构与状态机。

**完成标准：**

- [ ] 标出身份、账本、钱包、外部支付和运营边界。
- [ ] 每个外部调用都有幂等、重试和对账方案。
- [ ] 敏感身份数据与私钥具有独立权限模型。
- [ ] 文档明确法律、牌照和合规前置条件。
