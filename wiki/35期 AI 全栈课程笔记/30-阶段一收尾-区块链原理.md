# 30 阶段一收尾：区块链原理

> [!abstract] 核心问题
> 区块、哈希、Nonce 与 PoW 如何让分布式账本形成可验证的历史？

## 本节结论

- 区块链可以理解为由多节点共同维护、按顺序追加的可验证账本。
- 区块通过前一区块哈希形成关联，修改历史会使后续引用失效。
- PoW 通过反复计算寻找满足难度目标的哈希，使出块需要付出计算成本。
- 矿工或节点不仅打包交易，还要验证交易与区块是否符合协议规则。
- 钱包地址具有公开可追踪性，不等于现实身份天然匿名，业务使用仍需考虑隐私。

## 知识框架

### 1. 从交易到区块

```text
用户创建并签名交易
  -> 广播到网络
  -> 节点验证
  -> 候选交易进入区块
  -> 竞争产生有效区块
  -> 其他节点验证并接到已有链上
```

节点接受区块的前提是它符合协议规则，而不是仅相信某个打包者。

### 2. 区块通过哈希连接历史

简化区块可以包含：

```text
前一区块哈希
时间或高度
交易列表
Nonce
当前区块哈希
```

前一区块内容变化会导致其哈希变化，后续区块保存的引用随之不再匹配。

### 3. 哈希提供可验证摘要

哈希函数将任意长度输入映射为固定长度结果。输入发生变化时，输出通常会显著变化，因此可用于检查数据是否被修改。

哈希本身不负责保存交易、确认身份或保证业务正确，它只是共识和数据结构中的基础工具。

### 4. Nonce 与难度目标

PoW 挖矿可简化理解为：

```text
固定区块内容
  + 不断改变 Nonce
  -> 计算哈希
  -> 判断是否满足难度目标
```

找到结果困难，验证结果相对容易。难度机制用于调节产生有效区块所需的总体工作量。

### 5. 篡改历史需要重做后续工作

修改旧区块会改变它的哈希，也会破坏后续区块的引用。攻击者不仅要重新计算被修改区块，还要追赶并超过网络后续产生的有效链。由此产生的是成本与概率上的安全性，不是数学意义上的绝对不可修改。

### 6. 公开账本不代表完全匿名

链上地址未必直接显示姓名，但交易关系、时间、金额与业务数据可能帮助推断身份。系统设计不能把“地址没有实名字段”当作隐私保障。

## 实践任务

**建议产出：**

- 使用 Node.js 或 Go 实现一个教学用简化区块链。

**完成标准：**

- [ ] 区块包含交易、前一区块哈希、Nonce 和当前哈希。
- [ ] 可以验证整条链的引用与哈希。
- [ ] 修改历史区块后，链校验能够失败。
- [ ] PoW 难度可配置并能观察计算次数变化。
- [ ] 明确 Demo 不等同于生产级区块链协议。

- [ ] 为什么公开地址不等于完全匿名？
