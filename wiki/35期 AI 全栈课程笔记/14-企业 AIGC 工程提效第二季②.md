# 14 企业 AIGC 工程提效第二季②

> [!abstract] 核心问题
> 如何用规格驱动开发约束 Coding Agent，让需求、实现和验证可以追踪？

## 本节结论

- 规格驱动开发把需求和设计写入版本化文件，避免关键约束只存在于聊天历史。
- Requirements 描述目标和验收，Design 描述实现边界，Tasks 描述可执行步骤，三者不能互相替代。
- 任务应小到可以由单个执行者完成并独立验证。
- Subagent 可以隔离任务上下文，但主流程仍需负责依赖顺序、汇总与最终验收。
- 测试形式可以不同，核心要求是每个任务都有可重复的完成证据。

## 知识框架

### 1. 规格驱动而不是聊天驱动

```text
需求讨论
  -> requirements.md
  -> design.md
  -> tasks.md
  -> 实现与测试
  -> 规格和实现共同更新
```

聊天用于探索，规格文件用于形成承诺和恢复上下文。

### 2. 三类文档各自回答一个问题

| 文档 | 核心问题 | 典型内容 |
| --- | --- | --- |
| Requirements | 要解决什么、怎样算完成 | 用户场景、约束、验收条件 |
| Design | 准备怎样实现、边界在哪里 | 架构、数据、接口、风险与取舍 |
| Tasks | 具体按什么顺序执行 | 步骤、依赖、产物、验证方式 |

一个 Task 最好只对应一项清晰变更，并标注完成条件。

### 3. 变更要沿链路回写

需求变化时，应先更新 Requirements，再评估 Design 和未完成 Tasks。实现中发现的新限制也要写回 Design，避免文档成为过期快照。

### 4. Subagent 隔离执行上下文

父流程提供单个 Task 所需的最小上下文，执行者提交代码、说明和验证证据。父流程检查结果后再继续下一项，避免多个执行者同时修改同一边界。

### 5. 验证是任务定义的一部分

不同任务可使用：

- 单元测试验证纯逻辑。
- 集成测试验证模块协作。
- E2E 验证真实用户流程。
- 浏览器检查验证视觉和交互。
- 静态检查验证类型、格式和依赖。

“代码已经生成”不是完成标准。

## 实践任务

**建议产出：**

- 用 Requirements、Design 和 Tasks 驱动一个小功能开发。

**完成标准：**

- [ ] Requirements 包含可判断的验收条件。
- [ ] Design 说明模块、数据和主要风险。
- [ ] 每个 Task 有输入、产物和验证方式。
- [ ] 需求变化能从提交历史追溯到代码与测试。

## 复习检查

- [ ] Requirements、Design 和 Tasks 分别承担什么责任？
- [ ] 什么样的任务适合交给独立 Subagent？
- [ ] 为什么测试必须在任务拆分时就定义？
