# 16 企业 AIGC 工程提效第二季（终）

> [!abstract] 核心问题
> 如何把规格、Skills、评审和测试收束成一条最小可运行的 AI 研发流水线？

## 本节结论

- “数字劳动力”首先是一条有状态的工作流，而不是一个拥有全部权限的万能 Agent。
- 最小方案可以由一个人工入口、若干核心 Skills、状态文件和通知机制组成。
- 实现、Review、修复和测试要形成闭环，失败不能直接跳到下一阶段。
- 文档同步负责把实现变化和踩坑写回长期上下文，使任务可以跨会话恢复。
- 多 Agent 与 Worktree 应在单线流程稳定后再引入，避免过早增加协调复杂度。

## 知识框架

### 1. 最小流水线

```text
人工触发
  -> 读取需求
  -> 生成 / 更新 Requirements
  -> 生成 / 更新 Design
  -> 拆分 Tasks
  -> 实现
  -> Review
  -> 修复
  -> 测试报告
  -> 文档同步
  -> 人工批准
```

触发入口可以是命令或消息，但工作流状态必须保存在可检查的位置。

### 2. 核心能力按 Skill 拆分

可以先从四类能力开始：

- 规格与任务规划。
- 代码实现。
- Code Review。
- 测试执行与文档同步。

实际数量不重要，重要的是每个 Skill 有单一责任，并能独立产生可验证结果。

### 3. Review 与修复组成反馈回路

Review 输出应包含位置、问题、风险和建议验证方式。实现者根据意见修复，再重新执行相关检查，直到满足退出条件或转交人工判断。

### 4. 测试报告是工作流证据

报告应说明执行了哪些测试、环境是什么、哪些通过或失败、失败证据在哪里、哪些范围尚未覆盖。Jest、Playwright 或其他工具只是产生证据的手段。

### 5. Human-in-the-loop 是架构组件

需要人工确认的典型节点：

- Requirements 与业务目标是否一致。
- 安全、支付和权限设计是否可接受。
- Review 中的重大取舍。
- 合并、发布和生产资源变更。

### 6. 并行化要晚于可观测性

只有当单线流程的状态、日志、失败恢复和验收都稳定后，多 Worktree 并行才会提高吞吐，否则只会制造更多不可见冲突。

## 实践任务

**建议产出：**

- 实现一条可重复运行的最小 AI 研发命令。

**完成标准：**

- [ ] 可以从一个需求生成规格与 Tasks。
- [ ] Review 问题会回到实现阶段修复。
- [ ] 测试报告与文档同步有固定输出位置。
- [ ] 合并或部署前必须由人批准。

## 复习检查

- [ ] 为什么单一超级 Agent 不是好的起点？
- [ ] 测试报告和文档同步分别解决什么问题？
