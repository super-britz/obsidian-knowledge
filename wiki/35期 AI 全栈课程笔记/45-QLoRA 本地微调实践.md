# 45 QLoRA 本地微调实践

> [!abstract] 核心问题
> 如何在本地建立一条可复现的 QLoRA 微调链路，并确认训练产物真的可加载、可比较、可服务化？

## 本节结论

- 训练前先记录硬件、驱动、Python、PyTorch、CUDA 和磁盘基线，环境不可复现就无法判断失败原因。
- QLoRA 以低比特方式加载冻结的基座模型，只训练 LoRA Adapter；Adapter 不是一份可独立运行的完整模型。
- 正式训练前应先用小模型、少量数据和极少步数做冒烟测试，验证下载、量化、训练、保存与加载链路。
- 微调数据应训练稳定行为和边界，文档知识交给 RAG，订单等实时事实交给 Tool。
- 多卡 DDP 主要通过数据并行提升吞吐；是否使用多卡应由模型、显存、数据量和训练时间共同决定。

## 知识框架

### 1. 先建立环境基线

需要记录：

- GPU、显存、驱动和 CUDA 可用状态。
- CPU、内存、磁盘空间和模型缓存目录。
- Python 环境与包管理方式。
- PyTorch 是否能识别 GPU。
- 训练框架、依赖和模型版本。
- 数据、配置、随机种子和输出目录。

独立环境可以降低依赖冲突，但环境名称和版本本身不是目标，关键是能够通过脚本或锁定文件重建。

### 2. 训练工具栈的分层

```text
GPU 驱动 / CUDA
  -> PyTorch
  -> Transformers / PEFT / bitsandbytes
  -> LLaMA Factory
  -> 训练配置与数据
```

PyTorch 负责张量计算、自动求导和训练；Transformers 负责模型与 Tokenizer；PEFT 提供 LoRA 等参数高效微调；bitsandbytes 常用于低比特加载；LLaMA Factory 负责把训练流程配置化。

### 3. QLoRA 的训练对象

```text
低比特加载的冻结基座模型
  + 可训练 LoRA Adapter
  -> 任务行为发生变化
```

NF4 是面向神经网络权重分布设计的 4-bit 表示。低比特加载降低基座权重占用，但激活、梯度、上下文长度和批大小仍会消耗资源。

训练完成后通常保存的是 Adapter 配置与权重。推理时必须使用兼容的基座模型和 Tokenizer 加载它，或经过验证后执行合并导出。

### 4. 冒烟训练验证完整链路

冒烟测试不追求业务效果，只回答：

- 模型能否下载并加载。
- 量化配置是否生效。
- 数据格式能否解析。
- 前向、反向和保存是否成功。
- Adapter 能否重新加载并生成结果。

只有这条链路稳定后，才值得增加模型规模、数据量、训练轮次或多卡复杂度。

### 5. 客服数据应覆盖行为边界

数据至少覆盖：

- 统一语气和输出格式。
- 缺少必要信息时的追问。
- 不确定时拒绝猜测。
- 实时问题触发 Tool。
- 文档问题交给 RAG。
- 高风险、越权和非业务问题的拒答或转人工。

课堂中的合成数据适合验证链路，不足以证明生产效果。正式训练需要经过脱敏、去重、质量检查和独立测试集评估。

### 6. DDP 与模型分片不是一回事

DDP 中每个训练进程通常持有一份模型副本，处理不同批次的数据，并同步梯度：

```text
各进程计算本地梯度
  -> 通信后端聚合梯度
  -> 各进程执行一致更新
  -> 主进程保存 Adapter
```

如果单卡无法容纳模型，问题可能需要模型分片、参数分片或其他分布式方案，而不只是增加 DDP 进程。

### 7. 从训练产物到模型服务

服务启动时应明确加载：

- 基座模型与 Tokenizer。
- 量化配置。
- LoRA Adapter。
- 系统提示词和生成参数。

服务至少提供健康检查、请求校验、超时、日志和版本信息。模型 HTTP 接口只负责推理，不应同时承担订单查询、权限判断和完整 Agent 编排。

## 实践任务

**建议产出：**

- 完成一次可复现的 QLoRA 冒烟训练，并将 Adapter 包装成只提供推理的本地 HTTP 服务。

**完成标准：**

- [ ] 保存环境、模型、数据和训练配置。
- [ ] 冒烟训练后能重新加载 Adapter 并生成结果。
- [ ] 使用固定测试集对比基座模型与微调模型。
- [ ] 服务返回所用基座模型和 Adapter 版本。
- [ ] 合成数据与真实业务数据明确隔离。

## 复习检查

- [ ] QLoRA 中哪些参数被冻结，哪些参数被训练？
- [ ] 为什么 Adapter 文件不能脱离基座模型独立运行？
- [ ] DDP 与模型分片分别解决什么问题？
