# 43 Agent 与 Skills 编排

> [!abstract] 核心问题
> 如何把模型、工具、记忆、Skills 与 MCP 组合成一个能在真实工程中运行且权限可控的 Agent？

## 本节结论

- Agent 的价值不在于“接了一个模型”，而在于能围绕目标选择工具、维护状态、执行步骤并验证结果。
- Tool 负责访问外部数据和执行动作，模型负责理解、判断与组织输出，二者不能混为一谈。
- Skill 是可复用的能力单元，Workflow 负责顺序、分支、并行、循环和人工审批等控制逻辑。
- AIOps Agent 可以连接错误、日志、指标、代码和历史知识，但根因结论必须保留证据，写操作必须经过授权与审批。
- 项目和简历只能描述自己真正实现、验证并能解释的能力，框架名称和架构图不能代替工程证据。

## 知识框架

### 1. Agent 是一个受约束的任务系统

一个工程化 Agent 至少包含：

```text
目标与指令
  + 模型
  + Tools
  + Memory / State
  + Skills
  + Workflow
  + 权限与验证
```

模型本身不会直接读取订单、日志或代码仓库。系统需要通过 Tool、API 或 MCP Server 暴露受控能力，再把结果交给模型处理。

### 2. Tool、Skill 与 Workflow 分属不同层次

| 层次 | 主要职责 | 示例 |
| --- | --- | --- |
| Tool | 完成一次原子查询或动作 | 读取错误事件、查询日志、获取文件 |
| Skill | 封装可复用的问题解决方法 | 定位前端异常、检查发布风险 |
| Workflow | 控制多个步骤如何执行 | 顺序、并行、分支、循环、审批 |
| Agent | 根据目标和状态选择并协调能力 | 分析告警并生成处理建议 |

Skill 可以调用多个 Tool，也可以被 Workflow 或 Agent 调度。不要用一个宽泛的“工作流”概念掩盖每层的输入、输出与责任。

### 3. Memory 需要按用途分层

- 短期记忆：当前会话中的目标、消息和中间结果。
- 摘要记忆：对长对话或执行历史进行压缩，控制上下文长度。
- 长期记忆：经过筛选的项目约束、历史决策、常见问题和用户偏好。

长期记忆不能无选择地保存全部对话。写入前应判断内容是否稳定、是否敏感、是否有来源，以及何时失效。

### 4. MCP 是连接层，不是安全层

Agent 既可以消费外部 MCP Server 提供的工具，也可以把自己的能力以 MCP Server 形式提供给其他客户端。

接入代码仓库、云平台和监控系统时，应明确：

- 使用只读还是写权限。
- Token 能访问哪些仓库、环境和资源。
- 哪些参数需要校验或脱敏。
- 哪些动作必须由人确认。
- 调用、返回和变更是否可审计。

“能够连接”不等于“应该获得全部权限”。

### 5. AIOps Agent 的证据链

```text
错误事件 / 告警
  -> 关联日志与指标
  -> 定位服务、版本和时间窗口
  -> 读取相关代码与变更
  -> 检索历史事故和业务规则
  -> 生成根因假设与证据
  -> 人工确认或受控处置
```

数据源可以包括错误监控、云日志、性能指标、代码仓库、安全扫描和历史问题库。不同公司的平台可以替换，关键是统一事件标识、时间范围、发布版本和源码位置。

Agent 的输出应区分事实、推断和建议。自动修复、提交代码、发布或修改云资源属于高风险写操作，不应由诊断 Agent 默认执行。

### 6. AI Code Review 需要业务上下文

只读取单个变更文件的 Review 容易产生脱离实际的建议。更可靠的输入包括：

- 仓库规范与模块边界。
- 需求、设计与验收条件。
- 相关代码和测试。
- 历史缺陷与事故。
- 数据、安全和兼容性约束。

AI Review 适合作为补充检查层，不能替代作者自测、同行评审、自动化测试和上线监控。

## 实践任务

**建议产出：**

- 实现一个只读的 AIOps Agent 原型，串联错误事件、日志、代码与历史问题。

**完成标准：**

- [ ] 至少封装三个边界清楚的 Tool，并组合成一个可复用 Skill。
- [ ] 输出包含事件、日志、代码和历史证据的定位报告。
- [ ] 明确区分确定事实、根因假设和修复建议。
- [ ] Token 使用最小权限，敏感信息不进入模型上下文。
- [ ] 所有写操作默认关闭，并设计人工审批节点。

## 复习检查

- [ ] 为什么接入 MCP 后仍然需要单独设计权限边界？
