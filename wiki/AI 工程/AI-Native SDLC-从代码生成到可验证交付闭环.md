# AI-Native SDLC：从代码生成到可验证交付闭环

## 核心结论

AI-Native SDLC 不是“让 AI 多写代码”，而是把软件交付重构成一个闭环控制系统：

```text
意图
→ 可审查的需求与设计
→ 可批准的实现计划
→ Agent 执行
→ 确定性验证
→ 按风险分配的人类审查
→ 受控部署
→ 生产反馈
→ 新的意图
```

传统流程默认代码生产昂贵，因此大量组织机制围绕“怎样让人稳定地产出代码”设计。Agent 显著压缩实现时间后，系统总吞吐量不会自动提高，瓶颈会转移到需求澄清、上下文搜集、测试、PR 审查、审批和部署。若只加速编码，得到的通常是更大的待审队列和更快积累的风险，而不是更短的交付周期。

课程的真正主张是：**让机器扩大执行能力，让确定性系统约束行动边界，让人负责意图、价值取舍和高风险决策。**

## 一、从第一性原理重新定义软件交付

软件开发不是把文字翻译成代码，而是把现实问题逐步转换成可运行行为。转换过程有四类不可消除的风险：

1. **语义损失：** 原始目标在需求、设计、计划和代码之间逐步漂移。
2. **认知不足：** 实现者缺少代码库结构、历史决策、业务规则和组织政策。
3. **行为不确定：** Agent 能生成看似合理的结果，但不能只靠语言流畅度证明正确。
4. **风险不对称：** 一次普通格式错误代价很低，一次越权、数据迁移或生产误操作代价可能很高。

因此，一套可靠的 AI 工作流至少要满足五个条件：

- **意图可追溯：** 能从代码和 PR 追溯最初为什么要做。
- **上下文可获取：** Agent 在行动前能获得当前任务需要的高信号知识。
- **结果可验证：** 正确性由测试、构建、静态检查、浏览器观察或运行指标证明。
- **权限有边界：** 不可接受的动作由 Hook、CI、权限系统和审批门阻止，而不是只提醒模型谨慎。
- **经验可复用：** 事故、审查意见和执行经验能进入 `CLAUDE.md`、Skill、Eval 或下一轮 `intent.md`。

这与[[认知工作流-从问题澄清到行动验证]]的共同结构一致：先建立任务契约，再规定中间产物，把验证嵌入推导，最后用真实反馈更新模型。

## 二、14 节课程实际组成的六层系统

14 节内容不是 14 个孤立技巧，而是围绕六种系统能力展开：

| 系统层 | 课程内容 | 解决的问题 | 主要产物 |
| --- | --- | --- | --- |
| 意图与设计 | Introduction、`intent.md`、Requirements and design | 防止做得很快但做错问题 | `intent.md`、需求与设计规格 |
| 上下文与知识 | `CLAUDE.md`、Skills | 让 Agent 获得代码库规则与组织经验 | 仓库指令、按需加载的能力包 |
| 计划与执行 | Plan mode、Parallel sessions、Subagents | 先审查低成本计划，再控制并行实现 | `plan.md`、隔离的任务与工作区 |
| 验证与审查 | Feedback loop、Continuous evals、PR review | 让错误尽早暴露，并区分单次代码正确性与 Agent 能力退化 | 测试、Eval、分层审查结果 |
| 治理与交付 | Hooks、CI/CD integration | 把政策变成执行时控制，并限制生产权限 | Hook、状态检查、审批与部署工具 |
| 运行与学习 | Metrics、Closing | 让生产反馈自动形成下一轮可追踪工作 | 告警诊断、修复 PR、新 `intent.md` |

六层之间存在依赖顺序：没有稳定验证就不应提高自治，没有权限边界就不应开放生产动作，没有清晰意图就不值得并行生成更多代码。

## 三、关键产物的职责边界

### `intent.md`：保存问题，不急着保存答案

`intent.md` 记录想改变什么、为什么、成功标准、约束、非目标和关键未知。它的价值是保存最初意图，减少业务方、产品、架构和开发多次转述造成的语义损失。

它不应提前写成实现方案。若“用户需要更快看到结果”被直接写成“必须增加 Redis”，问题和答案就被错误地绑定，后续无法比较更便宜的解法。

### 需求与设计规格：把意图变成可观察行为

规格说明系统在各种情境下应表现为什么行为，并记录数据、接口、安全、合规和兼容约束。它回答“最终允许出现什么结果”，但不必细化到复制代码结构，否则会形成一份需要与代码同步维护的“第二套代码”。

### `plan.md`：把昂贵修改前移为便宜审查

计划列出修改范围、文件、顺序、测试、风险和回滚方式。先审计划的原因不是形式合规，而是错误越晚发现，返工成本越高：一句错误假设在计划阶段只需改几行文字，进入实现后可能扩散成大量代码、测试和迁移。

计划批准不是永远锁死方案。实现中发现新事实时，应显式更新计划或请求重新决策，而不是悄悄扩大范围。

### `CLAUDE.md`：稳定、仓库级、高频上下文

适合保存构建与测试命令、架构边界、目录职责、编码规则和反复出现的错误。它应短而高信号；内容过多会增加上下文噪音，过期规则还可能误导执行。

可以用一个简单判断决定是否加入：**这条信息是否会影响此仓库中大量任务，并且不写下来就会反复出错？**

### Skill：按场景加载的机构知识

Skill 适合封装安全审查、数据库迁移、前端可访问性、发布检查等可复用流程。与 `CLAUDE.md` 的差别是：前者按任务场景加载，后者默认描述仓库的稳定公共规则。

Skill 主要影响 Agent 怎样思考和执行，但仍是概率性约束。绝对不能发生的动作不能只写在 Skill 中。

### Test 与 Eval：验证两个不同对象

- **Test** 验证当前软件行为是否正确。
- **Eval** 验证模型、提示、`CLAUDE.md`、Skill、Hook 或 Agent 配置变化后，整个 AI 工作方式是否退化。

生产事故和高价值审查问题不应只进入复盘文档；能稳定复现的部分应转成测试或 Eval，使系统以后自动识别同类错误。

### Hook：在行动发生时执行政策

Hook 把“应该遵守”提升为“执行前检查”。它适合阻止读取密钥、危险 Git 命令、未批准的数据迁移或生产部署。

基本原则是：

```text
提供判断方法 → CLAUDE.md / Skill
验证产出质量 → Test / Eval / CI
限制不可接受行为 → Hook / 权限 / 审批
```

不要把 Hook 当成完整安全边界。真正的高风险操作仍需最小权限、隔离环境、短期凭证、分支保护和人类审批。

## 四、为什么必须把反馈拉近执行

Agent 最大的工程价值不只是第一次生成更快，而是可以在一次会话中多次执行：

```text
实现 → 运行验证 → 读取结果 → 定位差异 → 修正 → 再验证
```

反馈越晚，错误扩散范围越大，人工恢复上下文的成本越高。有效反馈必须具备三个属性：

- **可执行：** Agent 能直接运行测试、构建、lint、类型检查或浏览器检查。
- **可解释：** 失败结果能指向具体行为，而不只是“质量不佳”。
- **不可自我篡改：** Agent 不能通过删除测试、降低阈值或改写验收条件制造成功。

Bug 修复尤其适合“先写失败测试，再修实现”。先确认测试确实因目标 Bug 失败，随后固定验收条件，才能避免 Agent 同时修改问题和判定标准。

## 五、并行和多 Agent 的真实上限

并行会话提高的是代码生产吞吐量，Subagent 提供的是上下文隔离和职责分工。二者只有在任务边界清楚、文件冲突可控、结果可独立验证时才有价值。

真实上限通常不是机器能启动多少 Agent，而是团队能否审查和合并它们的输出。若审查能力不变，把两条待审任务扩成十条，只是把瓶颈从编码移到 PR 队列。

因此应先问：

1. 任务能否形成独立、可验证的交付物？
2. 是否会同时修改同一状态、接口或迁移？
3. 谁负责整合结论和处理冲突？
4. 人类审查预算是否足够？

不能满足这些条件时，串行执行反而更快。

## 六、审查应按风险分配，而不是平均用力

当 Agent 生成大量代码后，要求人逐行审查所有内容会重新建立人工瓶颈；完全依赖 Agent 自审又会让同一种盲点同时存在于作者和审查者中。

更合理的结构是分层审查：

- 自动测试、静态分析和确定性规则处理机械问题；
- 独立 Agent 按逻辑、安全、合规、性能等维度寻找问题；
- 人类重点判断意图是否正确、架构取舍是否合理、剩余风险是否可接受；
- 认证、支付、隐私、生产权限和不可逆迁移等高风险变更保留明确责任人。

人的角色由“重新执行所有检查”转为“决定目标、冲突和风险”。这不是减少责任，而是把有限注意力放在机器难以替代的判断上。

## 七、CI/CD 的自治程度必须由风险决定

Agent 接入 CI/CD 时，应从只读、可逆、低风险任务开始，例如解释失败、总结 flaky test、生成变更说明，再逐步开放自动修复和创建 PR。直接操作主分支或生产环境不应作为起点。

可以按环境设置不同自治等级：

```text
开发环境：验证通过后可自动部署
测试环境：允许自动准备，关键动作受策略约束
生产环境：Agent 准备变更与证据，人批准发布和高风险回滚
```

提高自治前应先证明三件事：验证能捕获主要错误、权限只能执行必要动作、失败时存在更快且演练过的回滚路径。

## 八、生产指标如何关闭循环

生产系统提供的不是“任务完成证明”，而是新的现实证据。课程建议把检测和解释分开：确定性程序判断错误率、延迟、构建失败率或交付周期是否越界，模型负责收集上下文和诊断可能原因。

不同严重度对应不同动作：

```text
轻微偏离 → 记录并观察
明显偏离 → Agent 只读诊断
严重偏离 → 创建修复 PR、请求人工处置或执行预批准运行手册
复杂问题 → 生成新的 intent.md，重新进入完整生命周期
```

不要让每个指标波动都直接触发自主修改。检测阈值、行动权限、最大尝试次数、升级条件和退出机制必须是显式的。

## 九、与认知工作流的统一解释

这套 SDLC 可以看成[[认知工作流-从问题澄清到行动验证]]在软件工程中的实例：

| 认知工作流 | AI-Native SDLC |
| --- | --- |
| 写清背景、目标、约束、已知和未知 | `intent.md` |
| 规定可检查的中间产物 | 规格、`plan.md`、PR |
| 分开事实、假设与价值判断 | 需求事实、技术假设、风险取舍 |
| 把验证嵌入推导 | Test、Eval、CI、浏览器反馈 |
| 用最低成本行动验证关键未知 | 小范围实现、测试环境、灰度发布 |
| 根据现实反馈更新认识 | 指标越界、事故复盘、新 `intent.md` |

它不是一次性瀑布流程。任何阶段发现关键假设错误，都应回到最近的上游产物修正。所谓闭环，不是让流程自动转一圈，而是让新证据能够改变目标、方案和后续行动。

## 十、最小可行实施路径

不应一次部署课程里的全部机制。正确顺序由风险依赖决定：先让结果可验证，再扩大执行能力。

### 阶段 1：建立统一验证入口

为仓库提供一个人和 Agent 都能执行的 `verify` 命令，至少统一 lint、类型检查、测试和构建。CI 运行同一个入口，并保护主分支。

**完成标志：** Agent 无法只挑容易通过的检查来宣称完成。

### 阶段 2：建立任务契约

对中等以上变更保存 `intent.md`、规格和 `plan.md`，并在 PR 中关联。小修复可以简化形式，但仍要保留问题、验收条件和风险。

**完成标志：** 能从 PR 回答为什么做、做成什么样、怎样证明完成。

### 阶段 3：沉淀高信号上下文

维护简短的 `CLAUDE.md`，把重复出现的场景知识提取为 Skill。每次复盘只沉淀会影响未来行为的信息，避免建立无人维护的文档堆。

**完成标志：** 同类任务不再反复从人脑重新解释相同规则。

### 阶段 4：分层审查与持续 Eval

让自动检查解决机械问题，让独立审查 Agent 寻找特定风险，人类保留高风险批准。把历史事故和代表性任务做成回归 Eval。

**完成标志：** 修改模型或指令后，能发现工作方式是否退化。

### 阶段 5：增加执行时治理

对危险动作添加 Hook、最小权限和环境隔离；逐步开放自动修复、创建 PR 和测试环境部署。

**完成标志：** 即使 Agent 判断错误，也不能轻易越过关键控制边界。

### 阶段 6：连接生产反馈

先做只读诊断，再做受限的自动修复或预批准运行手册。复杂问题重新生成任务契约，不直接由告警驱动无限修改。

**完成标志：** 生产证据能进入下一轮工作，同时存在预算、审批和退出机制。

## 十一、常见误区与边界

- **把文档数量当成熟度：** 如果规格、计划和代码重复维护同一细节，只会增加漂移面。
- **把 `CLAUDE.md` 写成百科全书：** 默认上下文越多不等于判断越好，应优先保留高频、稳定、能改变行为的规则。
- **在验证成熟前扩大并行：** 生成速度提高后，审查和合并会成为更严重的瓶颈。
- **让同一个 Agent 同时定义标准、实现并批准：** 它可能通过修改验收标准证明自己正确。
- **把概率性提示当安全控制：** Skill 能降低犯错概率，不能代替权限和确定性阻断。
- **先做自动部署，后补回滚：** 自治程度必须受可验证性、可逆性和故障半径约束。
- **让模型判断所有指标异常：** 异常检测应尽量确定性，模型适合解释、归纳和提出候选行动。
- **假设企业流程都应完整照搬：** 小团队和低风险项目应采用更轻的产物和审批，保留机制而不是复制仪式。

## 十二、实践检查清单

开始任务前：

- 真正要改变的用户或系统结果是什么？
- 哪些是事实，哪些是技术假设，哪些是价值取舍？
- 什么证据会证明任务完成或推翻当前方案？
- 哪些动作可以交给 Agent，哪些必须由人决定？

实现过程中：

- Agent 是否先读意图、规格和仓库约束再行动？
- 计划是否说明范围、测试、风险和回滚？
- 反馈是否足够快、可执行且不能被轻易篡改？
- 并行任务是否独立，人工审查能力是否匹配？

进入生产前：

- CI、权限和审批能否在 Agent 犯错时阻止高风险结果？
- 是否使用最小权限和隔离环境？
- 回滚是否比部署更快，并且实际演练过？
- 生产指标越界后，不同严重度分别触发什么动作？

任务结束后：

- 哪项经验应进入测试或 Eval？
- 哪项稳定规则应进入 `CLAUDE.md` 或 Skill？
- 哪项只是一次性上下文，不应污染长期知识？
- 新证据是否要求修改意图、规格或控制边界？
