# 任务规划与控制

> [!abstract] 规划不是“先想完再执行”，而是在复杂目标下，把模糊意图转为有产物、依赖、范围和验收条件的子任务，并按真实执行结果持续修订。计划提出行动假设；工具回执和验收才决定任务是否完成。

## 第一性原理

单次 ReAct 能处理局部下一步，却不会天然知道复杂任务该覆盖哪些维度、哪些步骤互相依赖、何时信息已经足够。直接执行常导致资料堆积、重复检索、前置条件缺失或无限补充。

```text
目标 + 输出契约 + 已知事实 + 可用能力/预算
→ 拆成可验收子任务 → 声明依赖与范围
→ 调度执行并记录回执 → 检查缺口
→ 补充、交付、降级或停止
```

规划的核心是把任务结构外置，使系统能调度、恢复、审计和控制成本。

## 子任务的最小契约

| 字段 | 要解决的问题 |
| --- | --- |
| **产物（Produces）** | 做完后交付什么可复用结果？ |
| **输入（Consumes）** | 依赖哪些已验证事实或前序产物？ |
| **依赖（Dependencies）** | 哪些任务完成后才能开始？ |
| **范围（Boundaries）** | 做什么、不做什么，如何避免重叠？ |
| **能力与风险** | 可用工具、权限、预算、审批要求是什么？ |
| **验收与停止** | 何时算够，何时必须交付或停止？ |

没有这些字段，计划只是待办列表：既无法保证顺序，也无法判断结果是否可用。

## 调度与反馈

```text
A：收集权威基础事实
├─ B：分析产品（消费 A）
└─ C：分析市场（消费 A）
      ↓
D：综合（消费 B、C）

执行：A → [B || C] → D
```

- 无依赖任务可并行，但仍要受并发、限流、共享资源与副作用约束。
- 严格依赖任务串行执行。
- 部分依赖任务用 DAG / 拓扑调度；缺失输入时不应强行执行。

初始计划必然不完整。每轮执行后，根据工具回执、产物和未满足验收项更新计划版本；若缺少事实，应补充最少的新任务，而不是重跑全部流程。

## 停止与交付

“覆盖度”可帮助发现缺口，但模型评分不是完成证明。停止条件至少包括：

1. **成功：** 关键验收项满足，且有可追溯证据。
2. **继续：** 存在可恢复缺口，且预算、权限、时间和重试次数允许。
3. **降级：** 已有部分结果可安全交付；必须标明缺口、原因和恢复入口。
4. **停止：** 预算/超时/最大迭代耗尽、审批不足、依赖不可恢复失败或风险升级。

[[wiki/AI Agent 架构/06：Hooks 与事件控制|Hooks 与事件控制]]应暴露计划、任务开始/结束、预算临界、暂停与审批事件；运行时状态机而非模型偏好，负责取消、重试和恢复。

## 工程决策

- **先定义交付物与验收项，再要求分解。** 否则只会放大模糊需求。
- **计划持久化且版本化。** 保存任务 ID、输入、产物指针、依赖、状态、失败原因和消耗；不把唯一计划藏在对话文本中。
- **模型提计划，控制面裁决。** 用确定性规则检查结构、权限、预算、循环次数和验收；高风险动作接入审批。
- **只在复杂任务启用规划。** 多维度、多个信息源、长流程或需要恢复时值得付出协调成本；单步稳定任务直接执行。
- **把部分完成作为正式结果。** 不为表面完整编造结论。
- **观测计划质量。** 记录重复工作、依赖等待、计划变更、无效迭代、预算消耗、验收通过和部分交付比例。

## 常见误解

- 计划完成不等于用户目标完成；必须看外部回执和验收。
- 更多子任务不等于更好；过度分解会让协调成本超过执行收益。
- 并行不是默认优化；依赖、写冲突和配额都可能要求串行或互斥。

## 复习

1. `Produces / Consumes` 如何同时帮助避免依赖错序和重复工作？
2. 当质量评估建议继续、但预算耗尽时，应怎样安全交付？
