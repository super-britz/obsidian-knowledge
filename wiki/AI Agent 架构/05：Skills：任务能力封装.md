# Skills：任务能力封装

> [!abstract] Skill 不是给 Agent 加一个新工具，而是把“完成某类任务所需的角色指令、工作流知识、最小工具集和资源约束”封装为可选择、可复用、可按需加载的能力单元。它解决任务差异、权限扩散和上下文膨胀三件事。

## 第一性原理：为什么一个通用 Agent 不会自动胜任所有任务

同一个模型可以处理多类任务，但不同任务要求的目标、判断标准、过程知识、可用工具和成本上限并不相同。若只给一个通用 Prompt 和全部工具：

```text
任务类型变化
→ 所需工作流与专业判断变化
→ 通用 Prompt 无法稳定给出正确优先级
→ 全量工具增加选择空间与权限风险
→ 全量资料和 Schema 占据上下文
→ Agent 看似能力很多，实际更容易选错、跑偏或耗尽预算
```

Skill 将与某类任务稳定相关的上下文和边界显式打包：

```text
任务意图
→ 选择匹配的 Skill
→ 装载角色目标、步骤、示例与完成标准
→ 仅暴露该任务需要的工具和参数上限
→ 按需加载深入资料或脚本
→ 在既定边界内执行、验收或降级
```

因此，Skill 的本质是**任务特化的上下文与能力配置**，而不是人格设定或提示词模板的别名。

## 一个 Skill 应封装什么

| 要素 | 解决的问题 | 缺失后的典型失败 |
| --- | --- | --- |
| 适用条件与任务目标 | 什么时候应选择该 Skill | 名称相似却任务不匹配，或所有任务都落到 generalist |
| 角色与工作流指令 | 先做什么、依据什么判断、何时完成 | 输出风格像专家，但步骤、证据和验收随意 |
| 最小工具白名单 | 任务能做什么、不能做什么 | 工具选择困难、权限过宽、意外副作用 |
| 参数与预算约束 | 成本、输出风格、推理深度的可接受范围 | Token、时间或随机性失控 |
| 示例、参考资料与脚本 | 领域操作细节从哪里获得 | 主指令过长，或模型临时猜测专业流程 |
| 调用与降级规则 | 谁能触发、失败时回退到哪里 | 高风险 Skill 被自动调用，或可选模块缺失即整体失败 |

角色描述只有与工具、资源和完成标准共同约束时，才成为可重复的工程能力。

## 渐进式披露：把上下文当作稀缺资源

Skill 的另一层价值不只是复用，也是**按需装载上下文**。合理的加载层级是：

```text
启动：只加载名称、description 等轻量元数据
→ 匹配任务：加载完整 SKILL.md 的流程与边界
→ 具体步骤需要：再读取 reference、examples 或执行脚本
```

这样做的因果关系是：

```text
上下文窗口与预算有限
→ 不相关的工具 Schema、参考资料会挤占当前决策空间
→ 先用少量元数据完成路由
→ 再只加载当前任务必要的知识
→ 既减少成本，也减少无关内容干扰决策
```

渐进式披露不等于可以无限塞资料；加载后的内容仍需要有明确来源、优先级、长度上限和失效处理。

## Skills 与 MCP 的分工

```text
MCP：提供“能连接什么能力”的标准管道
Skills：提供“在什么任务中、按什么步骤、以什么边界使用能力”的操作手册
```

例如，MCP 可以连接 Jira；一个项目管理 Skill 则告诉 Agent 何时查询事项、怎样创建 Sprint、需要哪些审批，以及哪些字段或操作不得自动执行。

因此：

- 没有 MCP 的 Skill 仍可指导本地工具或纯文本工作流；
- 没有 Skill 的 MCP 工具仍可被调用，但 Agent 可能不知道正确的业务顺序；
- Skill 的工具白名单不能替代执行层权限校验，MCP Server 和工具运行时仍必须实施真实授权与策略控制。

## 约束与失败表现

- **System Prompt 模糊：** Skill 只有角色标签，没有任务步骤、证据要求或完成标准，表现不稳定。
- **工具权限过宽：** 为了“万能”暴露文件写入、Shell、外发等能力，既增加选错概率也扩大副作用。
- **没有参数与预算约束：** 长任务无限扩张、成本上升，或随机性与输出格式不符合任务目标。
- **全部内容启动时加载：** 大量工具定义、领域资料和示例占用上下文，反而降低当前任务的可用信息密度。
- **没有调用与降级规则：** 可选依赖出错导致整体失败；有副作用的能力被模型在不恰当场景自动调用。
- **把 Skill 当安全边界：** frontmatter 或 Prompt 中的规则可能被忽略或误用；真正的权限与执行限制必须在运行时强制实施。

## 工程决策

1. **按稳定任务结果划分 Skill，而不是按部门或人设命名。** 一个 Skill 应能说清输入、关键步骤、完成证据与不适用条件。
2. **description 用于路由，不用于承载全部知识。** 简洁描述触发条件；具体流程、例子和参考资料分层放入按需内容。
3. **默认最小工具集和最小预算。** 只有当前任务确实需要时才扩展工具、模型能力或上下文资源。
4. **把高风险 Skill 设计成显式触发。** 部署、发布、删除、外发等副作用任务需要用户确认或专门审批，不应仅因语义匹配而自动运行。
5. **用可观测结果评估 Skill。** 对比成功率、人工返工、成本、耗时、工具失败和安全拦截，而不是只看输出是否“像专家”。
6. **保持可降级路径。** 专用 Skill 不可用或不匹配时，回退到更简单的通用流程或请求用户补充，而不是静默套用错误角色。

## 不要把实现示例当成原理

- Shannon Preset、Markdown + YAML、`SKILL.md` 和不同平台的调用字段都是封装语法；稳定机制是“任务路由 → 受约束的上下文与能力装载 → 执行与验收”。
- 允许模型自动调用、仅允许用户调用、在子代理中运行等设置属于控制策略；应按副作用和可验证性选择，不能只追求自动化。
- Skill 的脚本和引用资料属于扩展能力，仍需要版本管理、来源验证、资源限制和与工具相同的执行安全边界。
