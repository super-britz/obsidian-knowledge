# 分层模型路由与韧性

> [!abstract] 分层模型策略不是给请求贴上“简单/复杂”标签，而是在质量、能力、时延、可用性与成本彼此冲突时，为每次调用选择**满足硬约束的最低成本路径**，并在证据显示不足或依赖故障时受控地升级、切换或停止。

## 第一性原理：模型能力昂贵且不均质，任务需求也不相同

不同模型的推理、视觉、代码、工具调用、上下文、结构化输出、时延和价格并不相同。若所有请求都交给最强模型，会为简单任务支付不必要成本；若只按便宜程度路由，又会在缺少必要能力时稳定地产生低质量结果。模型选择因此是一个受约束的资源分配问题，而不是单一的复杂度预测。

```text
任务目标、输入形态与输出契约
→ 识别硬能力、权限/合规、时延和预算约束
→ 在满足硬约束的候选中估计复杂度与预期质量
→ 选择最低成本的初始层级与健康 Provider
→ 观察质量、成本、限流和故障证据
→ 必要时同能力切换、升级，或明确失败/转交
```

所以，分层路由的核心原则是：**能力匹配优先于成本优化；质量反馈优先于一次性分类。**

## 路由决策：先排除不能做的，再比较谁更合适

路由先根据任务契约筛掉不合格候选：需要图像时必须有视觉输入能力，需要代码变更时要满足编码与工具约束，需要长上下文时要满足窗口和成本边界，需要结构化输出或特定地域/合规时也必须显式检查。只有在这些硬条件相同的模型之间，Small / Medium / Large 等层级才是有意义的成本与时延选择。

复杂度可用长度、多步目标、工具数量、推理/代码等启发式信号快速估计；高价值或边界任务可让低成本分类器提供第二个判断。两者都是近似值，不能把“复杂度分数”误当成真实质量。对于验收明确的任务，应使用结果证据决定是否升级：格式校验、工具回执、测试、评审或用户反馈比模型自报置信度更可信。

“先用较低层尝试、失败再升级”只适用于可安全重试、输入稳定且不会造成重复副作用的任务。涉及工具写入、付款、发信或昂贵长上下文时，应先计算失败代价；必要时直接选择足够能力的模型或先取得审批。

## 统一控制面：配置、状态和路由不能散落在业务代码中

统一 LLM Manager / Router 应持有模型清单、能力矩阵、层级偏好、允许的 Provider、定价版本、缓存、限流、预算、使用量和健康状态。调用方提交的是任务需求与约束，不应在各处硬编码模型名称；这样模型下线、价格变化、能力更新或策略收紧时，才能集中调整、灰度和回滚。

路由记录至少要关联任务/会话、请求特征、候选与最终模型、Provider、路由原因、输入输出 Token、缓存命中、延迟、成本、质量结果、升级和 fallback 原因。它既支持 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|诊断闭环]]，也为 [[wiki/AI Agent 架构/23：Token 预算与成本护栏|预算护栏]] 提供实际消耗证据。

价格表应版本化并区分输入、输出、缓存、批处理和区域等计费维度；未知或价格失效的模型不应静默按乐观价格运行。定期与 Provider 账单核对，才能把“估算成本”变成可用的预算信号。

## 韧性与降级：可用不等于随意换模型

Provider 的瞬态错误、限流和超时是独立于模型质量的故障。熔断器在连续可恢复失败后临时跳过不健康 Provider，冷却后仅允许少量探测请求；同层的健康备选可以维持服务。但 fallback 前必须重新检查能力、上下文限制、数据边界与输出契约。

若没有满足硬条件的备选，应返回可解释的受限失败、排队或降级功能，而不是把需要视觉/深推理/工具能力的任务静默转给不具备该能力的模型。跨层降级应只用于明确允许质量下降的场景；跨层升级则要受 Token、成本、重试次数和时延预算限制。缓存可以减少稳定前缀和重复任务的成本，但缓存键必须包含模型、提示词版本、工具/权限上下文和用户/租户范围，避免把旧答案或其他用户结果当作命中。

## 工程决策

1. 为每类任务定义路由契约：必要能力、输入输出格式、可否重试、质量验收、最大时延和预算；不要只暴露一个 `complexity` 数字。
2. 建立能力矩阵与模型层级的两个维度：先按视觉、代码、推理、长上下文、工具、结构化输出和数据边界过滤，再从合格候选中选择最低成本层级。
3. 采用“初始路由 + 结果验证 + 有界升级”而非一次性判断；对关键任务记录升级原因，用失败样本反校准规则和阈值。
4. 集中管理模型、Provider 优先级、价格、限流、缓存和预算，支持版本化、灰度、回滚与实际账单校验；业务代码只声明需求。
5. 将 Provider 故障与质量不足分开处理：前者走熔断和同能力 fallback，后者走升级、重新规划或人工转交；不要把两种失败混为“换个模型试试”。
6. 监控按能力/层级/Provider 的成功率、延迟、限流、升级率、缓存命中和实际成本；Large 占比或升级率异常是路由策略需要复查的信号，不是自动故障结论。

## 常见误解

- **“Small / Medium / Large 就等于质量的绝对排序。”** 层级只是运营抽象；具体能力和输出稳定性必须逐模型验证。
- **“复杂度高就必然用 Large。”** 若任务缺少必要输入、工具或权限，再强的模型也不能完成；反之，有些高文本复杂度任务可通过结构化流程拆解。
- **“Fallback 越多越可靠。”** 不受约束的切换会破坏能力、输出或数据契约；应该优先同能力备选，并保留失败原因。
- **“缓存命中就是可复用答案。”** 提示词相同不代表身份、权限、时效、工具状态和任务目标相同。

## 复习

- 为什么能力匹配要先于成本？——没有视觉、工具或所需上下文的模型不构成有效候选，便宜也无法弥补硬能力缺口。
- 为什么不能只做一次复杂度分类？——任务理解和质量判断都有不确定性；真实结果才是升级或重新路由的证据。
- 熔断器和质量升级分别处理什么？——熔断器隔离 Provider 的可用性故障；升级处理当前能力不足，二者的原因、成本和回退策略不同。
