# Background Agents 持久化后台任务

> [!abstract] Background Agent 让任务在用户离线后仍能按计划运行、恢复和交付结果。它解决的是“会话断开后任务如何继续”的问题，但也移除了实时监督；可靠性不来自一个 Cron 表达式，而来自持久状态、受控触发、可核对执行记录和可停止的副作用。

## 第一性原理：用户会话不是任务的可靠生命周期

同步请求把“用户在线、网络连接、进程存活”和“任务完成”绑在一起。长任务、周期监控和批处理一旦超过请求生命周期，就会丢失进度、无法恢复，也不能让用户在之后查询发生过什么。把任务移到后台后，系统又必须独自处理时间、故障、成本、权限和重复执行。

```text
用户声明目标、时间和资源边界
→ 将调度定义与任务状态持久化，并立即返回任务标识
→ 到达触发条件后，在受限工作流中创建一次执行
→ 记录状态、进度、成本、结果和失败证据
→ 按重试、暂停、取消与预算规则决定恢复、停止或告警
→ 用户或系统根据历史、通知和审计继续管理任务
```

因此，Background Agent 的本质是**由持久化控制面管理的、脱离会话的受限任务生命周期**，不是“把同步 Agent 放进定时器”。

## 调度与业务状态：一个负责执行，另一个负责解释

工作流/调度引擎适合保存触发与执行恢复所需的状态；业务数据库适合按用户、租户、任务、时间和结果查询配置、执行历史与审计。两者看似重复，实际服务不同：前者保证系统能继续做事，后者让用户和运营者知道“什么任务被谁创建、何时会跑、跑过什么、花了多少”。

这是一条双系统状态链，因此创建、暂停、恢复和删除都不能假设天然原子。创建一端成功而另一端失败时要补偿或标记待修复；删除不能只删业务记录而让底层调度继续运行。定期对账并清理孤儿记录是恢复不一致的机制，但遇到暂时性查询错误应保留不确定状态并告警，不能把“查不到”直接当成“应删除”。

[[wiki/AI Agent 架构/21：Temporal 持久化工作流|Temporal 持久化工作流]]提供了可恢复执行的基础；Background Agent 在其上补充“何时触发、谁拥有、如何管理和怎样对用户可见”的产品控制面。

## 触发与生命周期：时间规则也必须受约束

一个调度定义至少应包含任务目标、Cron/事件触发规则、明确的 IANA 时区、下次运行时间、超时、并发/重叠策略、每次执行预算、所有者与租户范围。用户说“每天 9 点”并不完整：必须明确是哪个时区，以及夏令时、错过触发和暂停恢复后如何计算下次运行。

创建时需要同时验证语法和业务限制：最小间隔防止高频触发，用户/租户配额限制任务数量，系统上限收紧用户预算与超时，身份和租户范围决定谁可管理任务。暂停、恢复、取消应是幂等状态转换：重复请求不产生额外触发；恢复时返回新计算的下次运行时间，而不是假装沿用过期计划。

调度只负责“何时尝试执行”，并不保证每次结果都有效。每一次运行都应有独立 Run ID、输入快照、状态、开始/结束时间、成本、输出位置和错误信息；这让重试、通知、审计和用户查询都有可追溯对象。

## 成本与恢复：离线执行必须有硬终点

后台任务不会因为用户关闭页面而停止，因而必须把限制写进运行时：单次 Token/费用、累计费用、超时、最大重试、最小触发间隔、并发数和连续失败阈值。达到上限时任务应明确停止、暂停或降级，并通知用户；不能把“后台会继续处理”变成无限消耗。

重试只适合可恢复的暂态失败。对发送通知、写数据库、调用支付或其他外部副作用，重试可能造成重复结果；需要幂等键、去重、状态查询或人工处理。连续失败、重复相同输出或超过预算时，应暂停调度并留下诊断证据，而不是一直按 Cron 再次触发。成本规则与 [[wiki/AI Agent 架构/23：Token 预算与成本护栏|预算护栏]]、状态/错误证据与 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]] 共同构成离线运行的刹车系统。

## 权限与副作用：用户不在场时默认更保守

后台触发不能把“曾经登录过”视为无限期授权。执行时要重新建立任务所属用户和租户的可信上下文，并按当前策略检查任务、工具、数据范围和账户状态；权限被收回、租户被禁用或策略收紧时，后续运行应被阻止或要求重新授权。[[wiki/AI Agent 架构/26：多租户隔离与资源边界|租户隔离]]限制任务可见的数据范围，[[wiki/AI Agent 架构/24：策略治理与授权决策|策略治理]]决定其当前是否可做，[[wiki/AI Agent 架构/25：安全执行与能力沙箱|安全执行]]限制执行器实际能接触的能力。

删除数据、修改权限、购买、发信、对外发布等高后果操作不应由静默的定时任务直接完成。可将后台任务限制为收集、分析、生成草稿和提出建议；真正不可逆的动作要求明确的预授权、二次确认或转为人工处理。每次执行记录任务版本、触发原因、实际权限、工具调用、结果与失败原因，才能在事后解释“它为什么这样做”。

## 工程决策

1. 将后台任务建模为持久化的调度定义和独立执行记录，不把浏览器会话、内存对象或聊天历史当成唯一状态来源。
2. 创建时强制填写/展示时区、下次运行时间、最小间隔、超时、预算、重叠策略和通知方式；对“每天 9 点”这类自然语言请求，先转为可确认的具体时间规则。
3. 将调度引擎和业务库的写入视为分布式状态变更：设计补偿、幂等 API、对账任务和孤儿告警；删除要先停止底层触发，再更新业务状态。
4. 为每次运行分配 Run ID，并记录输入快照、版本、开始/结束、成本、状态、输出与错误；连续失败、超预算或重复副作用风险应自动暂停并通知。
5. 对外部副作用使用幂等键和状态核验；重试仅针对明确可恢复的失败，且受次数、时间和预算限制。
6. 以“用户不在场”作为更高风险等级：重新校验当前权限与租户，禁止或审批高后果动作，使用最小权限执行环境。

## 常见误解

- **“Background Agent 就是 Cron 加一个 prompt。”** Cron 只解决触发；状态持久化、失败恢复、审计、预算和权限才决定它能否安全运行。
- **“工作流引擎有状态，业务数据库就不需要。”** 引擎状态面向执行恢复；用户查询、归属、报表和审计需要独立的业务索引与记录。
- **“自动重试会提高可靠性。”** 对非幂等副作用，重试会重复发信、写入或扣费；必须先确认幂等与恢复条件。
- **“创建时授权过一次就够了。”** 后台任务可能在数天后执行，期间权限、账户、策略和租户状态都可能变化。

## 复习

- 为什么后台任务不能依赖用户会话？——会话、连接和进程都会结束；任务进度、调度和结果必须存放在可恢复的持久系统中。
- 为什么需要对账孤儿调度？——调度引擎与业务库的双系统操作会部分失败或被外部修改；不对账就会出现“界面显示不存在但任务仍在运行”。
- 为什么后台操作要比交互式操作更保守？——用户不在现场及时发现或确认，错误会在更长时间、更大规模中累积。
