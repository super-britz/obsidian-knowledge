# 结构化推导与证据验证

> [!abstract] Chain-of-Thought 的工程价值是把多步问题外化为可检查的中间论断、计算和结论，减少部分跳步错误并改善沟通。它不是模型私有推理的完整窗口，也不能用“解释看起来合理”代替外部证据。

## 第一性原理

LLM 默认直接生成答案。遇到多步计算、逻辑约束、因果分析或调试时，错误常藏在被跳过的条件、错误前提或错误计算中；只有最终答案，系统难以定位问题。

```text
问题 + 已验证条件 + 输出契约
→ 拆成中间论断 / 计算 / 假设
→ 核对关键步骤的来源、规则或测试
→ 得出带条件的结论
```

中间步骤的价值是提供检查点，不是让输出更长。

## 理由、推导与证据要分开

| 产物 | 用途 | 能否证明正确 |
| --- | --- | --- |
| **面向用户的理由** | 解释结论、说明关键条件 | 不能；可能简化或遗漏 |
| **结构化中间论断** | 便于逐项检查、调试和交接 | 不能单独证明；每步都可能错 |
| **模型私有推理** | 模型内部生成过程 | 不应被当作完整审计记录 |
| **可验证证据** | 来源、工具回执、计算、测试、状态变更 | 可在明确范围内复现和核对 |

生产系统应审计最后一项。解释文本可帮助人理解，但不能取代来源、测试或真实环境观察。

## 每一步的最小契约

| 要素 | 要问什么 |
| --- | --- |
| **输入条件** | 依赖哪些事实、假设或前一步产物？ |
| **规则/操作** | 使用什么公式、业务规则、查询或变换？ |
| **中间结论** | 这一步产出什么供下一步使用？ |
| **验证方式** | 用什么来源、重算、测试或回执发现错误？ |
| **不确定性** | 哪些前提尚未证实，哪些情况会改变结论？ |

数学用重算或程序核对；调试要把“假设”与“观察”分开，用日志或复现证伪；研究与因果分析要标明来源、时效及不能推出的部分。

## 与规划、ReAct 和树形搜索的分工

| 机制 | 适用问题 | 何时不用 |
| --- | --- | --- |
| **结构化推导** | 条件基本齐全、路径明确的多步推导 | 缺事实、目标不清或需比较多方案 |
| [[wiki/AI Agent 架构/02：ReAct 循环|ReAct]] | 需要检索、查询或操作环境获取事实 | 不需要外部信息时不必增加工具循环 |
| [[wiki/AI Agent 架构/10：任务规划与控制|任务规划]] | 多目标、长流程、依赖与验收复杂 | 单步稳定任务不必规划 |
| Tree-of-Thoughts | 必须展开、比较并回溯多条路径 | 单一路径足够时成本过高 |

缺事实先观察，目标不清先规划，分支需要比较才搜索；不要用更多文字掩盖选择错了机制。

## 置信度与输出控制

步骤数量、连接词、统一格式和模型自报分数，最多说明答案“像一段推导”，不等于校准后的正确率。质量判断应由强到弱分层：

1. **硬验证：** 解析、重算、类型检查、测试、策略和权限。
2. **证据一致性：** 关键事实是否能回溯到可靠、及时、可访问的来源或工具回执。
3. **结构检查：** 是否遗漏前提、循环论证、前后矛盾或结论超出证据。
4. **模型辅助评价：** 清晰度、完整性和受众适配。

若问题来自事实缺失，正确动作是检索、调用工具或请求澄清，而非要求模型再解释一遍。

对用户只展示最少充分理由；对运行时保存结构化步骤、证据指针、验证结果和未决条件。不要把冗长逐步文本无限回填到上下文，相关策略见[[wiki/AI Agent 架构/07：上下文工程|上下文工程]]。

## 工程决策

- 将 CoT 设计为**结构化推导契约**，明确输入、步骤格式、结论、验证要求和不确定性表达。
- 为关键中间论断接入外部验证：计算重算、代码测试、事实来源、业务后置条件。
- 解析器支持多种格式和安全降级；解析失败时请求重述或保留原始交付，不篡改事实。
- 启发式置信度只能触发澄清、额外验证或人工复核，不能绕过权限、预算和审批。
- 按复杂度限制步骤和 Token，观测硬验证失败率、澄清率、事实纠错率、成本和延迟，而不是只看解释长度。

## 常见误解

- 逐步解释不等于模型私有思维的真实记录。
- 逻辑链顺畅不等于前提正确；错误事实会导出错误结论。
- 多次相似推导或投票也不保证真相；共同前提错误会一致地错。

## 复习

1. 为什么用户可读的解释不能作为高风险决策的审计证据？
2. 一个步骤依赖外部事实时，如何分别验证“推导正确”和“前提正确”？
