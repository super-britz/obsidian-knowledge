# Agentic Coding 受控代码变更

> [!abstract] Agentic Coding 的目标不是续写代码，而是在已有系统中完成一次可交付的变更。代码库含有跨文件契约、隐含依赖和真实副作用；因此可靠交付必须把“理解 → 最小修改 → 隔离验证 → 可审查交付”连成闭环，而不能把生成的文本直接当成完成。

## 第一性原理：代码变更会改变一个相互依赖的系统

一段代码是否正确，不由它在当前文件中是否“看起来合理”决定，而由它是否仍满足调用方、依赖、配置、测试和运行环境共同形成的契约。把整个仓库塞给模型既不可扩展，也不会自动告诉模型真正的影响范围；直接在宿主执行又会将错误变为文件、网络或生产副作用。

```text
任务目标与验收条件
→ 按需定位相关符号、调用链、配置与测试
→ 提出范围最小、可解释的变更计划
→ 以锚点应用变更，并保留清晰 diff
→ 在受限副本运行未被污染的验证
→ 根据真实失败修复，或在上限处停止并交给人
→ 用 diff、测试证据与审批决定是否合并
```

因此，Agentic Coding 的本质是**对代码副作用进行受限探索和验证的工程闭环**，不是更强的代码补全。

## 上下文与编辑：只建立完成当前变更所需的证据

代码理解应从任务入口出发，先找相关标识符、错误信息、接口和测试，再沿调用关系、依赖图与配置扩展；关键词搜索适合精确定位，AST/LSP 与语义搜索补足结构和意图。读取范围应受工作区、文件大小和任务相关性约束，避免无关上下文稀释判断。其原则与 [[wiki/AI Agent 架构/07：上下文工程|上下文工程]] 一致：上下文不是越多越好，而是要足以支持当前决策。

写入时区分新建/小文件与已有大文件：前者可以整体生成，后者应使用“前后唯一文本锚点 + 预期旧内容”进行精确编辑。行号会随并发修改和前序操作漂移；锚点失配应停止并重新读取，而不是猜测位置或覆盖整个文件。每次编辑都应产生可审查 diff，并限制到任务允许的路径与文件集合。

## 验证闭环：测试是反馈，不是通行证

[[wiki/AI Agent 架构/02：ReAct 循环|ReAct]] 在编码任务中的具体形式是：**编辑 → 测试 → 分析失败 → 修复 → 再测试**。失败输出、堆栈、相关代码和改动历史共同构成下一轮上下文；修复不应只针对报错文本，还要判断根因与影响范围。

循环必须有边界：限制最大轮数、墙钟时间、资源和重复相似修复；若未收敛，应保留失败证据并升级给人。测试也必须防污染：在隔离副本中执行，保留原始测试与测试数据，区分 Agent 可改的源代码和不可随意改的验收条件。**测试通过**只说明已覆盖的检查在当前环境通过，不能替代覆盖评估、代码审查或生产验证。

## 执行与安全：沙箱、策略和供应链分别守住不同边界

Agent 写出的代码与其安装、调用的依赖都应视为不可信。执行环境需要默认最小能力：受限文件路径、非特权身份、默认关闭网络、只读基础环境，以及内存、CPU、磁盘和超时上限。Docker、WASI 或更强隔离机制是实现手段；重点不是技术名词，而是运行时没有被显式授予的能力就无法使用。

[[wiki/AI Agent 架构/25：安全执行与能力沙箱|沙箱]]回答“执行器能接触什么”；[[wiki/AI Agent 架构/24：策略治理与授权决策|策略治理]]回答“这项操作是否被允许”；依赖白名单、审计和人工审批守住“引入什么代码”。三者不可互相替代：网络沙箱不能说明某个包安全，代码扫描也不能阻止错误地改写生产配置。

删除文件、修改生产/安全配置、读写密钥、开启网络、安装依赖、推送分支或创建 PR 都是不同等级的外部副作用，应按风险设为禁止、需要审批或只允许在隔离环境中执行。

## 交付与协作：把 Agent 的结果变成人能判断的变更

Git 工作区不是 Agent 的空白画布。开始前应检查并隔离已有未提交改动，避免混入用户工作；完成后交付任务目标、修改文件、关键设计取舍、完整 diff、运行命令、测试结果、未覆盖风险和回退方式。commit/PR 是审查载体，不是“测试绿了”后的自动奖励。

复杂任务可以把检索导航、生成、小范围审查、测试分析分别路由给不同模型或角色；但分工只是在成本、速度和专业性上的优化。最终仍需由同一验证链确认：变更是否满足契约、测试是否可信、权限是否允许、影响是否可接受。过程证据应接入 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]]，成本与重试应受 [[wiki/AI Agent 架构/23：Token 预算与成本护栏|预算护栏]] 约束。

## 工程决策

1. 先为任务写清目标、不可变约束、允许路径、验收命令和禁止副作用；缺少验收条件时，先澄清或只输出计划/diff，不直接执行。
2. 采用“检索 → 读取 → 计划 → 最小编辑”的顺序；锚点或工作区状态不匹配时中止重读，禁止按过期行号盲改。
3. 在临时副本或受限分支验证，保留原始测试；将单元、集成、静态检查和必要的人工验收按风险组合，而非只运行最快的一条测试。
4. 为循环设置迭代、时间、Token 和资源上限，并记录每轮假设、diff 与测试结果；重复修复或不收敛时交给人，而非无限重试。
5. 将网络、目录、命令、依赖安装、Git push/PR 与生产配置拆成独立能力；高风险能力默认拒绝，获得明确授权后再开启。
6. 交付前审查 diff 与工作区状态，确认没有覆盖用户改动、泄露凭据或把测试改成自证；PR/提交说明应附验证证据与剩余风险。

## 常见误解

- **“给模型整个仓库就能理解系统。”** 大量无关文本会掩盖任务线索；应按调用链和验收条件建立最小相关上下文。
- **“测试全绿就可以自动合并。”** 测试可能覆盖不足、被污染或与生产不同；合并还取决于 diff、风险、授权和审查。
- **“沙箱解决了 Coding Agent 的安全问题。”** 它只收缩执行能力；供应链、密钥、Git 权限和业务授权仍需独立控制。
- **“多模型协作天然更可靠。”** 分工增加接口、压缩和协调成本；没有共同的验证证据，只是更复杂地猜测。

## 复习

- 为什么要从任务入口按需理解代码，而不是读取全仓库？——正确性取决于相关契约和影响链；无关代码既耗费窗口，也会干扰定位。
- 为什么精确编辑要用锚点而不是行号？——行号会漂移；锚点能让执行器确认它修改的仍是预期位置。
- 为什么测试、沙箱和 Git 审查缺一不可？——它们分别提供行为反馈、限制运行时爆炸半径、让人核验变更意图；没有任何一个能替代另两个。
