# Token 预算与成本护栏

> [!abstract] Agent 会自主拆分、循环、并行调用模型，却不知道“花到什么程度该停”。Token 预算把可消耗资源变成任务、会话和 Agent 都必须遵守的约束：执行前判断是否允许，执行后记录实际用量；接近上限时降速或请求决策，达到硬上限时停止。它控制失控概率，不保证估算精准，也不替代质量和权限判断。

## 第一性原理：没有边界的自主调用，成本就没有上界

一次模型调用的 Token、模型档位、重试次数与子任务数量都会改变成本。若 Agent 只以“完成任务”为目标，它会继续检索、推理和调用，直到碰巧完成、超时或耗尽共享资源；多 Agent 并发会放大这一问题。

```text
任务目标驱动继续调用
→ 单次、会话累计与并行 Agent 的消耗叠加
→ 预先定义各范围可接受的资源上限
→ 每次调用先检查剩余额度，并限制本次最大输出
→ 执行后以实际用量结算、告警和调整后续行为
```

预算不是报表，而是**参与调度的资源护栏**：它回答“这一步还能不能做、最多做多少、超出后怎样退出”。

## 多层预算：不同范围，需要不同的刹车

原章给出 Task、Session 与 Agent 三层：

- **Task：** 限制一项工作最多消耗多少，防止单个复杂请求无限扩张。
- **Session：** 限制连续交互的累计消耗，防止许多小任务绕过单次上限。
- **Agent：** 在多 Agent 协作中分配局部额度，防止一个角色独占总资源。

这些上限不能只各自检查。一次调用只有同时满足适用范围的剩余额度才应继续；并发时，检查与预留/扣减必须受同步保护，否则多个调用都读到“尚有余额”，最终合计超支。

## 预算闭环：先预估，后结算，再决定下一步

```text
收到调用计划
→ 估算本次输入、输出与模型成本，检查多层剩余预算
→ 允许时传入 max_tokens / 模型档位等执行边界
→ 执行完成后记录实际输入、输出、模型、成本与任务身份
→ 更新剩余额度、仪表盘与后续调度策略
```

**预估**用于避免明显超限，**实际用量**才用于结算和复盘；两者有误差，不能把预估当账单。失败或超时也可能已经产生模型成本，因此记录策略要明确“什么结果算已消费”，并以任务/调用身份支持审计。

## 从硬拒绝到受控降级

预算压力不是只有“通过/拒绝”两种状态：

- **软阈值：** 接近上限时提示、减少并发、降低模型档位、缩短输出或暂停等待审批。
- **背压：** 对可延迟任务逐步减速，给系统和用户留出调整空间；在 Temporal 场景中，应由 Workflow 等待，而不是让 Activity 的 Worker 线程睡眠。
- **硬限制：** 到达不可突破的上限时停止新的高成本调用，并返回已完成部分、剩余风险和可选行动。
- **熔断：** 某主体持续超限或异常时，暂时拒绝进入，经过受控探测再恢复，避免级联占用。

降级必须是显式产品契约：用户要知道结果是部分完成、低成本模式还是等待审批，不能悄悄以低质量结果伪装完成。

## 可靠记账：重试不能变成重复收费

预算系统同时是并发和副作用系统。网络抖动、Workflow/Activity 重试或多个记录路径都可能让“实际调用一次”被记多次，或已花费却未入账。

原章强调幂等键、同步更新和双路径记录保护。工程上应为每笔用量保留稳定的调用身份，并在持久化层保证同一身份只结算一次；预算启用时由明确的单一路径记录，避免编排层和执行层重复记账。它与 [[wiki/AI Agent 架构/21：Temporal 持久化工作流|持久化工作流]]的原则一致：重试提高完成率，也会放大副作用重复的风险。

## 工程决策

1. 先按产品承诺定义 Task、Session、Agent 的默认预算与允许的例外，再实现检查逻辑；不要把单一全局 Token 数当成全部治理。
2. 每次高成本调用都做“剩余额度 + 本次预估”的事前判断，并把最大输出、并发和模型选择纳入执行约束；执行后写入实际用量。
3. 将硬停止、软阈值、审批、背压和熔断分别用于不同风险等级；成本敏感批处理优先硬限制，高价值长任务可请求审批或返回部分结果。
4. 将用量、成本、超限、背压和熔断状态接入 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]]，并定期比对估算、实际账单与用户价值，校准预算和模型策略。
5. 预算只管“能花多少”，不判断“能不能做”；工具权限、数据访问与审批规则应交给下一章的策略治理。

## 常见误解

- **“设了单任务上限就不会超支。”** 连续会话与并行 Agent 仍会累计消耗，需要多层范围共同约束。
- **“估算值就是成本。”** 估算有误差，最终应以实际输入/输出 Token、模型定价和记录规则结算。
- **“预算一到就直接报错。”** 对可恢复场景，更好的契约可能是降级、部分结果或审批；但这不能突破硬上限。
- **“重试只影响延迟。”** 若用量记录不幂等，重试还会污染账单和剩余预算。

## 复习

- 为什么 Token 预算必须是多层的？——单次任务、连续会话和协作角色的失控方式不同，单一限制容易被累计或并行绕过。
- 为什么同时需要预估与实际记录？——预估决定是否发起调用，实际用量才说明真正花费了什么；两者误差需要被看见和校准。
- 接近或超过预算后怎样处理？——按风险选择降级、背压、审批、硬停止或熔断，并清楚告知任务的最终状态。
