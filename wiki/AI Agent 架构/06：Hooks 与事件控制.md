# Hooks 与事件控制

> [!abstract] Hook 不是额外的日志函数，而是在 Agent 生命周期的关键状态变化处建立“观察、干预与扩展”的控制点。它让运行时能看见发生了什么、在需要时暂停或审批，并在不改核心业务循环的前提下接入监控、策略和通知。

## 先分清三件事

- **事件（Event）：** 某件事已经发生的事实记录或通知，例如“工具已返回”“审批已请求”。
- **Hook：** 注册在某个生命周期点或事件上的处理逻辑，用于观察、拦截或扩展。
- **状态机（State Machine）：** 任务当前状态及其允许迁移的权威来源，决定任务此刻能否继续。

事件负责传播“发生了什么”；Hook 决定在相应时点执行什么附加逻辑；状态机负责裁定“系统现在是什么状态、下一步是否合法”。三者可以协作，但不能互相替代。

## 第一性原理：为什么 Agent 运行时需要事件控制面

Agent 不是一次函数调用，而是持续变化的运行过程：模型推理、工具调用、工具回执、预算变化、错误、暂停、恢复和完成都会发生。若这些变化只埋在核心代码的日志与分支中：

```text
执行过程变化
→ 观察、审批、通知、监控逻辑散落在业务代码中
→ 核心循环与外围需求强耦合
→ 难以实时了解进度，也难以安全地暂停、恢复或扩展
```

Hooks 将状态变化转换为明确事件，并将关注点分离：

```text
运行时状态变化
→ 产生带关联信息的结构化事件
→ 观察者订阅事件以记录、展示、计量或告警
→ 控制 Hook 在关键点提出暂停、取消或审批要求
→ 运行时根据权威状态继续、等待、恢复或停止
```

因此，Hook 的本质是**在不确定的 Agent 执行路径旁边建立控制面**，而不是把所有逻辑都塞入回调。

## 先区分两类 Hook：观察与控制

| 类型 | 目的 | 对主流程的关系 | 典型例子 |
| --- | --- | --- | --- |
| 观察型 | 知道发生了什么 | 默认异步、可降级，不应阻塞主流程 | 日志、前端进度、指标、通知、Token 告警 |
| 控制型 | 改变是否或如何继续 | 必须有明确同步点和状态语义 | 暂停、恢复、取消、人工审批、策略拦截 |

二者不能混用：

- 将每个日志事件同步等待，会让观测系统拖垮 Agent；
- 将审批或取消做成“尽力而为”的异步通知，则关键副作用可能在决定到达前已经发生。

## 事件契约与权威状态

事件至少应能回答：**谁的什么状态，在什么时候发生了什么，相关上下文是什么。**

```text
workflow / task ID
+ agent / tool ID
+ event type
+ timestamp 与序号或因果关联
+ 人类可读说明
+ 结构化 payload
```

事件契约让前端、审计、监控和自动化扩展共享同一语言；但事件流本身不应被当成唯一事实来源：

- 事件可能重复、延迟、丢失或被消费多次；
- 高吞吐事件可能被采样或丢弃；
- 暂停、审批、取消等最终状态必须存入可恢复的权威状态机。

简言之：**事件告诉外部“发生了什么”，状态机决定系统“现在是什么状态、能否继续”。**

## 暂停、恢复、取消与审批

长任务的控制不能依赖轮询。真正的暂停语义应是：

```text
策略或用户提出控制请求
→ 运行时持久化控制状态
→ 目标工作流在安全检查点进入等待
→ 信号传播给相关子工作流
→ 收到恢复、取消或审批决定
→ 按状态机恢复、拒绝或终止
```

人工审批是控制型 Hook 的典型场景：

1. 策略判断当前动作需要人工确认；
2. 运行时记录待审批动作、理由、影响与关联任务；
3. 工作流等待决定，而不是继续执行；
4. 同意、拒绝或超时分别驱动不同状态迁移；
5. 决定与最终动作均可审计。

审批只是额外护栏，不能取代工具执行层的权限校验；即使审批通过，执行层仍应检查当前授权、参数和环境状态。

## 约束与失败表现

- **阻塞式观察 Hook：** 日志、推送或指标系统慢下来，就拖慢核心循环；观察应有队列、超时和降级策略。
- **事件风暴：** 每个 Token 或微小中间状态都持久化，淹没高价值的完成、错误和审批事件，并推高成本。
- **状态与事件不一致：** 只消费事件、不维护权威状态，重启或乱序后无法判断任务真实位置。
- **竞态与信号丢失：** 暂停、恢复和状态检查之间没有明确顺序，或父工作流控制没有传播给子工作流。
- **审批语义不完整：** 没有超时、拒绝、审计和关联任务，导致任务长期悬挂或无法追责。
- **把 Hook 当安全执行：** Hook 可以提出或拦截策略，但底层工具若没有权限与参数强制校验，仍可能被绕过。

## 工程决策

1. **先定义少量高价值事件。** 优先覆盖生命周期、工具调用与回执、错误、预算阈值、审批和最终结果；不要为每个内部细节建立永久事件。
2. **为事件分级并定义投递语义。** 审批、取消、完成、错误通常需要可靠记录；流式输出、细粒度进度可采样、限速或丢弃。
3. **让观察 Hook 非阻塞。** 使用有界队列、批处理和超时；当观察链路不可用时，核心任务应按预定策略继续或安全降级。
4. **让控制 Hook 显式接入状态机。** 暂停、恢复、取消和审批必须有持久化状态、关联 ID、超时和子工作流传播规则。
5. **控制点放在副作用之前。** 对发布、删除、付款、外发等动作，在工具调用前触发策略与审批，而不是事后补救。
6. **用事件改进系统，而非只展示系统。** 将工具错误、重试、预算、人工介入和恢复结果汇总为指标，反向调整 Skill、工具契约和 ReAct 策略。

## 不要把实现示例当成原理

- Callback、事件总线、Redis Streams、持久化工作流信号和脚本 Hook 的实现复杂度不同；稳定原则是“观察逻辑与控制逻辑分离，并以明确状态语义连接运行时”。
- 简单短任务可用内存 Callback；需要长时间运行、可暂停和故障恢复时，应选择具备持久化状态与可靠控制信号的运行时。
- 事件名本身不是架构。关键是每个事件的触发条件、payload、可靠性、幂等处理和与状态机的关系。
