# 从 Agent 闭环到生产系统

> [!abstract] 不把这套笔记当作 45 个概念逐章背诵，而是围绕一个目标学习：让 LLM 在不确定环境中，能够在受限条件下持续行动，并以外部证据证明任务完成。章节是证据和工具；闭环能力才是主线。

## 第一性原理：Agent 的本质是受约束的任务闭环

LLM 只能根据当前输入生成候选输出，不能天然保证动作发生、结果正确、状态连续或成本受控。要完成真实任务，系统必须补齐以下闭环：

```text
目标状态与完成证据
→ 组织当前状态和必要上下文
→ 模型提出下一步候选动作
→ 工具在真实环境中受限执行
→ 读取回执并更新状态
→ 在预算、权限、时间与停止条件内继续、恢复或终止
```

学习优先级由此决定：**先掌握闭环必需条件，再学习复杂模式；先能解释失败，再考虑增加能力。**

## 主线一：最小闭环——让动作可验证

**先学：** [[wiki/AI Agent 架构/01：Agent 的本质|01 Agent 的本质]] → [[wiki/AI Agent 架构/02：ReAct 循环|02 ReAct 循环]] → [[wiki/AI Agent 架构/03：工具与行动边界|03 工具与行动边界]] → [[wiki/AI Agent 架构/10：任务规划与控制|10 任务规划与控制]]。

要掌握的能力不是“让模型多想”，而是为一个任务写清：

- 目标状态是什么；
- 什么外部回执能证明完成；
- 允许哪些动作，谁执行、谁校验；
- 何时继续、重试、转人工或停止。

**学会的标准：** 能把“帮我研究一个主题”改写为有工具、状态、完成证据和停止条件的最小 Agent，而不是只写一段 Prompt。

## 主线二：决策工作集——让系统在正确时刻看到正确信息

**再学：** [[wiki/AI Agent 架构/07：上下文工程|07 上下文工程]] → [[wiki/AI Agent 架构/08：记忆架构|08 记忆架构]] → [[wiki/AI Agent 架构/09：多轮对话与会话状态|09 会话状态]] → [[wiki/AI Agent 架构/35：上下文压缩的多层防线|35 上下文压缩]] → [[wiki/AI Agent 架构/36：Tool Result 外溢与上下文预算|36 Tool Result 外溢]] → [[wiki/AI Agent 架构/37：分层压缩与相关性衰减|37 分层压缩]]。

核心判断：

```text
当前这一步决策需要什么证据？
→ 应放入 Prompt、保存在 Session、写成 Memory，还是外置后按需取回？
```

**学会的标准：** 能解释某条信息为何必须保留、何时过期、超预算时应删除、压缩还是外溢；不再把历史聊天、长期记忆和检索结果混为一谈。

## 主线三：运行时可靠性——让失败可见、可控、可恢复

**重点学：** [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|22 可观测性]] → [[wiki/AI Agent 架构/23：Token 预算与成本护栏|23 Token 预算]] → [[wiki/AI Agent 架构/34：DAG 与 Agent Loop 的控制流边界|34 DAG 与 Agent Loop]] → [[wiki/AI Agent 架构/40：可恢复 Agent Turn 与安全续跑|40 持久化续跑]] → [[wiki/AI Agent 架构/42：Agent 超时的阶段所有权|42 超时]] → [[wiki/AI Agent 架构/43：卡循环的证据与止损|43 卡循环]] → [[wiki/AI Agent 架构/44：并行工具的调用级安全|44 并行工具]]。

这里的因果链是：

```text
模型与工具都会失败
→ 必须知道失败发生在哪一阶段
→ 必须限制重试、时间、并发与成本
→ 中断后只在仍安全、仍有效时恢复
→ 所有结果都能被定位、解释和复盘
```

**学会的标准：** 面对“任务卡住、重复调用、花费异常、进程崩溃、并发冲突”，能指出应由哪个状态、指标或控制器处理，而不是只提高 `max_iterations`。

## 主线四：治理与副作用——让系统有能力但不越界

**必须并行学习：** [[wiki/AI Agent 架构/24：策略治理与授权决策|24 策略治理]] → [[wiki/AI Agent 架构/25：安全执行与能力沙箱|25 安全执行]]；涉及界面操作时学习 [[wiki/AI Agent 架构/28：Computer Use 受控界面操作|28 Computer Use]] 与 [[wiki/AI Agent 架构/45：Computer Use 的多生命周期上下文|45 Computer Use 上下文]]。

```text
模型可能判断错误
→ 错误可能成为真实外部副作用
→ Policy 决定是否允许
→ Sandbox 限制实际能力
→ 审批、预算、审计与回执控制后果
```

**学会的标准：** 能区分“模型说可以”“策略允许”“运行时做得到”“业务已完成”这四件不同的事。

## 按需扩展，而非线性深挖

以下主题只在最小闭环已遇到明确瓶颈时重点学习：

| 真实瓶颈 | 再进入的主题 |
| --- | --- |
| 已知依赖很多，需要确定性调度 | [[wiki/AI Agent 架构/14：DAG 依赖调度|DAG]]、[[wiki/AI Agent 架构/21：Temporal 持久化工作流|Temporal]] |
| 角色、权限、上下文或专长确实不同 | [[wiki/AI Agent 架构/13：多 Agent 编排与协调|多 Agent]]、[[wiki/AI Agent 架构/16：Agent Handoff 与数据交接|Handoff]] |
| 早期选择高度不确定，且错误代价高 | [[wiki/AI Agent 架构/17：Tree-of-Thoughts 多路径搜索|ToT]]、[[wiki/AI Agent 架构/18：Debate 多视角对抗与综合|Debate]] |
| 任务本身是研究、浏览器操作、编码或后台任务 | [[wiki/AI Agent 架构/27：Deep Research 证据驱动研究|Deep Research]]、[[wiki/AI Agent 架构/28：Computer Use 受控界面操作|Computer Use]]、[[wiki/AI Agent 架构/29：Agentic Coding 受控代码变更|Agentic Coding]]、[[wiki/AI Agent 架构/30：Background Agents 持久化后台任务|Background Agents]] |

**不要因为名称更复杂就升级。** 多 Agent、ToT、Debate 和长期工作流都是用额外成本交换特定控制收益；若不能说明它修复哪一种已观察失败，就暂不引入。

## 推荐学习顺序

```text
01 → 02 → 03 → 07 → 10
→ 22 → 23 → 24 → 25
→ 34 → 40 → 42 → 43 → 44
→ 按项目需要选择多 Agent、研究、Computer Use、Coding 或后台任务
```

第 8、9、35、36、37 是第二主线的关键补充，应在第一次遇到上下文遗漏、长会话、工具结果过大或历史污染时回看；它们不是“以后再学”，而是从最小 Agent 变成可持续 Agent 的必经环节。

## 复习

1. 为什么“模型生成了答案”不能证明“任务已完成”？
2. 一项新能力加入 Agent 前，应先证明最小闭环在哪个环节失败？
3. 为什么多 Agent、Planning 和 Reflection 都应由具体缺口触发，而非默认启用？
