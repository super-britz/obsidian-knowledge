# 延迟加载与工具发现

> [!abstract] 工具过多真正消耗的是完整 Schema 目录的 token，而不是工具条目数。延迟加载将冷工具的 Schema 从默认 Prompt 移出，按需通过工具发现取回；但必须保留开场高频能力、以 Schema 内容维护 Session 工作集，并始终把“模型是否看见工具”与“运行时是否允许执行”分开。

## 第一性原理：模型不需要每轮阅读整本能力目录

每轮请求携带的工具定义会反复消耗上下文、成本和注意力。工具数量无法代表负担：简单读取工具的 Schema 很小，带嵌套对象、枚举和复杂选项的自动化工具可能单独占据大量 token。因此应对**实际序列化后的 Schema token**建立预算，而不是设“超过 N 个工具就延迟”的数量阈值。

```text
完整可用工具集
→ 估算 Schema token 成本
→ 常驻 Warm Set + 必须常驻工具
→ 冷工具 Schema 延迟
→ 模型通过描述性目录和 tool_search 发现所需能力
→ 取回 Schema 后加入本 Session 的 Warm Set
```

这不是缩减运行时能力，而是将模型的默认认知负担从“记住全部目录”改为“先发现，再精确使用”。预算估算宁可保守，低估 Schema 体量会让本应保护上下文的机制失效。

## 延迟条件：预算超限之外，还有高成本低频类别

只有总预算超限才延迟，会遗漏一类持续浪费：某些工具虽然没有把总量推过阈值，却在特定任务中几乎从不使用，例如平台专属 GUI、调度或后台控制能力。它们适合被列为**类别性冷工具**，以减少每个新 Session 的默认 Schema 负担；真正需要时再付一次发现往返。

但延迟的目标不是最大化藏起的 token，而是最小化**用户可感知的总成本**。必须结合以下因素判断：

- 冷启动时该工具是否常被第一步使用；
- 首次检索的额外轮次是否直接延迟用户第一条回复；
- 工具常驻时是否位于稳定、可缓存的 Prompt 前缀；
- 工具名称和目录描述是否足以让模型主动搜索到它。

常驻在缓存稳定前缀中的大 Schema，其增量成本会被多轮会话摊薄；反之，被错误延迟的开场工具会在每个新会话收取一次明显的交互延迟税。

## Never-defer：高频开场路径比目录体积更重要

有些能力即使 Schema 很大也应常驻：开场就经常调用的工具、无法依赖其他目录发现的关键能力、以及某些隐式路径失败后的可靠兜底。若模型尚未拿到 Schema 就尝试猜测参数，会导致无效工具调用或额外的一轮补救；这比常驻少量 Schema 更贵。

因此分类不能从工具的“危险性”或“体积”直接推出，而要从会话的真实调用时刻和冷启动日志中得到。每个工具至少要评估：首用分布、冷启动命中率、搜索成功率、Schema token 成本和常驻缓存摊薄后的实际费用。

## Warm Set：按内容缓存能力，而不是按名称记忆

工具 Schema 被检索后应加入 Session 级 Warm Set，使后续轮次无需再次搜索。Warm Set 不应跨 Session 假定已热：每个新 Session 都要从冷集合开始，产品体验的关键往往正发生在第一次请求。

更重要的是，Warm Set 的有效性取决于 Schema **内容**而不是工具名。MCP Server 升级后，同名工具的参数、枚举或语义可能改变；若仍按名称复用旧定义，模型会构造畸形调用，甚至触发语义不同的操作。以工具集或 Schema 内容指纹作为 key，才能在定义变化时自动失效并重新发现。

## 发现与授权：优化可见性，不替代执行边界

Deferred Loading 只影响模型当前看到哪些 Schema。模型仍可能从工具目录、Skill、历史或猜测中知道某个工具名，并尝试调用它；因此“没有放进 Prompt”绝不是拒绝执行的安全边界。

```text
工具发现层：目录、tool_search、Warm Set → 解决模型如何找到能力
执行授权层：策略、参数、工作区、审批、审计 → 决定该调用能否发生
```

将两者分开还能保持工具数组和缓存前缀稳定：检索策略可以变化，授权仍在执行时对每次调用强制判断。[[wiki/AI Agent 架构/25：安全执行与能力沙箱|安全执行]]与[[wiki/AI Agent 架构/24：策略治理与授权决策|策略治理]]才是危险能力的真正防线。

## 工程决策

1. 将所有可用工具序列化为紧凑 Schema，按保守 token 比率建立预算；用真实 token/延迟监控校准，不按工具数量切换模式。
2. 同时定义预算触发和类别触发：将昂贵、低频、任务特定的工具设为冷集合，但根据冷启动日志维护 never-defer 的开场工具清单。
3. 为工具发现目录提供描述性的名称、用途和检索词；如果模型无法提出有效查询，延迟只会变成能力不可见。
4. 以 Session 为单位维护 Warm Set，并用 Schema/工具集内容指纹失效；Server 更新、工具范围变化或策略变化后重新构建。
5. 对每种工具跟踪冷启动首用时间、搜索次数、搜索失败、Schema token、缓存命中、首次响应延迟和实际调用率，以验证延迟收益。
6. 将延迟加载严格定位为 Prompt 与检索优化；每个工具调用仍由运行时权限、参数约束、审批和审计独立决定。

## 常见误解

- **“工具超过某个数量就应该延迟。”** 数量忽略 Schema 体量的数量级差异；应预算真实 token 成本。
- **“延迟越多，成本一定越低。”** 被延迟的开场工具会把搜索往返加到第一条回复；缓存前缀中的常驻 Schema 也可能更便宜。
- **“Warm Set 缓存工具名就够了。”** 同名工具的 Schema 会变化，必须按内容指纹失效，否则模型会用旧参数调用新工具。
- **“不把危险工具 Schema 给模型就是权限控制。”** 模型仍可能猜到或检索到工具名；真正的拒绝必须发生在执行时。

## 复习

- 为什么 Schema token 比工具数量更适合做预算？——Schema 的复杂度差异巨大，数量相同的工具集可能有数量级不同的 Prompt 成本。
- 为什么有些大 Schema 仍要常驻？——若它们处于高频开场路径，检索延迟会直接伤害每个新 Session 的首次体验；缓存还能摊薄常驻成本。
- 为什么发现与授权必须分开？——发现解决模型怎么找到工具，授权解决调用能否执行；将两者混用会同时损害可用性与安全性。
