# 卡循环的证据与止损

> [!abstract] 卡循环检测不是阻止 Agent 犯第一次错，而是在它已有重复、无进展或同类失败的证据后，限制尾部浪费并促使换路。可靠做法是聚合多种循环形状，按证据分级为继续、提醒和停止；但第一道防线始终是会如实拒绝危险输入的工具契约。

## 第一性原理：探测器只能约束重复，不能挽回第一次伤害

一次 `file_write` 因缺失必填内容而把零值空字符串写入文件，却报告成功；Agent 发现目标仍未达到后再次调用。重复探测在后续相同调用时能够触发，但文件在第一次副作用时已经被截断。

```text
工具输入/结果
→ 累积重复或无进展证据
→ Continue / Nudge / ForceStop
→ 减少继续重复的成本
```

因此检测解决的是“同一种错误还要做几遍”，不是“第一次操作是否安全”。不做事却报成功、参数缺失、越权或不可逆副作用，必须由 [[wiki/AI Agent 架构/03：工具与行动边界|工具契约]]、校验和权限边界在调用前阻止。

## 多证据而非单规则：无进展有不同形状

相同调用连续出现、在“读→改→读”中分散复现、同工具反复报同类错误、相关工具围绕一个主题打转、连续搜索无结果，都可能表示卡住；但也可能是正当批处理、恢复或重试。单一“重复调用”规则必然在误报与漏报之间失衡。

所以探测器应是证据聚合：每条路径为一种可观察的无进展定义服务，按明确顺序裁决。名单不是固定资产，而是事故、回归测试和误报共同塑造的经验模型；一个无人能解释其失效模式、且误报多于命中的探测器，应在证明被其他信号覆盖后删除。

## 分级裁决：给失败留余地，但让提醒必须升级

- **Continue：** 证据不足，允许正常工作继续。
- **Nudge：** 向模型注入“可能重复”的信号，给一次改变策略的机会。
- **ForceStop：** 注入停止信息后再进行一次**不带工具**的总结调用，向用户说明进展、阻塞点和终止原因。

Nudge 若能无限发生，就只是日志；应在滚动窗口内升级为 ForceStop。阈值也不应把失败和成功同等对待：重复失败常是网络重试或逐步恢复，重复成功更可能是白做或工具谎报。刚从错误恢复到成功时，也不应立即以重复处罚它。

## 让错误可读：检测的上游是工具验证与类型化结果

卡循环策略只能观察工具层报告出来的事实。工具在任何系统调用、子进程、GUI 或外部服务之前，应拒绝所有声明为必填却缺失的字段；不能让零值悄悄变成“成功但破坏性”的操作。覆盖整个工具注册表的契约测试，能把这条要求从个别修复变成系统约束。

共享、类型化的校验错误也让检测器能识别“同工具、同参数、连续校验失败”并更早停止，而不是等待宽松的通用错误预算。类型化不是为了文本好看，而是向控制层提供可判定证据。

## 工程决策

1. 把循环检测定位为第二道止损：先为有副作用的工具设置必填字段校验、权限、幂等和可验证结果，再处理重复尾部。
2. 为不同无进展形状建立独立、可解释的探测路径；记录命中、误报、漏报和覆盖关系，不以探测器数量衡量成熟度。
3. 使用 `Continue → Nudge → ForceStop` 分级策略，并限制 Nudge 的次数；ForceStop 保留一次无工具总结，避免用户只看到被砍断的运行。
4. 为成功重复和错误重试设置不同预算；豁免应足够窄，并通过代表性批处理、恢复与失败重试测试验证。
5. 将校验错误、工具结果和停止原因类型化，连同摘要写入 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]]，以事故证据驱动阈值调整、增加或删除探测器。

## 常见误解

- **“重复调用一律是循环。”** 重复可能是正当批处理、恢复或失败重试；关键是重复是否持续缺少新证据或产出。
- **“把阈值调低就能防止第一次破坏。”** 任何重复探测都需要至少两个数据点；第一道防线必须在工具副作用之前。
- **“Nudge 已经解决问题。”** 不升级的提醒可以被无限忽略，不能真正限制尾部消耗。
- **“探测器越多越安全。”** 无事故依据或误报过多的规则会训练团队忽略告警；应证明删除后仍有覆盖。

## 复习

- 为什么循环检测不能替代工具校验？——检测只能在重复证据出现后行动，第一次错误副作用已经发生。
- 为什么错误预算通常比成功重复更宽？——重试失败常是恢复路径，而相同成功的再次执行很少带来新进展。
- ForceStop 为什么还要一次无工具总结？——停止应向用户解释已完成、卡在何处和为何结束，而不是留下无上下文的中断。
