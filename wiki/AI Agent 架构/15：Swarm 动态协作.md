# Swarm 动态协作

> [!abstract] Swarm 用“协调者的事件循环 + 多个自主 Worker”处理运行中才出现的新发现、任务和人类反馈。它比静态 DAG 更灵活，但也更难收敛、验证和控制成本；中心协调不是削弱自治，而是为自治划定共同目标、资源边界和停止条件。

## 第一性原理

[[wiki/AI Agent 架构/14：DAG 依赖调度|DAG]]假设任务和依赖能在开始前画清。若执行中发现重要线索、某项工作失败、用户改变重点或 Worker 需要互相请求帮助，静态图会变成约束。此时需要按运行时事件重新分配工作。

```text
目标 + 当前计划 + 团队状态 + 用户输入
→ Lead 根据事件决定创建、分配、复用、取消或停止任务
→ Worker 在权限与预算内独立执行 ReAct
→ 产物、消息、状态与验证结果回到协作面
→ Lead 更新全局计划，直到验收、降级或终止
```

动态分工的代价是局部最优会相互冲突：多个 Worker 可能重复探索、写入冲突、追逐同一错误假设或无限等待。因此 Swarm 的核心不在“群体涌现”，而在**用显式协调维持全局收敛**。

## Lead 与 Worker 的分工

| 角色 | 应负责什么 | 不应负责什么 |
| --- | --- | --- |
| **Lead** | 规划、资源分配、状态汇总、质量门、任务重分配、停止与向用户汇报 | 代替所有 Worker 执行细节，或每一步都用 LLM 反复微观管理 |
| **Worker** | 在明确任务、最小权限和预算内观察、行动、产出、报告 idle / 失败 | 擅自扩大目标、无限派生任务或把局部猜测当作全局结论 |

Lead 应由 `idle`、任务完成/失败、定期 checkpoint、预算临界和人类输入等事件驱动，而非高频轮询。Worker 完成当前任务后进入 idle，可被复用；但复用前仍须重新授予任务范围、输入、权限、预算和验收条件。

## 协作状态与通信

协作至少需要两类通道：

- **Workspace：** 面向团队的共享产物与公开发现，适合可复用、可能影响多个任务的信息。
- **P2P 消息：** 面向明确接收者的请求、委派、澄清和通知，避免把所有沟通广播给全体。

两者都不是权威业务数据库。共享内容应有作者、时间、任务 ID、来源、版本、可见范围和保留期；外部输入进入 Workspace 前须隔离与校验。否则“共享上下文”会迅速变成噪声、过期信息或跨任务污染，反而降低 [[wiki/AI Agent 架构/07：上下文工程|上下文工程]]的信号质量。

## 收敛、验证与人机协作

Worker 报告完成只能说明它停止执行，不说明产物合格。Lead 应优先用低成本、确定性的检查（文件是否存在、结构是否完整、测试/解析是否通过、来源是否齐全）筛掉明显缺陷；高风险结论再进入外部验证或人工审批。

收敛条件要同时覆盖局部和全局：单个 Worker 的无进展迭代、反复错误和预算耗尽应触发 idle 或停止；所有 Worker idle 且没有待办，并不自动代表用户目标完成，仍须检查全局验收项和未决风险。

人类输入应成为一等事件：可以改变优先级、补充约束、要求中间交付或取消工作。但人类指令也应经过身份、权限和影响范围检查，并记录是谁在何时改变了什么计划；“可实时干预”不等于绕过安全边界。

## 工程决策

- **从 DAG 开始，按证据升级。** 只有任务会动态生成、跨 Agent 协作频繁或需要运行中人类反馈时，才承担 Swarm 的协调成本。
- **限制自治的扩张面。** 为最大 Worker 数、任务派生深度、并发、总 Token、每任务超时和总运行时间设置硬上限。
- **将质量门放在汇合处。** 任务完成、任务复用、外部写入和最终交付前分别执行适当验证；不要只依赖 Lead 或 Worker 的自我报告。
- **持久化协作事件。** 记录计划版本、任务委派、消息、Workspace 产物、状态变迁、预算和人工干预，才可恢复、审计和复盘。

## 常见误解

- **Swarm 就是完全去中心化：** 动态协作仍需要全局目标、验证和停止权；否则强耦合任务容易互相干扰。
- **Agent 越多越聪明：** Agent 数量会同时放大重复工作、通信、上下文和验证成本。
- **共享 Workspace 等于共享真相：** 它只是一层协作介质，内容仍可能错误、过期或越权。
