# 本地 Agent Harness 与用户控制面

> [!abstract] 本地 Agent 能接触真实文件、终端、已登录账号和桌面界面，因此它的价值与风险来自同一件事：真实执行能力。可靠的 Harness 不能只让模型“会调用工具”，而要把每次工具调用编排为可准入、可并行、可审计、可中止的受控副作用。

## 第一性原理：本地执行拥有真实权限，错误不能靠重启容器抹掉

云端沙箱通常可以销毁重来；本地 Agent 面对的是用户真实工作区、凭据、内网和 GUI 状态。模型的误解、网页提示注入或重复尝试都可能立即成为删除文件、泄露数据、错误提交或越权访问。因而，本地执行的难点不是获得工具，而是把工具能力从“模型能提出”变为“运行时确认后才可发生”。

```text
任务与当前本地状态
→ 模型提出工具意图
→ 串行检查去重、能力、策略、审批与用户 Hook
→ 对已批准且互不冲突的操作并行执行
→ 串行记录结果、审计、检测无进展并更新上下文
→ 继续、要求人介入，或在边界处停止
```

本地 Agent Harness 的本质是**把高权限工具调用转化为用户可控制的执行生命周期**，而不是一个不断调用 LLM 的 `for` 循环。

## 三阶段 Harness：安全、效率与一致性不能由同一并发策略兼顾

每轮工具调用需要分离三个阶段：

- **串行准入：** 对每个调用进行去重、跨轮缓存失效判断、权限与路径/网络边界检查、用户审批和 Pre-hook；任何拒绝都应带原因返回给模型，而不是悄悄忽略。
- **并行执行：** 只有已获准且资源不冲突的调用才能并发；共享文件、同一 GUI 会话、依赖前一步输出或不可幂等外部操作仍应串行或显式加锁。
- **串行收尾：** 依次运行 Post-hook、记录审计、处理缓存/写入失效、评估循环信号，并把真实工具回执追加给下一轮。

这种分工与 [[wiki/AI Agent 架构/03：工具与行动边界|工具与行动边界]] 的原则一致：模型提供意图，执行器负责验证、执行和返回事实。它也是 [[wiki/AI Agent 架构/02：ReAct 循环|ReAct]] 在本地副作用环境中的具体运行时实现。

## 工具层：优先语义契约，坐标与视觉只作兜底

操作 GUI 时，应优先使用 Accessibility Tree、DOM 或其他语义 API：先观察应用/元素树，取得短生命周期引用，再针对引用执行点击、输入或读取。语义操作不依赖窗口位置、分辨率和缩放，也更容易审计“点的是哪个元素”。引用失效、界面变化或应用未暴露语义时，必须重新观察，不应把旧引用当作永久 ID。

坐标点击、键盘模拟和截图理解覆盖面更广，却受 DPI、焦点、弹窗、异步加载和视觉误判影响。它们应遵循 [[wiki/AI Agent 架构/28：Computer Use 受控界面操作|Computer Use]] 的闭环：明确目标和预期状态 → 执行最小动作 → 等待稳定 → 用 UI 状态或业务回执验证。浏览器使用独立 Profile 可隔离 Cookie 与历史，但不替代域名白名单、账号最小权限或敏感数据最小化传输。

## 控制面：权限、Hooks 与人工审批各有不可替代的职责

权限引擎应成为所有工具调用的必经路径：不可覆盖的硬封锁先拒绝明显灾难性操作；再检查配置拒绝规则、拆解复合 Shell 命令、处理显式自动允许，最后才进入用户审批。复合命令、重定向、命令替换和符号链接会改变真实含义，不能只用字符串前缀判断安全。文件、网络、浏览器等工具还需要各自的路径、域名、凭据和会话边界。

[[wiki/AI Agent 架构/24：策略治理与授权决策|策略]]回答“此时是否允许”，[[wiki/AI Agent 架构/25：安全执行与能力沙箱|执行边界]]限制“获准操作最多能接触什么”，人工审批处理“用户是否接受这次高后果副作用”。三者缺一不可。

Hooks 是用户的可编程控制面：在会话开始/结束、工具前/后注入组织规则、记录或拒绝逻辑，无须修改 Harness 本身。尤其是 Pre-hook 的拒绝，应通过受限协议把原因反馈给模型，让它调整计划。Hook 也必须最小权限：固定可信路径、禁止不受控 PATH 解析、限制运行时间与输出、记录版本和执行结果；否则它会变成新的隐蔽高权限通道。

## 收敛与上下文：长期自主不等于无限尝试

本地任务的上下文会增长、目标会漂移、调用会重复。Harness 应保留原始任务、最近回合和经验证摘要，并为下一轮工具结果预留容量；摘要失败要有重试/降级上限，不能为了压缩而无限调用模型。进度检查点可提示模型重新核对目标、已完成步骤和下一步，但不能代替真实工具回执。

循环检测要同时观察相同调用及参数的连续/窗口重复、重复失败、无状态变化、无效搜索与长时间空闲等信号。单一规则容易误伤正常重试，因此处理应分级：先 Nudge 提供新证据或换路建议，持续无进展才 ForceStop 并保留审计。优雅失败比无限重试更可靠；耗时、循环、Hook 拒绝和工具结果应接入 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]]。

## 本地与云端：执行位置和推理位置应分别治理

本地工具执行保留了对用户环境的控制；远程 LLM 推理则可能接收文件片段、命令输出和截图。两者分离有助于替换模型与限制数据发送面，但“工具留在本地”不等于数据不离开机器：必须明确哪些内容可发送、如何脱敏、采用哪家模型服务以及网络失败时如何降级。远程调用的模型选择、价格与失败切换可复用 [[wiki/AI Agent 架构/31：分层模型路由与韧性|模型路由]]，但不能绕过本地工具的权限与审批链。

## 工程决策

1. 将 Harness 设计为串行准入、受冲突约束的并行执行、串行收尾；将实际工具执行与模型文本彻底分离，拒绝“文本声称已完成”作为证据。
2. 为每种工具定义能力契约：可读写路径、网络域名、账号/Profile、最大输出、超时、并发性和副作用等级；默认拒绝，按需显式授权。
3. GUI 优先采用 Accessibility/DOM 等语义引用；坐标操作只作兜底，并要求重新观察和结果验证。独立浏览器 Profile 只做会话隔离，不赋予额外访问权限。
4. 建立不可覆盖硬封锁、复合命令解析、工具专项检查和人工审批；所有 Hook 同样纳入受限路径、版本、超时、输出与审计治理。
5. 为上下文压缩、工具重试、网络退避和循环检测分别设定上限与停止行为；未收敛时保留当前状态，要求用户或人工接手。
6. 记录调用意图、批准/拒绝原因、Hook 结果、实际参数、输出摘要、UI/文件状态、循环信号和最终结果；将高风险操作设计成可预览、可中断、可回退。

## 常见误解

- **“本地运行就天然更私密。”** 工具本地执行不代表上下文不会发送给远程模型；数据传输范围仍需明确控制。
- **“坐标点击能够操作一切，因此足够通用。”** 通用性换来脆弱性；有语义 API 时应优先语义引用，坐标必须验证。
- **“有用户审批就不需要策略。”** 审批无法覆盖高频低风险检查，也不能替代不可配置的硬封锁与专项边界。
- **“循环检测就是限制最大迭代数。”** 最大迭代只是最终刹车；互补信号能更早识别重复、无进展和卡死，并给模型纠正机会。

## 复习

- 为什么准入和收尾要串行、执行可并行？——准入需要一致的安全决策，收尾需要确定的审计与状态更新；无冲突执行才适合并发提升效率。
- 为什么 Hook 是用户控制面而不是给模型的能力？——它把组织规则注入必经事件点，并可阻止或记录执行，而不扩大模型自身权限。
- 为什么本地 Agent 要比云端 Agent 更强调停止机制？——它直接作用于不可轻易重置的用户环境；无限或错误尝试的累积后果更大。
