# 工具与行动边界

> [!abstract] 工具不是给 LLM 增加“外挂知识”，而是把语言模型提出的意图转换为受约束的外部能力调用。模型只能请求调用；程序必须校验、授权、执行、限流并返回可判断的事实结果。

## 第一性原理：为什么“会说”不等于“能做”

LLM 的输出是基于已有上下文的文本或结构化 Token。它不能自行取得今天的利率、读取私有文件、进行可靠计算或改变外部系统状态。即使模型能说出正确的行动步骤，也不代表行动已经发生。

工具补上的不是“答案”，而是与真实环境交互的能力：

```text
任务目标
→ LLM 根据可见工具提出调用意图
→ 结构化请求：工具名 + 参数
→ 执行侧校验参数、权限、预算与策略
→ 在超时、限流与隔离边界内执行
→ 返回结构化事实结果
→ ReAct 根据结果判断下一步或验收完成
```

因此，**Function Calling 不是 Function Execution**：

- 模型负责选择并提出请求；
- 工具契约告诉模型“能做什么、何时做、怎样填参数”；
- 执行层拥有实际副作用的控制权；
- `ToolResult` 为后续决策提供事实，而不是模型自述。

## 工具契约：语言意图与确定性程序之间的边界

工具定义本质上是一份面向两个对象的契约：模型据此选择和填参，程序据此验证和执行。

| 契约部分 | 回答的问题 | 缺失或模糊时的失败 |
| --- | --- | --- |
| 名称、用途与 description | 什么时候该用这个工具，什么时候不该用 | 选错工具，或根本不调用 |
| 参数类型、必填项、枚举、范围与示例 | 参数应怎样表达 | 字符串/数字错位、参数缺失、越界输入 |
| 权限、危险标记、沙箱与成本 | 谁能用、能做多大副作用、付出什么代价 | 越权、不可逆操作、成本失控 |
| 超时与限流 | 多久失败、调用频率上限 | 工具卡死、重复重试、额度耗尽 |
| 结构化结果与错误 | 这次调用发生了什么 | 模型无法区分成功、失败、部分成功与应否重试 |

`description` 不是给开发者看的备注，而是模型决策时的接口说明。好的 description 需要写清：适用场景、输入格式、约束和示例；若人类读者也无法据此填参，模型通常也无法稳定填对。

## 执行侧必须把模型输出视为不可信输入

模型输出 JSON 或符合 Schema，并不表示请求已经安全、合法或可执行。执行侧仍需要：

1. **解析与类型容错：** 将可接受的数字字符串、布尔字符串等规范化；
2. **确定性校验：** 验证必填项、枚举、长度、范围与业务前置条件；
3. **策略与权限判断：** 判断当前会话、用户和任务是否允许使用该能力；
4. **受限执行：** 应用超时、限流、资源限制和必要的沙箱；
5. **结构化回执：** 返回成功状态、输出、错误、耗时与可用于重试的元数据。

这条链路的因果关系是：**模型越能自主选择行动，执行层越不能把它的输出直接当作可信命令。**

## 工具数量也是决策成本

工具越多，不代表 Agent 越强。模型需要在每轮判断“该不该调用、调用哪一个、参数怎样填”；功能重复或无关工具会增加选择空间，降低选择质量。

因此，工具注册表的职责不只是发现工具，更应在任务开始前按以下条件缩小能力集：

```text
任务类型 → 必需类别
风险等级 → 排除危险能力或要求审批
成本预算 → 排除超预算能力
当前状态 → 仅暴露此刻可执行的工具
```

这是一种最小能力原则：给模型完成当前步骤所需的最小工具集，而不是全部系统权限。

## 约束与失败表现

- **description 或参数说明模糊：** 模型选错工具、填错参数；问题不应只通过更长 Prompt 修补。
- **只信任 Schema、不做服务端校验：** 格式看似正确但业务非法，或危险参数被执行。
- **没有失败结果协议：** 网络错误、参数错误和部分成功都变成“异常”，ReAct 无法决定重试、换工具还是停止。
- **没有超时、限流与成本控制：** 一次工具卡死或重复调用可拖垮整个 Agent 并耗尽额度。
- **暴露过多、重复或高风险工具：** 选择质量下降，权限与副作用边界被放大。
- **把调用成功当成任务成功：** API 返回成功不等于得到正确数据、更不等于用户目标已经实现。

## 工程决策

1. **先写“何时不该调用”，再写“能做什么”。** 将适用条件、禁止条件和风险写入 description、策略与审批流程。
2. **为每个工具定义最小、具体、可校验的参数。** 用类型、枚举、范围和示例减少模型与程序之间的解释空间。
3. **统一返回结果协议。** 至少区分成功、失败与错误原因，并记录耗时、可重试性和必要的外部证据。
4. **按任务动态过滤工具集。** 在当前任务只暴露相关能力；默认排除危险、高成本或无关工具。
5. **在执行层实施硬边界。** 超时、限流、认证、成本上限、输入校验和安全执行不能仅依赖 Prompt。
6. **把工具回执接回 ReAct 的完成判定。** 关键动作之后要检查外部状态，而不是让模型凭调用记录宣布完成。

## 不要把实现示例当成原理

- JSON Schema、装饰器、类继承和不同厂商的 Tool Use API 都是工具契约的不同语法；稳定原则是“结构化意图 → 受控执行 → 结构化回执”。
- Shannon 中的 `dangerous`、`rate_limit`、`timeout_seconds` 等字段，是把风险、资源和授权边界显式写进接口的示例；具体字段应随业务调整。
- 直接执行用户输入或模型生成的代码不是工具调用的必要条件；若确有需求，必须使用专门的受限执行环境，而不是将文本交给通用 `eval` 或 shell。

## 复习

1. 为什么模型输出一个合法的工具调用 JSON，仍不能直接执行？
2. 为什么工具 description 和参数说明属于系统行为的一部分，而不只是文档？
3. 如何证明工具调用成功之后，用户任务也已经完成？
