# 术语与系统边界

> [!abstract] 术语的价值不在于背定义，而在于避免把不同层次的东西当成同一种机制：模型决策不等于外部执行，当前工作集不等于可持久记忆，能力发现不等于授权，策略判断不等于沙箱隔离。查词时先定位它改变了哪一条系统边界。

## 第一性原理：用“谁拥有状态与副作用”区分概念

相近术语经常描述同一任务的不同层：有的描述模型如何决定，有的描述程序如何执行，有的描述信息如何保存，有的描述谁能授权。若只记字面定义，系统设计容易把责任交给错误的组件。

```text
目标与输入
→ 决策：谁提出下一步？
→ 能力：谁能执行动作？
→ 状态：什么被带入、保存和取回？
→ 控制：谁允许、限制、审计和恢复？
```

因此，术语解释应至少回答：它管理什么状态或副作用、由谁拥有、不能替代什么。

## 查术语时的最小问题集

面对陌生术语，不必先扩展完整定义，按以下顺序定位：

1. **它处理的是决策、执行、状态还是治理？**
2. **它新引入了什么可变状态或外部副作用？**
3. **它的所有者是谁：模型、运行时、工具、存储还是策略系统？**
4. **它依赖什么前提，失败时由谁给出回执？**
5. **它最常被错误地当作什么？**

若答不出第 2～4 项，这个词通常还不足以支持工程选型，应跳回关联的正式概念页。

## 工程决策

1. **只为易混淆且会改变架构责任的术语保留索引项。** 其余定义以原书术语表和正式概念页为准，避免维护第二套百科。
2. **在接口与 ADR 中写明边界，而非只写名词。** 例如写“Policy 决定是否授权，Sandbox 负责强制限制”，比写“启用安全机制”可测试得多。
3. **把时效内容留在来源层。** 框架名称、实现示例和具体配置会变；正式笔记只沉淀可迁移的责任划分和因果链。

## 常见误解

- **“Context 就是 Memory。”** Context 是本轮可见的工作集，Memory 是跨轮保存与取回的系统；两者有不同预算、隐私和过期策略。
- **“MCP 让工具安全。”** MCP 解决互操作；授权、输入验证、审批和沙箱仍需独立实现。
- **“有 Policy 就不需要 Sandbox。”** Policy 是决策层，Sandbox 才负责限制已执行代码的真实能力。

## 复习

1. 为什么 Tool、Skill 和 MCP 分别属于不同的系统层？
2. 为什么把聊天记录当作 Memory 容易制造隐私、成本和事实问题？
3. 在一次危险工具调用中，Policy、Guardrail 与 Sandbox 各负责什么？
