# 运行中操控与可靠交付

> [!abstract] 运行中的追问不是一条普通新消息，而是跨越活动并发边界的一次所有权转移。要让它既不丢失、也不并发双写或错投回复，必须把“被接收、被写入当前轮次、回复已送达”拆成独立状态，在下一次决策前提交，并用原子路由边界和交付后确认闭合竞态。

## 第一性原理：一条追问必须始终有且只有一个归宿

用户在 Agent 即将结束时追加要求，立刻启动第二个 Loop 会并发修改同一工作区；让当前 Loop 直接返回又会让已被 API 接收的追问无人处理。即使返回前看一次队列，也无法覆盖“检查后、路由撤销前到达”的竞态。

可靠操控的目标不是“尽快把文本塞进 Prompt”，而是让消息在每一时刻都有唯一所有者、每个逻辑轮次都有正确回复地址：

```text
入站消息
→ accepted：路由器转交给活动运行的邮箱
→ committed：迭代边界写入真实用户轮次
→ completed：对应回复成功送达后确认
```

三者不可合并。`accepted` 只说明运行接管了消息；`committed` 才说明文本已有对话转录这一持久归宿；`completed` 才说明用户确实收到答案。每条箭头都可能失败，因此每个状态都要有明确所有者与可恢复记录。

## 在决策边界提交：让新指令影响下一次行动，而不改写已选动作

当前 Run 应拥有自己的邮箱，并在每轮迭代开头非阻塞排空：过滤已撤回消息，将其合成一个真实用户 Turn，更新对话转录、`latestUserText` 等旁路状态，再请求下一次模型决策。

迭代边界同时满足两个条件：前一动作的结果已知，下一动作尚未选择。工具执行中途提交追问，会让上下文与已选动作不一致；等模型再答完才处理，又可能按旧指令多做一次昂贵或破坏性调用。多条消息能否合并不是实现偶然，而是产品策略；一旦合并，就必须规定答案归属和确认规则。

## 原子关闭注入窗口：迟到消息只能被当前 Run 接住或改走新 Run

普通迭代顶部排空还不足以处理终态回复阶段的追问。必须让路由器的入队与最终撤销共享同一把所有权锁：锁内检查是否仍有有效追问；有则排空并保持 Run 存活，无则关闭注入窗口。

```text
同一把路由锁内：
存在有效追问 → 当前 Run 提交它并继续
不存在有效追问 → 关闭注入窗口
```

因此发送方只有两个合法结果：消息在关闭前落地而由当前 Run 处理，或看到窗口已关闭后创建新 Run。不会出现“已 accepted、却没有任何运行拥有它”。这与 [[wiki/AI Agent 架构/40：可恢复 Agent Turn 与安全续跑|持久化恢复]] 共享同一原则：状态写入之外，所有权迁移也必须原子。

## 回复寻址与交付确认：按逻辑轮次送达，而非按物理 Run 猜测

一个物理 Run 可以吸收多个用户轮次，故不能只保存一个 Session ID 或“本次运行的消息 ID”。提交新追问时，先保留旧回复目标；若旧轮次已有待发送答案，先向旧目标发出中间回复，再把默认回复目标推进到新消息 ID。否则旧答案会被投到追问下，甚至直接消失。

入站渠道若是 at-least-once，`delivery_ack` 的唯一含义应是：**终态回复已经成功送达**。不能在入队或提交时确认；交付失败时保留未确认状态，让重连重放输入。重放依赖持久消息 ID 去重：系统需要判断该 ID 已属于活动 Run、已完成回复，还是应新建处理，而不是假设传输天然 exactly-once。

## 操作语义必须分离

- **追加追问：** 保留当前 Run，在下一决策前提交新信息。
- **撤回：** 删除尚未提交的排队消息；需要客户端消息 ID 与能覆盖延迟投递的墓碑。
- **中断：** 立即沿取消信号停止当前 Run，不能把“停止”当作一段等待模型阅读的 Prompt。
- **中断并发送：** 先取消旧 Run，并让替代请求在旧路由非活动后拥有新 Run，避免退出中的 Loop 与新请求相撞。

把它们塞进一个带模式字符串的 `steer` 接口，通常会混淆“是否已接受”“是否可撤回”和“何时终止”的所有权边界。

## 工程决策

1. 为每条入站消息显式记录 `accepted → committed → completed` 状态、所有者和持久身份；邮箱记录只在提交到对话后删除，重放确认只在回复送达后发出。
2. 仅在迭代边界提交追问，并同步更新对话转录与依赖最新用户意图的旁路状态；是否批量合并、如何分配回复目标应成为可测试的产品契约。
3. 用路由锁将“最终排空”与“关闭注入窗口”做成原子操作；不以队列长度检查替代所有权同步。
4. 以入站消息 ID 而非仅以 Session/Run 追踪回复地址和待确认集合；新轮次覆盖旧轮次前先交付旧答案。
5. 假设传输至少一次：交付后确认、持久 ID 去重，并记录接受、提交、交付失败、重放和取消事件以便诊断。
6. 将追加、撤回、中断与替代请求拆为独立路径；中断走取消信号，撤回保留墓碑，替代请求等待旧路由释放。

## 常见误解

- **“入队成功就是用户已得到处理。”** `accepted` 只转移了所有权；崩溃前尚未提交或交付的消息仍可能需要恢复或重放。
- **“返回前查看队列为空，就可以安全结束。”** 检查与撤销之间仍会到达新消息；必须以同一把锁原子地排空或关闭窗口。
- **“一次 Run 只需一个回复 ID。”** 合并追问后会产生多个逻辑轮次，单一 ID 会让中间答案错投或丢失。
- **“确认收到即可避免重复。”** 在 at-least-once 渠道中过早确认会丢消息；正确做法是允许重放并按持久 ID 幂等去重。

## 复习

- 为什么 `accepted`、`committed`、`completed` 必须分开？——它们分别代表所有权转移、对话归宿和用户可见交付，失败与恢复责任不同。
- 为什么追问要在迭代边界取出？——该点位于已知前效与未选后效之间，既不会改写已选工具，也能在下一次行动前让模型看到新意图。
- 如果在交付前发送 `delivery_ack` 会怎样？——回复发送失败后输入不再重放，用户会得到“请求被接收却永远没有答案”的丢消息结果。
