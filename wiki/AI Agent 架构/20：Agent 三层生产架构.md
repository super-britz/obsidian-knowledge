# Agent 三层生产架构

> [!abstract] 三层架构的目的不是按语言拆服务，而是把**任务控制权、危险副作用和模型适配**放到不同的失败与权限边界中：编排层负责可恢复的决策与治理，执行层负责受限行动，模型层负责 AI 能力接入。只有当隔离、恢复和独立扩缩容的收益超过分布式复杂度时，才值得拆开。

## 第一性原理

Agent 同时包含长时间任务、概率性的模型调用和可能修改外部世界的工具执行。若它们全部放在同一进程，工具会共享主服务的身份、内存和资源；一次 OOM、崩溃或恶意操作也可能同时丢失任务状态、拖垮用户请求并扩大权限影响面。

```text
任务需要持续决策、可恢复状态与治理
+ 工具需要最小权限、隔离和强制资源限制
+ 模型接入需要快速迭代和多 Provider 适配
→ 为三类责任建立独立边界与明确契约
→ 通过追踪、超时、状态和回执把它们重新组织成一个任务闭环
```

因此，三层架构的本质是**按责任、权限和故障域分离运行时**，而不是将单体代码机械改造成三个网络服务。

## 三层的不可替代职责

| 层 | 拥有什么 | 不应拥有什么 |
| --- | --- | --- |
| **编排层（Orchestrator）** | 任务状态机、路由、依赖、预算、审批、超时、重试、最终验收与对外任务身份 | 直接运行不受信任工具，或把模型原始输出当作已完成副作用 |
| **执行层（Agent Core）** | 工具/代码执行、能力白名单、参数校验、文件/网络/CPU/内存限制、结构化执行回执 | 业务级任务编排、跨任务长期真相或绕过上游授权 |
| **模型服务层（LLM Service）** | Provider 适配、模型路由、流式调用、Embedding、模型用量与错误归一化 | 作为任务状态的权威，或自行决定高风险工具副作用 |

语言只是实现选择。原文以 Go、Rust、Python 举例，分别利用工作流/并发、内存安全与隔离、AI SDK 生态；但更稳定的判断标准是：该层是否能满足其隔离等级、运行时生态、性能和团队维护能力。

## 跨层契约：把分布式调用变成可控任务

每次调用应传递并校验：任务/工作流 ID、调用链 ID、调用者身份、目标能力、输入版本、deadline、预算、幂等键和期望的结构化结果。各层只处理自己被授权的字段，并返回状态、产物引用、资源消耗、错误类别和可重试性。

- **追踪：** 同一工作流 ID 贯穿日志、指标、成本与审计，才能还原一次任务为何结束或失败。
- **超时：** 外层 deadline 必须覆盖内层，但内层应更早超时并释放资源；否则外层已放弃，内层仍在消耗成本。
- **重试：** 仅对可安全重试的调用重试；写外部状态的工具需要幂等键、去重或补偿，不能因为网络超时就盲目重放。
- **回执：** [[wiki/AI Agent 架构/03：工具与行动边界|工具执行]]返回的是受控事实回执，而非“模型说已完成”；编排层再据此更新任务状态。

## 状态与一致性：没有跨层原子事务

服务之间的“调用成功”不代表整个业务动作原子完成：编排可能已记录开始，执行层可能已经产生副作用，模型服务或网络却在返回前失败。把三次 RPC 当作一个事务会制造不可恢复的不一致。

```text
编排层持久化意图与状态
→ 以可重试活动调用执行层
→ 执行层用幂等键写入或返回产物引用
→ 编排层根据回执推进、重试、补偿或标记人工处理
```

持久化工作流适合承载这类恢复逻辑，但不会自动解决外部副作用的语义；状态权威、幂等边界、补偿策略和人工介入条件必须在接口中明确。

## 配置、健康与运行控制

生产问题常发生在“功能正常、运行不可控”的部分：依赖未就绪、配置不一致、密钥泄漏或某层已不可用却仍接收任务。

- **健康检查：** 将进程存活、接收流量能力和关键依赖可用性区分开；非关键依赖降级不应等同于整个服务失效。
- **配置：** 建立统一 schema、版本与校验；敏感值通过受管密钥/环境注入覆盖普通配置，不将密钥写入仓库或日志。
- **热更新：** 仅允许可安全动态变更的项（如限流、模型路由、阈值）；会改变状态语义或授权边界的配置需版本化、审计和受控发布。
- **容量：** 队列优先级、并发配额和每层资源上限应反映业务优先级，防止低优先级后台任务挤占用户正在等待的请求。

## 何时拆分，何时保持单体

应从风险和瓶颈出发，而不是从技术栈偏好出发：

| 信号 | 更可能需要独立边界 | 仍可先保持单体 |
| --- | --- | --- |
| 工具权限与不可信输入 | 需要独立执行沙箱和最小能力集 | 工具只读、输入受控、无外部副作用 |
| 任务时长与恢复要求 | 需要持久状态、可重放和独立 Worker | 短任务，可接受失败后重试 |
| 负载形态 | 编排、工具和模型需独立限流/扩缩容 | 低并发，瓶颈单一且可观测 |
| 团队运维能力 | 能维护追踪、部署、契约和故障演练 | 分布式调试成本会超过隔离收益 |

可先在模块边界和进程内接口上建立契约，等安全、恢复或伸缩压力真实出现后再拆服务。

## 工程决策

1. 先画出每类副作用、数据和权限的边界，再决定服务数量；不从“想用什么语言”倒推架构。
2. 让编排层成为任务生命周期和预算的唯一权威；模型、工具和队列不能各自维护互相矛盾的完成状态。
3. 为跨层操作定义 deadline、取消、幂等、错误分类和产物引用；把这些纳入契约测试。
4. 先实现端到端追踪、健康与降级，再增加优先级队列、热更新等运行优化。
5. 对不可信工具使用独立隔离和最小权限；对高风险结果保留审批与审计，沙箱不替代治理。

## 常见误解

- **“拆成微服务就更可靠。”** 未定义状态和失败语义时，网络调用只会增加不一致与排障成本。
- **“Rust 沙箱解决所有安全问题。”** 隔离执行不替代身份授权、数据范围控制、租户隔离和结果验证。
- **“LLM 服务应该掌控工作流。”** 模型服务适合提供能力，不应成为任务进度、预算或外部副作用的权威。
- **“配置热更新总是更好。”** 未审计的动态配置会使行为不可复现，并可能在运行中放宽安全边界。

## 复习

- 三层架构要解决什么？——将任务控制、危险执行和模型适配分隔到不同的权限与故障边界。
- 编排层的核心权威是什么？——任务状态、预算、deadline、路由和验收，而非直接执行工具。
- 最重要的跨层规则是什么？——可追踪的任务身份、由外向内递减的超时、幂等副作用和结构化回执。
- 何时不该拆？——隔离、恢复与独立伸缩的收益还不足以抵消部署、调试和运维成本时。
