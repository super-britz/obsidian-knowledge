# 安全执行与能力沙箱

> [!abstract] 当 Agent 执行用户代码、生成脚本或外部工具时，应假设它会尝试读取不该读的数据、联网外泄或耗尽资源。安全执行的目标不是判断代码“看起来是否善意”，而是让它即使恶意也只有最小能力和有限资源：默认无权限，显式授予只读目录、输入输出通道和受限运行时间；再以输入验证和输出审核补足沙箱外的风险。

## 第一性原理：不可信代码一旦继承宿主权限，影响面就等于宿主

原生进程常带有环境变量、文件系统、网络和 CPU/内存等环境权限。把未经验证的代码交给它执行，相当于把这些“环境授权”一并交出去；仅靠 Prompt、关键字过滤或事后日志无法阻止已经发生的读取、外联和资源耗尽。

```text
不可信代码或工具输入
→ 先拒绝继承宿主环境的默认能力
→ 仅授予完成任务所需的最小能力与资源额度
→ 在隔离运行时执行，并在超限时中断
→ 审核和限制输出，再决定是否把结果交给后续 Agent 或用户
```

因此，沙箱的本质是**在执行前减少可造成的伤害**：不依赖代码自觉，而依赖运行时不可越过的能力边界。

## 能力模型：从“默认拥有”改为“显式授予”

原章以 WASI 为例：文件系统、环境变量和网络不是默认继承的资源。执行实例只获得被预打开的目录、显式传入的环境变量，以及受控的 stdin/stdout/stderr；在所述 Preview 1 场景中，不提供网络 API。

- **文件：** 只预打开完成任务所需的目录，尽量只读；规范化路径并验证边界，避免 `..` 或符号链接指向宿主敏感位置。
- **环境：** 不继承宿主环境，按白名单注入必要变量，避免 API Key、数据库密码等意外暴露。
- **网络：** 默认没有外联能力；若未来确需联网，也应将目标、协议、凭证与流量作为单独、可审计的能力授予，而非直接打开宿主网络。
- **输入输出：** 通过内存管道传入输入、捕获 stdout/stderr，不把真实终端直接交给不可信程序。

能力应按任务最小化。为了方便而把工作目录、环境变量或网络整体开放，会把沙箱退化为普通宿主进程。

## 资源隔离：CPU、墙钟时间和内存是不同问题

死循环、巨大分配和大量实例都能在没有文件/网络权限时拖垮服务。原章采用多种独立限制：

- **Fuel：** 限制可执行的 WASM 指令量，约束 CPU 密集型循环。
- **Epoch / deadline：** 限制墙钟时间并支持中断；仅有 Fuel 无法处理等待 I/O 等不消耗指令的情况。
- **Store limits：** 限制内存、WASM 表、实例和 memory 数量，避免解释器或恶意模块无限增长。
- **并发与会话：** 执行器会话应有数量上限和过期时间；阻塞的 WASM 工作放到专门的阻塞执行环境，避免占住异步事件循环。

这些限制共同决定“最坏情况下能占用多少”。参数必须用真实解释器和真实任务压测：过小会让正常代码启动失败，过大则失去隔离价值。

## 三道防线：沙箱不是唯一检查点

```text
输入验证：模块格式、大小、声明资源、允许能力与参数
→ 沙箱执行：最小能力 + 多维资源限制 + 可中断运行
→ 输出审核：限制大小、标记失败/超限，并避免将不可信输出直接变成下一次高权限指令
```

第一道防线减少明显异常和错误配置；第二道防线承受“输入已绕过或就是恶意”的情况；第三道防线防止敏感输出、异常结果或提示注入沿 Agent 链路继续扩散。三者互补，不能因为有 WASI 就跳过前后的验证。

## 与策略治理的分工：允许不等于安全地执行

[[wiki/AI Agent 架构/24：策略治理与授权决策|策略治理]]决定某个用户、Agent 和任务**应否**使用代码执行工具；能力沙箱限制已被允许的执行**实际能接触什么、最多消耗什么**。两者必须串联：若只做策略，获准脚本仍可能读取宿主密钥；若只做沙箱，系统仍可能允许不该发生的任务。

工具返回还应包含执行身份、能力集合、资源消耗、超时/Trap 原因等结构化回执，接入 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]]，才能审计和校准隔离配置。

## 工程决策

1. 将所有由用户、模型或外部来源影响的代码和命令视为不可信，默认放入无宿主权限继承的沙箱；不要以“内部用户”或关键字过滤代替隔离。
2. 先定义每类工具最小的文件、网络、环境、输入输出和资源能力，再实现预打开目录与白名单；敏感目录、宿主凭证和写权限默认不授予。
3. 同时设置 Fuel、墙钟 deadline、内存/实例上限、并发和会话 TTL，并对超时、资源耗尽和取消规定统一的清理与用户反馈。
4. 将文件逃逸、网络外联、死循环、内存耗尽、模块过大和输出异常写成回归测试；每次升级 WASI 运行时、解释器或能力配置后重跑。
5. 不把沙箱返回文本直接当可信指令或事实；对输出做大小、结构和敏感性检查，再交给后续 Agent。

## 常见误解

- **“只读挂载就够安全。”** 它只限制写入；仍需限制可见目录、符号链接、环境变量、网络与资源消耗。
- **“Fuel 可以防所有超时。”** Fuel 约束 CPU 指令，等待 I/O 等情况还需可中断的墙钟 deadline。
- **“策略允许执行，就可以给完整系统权限。”** 策略是授权判断，不是最小能力执行；允许后仍必须在沙箱内执行。
- **“沙箱报错就说明攻击被完整处理。”** 还要检查审计、资源清理、输出处理与其他租户/会话是否未受影响。

## 复习

- 为什么要默认零权限？——不可信代码不应自动继承宿主文件、网络、环境和资源能力，显式授予才能缩小爆炸半径。
- 为什么 CPU 配额与超时要同时存在？——它们约束不同执行行为：CPU 密集循环会耗尽 Fuel，等待或阻塞需要 Epoch/deadline 中断。
- 因此策略与沙箱怎样协作？——策略先决定是否应调用工具，沙箱再限制允许调用的实际能力和资源；两者缺一不可。
