# 多租户隔离与资源边界

> [!abstract] 多租户不是给查询补一个 `WHERE`，而是在共享系统中持续证明“这次操作属于哪个组织”。认证先产生不可伪造的租户上下文；会话、工作流、向量检索和数据库都以它限定读写范围；再按租户限制预算和记录审计。任何一层遗漏范围，其他层的隔离都无法阻止泄露。

## 第一性原理：共享资源若没有可信归属，任一遗漏都会把边界打穿

多个组织共用数据库、缓存、工作流和向量库时，资源 ID 或相似度本身不携带“谁能看”的含义。若系统相信请求传来的 `tenant_id`，或某一读取路径没有带租户范围，攻击者或代码遗漏就能把共享底座变成跨组织的数据通道。

```text
已验证的 JWT / API Key
→ 解析并注入可信 TenantContext
→ 每次读、写、检索、启动或查询任务都带租户范围
→ 各存储层再次校验归属，跨租户按不存在处理
→ 按租户结算配额、记录审计并用跨租户测试验证
```

因此，多租户的核心不是“保存一个 `tenant_id` 字段”，而是**让不可信输入无法指定归属，并让每条数据路径都无法绕过归属**。

## 隔离机制：一个上下文，五个独立的执行边界

- **认证层：** 从 JWT 或已验证的 API Key 建立 `TenantContext`；后续代码只读 Context，不接受客户端传来的租户 ID。API Key 需要哈希保存、可禁用、可过期。
- **会话层：** 读取 Session 后核对其租户；不匹配返回 NotFound，避免暴露资源存在性。
- **工作流层：** Workflow 的状态不在普通业务库中，启动时需将租户写入元数据（如 Temporal Memo），查询状态时再次比对。
- **向量层：** 相似度只回答“像不像”，不回答“能不能看”；写入和检索都必须使用 tenant namespace 或 filter。
- **数据库层：** 业务数据带非空 `tenant_id`，查询、更新和删除都按当前 Context 过滤，不能只按资源 ID 或用户 ID 操作。

五层重复校验不是重复劳动：它们分别守住不同的存储和调用路径。中间件只负责建立上下文，不能替后续系统自动隔离。

## 隔离强度与成本：先决定爆炸半径，再选择存放方式

原章列出三种数据隔离形式：共享数据库共享 Schema、共享数据库独立 Schema、每租户独立数据库。前者成本和弹性最好，但最依赖应用层不遗漏过滤；后者逐步缩小单个实现错误的影响面，但会增加迁移、运维和成本。

选择的因果关系是：**数据越敏感、合规越强、单租户故障代价越高，越应接受更强隔离的成本。** 无论采用哪种形式，异步工作流、缓存、向量索引和导出任务仍要显式携带租户归属，不能因为数据库分开就忽略其他路径。

## 资源与失败表现：隔离数据，也隔离“谁能耗尽系统”

租户隔离还包括按套餐或合同独立限制 Token、请求速率、会话数和向量文档数。它把“某一客户持续消耗资源”限制在该客户预算内，并支撑计费和差异化服务；但它不自动解决全局容量不足，系统仍需整体并发与成本护栏。

典型失败信号包括：某个 Session/任务/文档 ID 可跨组织读取、向量检索出现其他客户内容、工作流状态查询无归属校验，或开发环境的跳过认证配置进入生产。跨租户访问应对外表现为 NotFound；内部则记录包含用户、租户、资源、动作和结果的审计事件，保留排查证据。

## 与授权和沙箱的边界：回答的是不同问题

[[wiki/AI Agent 架构/24：策略治理与授权决策|策略治理]]回答“这个主体是否可以做这个操作”；多租户隔离回答“它只能作用于哪个组织的数据与配额”；[[wiki/AI Agent 架构/25：安全执行与能力沙箱|安全执行]]回答“获准执行的代码能接触什么、最多消耗什么”。

三者缺一不可：只做授权，合法用户仍可能读到其他租户；只做租户范围，用户代码仍可能越权访问宿主；只做沙箱，也无法判断数据本来属于谁。

## 工程决策

1. 将 `TenantContext` 视为请求、任务和工具调用的必需输入；禁止在业务 API 中接受可直接决定数据范围的客户端 `tenant_id`。
2. 为会话、工作流、向量库、缓存和数据库分别列出“写入时如何绑定、读取时如何验证”的清单；新数据通道未完成两项前不接入生产。
3. 共享 Schema 时把 `tenant_id` 设为业务数据的必填归属，并通过仓储接口或查询审查减少漏过滤；强合规或高爆炸半径场景则评估 Schema/实例级隔离的成本。
4. 将跨租户读取、检索、任务状态查询、写入和删除写成 CI 回归用例；生产启动时拒绝 `skip_auth` 等开发绕过配置。
5. 将租户配额与 [[wiki/AI Agent 架构/23：Token 预算与成本护栏|Token 预算]]、审计和告警连接起来：超限要有明确的拒绝或降级行为，异常访问要可追踪。

## 常见误解

- **“认证中间件已经隔离好了。”** 中间件只提供可信身份；每个独立数据面仍要把身份变成实际过滤和核验。
- **“向量相似度高就应该返回。”** 相关性不是权限，向量查询必须先受租户范围约束。
- **“返回 AccessDenied 更清楚。”** 对跨租户资源，这会泄露资源存在性；对外使用 NotFound，审计中保留真实拒绝原因。
- **“按租户限额就不会有资源争抢。”** 它限制单租户占用；全局容量、并发和故障隔离仍需系统级治理。

## 复习

- 为什么不能相信请求携带的 `tenant_id`？——它是可伪造的输入；数据归属必须来自已验证凭证形成的 Context。
- 为什么向量检索也要租户过滤？——相似度没有权限语义，不加范围就可能召回其他组织的私有内容。
- 为什么五层都要验证？——会话、工作流、向量库和数据库是独立边界，一个遗漏就足以造成跨租户泄露。
