# 并行工具的调用级安全

> [!abstract] 工具能否并行，不取决于它是否“只读”，而取决于**这一次调用**能否与同批调用同时执行且不互相干扰。正确的并行化是：先为调用及参数证明并发安全；证据不足就串行；在结果身份、审批和预算边界就绪后，再用小批次换取延迟收益。

## 第一性原理：只读不等于可并发，名字也不足以证明安全

只读只回答“它是否改变状态”；并发安全回答“它能否与兄弟调用同时运行而不干扰”。一个读操作可能需要排他锁，因而不适合并发；两个写操作若作用于完全隔离的资源，也可能安全并行。按只读分批，回答的是错误问题。

同一工具的安全性还会随参数变化。`file_read` 通常稳定可并发；`bash` 执行 `cat config.yaml` 和 `git push` 的风险完全不同。于是调度器应对每个调用做判断：

```text
工具名 + 参数 + 当前约束
→ 并发安全？
→ 安全：进入并发批次
→ 无法证明：进入大小为 1 的串行批次
→ 按 tool_use_id 关联乱序结果
```

“无法证明”不等于拒绝工作，只是放弃并行优化。假阴性损失是少量延迟；假阳性可能让共享状态、文件或仓库损坏。

## Fail closed：多用途命令必须按实际形状分类

Bash 不能按工具名整体放行。保守分类至少要求：没有任何 shell 元字符、起始 token 位于明确的安全集合、且多用途二进制的子命令与参数形状被识别。管道、重定向、命令替换、`&&`、未知 token、未知子命令都会取消资格。

**换行和回车也是元字符。** 多行“单命令”实际可能是多条命令；若只检查第一行，第二条未分类命令就能绕过安全边界。对于 `git`、`docker`、`kubectl` 等多用途程序，起始 token 在白名单还不够，必须再证明具体子命令没有写入、外部执行或输出到文件等副作用。

## 并行前先完成协议与控制面准备

串行时可以按位置配对结果；并行后完成顺序会变化。工具状态与结果必须携带 `tool_use_id`，客户端按该身份更新对应调用，而不是按事件到达顺序猜测。只有所有消费方已经支持这种关联能力后，默认并行才安全；这延续了 [[wiki/AI Agent 架构/33：Agent 运行时契约与发布验证|运行时契约]] 中“先发布可探测协议，再翻转默认值”的原则。

并行也放大控制成本：同批审批的展示顺序不可保证，应在批次执行前完成审批；并发结果会更快撞上 [[wiki/AI Agent 架构/36：Tool Result 外溢与上下文预算|单 Turn 结果预算]]；日志和 Trace 交错会削弱因果可读性。因此并发批次应小、结果预算应按批次聚合、可观测性应保留调用身份与批次边界。

## 工程决策

1. 在调度器中引入调用级 `IsConcurrencySafe(tool, args, context)`，而不是把只读标签或工具名当作并发许可；新能力默认回退到旧行为，逐工具启用。
2. 对 shell 和多用途二进制采取 fail closed：元字符、换行、未知命令、未知子命令或无法证明安全的参数一律串行。
3. 将审批、权限和副作用前置到批次执行之前；并行化不应绕过 [[wiki/AI Agent 架构/25：安全执行与能力沙箱|安全执行]] 的既有边界。
4. 在开启默认并行前，为全部工具生命周期事件提供 `tool_use_id`，并验证各客户端能按 ID 处理乱序完成。
5. 控制批次大小，并把并发结果计入同一 Turn 的聚合预算；记录批次、调用身份、开始/结束时刻与分类理由，支持事后排障。

## 常见误解

- **“只读工具可以直接并行。”** 只读和并发安全是两个维度；只读操作也可能竞争锁、共享缓存或外部限额。
- **“bash 在白名单就安全。”** shell 内容、换行、子命令和参数才决定此次调用；未知应串行而非猜测。
- **“测试都通过就可以放宽分类。”** 并发错误依赖时序；保守证据和 fail closed 比一次测试通过更可靠。
- **“并行只是性能优化。”** 它还改变审批顺序、结果归因、上下文压力和调试轨迹，必须连同控制面一起设计。

## 复习

- 为什么“只读”不能作为并发许可？——它不说明调用是否会争用锁、共享状态或外部资源，也不说明隔离写操作是否可并行。
- 为什么安全性必须带参数判断？——同一工具的不同命令或参数可能从纯查询变成写入、执行或修改共享状态。
- 为什么先有 `tool_use_id` 才能默认并行？——并行完成乱序后，只有稳定身份能把输出和状态挂回正确调用，避免“结果正确但显示错误”。
