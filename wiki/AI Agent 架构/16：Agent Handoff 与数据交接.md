# Agent Handoff 与数据交接

> [!abstract] Handoff 不是把一段对话“转给下一个 Agent”，而是让接手者获得完成下一步所需的最小、可定位、可验证的状态与产物。交接机制应随协作复杂度升级：固定依赖传结果，运行中共享用 Workspace，需要协商才用 P2P 消息。

## 第一性原理

Agent 的上下文和运行状态彼此隔离。若接手者缺少前序产物、任务目标、完成状态或来源，它只能重复检索、猜测或在错误输入上继续；若把全部历史一股脑复制，又会耗尽上下文并传播无关信息与错误。

```text
任务契约声明产物与输入
→ 验证输入有人生产、范围可见且版本匹配
→ 按需要传递最小产物或引用
→ 接手者验证状态、来源和可消费性
→ 执行、写回新产物，并让下游可追踪
```

因此，Handoff 的本质是**受控的数据流协议**：既定义数据怎样到达，也定义谁能消费、何时有效、失败后怎样处理。

## 交接的最小契约

| 要素 | 要解决的问题 |
| --- | --- |
| **任务与目标** | 接手者为何接手，应该交付什么，而不是只看到一段结果 |
| **Produces / Consumes** | 上游交付什么类型的产物，下游需要什么输入 |
| **产物引用与版本** | 内容在哪里、由谁产生、何时产生、是否被更新 |
| **状态与验收** | 上游是成功、部分完成还是失败；下游能否安全开始 |
| **权限与范围** | 接手者能看什么、能改什么、数据可保留多久 |

[[wiki/AI Agent 架构/10：任务规划与控制|任务规划]]中的 `Produces / Consumes / Dependencies` 既是调度依据，也是 Handoff 的接口。启动前应检查每个 `Consumes` 都有合法生产者、依赖没有环、主题名称一致；否则系统会等待一个永远不会出现的输入。

## 三层机制：按复杂度选择

1. **结果注入：** 对线性链、扇出或固定汇合，向下游传递结构化 `dependency_results`。它最简单，但要限制字段和大小，优先传数值、状态、来源与引用，而非长文本。
2. **Workspace：** 对运行中出现、多个 Agent 可能复用的公开发现，按 Topic 写入并按序列号增量读取。它适合一对多共享，不适合替代权威数据库。
3. **P2P Mailbox：** 对请求、提议、接受、委派和澄清等双向互动，向明确接收者发送有类型的消息。没有协商需求时，使用它只会增加状态机、超时和重试复杂度。

从低到高升级，而不是默认使用最强机制：简单链式依赖用结果注入；共享发现才引入 Workspace；只有需要问答或协商时才使用 P2P。

## 等待、失败与一致性

等待“有消息/有 Topic”必须有超时、取消和退避策略；否则下游会永久轮询或死等。更重要的是，**存在产物不等于产物可用**：接手前要检查生产者状态、格式/类型、版本、来源和验收结果。

大对象、敏感内容或频繁更新的数据不宜在上下文、Workspace 或消息中复制。应存入有访问控制的权威存储，只传不可猜测的引用、摘要和校验信息；同时记录读取位置、版本与保留期。这样既控制 Token，也避免“同名 Topic”覆盖、陈旧数据和跨任务泄漏。

可恢复工作流还需让写入、消息顺序和时间可追踪、可重放；不要用不可复现的瞬时内存或系统时间作为唯一交接事实。

## 工程决策

- **先设计数据流，再设计 Agent 对话。** 画出谁生产、谁消费、谁拥有最终写入权，避免用聊天记录充当接口。
- **把结构化产物设为默认交付物。** 至少包含状态、来源、时间/版本、不确定性和外部引用；自然语言摘要只服务阅读。
- **把 Producer 校验前置。** 在运行前拒绝缺失生产者、循环依赖和不兼容主题；运行中仍监控超时、过期和失败传播。
- **最小化交接面。** 用字段白名单、大小上限、Topic 命名、访问范围、TTL 和审计记录控制传播；无双向协商就不用 P2P。

## 常见误解

- **Handoff 就是传完整上下文：** 完整历史既昂贵又含噪；真正需要的是当前任务的最小有效状态。
- **Topic 有生产者就能放心消费：** 还要确认生产者成功、版本正确、数据完整且接收者有权限。
- **Workspace 是数据库：** 它是短期协作层；权威业务状态、隐私与删除义务应落在专门存储中。
