# 上下文压缩的多层防线

> [!abstract] 上下文窗口是有限的，压缩又是一次有损且会占用窗口的模型调用。可靠做法不是等溢出后再摘要，而是以“提前保留余量 → 发送前复核 → Provider 超限后受限回退”守住连续性，并把压缩、外溢、缓存和留存视作不同问题。

## 第一性原理：恢复动作也必须装得进窗口

长任务会不断积累消息、工具结果和中间计划；一旦请求超过模型窗口，当前 Turn 无法继续。若此时才调用摘要器，摘要请求也需要携带历史并占用窗口，可能同样被拒绝，导致此前积累的工作状态无法恢复。

因此上下文治理的目标不是“尽量晚压缩”，而是**在仍有可用余量时，以最小必要损失重塑模型可见历史**：

```text
估算历史接近预算
→ 主动压缩，留下继续执行的余量
→ 请求发送前 Preflight 再次检查完整组装结果
→ Provider 仍报告超限时，仅进行一次受限 Reactive 回退
→ 成功后继续；失败则保留可诊断终态，而非无限重试
```

三道闸门并非重复：主动检查会受 token 估算误差影响；Preflight 能发现组装请求后的突增；是否真正装得下最终只能由 Provider 裁决。少任一道，就会缺少对一种失效模式的防线。

## 阈值与保留：从需要的余量倒推，而不是挑百分比

压缩阈值应先计算仍需容纳什么：本轮请求、预期响应、工具调用的增长以及压缩操作自身的余量；剩余容量才是可用历史预算。较高阈值会减少不必要摘要和信息损失，但前提是下一道闸门能接住估算误差；没有兜底时，高阈值只是把失败推迟到更难恢复的时刻。

压缩历史也不是简单“从头删除”。应保留：

- **开场约束：** 角色、任务边界和仍然生效的关键指令；
- **已验证摘要：** 对较早历史的有来源、可替换的工作记忆；
- **近期尾部：** 保持最小下限的最新对话和工具交互，以延续当前任务；
- **结构边界：** 工具调用及其结果必须成对，不能只切掉一半交互。

这是一种 Prompt 视图整形，而不是对真实记录的销毁；[[wiki/AI Agent 架构/08：记忆架构|长期记忆]]和 Session 留存仍有独立的正确性、隐私和审计标准。

## 摘要器也是不可靠的依赖，必须被限制

摘要模型可能超限、超时、返回空结果或丢失关键信号。它不能接收刚刚导致超限的完整输入，也不能无限压缩自己以前的摘要。工程上应：

1. 为摘要输入设置独立的 token/字节上限，并保持字符编码和工具交互边界完整；
2. 标记已压缩区间，避免对同一旧区域反复摘要造成累积失真；
3. 拒绝空摘要或异常结果，保留上一份可用摘要作为回退；
4. Reactive 压缩最多重试一次，且失败标志不复位，防止循环性消耗；
5. 按主动、Preflight、Reactive、摘要生成、历史写入等路径记录可区分遥测。

这将“上下文满了”从不可定位的故障，变成可以判断是预算计算、组装突增、Provider 限制还是摘要器本身失败的状态机。

## 压缩、外溢与缓存：解决的是不同约束

压缩会改写历史，而 Prompt Cache 依赖稳定前缀。若截断位置由当前历史长度这类变化输入决定，边界每轮移动，后续前缀持续失效，既损失缓存又反复付费。截断和整形边界应从上下文窗口、稳定会话目标等不随当前历史漂移的输入推导；缓存优化不能以牺牲必要压缩为代价，但必须显式衡量其成本。

单个巨大工具结果则不是“历史过长”的问题。将其摘要进转录仍会增加延迟和信息损失；应优先把完整结果外溢到 Prompt 外，只在上下文保留受限摘要或可检索指针。压缩模型看到的工作副本，同时将完整审计记录、用户要求的转录和交付物独立保存，避免把 Prompt 管理误当留存策略。

```text
整体历史逐渐过长 → 压缩工作上下文
单条工具结果过大 → 外溢并保留指针
需要完整证据或用户交付 → 原样持久化，不参与删除
```

## 工程决策

1. 为每个模型族计算上下文预算：从窗口中预留请求增长、响应、工具结果和压缩余量，再设置主动与 Preflight 阈值；将推导过程写入配置或注释。
2. 实施主动、Preflight、Reactive 三道闸门：Reactive 只允许一次受控回退，并以 Provider 的超限结果作为最终事实。
3. 以“开场约束 + 已验证摘要 + 有下限的近期尾部”重塑历史；任何切分都校验工具调用/结果配对和消息结构完整性。
4. 将摘要器当作独立依赖治理：输入上限、结果校验、旧摘要去重、单次回退与分级遥测缺一不可。
5. 让截断边界由稳定输入推导，监测压缩后的 cache hit、延迟和成本；不要让当前历史长度决定每轮不同的切点。
6. 先识别问题类型：单个超大结果走外溢，完整留存走独立存储，只有模型工作历史整体超预算时才压缩。

## 常见误解

- **“只有 Provider 报错时再摘要最省。”** 此时摘要器也可能放不进窗口，且每次长会话都会先浪费一次失败往返。
- **“阈值越低越安全。”** 过早压缩会增加调用、损失信息并破坏缓存；安全来自预留余量和分级兜底，不是盲目保守。
- **“摘要成功就可以覆盖原记录。”** 摘要是有损 Prompt 视图，不等于审计记录、用户交付物或长期事实来源。
- **“压缩能处理所有 token 问题。”** 单个超大工具结果更适合外溢；会话根本不会接近窗口时，压缩只会平添风险。

## 复习

- 为什么需要三道闸门？——估算、请求组装和 Provider 实际限制会在不同位置失败，必须用独立检查覆盖。
- 为什么压缩阈值不能只写成一个经验百分比？——它必须保证本轮请求、响应和压缩动作本身仍有空间，且要说明剩余风险由哪道防线承接。
- 为什么不能用压缩替代留存？——它优化模型输入而且有损；证据、交付物和完整历史需要独立持久化。
