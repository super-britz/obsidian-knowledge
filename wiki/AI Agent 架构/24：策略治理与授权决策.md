# 策略治理与授权决策

> [!abstract] Agent 的能力、用户、环境和风险会持续变化；把“谁能做什么、在什么条件下做”散落在业务代码的 `if` 中，会使规则难改、难审计、难灰度。策略治理把授权规则与业务实现分开：将事实输入交给可版本化的策略，返回允许、拒绝或需审批的可解释决策；但它只决定**是否应做**，不替代沙箱等执行层的真实限制。

## 第一性原理：变化的规则不能依赖分散的代码路径

同一个 Agent 请求可能涉及用户身份、操作类型、数据敏感性、预算、运行环境和时间窗口。若每个工具、Workflow 和 API 各自判断，规则会复制、漂移并互相矛盾；紧急修复也要修改业务代码和重新部署。

```text
请求带着身份、目标、环境与资源上下文进入系统
→ 在执行副作用前收集决策所需事实
→ 策略根据统一规则产出 allow / deny / require approval
→ 执行层只执行已被允许且受约束的动作
→ 保存原因、策略版本和有效模式，用于审计与回溯
```

因此，策略治理的本质是把“**授权判断**”变为独立、可测试、可发布和可追溯的决策接口，而不是把更多安全逻辑塞进 Agent Prompt。

## 最小决策契约：输入必须完整，输出必须可解释

原章的 `PolicyInput` 包含用户、会话、Agent、查询、模式、环境、预算和时间等上下文；`Decision` 则包含是否允许、原因、是否需人工审批、策略版本和审计标签。

这形成两个必要约束：

- **输入完整且可信：** 所有会改变结论的主体、对象、动作、环境与资源信息都要传入；缺少环境、工具、预算或身份，会让相同操作在不同风险下得到错误的同一决策。
- **输出可执行且可解释：** 不只返回布尔值，还要返回拒绝原因、审批要求和版本。调用方据此停止、转审批或继续；审计者据此回答“为何当时这样处理”。

策略决定应发生在进入 Workflow 或发起高风险工具调用之前；否则“先执行、后检查”已经失去授权意义。

## 安全默认值：未知不放行，拒绝不可被绕过

```text
没有匹配的允许规则 → 拒绝
任一 deny 规则命中 → 拒绝
允许规则全部满足且无 deny → 允许或要求审批
```

**默认拒绝**把未知情况视为需要显式授权的风险；**deny 优先**防止一条宽泛 allow 规则绕过更具体的危险操作、黑名单或预算限制。它们适合高风险授权面，但规则本身仍需测试：过宽的模式匹配会误杀，过窄的输入又会留下绕过路径。

## 策略也是生产变更：测试、灰度、版本与缓存

策略能热更新，不代表可以直接全量强制。原章提供 `off → dry-run → enforce` 模式和按用户/比例灰度：先记录“本会拒绝什么”，核对误杀和覆盖，再逐步真正阻断；紧急开关可退回 dry-run。

每次决策都应记录有效模式、原因、策略版本和最小必要输入摘要（如查询 hash 而非原文），并观察拒绝率、评估延迟、错误与缓存命中。缓存仅在键包含**所有影响决策的字段**时才安全；根据这一约束，策略热更新时还应清空缓存或以策略版本隔离缓存，避免继续返回旧规则的结论。

## 可用性与安全的取舍必须按风险选择

策略引擎故障时：

- **FailClosed：** 拒绝请求，适合删除、支付、数据导出等不可逆或高危动作；代价是策略服务异常可能阻断业务。
- **FailOpen：** 放行请求并告警，适合低风险、可回滚且可用性优先的场景；代价是故障窗口内可能绕过保护。

不要把任一模式设为全局真理。更合理的是按工具能力、数据等级和操作可逆性分层，并为策略故障设计明确的降级状态、告警和人工接管。

## 工程决策

1. 将策略评估放在关键执行前，并采用稳定的输入/输出契约；业务层只消费 Decision，不重复散落授权规则。
2. 默认拒绝、deny 优先，并为每条 allow/deny 规则写允许、拒绝和边界案例测试；避免只测试“正常请求”。
3. 新策略先 dry-run，再按主体或比例灰度 enforce；审查拒绝原因分布和误杀样本后才扩大范围，并保留快速回退开关。
4. 审计至少关联任务/会话、决策原因、有效模式、策略版本与输入摘要；用 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]]发现拒绝率异常或策略变更副作用。
5. 把“是否允许”与“如何安全执行”分开：策略可限制 Agent 选择，但实际工具还需权限校验、最小权限凭证、资源限制与沙箱。

## 常见误解

- **“用了 OPA 就完成安全。”** OPA 只输出决策；工具本身仍可能读取文件、联网或耗尽资源，必须在执行层限制。
- **“默认 allow 更方便。”** 它要求预见所有危险情况；未知输入会自然放行，尤其不适合高风险动作。
- **“缓存只要按用户即可。”** 环境、Agent、请求内容、预算和策略版本也可能改变结论；缓存键不完整就是绕过路径。
- **“策略更新不用发布就没有风险。”** 热更新缩短了生效时间，也缩短了误配的影响时间，仍需测试、灰度、审计和回滚。

## 复习

- 为什么策略要从业务代码分离？——授权规则变化快且跨多个执行点；独立决策接口才能集中维护、测试、发布和解释。
- 默认拒绝与 deny 优先各防什么？——前者防未知情况自动放行，后者防宽泛允许绕过已知危险规则。
- 策略引擎故障时如何选择？——按动作风险决定 FailClosed 或 FailOpen，并配套审计、告警、降级和人工接管。
