# Agent 运行时契约与发布验证

> [!abstract] Agent Loop 只解决“当前一轮怎样思考和调用工具”。一旦它成为可切换角色、跨会话记忆、接收渠道事件、后台自动触发并持续发布的产品，身份、状态、权限、集成、自动化和验证都必须成为可追踪、可恢复、可测试的运行时契约。

## 第一性原理：循环无法单独定义一个长期 Agent 产品

同一个模型循环如果由不同用户、渠道、Agent 配置、工作目录或后台触发器启动，实际能访问的数据、工具和副作用并不相同。若这些边界只存在于 prompt、前端或某个入口，切换角色、重试、重启、MCP 接入或定时任务都可能绕过它们。持久系统因此需要把“这是谁、处于什么状态、现在可做什么、怎样证明结果”从循环外显式传入并持续验证。

```text
可信身份与触发来源
→ 解析 Named Agent、Session、工作区、Memory 与策略范围
→ 进入共享 Harness，在同一权限和审计链内执行
→ 将审批、工具回执、输出、取消和失败写成可恢复状态
→ 通过契约测试、回放和故障注入验证行为
→ 经 Canary/监控发布；出现偏差可取消、回滚、追溯
```

所以，平台化 Agent 的本质是**让所有入口共享同一组运行时契约，而不是给同一个 Loop 叠加更多功能**。

## 作用域与状态：身份、Session、工作上下文和 Memory 不可混为一谈

Named Agent 可以组合指令、模型策略、工具/MCP 范围、网络目标、Skills 和默认工作方式，但它必须以最小权限建立独立作用域，并能解释每个最终配置值来自哪里。切换 Agent 时，应重建工具与集成范围，不能把上一角色的高权限或隐式配置带入下一角色。

状态也要分层：

- **工作上下文：** 当前任务在本轮需要的输入和中间事实，可压缩、可丢弃；
- **Session：** 可恢复的消息、事件、审批和任务终态，定义一次连续工作的边界；
- **Memory：** 跨 Session 才有价值的事实，必须带来源、时间、作用域和有效性。

压缩本身有损，低成本模型抽取也不保证事实正确。因此写入 Memory 前仍需去重、冲突处理、隐私过滤和评估；[[wiki/AI Agent 架构/08：记忆架构|记忆]]不能替代 [[wiki/AI Agent 架构/09：多轮对话与会话状态|Session 状态]]，更不能替代当前权限判断。

## 共享执行核心：入口和集成只能带来请求，不能带来额外权限

TUI、一次性 CLI、Daemon、Slack/Webhook、MCP、Schedule、File Watcher 和 Heartbeat 都应先验证来源，再绑定 Agent、Session 与租户/工作区，最后进入同一 Harness。渠道元数据、网页内容、MCP 返回和工具输出都是不可信数据：它们可以影响任务输入，但不能作为系统指令、权限声明或自动审批依据。

MCP 的 Client 与 Server 是两个方向的集成，但都应复用 [[wiki/AI Agent 架构/04：MCP 工具互操作|MCP]] 的能力协商、权限、审计和输出边界。自动触发相较交互式用户更缺少即时监督，应拥有更少权限，并定义幂等键、防重叠、有限重试、静默成功、可见失败和禁用方式。其持久化与取消语义可复用 [[wiki/AI Agent 架构/30：Background Agents 持久化后台任务|Background Agents]] 的控制链。

当执行需要用户输入或审批时，运行时要持久化明确的 `Pending` 状态，以便在断连、重启或重复投递后恢复，而不是把等待隐含在内存或一个长连接里。取消、超时和失败都需要可查询的终态；重复消息不能重复产生外部副作用。

## 权限与结果：授权属于运行时，输出属于不可信数据

共享 Harness 必须在每次工具调用时执行不可覆盖的破坏性操作封锁、操作者拒绝规则、复合命令/高风险参数分析、有作用域的允许规则和显式审批。自动批准不是全局信任开关，它必须受工具、参数、路径、目标、身份和触发来源共同约束。[[wiki/AI Agent 架构/24：策略治理与授权决策|策略]] 决定是否允许，[[wiki/AI Agent 架构/25：安全执行与能力沙箱|执行边界]] 限制执行器能接触什么；Named Agent 只声明更窄的默认范围，不能越过二者。

工具结果必须有大小预算和截断标记；完整内容可放在 Prompt 外，以引用或检索方式按需读取。无论来自网页、渠道还是 MCP 的文本，都不能重新解释为高优先级指令。这个原则把提示注入从“模型是否听话”转为“运行时不让不可信数据改变控制流”。

## 验证与发布：一次成功的 Demo 不是持续安全的能力

发布 Agent 改动要验证行为契约，而不只看一次演示：

1. **契约测试：** 工具 Schema、参数边界、允许/拒绝/审批、工作区和 Session 隔离、取消/超时终态、重试不重复副作用。
2. **Golden Trace 回放：** 保存合成、脱敏的意图、工具选择、归一化结果、审批与后置条件；变更模型、Prompt、工具或策略后比较语义与安全决策，而非逐字输出。
3. **故障注入：** 模拟模型不可用、畸形/超大 MCP 结果、Daemon 断连、重复消息、文件半写入、Session 过期和审批期间重启。安全失败是正确结果，挂起或伪造成功不是。
4. **分阶段发布：** 隔离 Canary/Shadow Run → 监控任务验收、权限违规、恢复率、延迟和成本 → 可实际演练的取消、回滚和审计检索。

这让 [[wiki/AI Agent 架构/22：Agent 可观测性与诊断闭环|可观测性]] 从“知道发生了什么”延伸为“变更是否允许进入生产”的证据链。

## 公开边界：经验可分享，资产与可识别细节必须隔离

可公开的是通用运行时不变量、公开命令、概念架构和合成示例；不应公开的是私有源码、未发布 API、生产拓扑、凭据、客户文件/消息、专有 Prompt、精确阈值和可重建系统的时间线。将内部经验改写为厂商无关的机制与合成数据，才能既传播工程知识，又不暴露攻击面或客户资产。

## 工程决策

1. 为每个请求创建显式运行时 Context：身份、来源、Named Agent、Session、租户/工作区、策略版本、工具/MCP 范围与预算；任何入口缺少这些字段时拒绝或进入受限模式。
2. 将 Context、Session 与 Memory 分层存储：压缩不直接写入长期记忆；长期事实必须包含来源、时间、作用域和删除/失效策略。
3. 将 TUI、Daemon、渠道、MCP 与自动触发器全部收敛到共享 Harness；渠道元数据和工具输出只作为不可信输入，绝不直接扩大权限。
4. 自动化任务默认比交互式任务权限更窄，并为 Schedule/Watcher/Heartbeat 定义去重、重叠、重试、取消、禁用和通知策略。
5. 把审批和用户追问保存为可恢复 Pending 状态；对重启、断连、重复投递和超时设计明确、幂等的状态转移。
6. 将发布前的契约测试、合成 Trace 回放、故障注入、Canary/Shadow 与回滚演练做成流水线关卡；以任务验收、权限违规、恢复率和成本作为发布证据。

## 常见误解

- **“Named Agent 隔离了所有风险。”** 它只是缩小默认配置范围；运行时仍需强制权限、租户、工作区与执行边界。
- **“渠道消息来自已登录系统，所以可以信任。”** 渠道身份可用于认证，但消息正文和元数据仍是可被操纵的数据，不能变成权限或系统指令。
- **“Golden Trace 要让输出逐字一致。”** 生成文案天然变化；应断言工具选择、审批、后置条件和安全决策等稳定语义。
- **“安全失败等于系统不可用。”** 对越权、畸形输入或不可恢复故障，明确拒绝、取消和可追溯终态比伪造成功更正确。

## 复习

- 为什么不同入口必须共享同一个 Harness？——否则渠道、调度或 MCP 可能绕过交互入口已有的权限、审计和停止边界。
- 为什么 Session 与 Memory 必须分开？——Session 保存一段连续执行的可恢复状态；Memory 是跨会话事实，写入标准和隐私风险都更高。
- 为什么发布要做故障注入和回滚演练？——真实风险常发生在模型不可用、结果畸形、断连和重试期间；未演练的恢复路径不构成可靠能力。
