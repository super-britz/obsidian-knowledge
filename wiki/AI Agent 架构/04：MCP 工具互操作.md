# MCP 工具互操作

> [!abstract] MCP 不让工具天然更可靠；它把“工具如何被发现、描述、调用和授权”的交互边界标准化，让 Client 与 Server 可以解耦复用。标准化降低集成成本，也扩大外部能力和信任边界，因此必须同时设计身份、权限、输出隔离与资源控制。

## 第一性原理：为什么工具接入会失控

如果每个 Agent 都为每个外部服务单独接 SDK、写认证、转换参数和处理错误，集成工作会随 Client 数量与服务数量相乘：

```text
N 个 Agent Client × M 个外部服务
→ N × M 套专用适配、认证和错误处理
→ 重复开发、语义不一致、升级难以同步
→ 工具难以跨应用、跨团队和跨运行时复用
```

MCP 用 Client 与 Server 之间的公共协议，将问题改写为：

```text
服务实现一次 MCP Server
→ Client 用统一方式连接、发现并协商能力
→ 以统一 Schema 提出调用请求
→ Server 在自己的授权与执行边界内完成操作
→ 返回标准化结果给 Client 与 Agent Loop
```

这使集成关系更接近 `N + M`：每个 Client 和每个服务各实现一次协议边界，而不是彼此两两适配。

## MCP 标准化什么，不标准化什么

### 它标准化互操作边界

- **发现与能力协商：** Client 先知道 Server 支持什么，并只使用双方已协商的能力；
- **能力描述与调用：** 工具及其输入输出以可理解、可验证的形式暴露；
- **通信与生命周期：** Client 与 Server 通过约定的 Transport 和消息流程交换请求、结果与状态；
- **授权交互：** 远程能力的身份和授权流程可遵循统一边界，而非散落在每个业务适配器中。

Tools、Resources、Prompts 的区别应按**谁发起、怎样发现、怎样交互**理解，而不是简单贴上“能写”“只读”的标签。

### 它不替代工具自身质量

MCP 不会自动解决：

- 工具 description 模糊、参数设计差或结果语义不清；
- Server 内部缺少输入校验、幂等性、超时与错误处理；
- Client 是否应该允许此次调用；
- 调用结果是否真的满足用户目标；
- 外部内容是否安全、可信或适合进入模型上下文。

因此，MCP 建立在 [[wiki/AI Agent 架构/03：工具与行动边界|工具与行动边界]] 之上：第 3 章规定一个能力怎样受控执行，第 4 章规定这些能力怎样跨系统互操作。

## 一个完整的互操作闭环

```text
选择可信 Server 与连接方式
→ 身份认证、授权和能力协商
→ Client 获取可用 Tools / Resources / Prompts
→ Agent 根据当前任务选择能力并提出结构化请求
→ Server 校验、执行并返回结果
→ Client 将结果作为不可信外部数据隔离后交回 Agent Loop
→ 根据结果继续、验收、重试、转交或停止
```

这里有三个不能省略的控制点：

1. **协商前不假设能力。** 未声明或未协商的可选能力不能被调用。
2. **Server 侧仍拥有执行权。** Client 或模型提出请求，不代表 Server 必须执行。
3. **结果进入模型前仍是外部输入。** 协议兼容不等于结果可信，更不等于它可以改变系统指令或触发新权限。

## 标准化为什么会带来新的安全问题

互操作提高了能力复用率，也使 Agent 更容易连接更多服务。能力面扩大后，攻击面与组合风险随之扩大：

| 风险 | 因果链 | 必要边界 |
| --- | --- | --- |
| 工具输出注入 | 恶意或被污染的 Server 返回文本 → 进入模型上下文 → 模型将数据误当指令 | 将工具输出明确标记为数据；隔离、过滤并限制其后续可触发的行动 |
| 权限组合攻击 | 单个工具权限较低 → 多个工具组合后形成读取、传输或破坏链路 | 最小工具集、敏感路径保护、跨工具策略与审批 |
| 伪装或错误 Server | 名称相近或来源不明的 Server → Client 连接并暴露数据或凭据 | Server 身份验证、来源审查、允许列表与固定配置 |
| 资源耗尽或下游故障 | 大响应、慢响应或连续失败 → 上下文、内存、时间和成本外溢 | 响应大小上限、超时、限流、熔断和可观测重试 |

Registry 可以帮助发现 Server 及其元数据，但它不是运行时信任决策的替代品。真正的安全边界仍在连接配置、身份、权限、执行隔离和结果处理上。

## 工程决策

1. **先判断是否存在跨 Client 复用需求。** 同一能力要被 IDE、桌面客户端、内部 Agent 或多个团队使用时，MCP 的协议成本通常值得；单一封闭系统中的简单内部调用可使用更轻的 Adapter。
2. **将协议兼容与业务适配分开。** HTTP 能调通不等于 MCP 兼容；不要把自定义远程函数接口误称为完整协议实现。
3. **将信任范围写成配置，而不是交给模型判断。** 固定可信 Server、域名、认证方式、可访问路径、响应大小、超时和成本边界。
4. **每次连接只授予最小能力。** 按任务过滤 Server 能力；对写入、发布、删除、外发等副作用保留策略检查和人工确认。
5. **把 Server 输出当数据，不当指令。** 输出需要来源标记、长度限制和必要的清洗；任何由输出诱发的新工具调用都必须重新通过权限与策略检查。
6. **为远程失败设计降级。** 对暂时故障采用有限重试和熔断；对能力不可用时让 Agent 改用替代工具、请求用户输入或明确失败，而不是无限循环。

## 不要把实现示例当成原理

- stdio、Streamable HTTP、不同 SDK 与客户端配置是协议落地方式；稳定原则是“先协商，再按契约互操作”。
- MCP Registry 是发现与元数据机制，不等于自动安全认证、权限授予或 Server 质量背书。
- MCP Server 能提供 Tools、Resources、Prompts 等能力，但不意味着每个 Agent 都应暴露或使用全部能力；能力暴露应服从任务、风险和成本。
