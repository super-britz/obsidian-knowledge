# 多 Agent 编排与协调

> [!abstract] 多 Agent 不是“多开几个模型”，而是把任务、状态、责任和结果分配给多个受控执行单元后再重新汇总。只有并行、专化或隔离带来的收益大于分解、通信、同步和综合成本时，才值得采用。

## 第一性原理

单 Agent 对独立任务通常只能串行处理；同时承担差异很大的工作时，提示、工具和上下文会互相干扰；一处超时或工具失败也可能让整条任务中断。拆分后可并行、按能力配置和隔离失败，但协调本身成为新的成本与故障来源。

```text
目标 + 可用能力 + 预算/风险边界
→ 分解为有输入、产物和验收的子任务
→ 按依赖与资源调度执行
→ 记录状态、来源、失败与消耗
→ 验证、处理冲突并综合交付
```

因此，编排的本质是**显式管理协作成本**，而不是把复杂性藏进多段角色 Prompt。

## 编排器的责任边界

编排器至少承担四件事：**分解、分配、协调、综合**。

| 责任 | 要回答的问题 |
| --- | --- |
| **分解** | 子任务分别产出什么，输入、范围、验收与失败策略是什么？ |
| **分配** | 哪个 Agent / 工具 / 模型更适合，拥有哪些最小权限与预算？ |
| **协调** | 哪些可并行，哪些必须等待，如何限流、暂停、取消和恢复？ |
| **综合** | 哪些结果可用、重复、矛盾或缺失，如何形成可追溯交付？ |

它不应成为“知道一切、执行一切”的中心 Agent。计划、任务 ID、状态、产物指针、预算和控制信号应由运行时持久化，而不能只存在某次对话里。

## 路由与执行模式

先判断单 Agent 是否已经足够：单步、低风险、无明显专化或并行收益的任务直接执行。确有多个可验收子任务时，再按结构选模式：

- **并行：** 子任务互不消费对方产物；设置并发上限，并考虑配额、共享资源和写冲突。
- **串行：** 后一步依赖已验证的前序产物；传递结构化产物，而不是整段对话文本。
- **DAG / 混合：** 仅在全部依赖就绪后启动节点，让独立分支并行、汇合节点等待输入。
- **动态协调：** 依赖、分工或重试路径会随执行事实变化时，再引入 Supervisor 一类的运行时调度。

“更多 Agent”不能作为路由依据；应比较关键路径时延、专化收益、失败隔离能力与新增 Token、综合、观测成本。

## 结果不是文本拼接

每个子结果应至少带有：任务 ID、状态、来源/证据指针、产物、消耗与不确定性。综合前先去重、过滤无效或失败产物、显式保留冲突和缺口；综合时再统一结构、比较证据并给出结论。

LLM 可以帮助归纳和表达，但不能凭语言流畅度裁定事实冲突。关键分歧必须回到来源、工具回执、测试或人工规则；无法消除时，应交付“已知、未知、冲突点和下一步”，而非伪造一致答案。

## 预算、控制与失败

多 Agent 会放大调用数和上下文复制，因此总预算应先预留综合、重试和降级空间，再按任务价值、复杂度和风险分配；平均分配只适合工作量确实相近的场景。并发上限应由 API 配额、工具容量和共享资源共同决定，而不是只追求吞吐。

暂停、取消、审批和超时必须传播到子工作流；子任务失败后要明确是重试、换能力、跳过并标记部分结果、阻塞下游，还是升级人工。忽略失败结果会把“不完整”伪装成“成功”。

## 工程决策

- **先证明单 Agent 不够。** 以可并行工作、稳定的专业边界、恢复需求或时延目标为证据，而不是为了架构新颖。
- **用子任务契约连接协作。** 明确 `Produces / Consumes / Dependencies / 验收 / 失败策略`，与 [[wiki/AI Agent 架构/10：任务规划与控制|任务规划]]保持同一套产物和依赖语义。
- **把协作当作运行时。** 为任务和汇合节点记录状态、预算、来源、控制信号与失败传播；[[wiki/AI Agent 架构/06：Hooks 与事件控制|Hooks]]负责暴露观察与控制入口。
- **观测端到端结果。** 比较关键路径、成功/部分交付率、冲突率、重试、成本和用户验收，不只看并发数或 Agent 数。

## 常见误解

- **多 Agent 天然更快：** 只有独立工作足够多且资源允许时才可能更快；协调和限流可能反而拖慢任务。
- **角色 Prompt 等于专家：** 专化仍需要合适工具、输入边界、评价标准和可靠的产物接口。
- **综合模型能解决矛盾：** 它只能组织已有材料；事实冲突需要证据验证，见 [[wiki/AI Agent 架构/12：结构化推导与证据验证|结构化推导与证据验证]]。

## 复习

2. 当两个研究 Agent 给出相互矛盾的关键事实时，编排器应怎样交付，为什么不能只让综合模型“选一个”？
