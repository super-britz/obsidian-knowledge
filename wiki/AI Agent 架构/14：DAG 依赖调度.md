# DAG 依赖调度

> [!abstract] DAG 用一张无环依赖图表达“什么必须先完成、什么可以同时开始”。它既避免串行任务浪费独立工作的时间，也避免盲目并行时在前置产物尚未就绪就开始计算；它不负责决定任务是否值得做或结果是否正确。

## 第一性原理

多个子任务的真实关系通常不是一条总顺序：全串行会让无关任务互相等待，全并行会让消费者在输入缺失时执行。把前置关系外化为边，调度器便能只等待必要的任务，并在满足条件时释放节点。

```text
任务契约（产物、输入、依赖、验收）
→ 校验为无环依赖图
→ 找到当前就绪节点并受限并发执行
→ 保存结构化产物和状态
→ 解锁消费者或传播失败
→ 汇合、验证并交付
```

**有向**说明产物的流向；**无环**保证至少存在可启动节点。若出现 `A → B → C → A`，所有节点都会等待，系统没有合法的启动顺序。

## 节点与边的最小契约

| 要素 | 作用 |
| --- | --- |
| **节点 ID** | 稳定标识任务、日志、重试与产物归属 |
| **Produces / Consumes** | 明确交付什么、谁可消费，避免下游从文本猜数据 |
| **Dependencies** | 明确必须先满足的控制顺序 |
| **验收与失败策略** | 定义“可解锁下游”的条件，以及失败时重试、降级、阻塞或人工升级 |

`Consumes` 不应只是“把上游整段回答塞进提示词”。优先传递有类型、来源和版本的产物指针；这既减少上下文复制，也让下游知道数据来自哪里、是否可用。

## 调度：就绪集而非固定顺序

```text
A：获取权威数据       B：获取竞品数据
        │                   │
        └──────┬────────────┘
               ↓
C：对比分析（消费 A、B）
               ↓
D：生成报告（消费 C）

执行：A ∥ B → C → D
```

调度器维护“依赖已满足的节点集合”：A、B 可并发；C 必须等待 A、B；D 再等待 C。并发数仍受 API 配额、工具容量、共享写入和预算限制，不能因图中可并行就无限启动。

纯串行适合隐式链式依赖；纯并行适合完全独立的小批任务；**只有存在多层、部分依赖时，DAG 的显式图与调度成本才值得引入**。依赖、任务数量或协作路径会在运行中不断变化时，静态 DAG 也不再是合适模型。

## 可靠性边界

图在执行前至少要校验：节点 ID 唯一、每个依赖目标存在、没有环、产物命名一致，并为等待和节点执行分别设置超时。循环检测只能防止死锁，不能防止“上游返回错误数据却被标记完成”。

因此应区分以下状态：

- **成功：** 产物通过该节点的验收，可解锁所需下游。
- **可恢复失败：** 在次数和预算内重试、替换能力或补充输入。
- **部分结果：** 只有允许降级的下游才能继续，最终交付须标明缺口。
- **不可恢复失败：** 阻塞依赖节点、取消无意义分支，或升级人工。

可恢复工作流还需保证状态转换可重放、时间与外部副作用可追踪；不能把一次执行时的随机值、当前时间或内存状态当成唯一事实。

## 工程决策

- **先画依赖，再写并发。** 通过 `Produces / Consumes / Dependencies` 证明并行安全；不要用“看起来独立”代替数据和副作用分析。
- **让运行时裁决就绪与失败。** LLM 可以提出图，但图校验、并发、超时、取消、重试和解锁条件应由确定性控制面执行。
- **把图和产物持久化。** 保存图版本、节点状态、输入输出指针、尝试次数、耗时与预算，才能恢复、审计和定位关键路径。
- **以关键路径衡量收益。** 优化目标是端到端时延、成功率和成本，不是节点数或最大并发数。

## 常见误解

- **DAG 就是并行：** DAG 同时表达必须等待的边；并行只是就绪节点的一种执行方式。
- **无环就一定能运行：** 图合法不代表依赖产物正确、权限足够或共享资源不会冲突。
- **完成即可解锁：** 需要区分完成、成功、部分完成和失败；否则错误会被快速传播到汇合节点。

## 复习

1. 为什么 DAG 能同时避免全串行的等待浪费和全并行的输入缺失？
2. 上游节点超时但返回部分数据时，哪些下游可以继续，应该由什么契约决定？
