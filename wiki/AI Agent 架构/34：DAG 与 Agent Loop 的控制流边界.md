# DAG 与 Agent Loop 的控制流边界

> [!abstract] 选择 DAG 还是 Agent Loop，不取决于系统是否“复杂”，而取决于**下一步控制流能否在执行前确定**：已知的依赖和阶段交给图或普通代码；必须先观察真实结果才能决定下一步的部分交给循环。可靠生产形态通常是“确定性外壳 → 自适应内核 → 确定性退出”。

## 第一性原理：控制流的知识出现在哪个时刻

执行系统必须决定下一步做什么。若任务启动前就能列出节点、依赖、成功条件和安全并发关系，控制流是**事前已知**的；继续让模型逐轮“发现”它，只会增加成本、时延与不确定性。若下一步取决于读取文件、检索网页、调用工具后才出现的事实，控制流是**依赖观察**的；强行画成图，就会把尚未知晓的分支不断补进 DAG。

```text
事前可知的控制流
→ DAG / 普通代码：声明节点、依赖、并行与校验

依赖运行时观察的控制流
→ Agent Loop：观察结果 → 决策下一步 → 行动 → 判断是否继续
```

因此问题不是“图还是循环更先进”，而是：**未知信息是否会改变下一步的顺序、次数或目标。** 只有会改变时，模型调用才值得买入适应性。

## DAG 的价值：把执行形状变成可检查的承诺

DAG 适用于节点可命名、边可预先声明、成功可确定性验证，且系统需要在执行前看到拓扑的工作。它提供的不是“线条”，而是以下能力：

- 合规或审计可在运行前审查将执行什么；
- 成本、失败和责任可按阶段归集，告警能落到具体节点；
- 可证明两条分支不会争用同一资源，才安全地并行；
- 固定 ETL、部署流程或批处理可由代码稳定复现，不必反复消耗模型调用。

若节点只是为了处理每次上线才发现的新例外而不断增加，说明图正在替作者枚举原本不可预知的观察；这时应把变化部分从图中收敛为循环，而不是无限扩张分支。[[wiki/AI Agent 架构/14：DAG 依赖调度|DAG 依赖调度]]仍负责其确定性边界。

## Agent Loop 的价值：用运行时策略处理未知分支

Loop 的每一轮用最新观察选择工具、参数或下一步目标；它适合“读取结果后才知道该查什么、修什么或何时停止”的任务。但它以每轮模型调用换取适应性，天然失去执行前完整可见的拓扑，也更难按固定阶段归因。

Loop 只能负责**提出受限候选动作**，不能吸收所有工作：Schema 校验、权限解析、路径归一化、预算检查和确定性后置条件都不需要模型，应放在循环外或工具边界。模型的“我完成了”只是声明；文件是否写入、测试是否通过、结果是否满足 Schema，才是可验证的终止证据。

迭代上限同样只是失控保险丝。若系统主要依靠撞上限结束，说明它缺少明确的目标、后置条件、预算或停止规则；[[wiki/AI Agent 架构/02：ReAct 循环|ReAct 循环]]需要被这些外部约束收敛。

## 生产形态：确定性外壳、自适应内核、确定性退出

将不确定性只留在真正需要它的部分：

```text
认证与来源识别
→ 解析路由、Session、工作区、权限与 Tool Registry
→ 固化历史快照与本轮预算
→ Agent Loop：观察 → 决策 → 行动（可重复）
→ 确定性校验、持久化终态、审计与通知
```

外壳让每个 Turn 在一致权限、工具和上下文内开始；内核处理无法预先列出的分支；出口用取消、超时、预算、权限拒绝、迭代限制和后置条件防止无限或伪成功。这也解释了为什么 [[wiki/AI Agent 架构/33：Agent 运行时契约与发布验证|运行时契约]]不能只写在 prompt 中：入口与循环都必须服从同一控制面。

## 连续性：持久化状态，而不是长寿命 Loop 对象

长驻 Daemon 只表示服务进程持续接收请求；一次 Agent Loop 应是 **per-turn** 对象。把状态挂在 Loop 实例上会导致重启恢复、内存增长和多会话隔离失真。跨轮连续性应来自两个显式机制：

1. **执行前持久化 Session：** 先留下可恢复记录，再执行工具和模型；中途崩溃至少有状态可追踪，结束后再写入回复与终态。
2. **历史快照传入本轮：** 每个 Turn 从已持久化历史构造输入，并避免把新用户消息重复放进 prompt 与 history；仅用于上一轮的 guardrail 也不写入长期历史。

这与 [[wiki/AI Agent 架构/30：Background Agents 持久化后台任务|后台任务]]的持久化控制链一致：对象存活不是可靠性，显式状态、幂等恢复和可查询终态才是。

## 工程决策

1. 先对每一步标记“事前可知”或“依赖观察”；全是前者时使用普通代码或 DAG，不为“灵活”引入 Loop。
2. 在 DAG 中保留预审、阶段告警、确定性校验与可证明并行；只将不可列举的分支收进 Loop，形成可审计的混合结构。
3. 将认证、路由、Session、权限、工具注册、预算和历史快照固定在每个 Turn 的循环外，防止轮间权限或工具范围漂移。
4. 将停止定义为可验证后置条件、预算、取消、超时与明确失败终态的组合；迭代上限只作为最后保险丝。
5. Loop 每个 Turn 新建；执行前写入 Session，按快照恢复历史，避免把临时系统提示或同一用户消息污染后续上下文。
6. 当任务要求事前展示执行内容、精确阶段归因、并行安全证明或低成本固定步骤时，优先选择图或代码，即使模型“也能做”。

## 常见误解

- **“DAG 节点多，说明应该改成 Loop。”** 节点数量不是标准；关键是这些节点能否在运行前稳定列出。大量事后补出的异常分支才是应引入 Loop 的信号。
- **“Loop 更灵活，所以固定流水线也应使用它。”** 对固定任务，灵活性只会变成重复决策成本和可跳过必经步骤的风险。
- **“Daemon 长驻，所以 Loop 可以跨消息保存状态。”** Daemon 的生命周期属于服务；对话连续性应由持久化 Session 和显式历史快照承担。
- **“达到最大迭代数就是正常结束。”** 那只是防失控的兜底；业务完成必须有可验证的后置条件或明确停止决策。

## 复习

- 为什么不能用“复杂度”区分 DAG 和 Loop？——复杂但事前可知的流程仍适合图；简单但下一步依赖未知观察的任务仍需要循环。
- 为什么生产系统常用混合结构？——认证、权限和校验需要确定性；只有基于真实观察的局部决策需要自适应。
- 为什么跨轮状态不能放在 Loop 对象里？——Loop 可重建、服务会重启；持久化 Session 与历史快照才可恢复、可隔离。
