# 可恢复 Agent Turn 与安全续跑

> [!abstract] 持久化的目的不是让 Agent “永远接着跑”，而是让中断的 Turn 有记录、可发现，并只在当前仍安全且仍有意义时受限恢复。可靠恢复需要阶段性 Checkpoint、索引化发现、开关/过期/尝试上限三道门，并将恢复后的执行一律视为无人值守。

## 第一性原理：中断后可恢复，不等于任何时候都应继续

进程崩溃、升级、OOM 或设备休眠会中断正在进行的 Turn。若没有记录，系统丢失状态；若无条件恢复，几天或几个月前的意图可能在用户不在场时继续执行破坏性操作。持久化因此需要同时回答两件事：**中断时留下什么**，以及**重启后为什么现在仍可继续**。

```text
阶段边界产生有价值状态
→ 写入 Checkpoint 与中断索引
→ 重启时低成本发现未完成 Turn
→ 检查恢复开关、意图时效与已尝试次数
→ 以无人值守权限和原并发路由恢复
→ 成功、失败、放弃或取消均写入明确终态
```

恢复是一项新的运行时决策，不是原执行的自动延长。用户当时的批准、文件版本、分支状态和环境都可能已失效；“曾经可以做”不能推出“现在仍应该做”。

## Checkpoint：在阶段边界保存，并在不可逆前先落盘

每轮迭代都保存会在热路径制造大量序列化与 I/O；只在最终保存又无法抵御中途崩溃。合适位置是阶段边界：模型回复完成、工具批次结束、昂贵的压缩摘要生成后，以及即将发生不可逆副作用之前。对密集边界做防抖即可；Checkpoint 要抵抗崩溃，不需要毫秒级追踪。

特别是危险操作前，Session 必须先写入持久层：即使执行过程中崩溃，系统至少能知道“执行意图与上下文曾到达这里”，而不是留下无法区分未开始、已调用或已完成的空洞。[[wiki/AI Agent 架构/34：DAG 与 Agent Loop 的控制流边界|per-turn Loop]] 的连续性本就来自显式 Session 与快照，而非内存对象存活。

## 发现与不变量：用索引定位中断，而不是扫描所有历史

启动时扫描全部 Session 寻找未完成 Turn，会使运行越久启动越慢，而且易漏掉某些状态。应维护一个持久化中断标记索引：每个 InProgress Turn 有一条小型标记，启动仅查询该索引，再按需读取对应 Session。

核心不变量是：

```text
Session.InProgress = true  ⇔  interrupted-turn 标记存在
```

它要求完整保存、增量补丁、成功结束、失败、取消和放弃等**所有**写路径同步维护两侧。只在主 `Save` 中维护、遗漏某个读改写补丁，会产生“已完成却仍被恢复”的孤儿标记，或“已中断却无法发现”的隐身 Turn。恢复系统自身一旦不可信，效果比没有恢复更危险。

## 恢复三道门：暂停、过期与尝试上限

发现 Checkpoint 后不能立即执行，至少经过三道相互独立的控制：

1. **恢复开关：** 运维可选择“发现但不续跑”，保留证据以便排障，而不是只能删除或自动执行。
2. **过期窗口：** 意图超过工作会话或业务允许的时效后，以可观测的“放弃”终态结束；陈旧意图不能因重启而重新获得执行权。
3. **尝试次数上限：** 防止持续失败的 Turn 反复在启动时触发恢复。计数必须在模型调用或高风险执行**之前**持久化；若事后才写入，调用期间崩溃会让次数永远不增长，形成启动死循环。

放弃不是静默删除，恢复也不应静默发生。两者都需要原因、时间、关联 Checkpoint 与操作者可查询的事件，才能在故障后解释系统为何没有或为何继续行动。

## 当前执行环境优先：恢复后永远是无人值守

是否有人值守取决于恢复这一刻，而不取决于 Session 最初来自桌面、CLI 还是渠道。Daemon 启动时恢复的 Turn 没有人可处理审批或阻止危险动作，因此必须一律采用无人值守的更窄权限、自动审批拒绝清单和通知规则。把原始来源直接当成当前监督状态，会把交互式特权授予一个空房间。

恢复还必须使用原 RouteKey 进入与正常入站请求相同的锁与并发控制。若绕过路由层，同一 Session 可能一边恢复、一边接收新请求，产生两个写者和不可预测的交错历史。[[wiki/AI Agent 架构/30：Background Agents 持久化后台任务|后台任务]]的调度与并发约束在恢复路径同样适用。

## 持久化不能替代：幂等、版本兼容与取消

Checkpoint 能说明“系统曾计划或尝试调用工具”，却无法证明副作用究竟有没有落地。邮件可能已发出、支付可能已扣款、Git push 可能已成功；盲目恢复会重复执行。因此外部副作用必须在工具层使用幂等键、操作 ID 或可查询对账状态，使重复尝试变成安全 no-op 或可判定结果。

持久状态还会跨版本存在。Checkpoint 应带格式/语义版本；新版本无法兼容读取时，必须记录可观测的放弃或迁移结果，不能让 Daemon 启动崩溃。最后，取消语义必须覆盖恢复：用户取消意味着清除中断标记并写入终态，而不是把一个“已取消”任务留给下次启动复活。

## 工程决策

1. 在模型完成、工具批次结束、昂贵摘要完成和不可逆动作前设置带防抖的阶段性 Checkpoint；保存的是可恢复状态，而非每个内部细节。
2. 使用持久化中断索引发现未完成 Turn，并在所有保存/补丁/终态路径上维护 `InProgress ⇔ 标记存在` 不变量。
3. 将恢复设计为显式策略：可全局暂停、按意图时效放弃、按尝试次数限制；在调用前先持久化本次尝试。
4. 恢复的 Turn 默认无人值守，重新应用更窄权限、审批和通知规则，并按原 RouteKey 获取正常的 Session 并发锁。
5. 为有外部副作用的工具实现幂等键、操作状态查询或对账；不要把 Checkpoint 当作“副作用成功”的证明。
6. 版本化 Checkpoint，并为不兼容、过期、取消、恢复失败和恢复成功写入可查询事件与终态；取消必须移除恢复资格。

## 常见误解

- **“每轮都 Checkpoint 最可靠。”** 它会把热路径变成频繁写盘；应在产生高价值状态、即将不可逆或可能长时间运行的阶段边界保存。
- **“有 Checkpoint 就该自动恢复。”** 陈旧意图、无人值守权限和环境变化都可能让恢复比失败更危险。
- **“恢复次数在失败后再记也行。”** 如果调用过程中崩溃，计数永远不会增加，启动恢复会无限循环。
- **“Checkpoint 防止重复副作用。”** 它只记录过程；外部效果是否落地必须由工具层幂等和对账保证。

## 复习

- 为什么中断发现要用索引而不是扫描全部 Session？——启动成本随历史增长，索引让稳态发现只访问未完成 Turn，并能承载一致性不变量。
- 为什么恢复后必须视为无人值守？——监督状态属于执行时刻；原 Session 的交互来源不能证明当前有人可审批或阻止危险操作。
- 为什么 Checkpoint 不能保证幂等？——它无法原子地证明外部副作用是否已落地，重复安全必须由工具协议提供。
