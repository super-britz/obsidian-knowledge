# Temporal 持久化工作流

> [!abstract] Temporal 的价值不是把普通函数“放到后台”，而是将长时任务的**编排决策与执行历史持久化**：Workflow 用可重放的确定性逻辑决定下一步，Activity 承担真实世界的副作用。进程故障后，系统用历史重建已做决策，并从已确认的位置继续，而不是从头猜测或依赖散落的手写状态机。

## 第一性原理

Agent 任务可能持续很久，且跨越搜索、模型调用、人工等待和外部工具。进程内状态会随崩溃丢失；把完成标记散写在数据库或消息队列中，又会把依赖、重试、聚合、超时和观察逻辑复制到每个业务流程。

```text
长时任务包含多个依赖步骤和真实副作用
→ 将“下一步做什么”的决策序列记录为可重放历史
→ 把真实执行封装为有结果、超时和重试策略的 Activity
→ 故障后重放确定性 Workflow，复用已确认的 Activity 结果
→ 从可靠状态继续，并保留可检查的事件轨迹
```

因此，Temporal 的本质是**事件历史驱动的持久化编排**。它恢复的是工作流的决策状态，不是回滚外部世界。

## Workflow 与 Activity：决策和副作用必须分开

| 角色 | 应承担的内容 | 关键约束 |
| --- | --- | --- |
| **Workflow** | 步骤顺序、依赖、分支、等待、超时、重试策略、取消与状态推进 | 必须确定性、可重放；不能直接访问不稳定外部世界 |
| **Activity** | 网络请求、LLM 调用、数据库/工具操作、文件处理等真实工作 | 可以有副作用；需明确超时、重试、幂等与结果契约 |

同一段 Workflow 在重放时必须给出同样的命令序列。因此当前时间、随机数、普通 HTTP、环境变量和非受控并发都不能直接决定 Workflow 分支；它们应使用工作流提供的确定性 API，或移入 Activity 并把结果记录回来。

这并不表示 Activity 可以随意重试。若 Activity 已经写入外部系统、但在返回前发生网络故障，编排层无法仅凭“超时”判断副作用是否发生。写操作需要幂等键、查询确认、补偿或人工处理路径。

## 用事件历史恢复，而非用快照猜状态

活动的调度、完成、失败、定时器和外部信号都形成历史。Worker 失效后，新的 Worker 重放这些事件：过去已完成的 Activity 不再重新执行，而 Workflow 重新计算到当前决策点后继续。

这带来三个直接收益：

1. **恢复：** 进程、容器或 Worker 故障不会自然抹掉已确认的进度。
2. **统一控制：** 超时、重试、依赖、并行和取消以工作流级别表达，而不是每个业务函数各自实现。
3. **可追溯：** 事件历史可用于定位失败步骤、检查输入和重放问题，形成“时间旅行”式的调试证据。

但事件历史不是业务真相的唯一存储：大对象应外置并传引用，敏感数据需最小化和治理，无界循环必须控制历史增长。

## 版本门控：运行中的历史也是接口

Workflow 一旦启动，其历史就定义了旧代码期望重放的命令顺序。直接插入、删除或改变关键命令，可能让新代码无法解释旧历史，造成非确定性错误。

```text
旧历史需要按旧分支重放
+ 新实例需要执行新功能
→ 在稳定变更点记录版本标记
→ 重放旧历史走旧分支，新实例走新分支
→ 迁移结束后再按生命周期清理旧分支
```

版本标记应按**功能语义**命名并记录迁移目的，而不是使用模糊编号。版本门控解决的是工作流历史兼容，不替代 API、数据 schema 或外部副作用的迁移方案。

## 信号、查询与人工控制

运行中的任务需要外部控制，但读状态和改状态不能混为一谈：

- **Signal：** 传入会改变工作流状态的命令，如暂停、恢复、取消、补充输入或审批结果；应校验身份、顺序、幂等和可接受状态。
- **Query：** 读取当前状态、进度或等待原因，不应产生副作用，也不应改变后续执行。
- **取消与超时：** 取消应向正在执行的 Activity 传播，并由流程定义已启动副作用的收尾策略；不同超时分别约束单次执行、总体调度窗口和心跳失联。

这与 [[wiki/AI Agent 架构/06：Hooks 与事件控制|事件控制]]互补：Hook 可观察生命周期，Temporal Signal/Query 将受控交互纳入持久化状态机。

## 并行、子工作流与终止边界

独立任务可以并行调度，必要时采用“达到足够结果即可继续”的等待策略；复杂且可独立治理的子任务可用子工作流隔离重试、可视化与失败边界。并行不是默认优化：必须先确认输入独立、限流预算和结果汇合语义。

每个工作流还应有明确的：

- **总 deadline、Activity deadline 与心跳策略；**
- **最大重试次数、不可重试错误及降级路径；**
- **事件历史/循环上限与 Continue-As-New 轮换策略；**
- **完成、部分完成、取消和人工接管的最终状态。**

“Fire-and-forget”只适合非关键且可丢失/可补偿的旁路工作；不要把关键审计、扣费或状态写入伪装成不需要等待的后台调用。

## 工程决策

1. 仅将需要跨进程恢复、长等待、多步依赖或统一治理的任务建成持久化工作流；短且无状态的请求无需引入额外运行时。
2. 先划分 Workflow 的确定性决策与 Activity 的真实副作用，再实现业务逻辑；这是重放安全的前提。
3. 为所有可写外部系统的 Activity 定义幂等、超时、重试和不确定结果的处理，而不是依赖“Temporal 会自动恢复”。
4. 每次修改运行中 Workflow 的命令顺序或分支时使用版本门控，并在部署前对历史进行重放测试。
5. 将工作流 ID、事件历史、Activity 回执、预算和取消原因接入观测与审计，使恢复过程可解释。

## 常见误解

- **“Temporal 像数据库事务，会自动回滚所有副作用。”** 它持久化编排历史；外部写入仍要自行处理一致性。
- **“所有业务代码都应写进 Workflow。”** 有副作用或不确定性的信息应放在 Activity，否则重放会失效。
- **“能重试就不需要幂等。”** 重试恰恰会放大重复执行的风险。
- **“版本升级只要滚动发布。”** 运行中的工作流还会重放旧历史，命令序列变化必须兼容。
- **“历史越多越方便调试。”** 无界历史会拖慢运行和存储，应外置大数据并定期轮换。

## 复习

- Temporal 要解决什么失败？——长时、多步骤任务在进程故障后丢失进度，且手写状态机难以统一治理。
- 核心分工是什么？——Workflow 负责确定性编排，Activity 负责真实副作用。
- 为什么要版本门控？——旧历史必须能被新代码重放，运行中的 Workflow 也是兼容接口。
- 最关键的边界是什么？——持久化编排不等于外部操作原子；副作用仍需幂等、确认或补偿。
