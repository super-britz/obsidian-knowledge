# Agent 超时的阶段所有权

> [!abstract] 超时不是给整轮 Agent 随便设一个秒数，而是判断“承诺推进某个阶段的组件已沉默多久”。先为模型、工具、审批和传输分配等待所有权，再让各自时钟独立处理；否则短超时会误杀正当工作，长超时会掩盖真实卡死。

## 第一性原理：时间只有在知道谁该推进时才有意义

大型图像渲染耗时八分钟，可能仍在工具自己的十分钟契约内；LLM 数据流输出半句话后八分钟没有新字节，则是 Provider 或传输已失去进展。单一整轮计时器无法同时处理这两类等待；“任何活动都重置”又会让无用循环无限续命。

```text
TurnPhase
→ 指定等待所有者
→ 定义该所有者的进展信号、时限与取消方式
→ 对应 Watchdog 只观察自己的阶段
→ 以带原因的终态传播结果
```

一段等待只能有一个所有者。没有所有者，计时器只是掩盖设计空洞；两个计时器同时拥有它，则会对错误和取消权产生冲突。

## 阶段与时钟：分别观察模型沉默、传输静默和工具逾期

Loop 应显式暴露 `TurnPhase`。严格等待远端模型的 `awaiting_llm`，以及最终强制停止总结的 `force_stop`，才计入 LLM 空闲；工具执行、审批、重试、压缩与消息注入各由自己的组件限制。阶段实例还应有迁移序号，避免同一次等待重复告警，并允许重新进入时重新计时。

三只时钟各答一个问题：

- **Soft Idle：** 这一模型等待阶段多久没有活动？只报告一次状态，不取消。
- **Hard Idle：** 该模型等待是否超过策略上限？以类型化原因取消 Run，并在外层传输截止前留出清理余量。
- **流间隙 Watchdog：** 流式响应最近是否仍有数据块？它在响应体内部按字节/数据块间隔计时，不能由整轮经过时间代替。

它们不可互相重置：工具完成不能证明卡住的流恢复，Provider token 也不能延长工具超时。流间隙超时时保留部分文本；没有任何文本则返回明确占位与终态，不应默认对同一上游改用非流式重试。

## 嵌套调用与超时终态：计时可临时借用，结果必须可解释

压缩是本地阶段，不应计入模型空闲；但压缩内部调用 LLM 生成摘要时，远端阻塞仍需覆盖。用 `EnterTransient(awaiting_llm)` 临时借用模型阶段，并通过幂等恢复闭包归还外层阶段，比在业务逻辑散落“暂停/恢复 Watchdog”可靠。

若阶段跟踪器出现嵌套错误或遗漏恢复，它已不能可靠判断当前等待什么。生产环境不应依据坏数据贸然取消合法、昂贵的操作；应记录结构性错误并停用本次 Watchdog。严格开发环境则尽早失败。代价是可能放过真实卡死，因此“监测失效”本身必须可观测。

Hard Idle 不是通用的 `context canceled`：取消原因、阶段、部分输出和终态状态都要传给 Provider、推测性工具、持久层和调用方，才能区分用户取消、模型无进展与正常完成。它也让 [[wiki/AI Agent 架构/40：可恢复 Agent Turn 与安全续跑|恢复逻辑]] 知道这是一轮超时截断，而非成功结束。

## 工程决策

1. 为每个 TurnPhase 写明等待所有者、进展信号、合法时长与取消边界；不要用一只泛化计时器覆盖模型、工具和审批。
2. 将 Soft Idle 作为可见性事件、Hard Idle 作为策略取消，并在流式 Provider 边界另设逐数据块间隙计时。
3. 为嵌套远端调用提供成对、幂等的临时阶段 API；用退出断言和严格模式发现阶段漂移。
4. 阶段数据不可信时，显式停用或降级 Watchdog，并记录覆盖损失；超时终态必须保留类型、阶段、部分输出和清理结果。

## 常见误解

- **“整个 Run 一只超时器就够。”** 它会误杀合法长工具，或让死亡的模型/传输等待太久。
- **“任何活动都应重置计时。”** 不同所有者的进展不能相互证明，会把真正卡死的阶段无限续命。
- **“压缩不计入空闲，就无需监测。”** 本地整理可排除，但内部 LLM 调用仍需临时进入模型等待阶段。
- **“阶段状态异常时直接取消最安全。”** 不可信状态也无法证明应杀掉什么；必须明确停用、降级或严格失败的取舍。

## 复习

- 为什么先问“谁拥有等待”而不是先设 90 秒？——只有知道推进者、进展信号和合法时长，超时才不会混淆不同等待。
- Soft 与 Hard 为什么要分离？——前者只增加可见性，后者改变执行；可分别调整告警噪声和取消策略。
- 为什么流间隙不能由整轮时间代替？——整轮时钟不知道响应体内部是否仍有数据块，无法精确识别“输出一部分后静默”的故障。
