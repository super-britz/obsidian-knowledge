# Prompt Cache 的字节稳定性

> [!abstract] Prompt Cache 复用的不是“意思相同”的请求，而是从开头开始逐字节相同的序列。可缓存性因此是一份 Request Builder 的序列化契约：稳定内容必须稳定编码、稳定排序并置于易变内容之前；权限、检索和缓存各自维护边界，任何有意重写都要能追溯其对前缀的影响。

## 第一性原理：第一个不同字节就是复用边界

两个请求即使表达同一逻辑，只要工具数组顺序、Map 序列化、空值表示、时间戳或历史截断位置不同，Provider 就会从第一个差异处停止复用后续前缀。缓存因此不是 Provider “猜中语义”的偶然优化，而是系统向 Provider 提供的稳定字节接口。

```text
稳定的系统规则 | 稳定排序的工具 Schema | 可复用历史前缀 | 当前 Turn 与易变内容
──────────────────────────────────────────────────────────────────────
逐字节保持不变的部分越长，后续请求可复用的前缀越长
```

若同一逻辑状态会生成不同 Wire 字节，缓存命中就只能靠运气。正确的验证对象是实际发出的 Request 表示，不是内存对象是否 `Deep Equal`：实现必须确定性排序、规范空值与默认字段、固定序列化格式，并避免让当前时间等易变值污染前部。

## Breakpoint 是稀缺的架构资源

Provider 通常只提供有限数量的缓存断点，不能为每个逻辑区域各加一个标记。应按两维分配：**这些字节由谁共享**，以及**它们变化得多快**。典型顺序是：

1. 跨用户、跨 Session 稳定的 Persona 与核心规则；
2. 完整、确定排序的工具 Schema 目录；
3. 随对话增长但可滚动复用的历史前缀；
4. 单 Session 稳定的指令、Sticky Context 或用户级目录；
5. 当前用户消息、时间、临时状态等易变内容。

断点放错位置会让本可复用的工具目录或滚动历史变冷；增加新的逻辑区域时必须重新分配已有插槽，而不是把更多 Marker 当作自动收益。关键原则是：**易变值永远放在最后一个能共享的稳定边界之后。**

## 缓存、工具发现与授权：三个边界不能合并

工具 Schema 的展示、工具的按需发现和运行时授权经常被误写成同一个“过滤工具”步骤，实际职责不同：

```text
缓存边界：保持工具数组字节稳定，保证前缀复用
发现边界：决定模型当前看到哪些 Schema，支持按需检索
授权边界：在执行时按身份、参数、工作区与审批决定能否调用
```

为了反映临时权限而删除或重排工具 Schema，会使稳定目录变冷，却仍无法替代执行期拒绝；仅隐藏 Schema 也不能阻止模型猜测工具名。应让 [[wiki/AI Agent 架构/38：延迟加载与工具发现|延迟加载]]管理模型可见性，让[[wiki/AI Agent 架构/24：策略治理与授权决策|策略]]和[[wiki/AI Agent 架构/25：安全执行与能力沙箱|执行边界]]在真正调用时强制授权。

这类分离还让缓存前缀保持稳定：权限变化影响调用结果，而不改写全部工具定义。

## Fork 真实 Request：追加比重建更可信

派生 Turn 后建议、推测调用或其他相近请求时，最容易破坏缓存的方式是从高层状态重新构建“等价”请求。一个默认字段、工具重排、不同的推理预算或模型参数，都会使原本热的父请求前缀变冷。

正确做法是在 Dispatch 时捕获真实 Request Artifact，从它 Fork：复制可变消息容器，只追加明确的派生消息；将工具数组和其他父前缀视为只读；仅允许被显式列出的字段变化。Fork 完成后不要再为了单次调用“优化”输出上限、温度、工具范围或推理预算，除非确认这些字段不属于缓存契约。

这和 [[wiki/AI Agent 架构/34：DAG 与 Agent Loop 的控制流边界|真实执行 Artifact]] 的原则一致：应从系统实际使用的对象派生，而不是从近似的高层意图重新推导。

## 观测漂移：命中失败只是症状，不是原因

Cache Miss 只说明复用失败，不能说明第一个不同字节在哪里。每次有意的原地重写——如分层压缩、观察窗口裁剪、图片剥离或查询预算调整——应记录动作、消息索引、旧/新哈希、层级与原因；再与相邻请求日志关联，才能区分“有意改写导致的必然失效”和“非确定性序列化导致的意外漂移”。

观测还要区分归因与策略：流量来源字段可以比较不同渠道、调度或客户端的成本与 cache ratio，却不应被偷偷当成 TTL 或缓存控制开关。评估缓存设计时同时看：

- Cache Read 与 Cache Creation；
- 延迟、每个用户 Turn 的模型调用数与总成本；
- 任务完成率、质量和安全约束是否仍成立。

高命中率可能伴随不必要的调用；低缓存创建比也可能隐藏无法完成任务的请求。缓存是运维信号，不是独立的产品目标。

## 工程决策

1. 将实际发送的 Provider Request 作为缓存契约快照；为连续请求写字节级 diff 测试，覆盖 Map、数组排序、默认字段、空值和时间等漂移来源。
2. 按共享范围与变化频率分配有限 Breakpoint：跨用户规则、稳定工具目录、滚动历史、Session 稳定上下文依次安排，将当前 Turn 和易变值放在最后。
3. 为工具 Schema 建立确定性排序与规范编码；权限变化不改写 Schema 数组，工具发现和执行期授权分别实现。
4. 从已 Dispatch 的真实 Request Fork 后续请求，只追加明确差异；Fork 后的共享前缀不可变，任何额外调参先评估其缓存影响。
5. 对每次 Prompt 重写记录前后哈希、位置、原因和预期影响；当无重写仍发生漂移时，优先排查非确定性序列化。
6. 将缓存指标与成本、延迟、调用次数和任务成功率联动评估，并明确哪些字段只是流量归因而非 Provider 缓存策略。

## 常见误解

- **“语义相同的 Request 应该命中缓存。”** 缓存匹配字节前缀；Map 顺序、字段缺省或一个移动的截断边界都足以失效。
- **“多放几个缓存标记总会更好。”** 插槽有限，Marker 位置改变还可能修改原本希望复用的字节；应按共享和稳定性做取舍。
- **“按权限过滤 Schema 更安全。”** 它会打散工具前缀，且不能替代执行期授权；隐藏与拒绝是不同机制。
- **“重建一个逻辑等价的 Fork 没关系。”** 默认值和序列化细节会漂移；应从实际已发送的请求 Artifact 派生。

## 复习

- 为什么缓存问题要从 Wire 字节而不是对象比较开始？——Provider 的复用在第一个不同字节结束，内存对象的语义相等无法证明实际前缀一致。
- 为什么 Breakpoint 要按共享范围分配？——有限插槽应优先覆盖跨更多请求且变化更慢的字节，才能获得最大复用。
- 为什么授权不能通过改写工具数组实现？——授权是执行时决策；改写 Schema 只会损害缓存，还留下其他调用路径的安全空洞。
