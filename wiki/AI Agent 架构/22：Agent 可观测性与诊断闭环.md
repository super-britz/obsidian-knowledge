# Agent 可观测性与诊断闭环

> [!abstract] 可观测性不是多打日志，而是为运行决策保留可关联的证据：先由指标发现趋势，再用追踪定位一次任务的链路，最后用日志还原细节。它让“系统慢了或失败了”变成可回答的因果问题，但也要受成本、数据量和隐私边界约束。

## 第一性原理：未知内部状态，无法可靠改进系统

Agent 的一次结果跨越编排、模型、工具、记忆与外部服务。用户只看得到慢、错、贵或中断；若没有运行证据，团队无法区分是整体退化、某类任务异常，还是单次依赖失败。

```text
一次 Agent 任务
→ 各层产生耗时、结果、资源消耗与错误
→ 记录可聚合、可串联、可还原的证据
→ 发现异常 → 定位根因 → 采取修复、降级或限额措施
```

因此，观测的目标不是“记录一切”，而是用最小必要证据支持性能、可靠性、成本与质量相关的行动。

## 三类证据各解决一个问题

- **Metrics（指标）**：把大量运行聚合成成功率、延迟分位数、Token/成本、错误率等趋势，用来回答“是否普遍变差、何时告警”。
- **Traces（追踪）**：将一次请求的 Span 串成链路，用来回答“这一任务卡在哪一跳、调用顺序与耗时是什么”。跨服务要传播 Trace Context。
- **Logs（结构化日志）**：记录错误、输入摘要、策略版本、回执等上下文，用来回答“当时具体发生了什么”。日志应带 `trace_id`，才能从日志回到追踪。

指标发现面，追踪缩小到一次路径，日志补足细节；它们不是可互相替代的三套系统。

## 从症状到根因的诊断闭环

```text
用户反馈“下午任务很慢”
→ 指标按任务类型、版本和时间确认范围，并检查 P99 延迟、失败率、Token/成本
→ 在异常窗口找到慢 Trace，定位编排、LLM、检索或工具调用的耗时段
→ 用同一 trace_id 的结构化日志确认错误、输入规模、重试与回执
→ 修复、降级、限流或调整预算，并用指标验证是否恢复
```

这里的机制推导是：**聚合数据可发现变化但会丢失个例；单次链路可归因但成本更高；文本细节可解释但难汇总。** 所以应以共同任务/Trace 身份将三者关联，而不是孤立查看仪表盘或日志。

## 约束：可观测性本身也是生产负载

来源事实表明，高基数标签、全量 Trace 采样和循环逐条日志会推高内存、存储与查询成本；不加区分的健康检查还会把非关键依赖波动放大为服务重启。

- 指标标签只保留有限且稳定的维度，如工作流类型、状态、版本；不要放用户 ID、任务 ID 或时间戳。
- Trace 采用按比例或按错误/关键路径提高的采样策略；保留足以排障的上下文，避免采集秘密和整段敏感 Prompt。
- 日志记录结构化摘要与关键状态，不把高频循环逐项输出。
- 健康检查区分**关键依赖**和可降级的非关键依赖；告警还要定义级别、阈值、持续时间与责任人。

## 工程决策

1. 从故障与成本决策反推指标：每个关键任务至少能看到完成状态、端到端延迟、失败类型、Token/成本和版本；不要为了“完整”先堆指标。
2. 为一次任务分配并传播任务 ID/Trace Context，在编排、模型、工具和存储边界统一关联；否则跨层问题只能靠猜。
3. 仪表盘用于持续判断趋势，告警用于要求行动，追踪与日志用于排障；三者的留存、采样和字段按服务等级与隐私分类配置。
4. 可观测性不能替代质量评估和业务审计：模型回答是否正确、操作是否合规，仍需要独立的评测、策略和审计证据。

## 常见误解

- **“日志足够多就能排障。”** 日志难以发现总体趋势，也难重建完整调用链；应以指标和 Trace 缩小范围。
- **“所有 Trace 都采样最安全。”** 全量采样可能使观测系统本身成为成本和性能瓶颈；关键是有策略地保留异常与关键路径。
- **“依赖不可用就必须整体不健康。”** 非关键能力可降级；把它判为致命会放大局部抖动。
- **“看到延迟就知道根因。”** 延迟只是症状；还需链路、错误、重试和输入规模等证据交叉验证。

## 复习

- 为什么三支柱必须关联？——它们分别保存趋势、链路和细节，单独使用都会留下盲区。
- 若 P99 延迟上升，下一步是什么？——按任务/版本缩小指标范围，再用异常窗口的 Trace 定位耗时段，并用关联日志验证原因。
- 因此如何控制观测成本？——限制标签基数与日志字段，按风险采样，按关键性配置健康检查、留存和告警。
