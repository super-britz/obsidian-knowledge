# 上下文工程

> [!abstract] 上下文工程是在每次模型调用前，选择**完成当前一步所需的最小可靠信息集**。它不是把更多历史塞进 Prompt；无关、过期或不可信的信息会占用窗口，并误导决策。

## 第一性原理

LLM 只能依据本次请求中实际注入的 Token 生成下一步。目标、权限、任务进度、工具回执和历史结论若没有以合适形式进入当前工作集，模型就不能稳定使用它们。

```text
当前目标 + 不可突破的约束 + 已验证状态 + 本步相关证据/工具
→ 构造工作集 → 模型提出下一步 → 执行并观察 → 更新外部状态
```

因此要问的不是“如何记住全部”，而是：**为了安全完成下一步，什么信息必须在场，什么信息应留在外部并保留指针？**

## 三层责任

| 层 | 用途 | 不能替代 |
| --- | --- | --- |
| **当前上下文** | 支撑本轮决策 | 长期事实库或任务状态机 |
| **任务状态** | 记录目标、步骤、审批、产物和失败 | 对话历史 |
| **长期记忆** | 跨任务召回经验与偏好 | 权威业务记录或当前上下文 |

把三层混在一起，会出现两种错误：把长历史每轮全塞进 Prompt，或把只应短暂存在的信息误写成长期记忆。

## 四个操作

| 操作               | 解决什么       | 正确做法                   |
| ---------------- | ---------- | ---------------------- |
| **外置（Write）**    | 窗口有限、会话会结束 | 将计划、关键回执、产物和原文位置写入外部状态 |
| **选择（Select）**   | 全量历史是噪音    | 按当前步骤、权限、时效和来源取回少量证据   |
| **压缩（Compress）** | 工具结果和历史太长  | 保留结论、依据、未决问题与恢复指针      |
| **隔离（Isolate）**  | 子任务信息密度不同  | 在独立上下文中完成子任务，只回传受约束结果  |

每项信息都应能回答：来源是什么、为什么本轮需要、何时过期、超预算时先删还是先压缩。

## 上下文契约

建议稳定前缀与可变工作集分离：

```text
稳定前缀：系统边界、任务目标、输出契约、权限与预算
可变工作集：当前步骤、已验证状态、相关证据、最近回执、可用工具
外部指针：完整历史、长工具输出、文件/URL、检索记录、原始证据
```

Prompt Cache 只能复用重复前缀，降低成本和延迟；它不判断信息是否相关，更不能让过期状态变正确。先保证上下文正确，再谈缓存命中。

## 边界与工程决策

- **检索先过滤再排序。** tenant/user/project、权限、来源和时效应先于语义相似度；检索内容也可能包含提示注入或错误指令。
- **把关键状态留在权威外部存储。** 不把任务进度、审批或副作用事实只留在聊天文本里。
- **为每种内容设预算。** 目标、约束、关键回执优先级高于闲聊和长原文；超过预算时压缩低优先级内容。
- **子任务只返回决策需要的结果。** 主 Agent 获得结论、证据指针、置信边界和未决问题，不接收全部中间文本。
- **观测“看错了什么”。** 记录截断、检索命中、过期证据、压缩失败、提示注入拦截和恢复成功率。

## 常见误解

- 大窗口提高容量，不保证模型能正确选用所有信息。
- 向量检索只给候选，不替代权限、来源和事实验证。
- “最近 N 条消息”只是截断策略；不能裁掉目标、审批、关键回执和未完成任务。

## 复习

1. 为什么任务状态不能只存在于对话历史中？
2. 一段历史被压缩后，哪些信息必须保留以便恢复或追责？
