# 35期 AI 全栈课程学习地图

本页回答“46 节课之间是什么关系”。逐节内容从 [[wiki/直播课/课程笔记/00-索引|35期 AI 全栈课程笔记]] 进入；学习优先级与作品方向见 [[35期 AI 全栈课程学习总纲]]。

## 总体主线

```text
AI 辅助开发
  -> 前端与云架构
  -> 可验证的企业 AI 工作流
  -> 复杂业务与系统边界
  -> 性能、可观测性与图形学
  -> 大模型、RAG、微调与 Agent
  -> 本地智能客服系统
```

课程并不是把工具名和技术名并排堆在一起。它试图完成一次能力升级：从“能让 AI 生成代码”，走到“能设计、实现、验证、部署并解释一个复杂系统”。

## 阶段地图

| 阶段 | 课程 | 核心问题 | 阶段产出 |
| --- | --- | --- | --- |
| 课程定位与 AI 开发工作流 | 01-05 | 如何把想法、需求、设计、代码、测试和部署连接起来？ | 一个经过浏览器验证和自动化测试的前端产品 |
| 前端架构与阶段一实战 | 06-12 | 页面之外，缓存、BFF、Serverless、后端分层和状态如何协作？ | 一个有清晰请求链路和类型安全接口的全栈应用 |
| 企业 AIGC 工程提效 | 13-18 | 如何让 AI 在长任务中按角色协作、保留状态并接受验证？ | 一条需求、实现、评审、测试、文档同步的研发流水线 |
| Web3、区块链与 Serverless | 19-30 | 钱包、合约、授权、链上状态与云端渲染如何工作？ | 不接真实资金的 DApp 与 SSR / Serverless 实验 |
| 复杂业务与工程质量 | 31-36 | 实时交易、跨境流程、性能、安全和可观测性如何进入架构？ | 交易系统模拟器、性能报告或 AIOps 原型 |
| 图形学 | 37-39 | 浏览器如何组织 3D 场景、渲染管线、模型资产与 GPU 计算？ | 一个可交互、可测量性能的 3D 展示 |
| 大模型应用工程 | 40-46 | 模型、微调、RAG、工具与 Agent 如何按职责组成业务系统？ | 本地模型服务、RAG、业务 API 与 Agent 组成的客服原型 |

## 五条能力链

### 1. 从生成代码到交付产品

前置课程：01-05、09-12。

目标不是得到一段能运行的代码，而是建立完整证据链：

```text
需求 -> 设计 -> 实现 -> 浏览器验证 -> 自动化测试 -> 部署 -> 复盘
```

AI 可以参与每一步，但最终质量由可运行结果、测试与人工判断确认。

### 2. 从前端页面到系统架构

前置课程：05-12、23、28-29、36。

需要能解释：

- 浏览器请求如何经过 CDN、边缘、网关、函数和数据服务。
- CSR、SSR、Streaming SSR 与 Hydration 如何影响性能和部署。
- 缓存、队列、权限、日志和成本为什么是前端项目的一部分。
- BFF 与类型安全接口如何降低前后端协作成本。

### 3. 从单个 AI 到可控工作流

前置课程：13-18、34、43-44。

核心变化是把复杂任务拆成不同职责：

```text
Planner -> Implementer -> Reviewer -> Validator -> Human approval
```

稳定的工作流需要明确输入输出、保存任务状态、隔离权限，并让测试或独立验证者检查结果。

### 4. 从技术名词到复杂业务模型

前置课程：19-35。

Web3、交易所和跨境系统的价值在于训练系统思维：

- 资产、身份、授权和状态如何建模。
- 实时数据、异步任务、风控和审计如何进入前后端流程。
- 哪些操作必须由用户签名或人工确认。
- 技术实现如何受到资金安全和合规边界约束。

### 5. 从调用模型到设计大模型系统

前置课程：40-46。

需要牢牢记住：

| 机制 | 主要职责 |
| --- | --- |
| Prompt | 当前任务的角色、格式和边界 |
| QLoRA | 稳定语气、格式和行为倾向 |
| RAG | 文档知识、FAQ 与来源依据 |
| Tool / API | 订单、物流、库存等实时事实 |
| Agent / Workflow | 路由、工具执行、状态、回退和人工转接 |

模型“回答得像客服”与系统“真的查询了订单”是两个不同的验收目标。

## 按目标选课

### AI 全栈交付

建议顺序：01-12 -> 13-18 -> 34-36 -> 43-46。

重点补齐需求、架构、验证、部署、可观测性和 Agent 编排。

### Serverless 与云架构

建议顺序：05-08 -> 10-12 -> 23 -> 28-29 -> 36。

重点建立请求链路、运行时、缓存、权限、成本和故障定位模型。

### Web3 与交易系统

建议顺序：19-22 -> 24-27 -> 30-33。

只使用测试网或 mock 数据练习，重点理解合约交互、授权、实时数据与风控。

### 性能与图形学

建议顺序：35 -> 37-39。

先掌握浏览器性能分析，再进入渲染循环、GPU 管线和 3D 资产工作流。

### 大模型应用工程

建议顺序：40 -> 41-42 -> 43-44 -> 45-46。

先理解模型与职责边界，再做 RAG、Agent、本地训练和客服系统集成。

## 稳定结论

- 工具使用门槛会下降，长期能力来自问题分解、架构判断和验证。
- AI 生成结果必须经过运行、测试和独立评审，不能只看输出是否完整。
- 前端工程师需要理解后端、云服务、权限、数据和可观测性，才能交付完整系统。
- 微调不是知识库，RAG 不是实时数据库，Agent 也不是无边界自动执行器。
- 项目价值由可展示结果、技术取舍和验证证据共同决定，不由技术名词数量决定。
