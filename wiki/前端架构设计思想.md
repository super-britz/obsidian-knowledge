# 前端架构设计思想

## 先给结论

前端架构的本质不是选择 React、Vue、Monorepo 或微前端，而是：

> 设计一套规则，让系统发生变化时，变化只影响应该影响的部分。

所有前端架构思想最终都在解决四个问题：

1. **边界**：一次变化应该在哪里停止？
2. **状态**：一份事实由谁负责，如何变化？
3. **依赖**：怎样保护稳定业务规则，不被易变工具拖着走？
4. **失败**：系统出错后，如何知道自己在哪里并恢复？

还要用一把成本尺约束它们：

> 架构机制减少的长期变化成本，必须大于新增的理解和维护成本。

口诀：

> 划边界，定状态，理依赖，防失败；复杂度由真实问题付费。

## 一、为什么前端需要架构

任何前端系统都可以抽象成：

```text
用户输入 + 服务端数据 + 设备环境 + 时间变化
                    ↓
                  状态转换
                    ↓
界面展示 + 网络请求 + 本地存储 + 设备操作
```

也就是：

```text
输入 -> 状态 -> 输出
```

前端变复杂，不是因为页面多，而是因为：

- 输入来自用户、网络、设备和定时任务，并且异步到达。
- 状态之间存在依赖，同一事实还可能出现多个副本。
- 一个需求变化可能沿依赖关系传播到很多文件。
- 网络、权限、存储和设备随时可能失败。
- 多个人需要同时开发、测试、发布、回滚和排查。

因此可以得到：

```text
架构质量
≈ 变化局部性
+ 状态可预测性
+ 依赖可理解性
+ 失败可恢复性
```

这不是精确计算公式，而是一组判断维度。

## 二、前端架构设计思想有哪些

| 根本问题 | 设计思想 | 主要作用 |
| --- | --- | --- |
| 变化到处传播 | 模块化、关注点分离、信息隐藏 | 建立边界，把变化限制在局部 |
| 复杂行为难以复用 | 组合优于继承 | 用小能力组合复杂行为 |
| 多份数据互相冲突 | 单一事实来源 | 明确谁拥有最终事实 |
| 状态变化难以追踪 | 单向数据流 | 建立清楚的因果链 |
| 异步流程出现非法组合 | 状态机 | 只允许合法状态和转换 |
| 业务规则被 UI、网络绑死 | 纯逻辑与副作用分离 | 让规则可测试、可复用 |
| 更换框架或 SDK 牵动业务 | 依赖倒置 | 让易变实现依赖稳定规则 |
| 外部数据变化穿透系统 | 稳定接口、运行时契约 | 在边界吸收外部变化 |
| 网络和设备失败后状态混乱 | 容错与恢复 | 明确重试、幂等、回滚和恢复 |
| 线上问题只能靠猜 | 可观察性 | 还原用户操作与系统因果链 |
| 为未来预先堆积复杂设计 | 渐进式架构 | 只为已经出现的问题付费 |

这些思想不是彼此独立的知识点，而是从“边界、状态、依赖、失败”四个根问题推导出的工具。

## 三、边界：让变化停在应该停止的地方

### 1. 模块化

假设修改“订单金额计算规则”，需要同时修改页面、表格、Store、请求参数、工具函数和另一个页面，说明系统没有围绕变化建立边界。

```text
代码可以随意互相调用
  -> 依赖路径增加
  -> 一处变化沿依赖扩散
  -> 修改和回归范围扩大
```

因此得到模块化原则：

> 把经常一起变化的代码放在一起，把变化原因不同的代码分开。

例如按业务能力组织订单模块：

```text
order/
├── api
├── model
├── components
├── pages
└── index
```

外部只通过 `order/index` 使用订单能力，不直接引用内部文件。

判断模块边界时，不要只问代码长得像不像，而要问：

> 它们是否因为同一个业务原因发生变化？

### 2. 关注点分离

页面渲染、业务规则、接口转换、权限和埋点的变化原因不同：

```text
视觉变化       <- 设计调整
业务规则变化   <- 产品需求
数据结构变化   <- 后端接口
权限变化       <- 安全策略
埋点变化       <- 数据分析
```

变化原因不同却放在一起，任何一种变化都会修改同一个组件。

因此可以分为：

- 页面组件：组合和展示。
- 业务模型：规则和状态转换。
- 数据访问层：远程通信和数据转换。
- 基础设施层：存储、日志和设备能力。

分离不是文件越多越好。只有两部分确实会独立变化，拆分才有价值。

### 3. 信息隐藏与稳定接口

模块暴露的内部细节越多，外部依赖它的方式越多，未来修改自由度越低。

表达业务能力：

```ts
orderService.cancel(orderId)
```

通常比泄露实现细节更稳定：

```ts
api.patch(`/orders/${orderId}`, {
  status: 4,
  cancelFlag: 1,
})
```

前者告诉外部“能做什么”，后者让外部知道了路径、字段和状态编码。

### 4. 组合优于继承

深层继承会让子类绑定父类结构，修改父类可能影响整棵继承树。组合把复杂行为拆成独立能力：

```text
列表能力 + 分页能力 + 编辑能力 + 权限能力
```

组件组合、Hooks、Composables、中间件、插件和 Slot 都体现了这一思想。

组合也不能无限拆分。单元太碎，会让一个业务行为散落在大量文件中。

## 四、状态：明确事实由谁负责

### 1. 单一事实来源

同一事实存在多个可修改副本，就必须不断同步：

```text
副本数量增加
  -> 同步路径增加
  -> 时序和失败组合增加
  -> 不一致概率增加
```

因此：

> 一份业务事实只能有一个权威所有者，其他地方通过读取、缓存或计算得到。

例如购物车商品是原始状态，总价可以计算得到：

```ts
const total = items.reduce(
  (sum, item) => sum + item.price * item.quantity,
  0,
)
```

没有独立修改总价的业务需求时，不应同时保存 `items` 和 `total`。

单一事实来源不等于只能有一个物理副本。服务端数据可以缓存在客户端，关键是明确：

- 谁拥有最终写入权？
- 缓存何时失效？
- 冲突时以谁为准？
- 多个副本如何重新同步？

判断状态放在哪里，可以问：

1. 谁负责修改？
2. 谁需要读取？
3. 它需要存活多久？

状态应放在能够覆盖消费者的最小公共范围，而不是默认放进全局 Store。

### 2. 单向数据流

如果组件互相修改状态：

```text
A 修改 B
B 修改 C
C 又修改 A
```

系统行为就会依赖隐含的执行顺序。

把变化收敛成：

```text
事件 -> 决策 -> 状态变化 -> 界面更新
```

状态可以被读取，但只能通过明确事件和规则修改。React、Redux、Vuex 和 Pinia 只是实现方式，真正重要的是因果链能否追踪。

### 3. 状态机

多个布尔值容易组合出业务上不存在的状态：

```text
isLoading = true
isSuccess = true
isError = true
```

如果业务只有有限合法阶段，就直接建模阶段：

```ts
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'empty' }
  | { status: 'error'; error: Error }
```

状态机不仅描述“现在有什么值”，还描述“当前处于什么阶段，下一步允许发生什么”。它适合登录、支付、文件上传、蓝牙连接、OTA 和多步骤表单。

简单流程先用一个 `status` 或联合类型即可，不必立即引入完整状态机框架。

## 五、依赖：保护稳定业务规则

业务规则通常比技术工具稳定：

```text
“订单必须付款”       较稳定
“使用 Axios 请求”    较易变化
```

如果业务代码直接依赖 Axios、`localStorage`、小程序 API、埋点 SDK 或 UI 框架，更换工具时业务规则也会被迫修改。

### 1. 纯逻辑与副作用分离

代码可以分为：

- 确定性计算：相同输入得到相同输出。
- 副作用操作：与网络、存储、时间、设备和导航交互。

```ts
function calculateDiscount(order: Order): number {
  return order.amount >= 1000 ? 100 : 0
}

async function submitOrder(order: Order) {
  const discount = calculateDiscount(order)
  return api.createOrder({ ...order, discount })
}
```

可以把它记成：

```text
副作用层获取输入
  -> 纯业务逻辑计算
  -> 副作用层提交结果
```

这也叫“函数式核心、命令式外壳”。收益是业务规则可以脱离浏览器、接口和框架独立测试。

### 2. 依赖倒置

稳定规则定义自己需要什么能力，易变实现去满足这个能力：

```ts
interface OrderRepository {
  create(order: Order): Promise<OrderResult>
}
```

```text
页面 -> 业务用例 <- Axios 实现
                 <- Fetch 实现
                 <- Mock 实现
```

依赖倒置不是要求所有函数都建立接口。实现确实可能替换、需要测试替身或存在多个运行环境时，它才值得引入。

### 3. 运行时契约

TypeScript 只能检查开发期类型，不能保证服务端响应、本地旧数据、URL 参数或蓝牙消息在运行时合法。

```text
外部数据
  -> 运行时校验
  -> 版本兼容
  -> 转换成内部模型
  -> 业务规则
```

适配层负责吸收外部字段、状态码和协议版本变化，避免这些细节穿透整个系统。

## 六、失败：让系统知道自己在哪里

前端运行环境天然不可靠：

- 网络断开或请求超时。
- 用户重复点击。
- 页面刷新或应用退出。
- 设备离线。
- 多端并发修改。
- 前后端版本不一致。

所以失败不是成功路径之外的例外，而是系统必须表达的状态。

> 健壮性不是避免失败，而是失败发生后，系统仍然知道自己在哪里。

架构要回答：

```text
失败如何识别？
是否可以重试？
重复执行是否安全？
中断后如何恢复？
谁拥有最终事实？
用户是否知道当前结果？
```

由此可以得到：

- 幂等：重复执行不会产生重复结果。
- 超时：不能无限等待，但超时不代表服务端一定失败。
- 重试：只重试可恢复且安全的操作。
- 降级：非核心能力失败不阻断主流程。
- 乐观更新与回滚：先更新界面，失败后恢复。
- 服务端最终裁决：关键业务事实以服务端为准。
- 断点恢复：长流程保存当前阶段和恢复条件。

### 可观察性

恢复的前提是知道发生了什么。系统需要串起：

```text
用户动作
  -> 业务事件
  -> 状态转换
  -> 外部调用
  -> 执行结果
```

日志、埋点、错误监控和 Trace ID 应帮助回答：用户做了什么、系统当时是什么状态、哪一步失败、使用哪个版本，以及能否安全恢复。

以 OTA 为例，不能只记录“升级失败”，而应记录任务、升级阶段、命令、响应、超时或断连位置和恢复结果。

## 七、渐进式架构：只为真实问题付费

架构机制也有成本：更多目录、文件、抽象、配置、学习成本和排查路径。

```text
引入价值
= 持续减少的变化成本
- 新增的理解与维护成本
```

典型演化可能是：

```text
单页面组件
  -> 提取重复组件
  -> 分离业务状态
  -> 按业务模块组织
  -> 建立跨模块接口
  -> 独立构建或部署
```

这不是必须完成的成熟度阶梯。只有某类问题反复出现，而且收益长期大于成本时，才进入下一步。

常见架构形式解决的是不同层面的问题：

| 架构形式 | 主要解决的问题 | 底层思想 |
| --- | --- | --- |
| 组件化 | UI 重复和局部变化 | 模块化、组合 |
| 分层架构 | 职责混杂 | 关注点分离 |
| 按业务组织 | 业务变化跨越技术目录 | 变化局部性 |
| 单向数据流 | 状态修改混乱 | 明确因果链 |
| 状态机 | 流程存在非法状态 | 合法状态建模 |
| Clean / Hexagonal | 业务被框架和基础设施绑定 | 依赖倒置 |
| BFF | 前端被多个后端接口拖累 | 接口适配、边界隔离 |
| Monorepo | 多项目共享和版本协作困难 | 依赖治理 |
| 微前端 | 大型团队不能独立开发和发布 | 组织边界、部署隔离 |
| SSR / SSG / CSR | 首屏、SEO、交互和成本冲突 | 计算位置选择 |
| 插件化 | 功能需要按需扩展 | 稳定接口、信息隐藏 |

它们不是同一维度上的竞争方案。一个系统可以同时使用 Monorepo、业务模块、组件化、单向数据流和部分 SSR。

## 八、如何使用这些思想

不要先问“应该使用什么架构”，而要先描述症状：

| 看到的症状 | 优先检查 |
| --- | --- |
| 改一个需求要修改很多无关文件 | 模块边界、关注点分离 |
| 同一数据在多个地方不一致 | 状态所有权、派生状态 |
| 多个布尔值产生非法流程 | 状态机 |
| 点击之后不知道发生了什么 | 单向数据流 |
| 业务规则离开页面就不能测试 | 纯逻辑与副作用分离 |
| 更换接口或 SDK 导致业务大改 | 依赖倒置、适配层 |
| 外部脏数据穿透页面 | 运行时契约 |
| 重复点击产生重复结果 | 幂等 |
| 失败后不知道是否已经成功 | 最终事实、结果查询、恢复设计 |
| 线上问题只能靠猜 | 可观察性 |

使用顺序是：

```text
描述具体症状
  -> 找到边界、状态、依赖或失败问题
  -> 选择成本最低的工具
  -> 定义预期改善
  -> 用代码、测试和线上信号验证
```

一次只解决一个主要问题，不要把所有架构思想同时套进项目。

## 九、架构检查清单

1. 一个需求变化，需要修改多少无关文件？
2. 一份业务事实由谁负责修改和最终裁决？
3. 从用户操作到界面结果，因果链是否清楚？
4. 业务规则能否脱离 UI、网络和设备独立测试？
5. 外部接口、SDK 或框架变化，会不会穿透整个系统？
6. 网络失败、重复操作和流程中断后，系统如何恢复？
7. 当前问题真的值得引入这份复杂度吗？

## 最终记忆

只记一句话：

> 前端架构通过边界控制变化，通过状态表达事实，通过依赖方向保护稳定规则，通过失败设计保证系统可恢复。

再记一个口诀：

> 边、状、依、错，加一把成本尺。

需要细节时，再回到对应章节查工具，不必背诵所有术语。
