# 前端架构设计思想

## 核心结论

> 前端架构，是对系统边界、模块职责、依赖方向、状态归属和运行流程所做的一组关键约束。

它解决的不是“代码放在哪个文件夹”，而是：

- 谁负责什么？
- 谁可以依赖谁？
- 状态由谁拥有和修改？
- 数据怎样流动？
- 外部失败怎样处理？
- 需求变化会影响哪里？

前端复杂度可以记成四个词：

> **状态、异步、边界、变化。**

## 一、从第一性原理理解前端

前端最基本的任务是：

```text
接收输入
  -> 根据当前状态做出转换
  -> 产生用户可见结果
```

输入包括用户操作、服务端数据、URL、浏览器环境和时间事件；输出包括界面变化、网络请求、本地存储和页面跳转。

因此，前端可以抽象成：

```text
用户事件 + 外部数据 + 当前状态
                ↓
             状态转换
                ↓
       界面 + 请求 + 存储 + 导航
```

如果输入确定、状态很少、没有网络、需求不变化，前端会非常简单。现实恰好相反：状态很多、事件异步、外部不可靠、需求持续变化，所以需要架构。

## 二、前端架构是什么

架构不是 React、Vue、微前端或 Monorepo，这些只是具体工具或方案。架构真正决定的是几个难以轻易修改的问题。

### 1. 系统怎样划分

系统可以按商品、订单、支付、用户等业务能力划分，也可以按展示层、应用层、业务层、基础设施层划分。

划分的目的，是让开发者不必每次理解整个系统。

### 2. 模块怎样依赖

```text
页面 -> 业务用例 -> 业务规则
基础设施 -> 业务定义的接口
```

依赖方向决定了一个变化会传播到哪里。

### 3. 状态属于谁

- 输入框状态属于组件。
- 筛选条件可以属于 URL。
- 登录状态属于应用会话。
- 商品数据的权威来源在服务端。
- 请求缓存只是服务端数据的本地副本。

状态归属不清，就容易产生多份互相矛盾的数据。

### 4. 数据和事件怎样流动

```text
用户点击
  -> 发出事件
  -> 执行业务规则
  -> 更新状态
  -> 重新渲染界面
```

流程越明确，系统越容易解释和调试。

### 5. 系统怎样面对外部世界

前端必须与服务端、浏览器、本地缓存和第三方服务交互。架构需要规定数据怎样校验、请求失败怎么办、是否允许重试、重复请求是否安全，以及错误如何展示和记录。

因此，前端架构可以概括为：

> 通过明确边界、依赖、状态和流程，控制系统复杂度及其传播。

## 三、为什么前端会复杂

### 1. 状态多：系统可能处于什么情况

假设页面只有三个独立状态：

- 是否登录
- 是否正在请求
- 是否出现错误

理论上已经存在：

```text
2 × 2 × 2 = 8 种组合
```

继续加入权限、弹窗、缓存、分页和表单状态，组合数量会快速增长。

问题不仅是状态数量多，还包括一些组合可能不合法。例如“正在请求”“请求成功”“请求失败”三个值可能同时为真，但业务上不应该出现这种情况。

因此，状态复杂度的本质是：

> 系统存在多少种可能状态，哪些状态合法，我们能否准确判断当前状态。

### 2. 异步多：事情可能以什么顺序发生

同步代码可以按书写顺序理解，异步事件不一定：

```text
发出请求 A
发出请求 B
请求 B 返回
请求 A 返回
```

如果 A 是旧请求，它可能用旧结果覆盖 B 的新结果。

还可能出现：

- 用户连续点击两次。
- 请求超时，但服务端已经成功。
- 页面离开后请求才返回。
- 自动重试造成重复操作。
- 缓存更新早于或晚于界面更新。

状态回答的是“系统可能处于什么情况”，异步回答的是“系统通过什么顺序到达这个状态”。只要顺序不同会产生不同结果，就存在时间复杂度。

### 3. 边界多：外部世界不受前端控制

前端处在多个边界之间：

```text
用户
  ↓
浏览器
  ↓
前端应用
  ↓
网络
  ↓
服务端
  ↓
数据库或第三方服务
```

前端无法保证：

- 用户输入一定正确。
- 网络一定稳定。
- 服务端一定及时响应。
- 接口数据一定符合类型。
- 本地缓存一定是最新版本。
- 第三方服务一定可用。

只要跨越边界，原来的假设就可能失效。因此，边界复杂度的本质是：

> 边界另一侧存在多少不确定性，失败会怎样传入当前系统。

前端保存的服务端数据通常不是事实本身，而是事实的本地副本：

```text
服务端事实
  -> 网络传输
  -> 前端缓存
  -> 界面显示
```

副本与原始数据可能暂时不一致，这也是前端复杂度的重要来源。

### 4. 变化多：修改会传播到什么地方

即使系统当前完全正确，也会不断面对业务规则、页面设计、接口字段、浏览器能力、框架依赖、团队成员以及性能和安全要求的变化。

变化本身不可避免，真正的问题是变化传播：

```text
后端修改一个字段
  -> 请求层修改
  -> 状态结构修改
  -> 多个组件修改
  -> 测试修改
```

如果模块紧密耦合，一个局部变化会引发系统级修改。因此，变化复杂度的本质是：

> 一个变化会传播多远，需要多少人、多少模块共同修改。

## 四、四种复杂度如何相互作用

这四种复杂度不是简单相加，而会互相放大：

```text
状态越多
× 异步顺序越多
× 外部边界越多
× 变化越频繁
→ 系统越难预测
```

例如“提交订单”同时包含：

- **状态**：编辑中、提交中、成功、失败、结果未知。
- **异步**：请求可能超时、乱序或重复。
- **边界**：操作需要经过网络和服务端。
- **变化**：订单规则、支付方式和接口可能调整。

所以真实问题通常无法只用一种架构思想解决。

## 五、规模为什么不是第五种复杂度

代码量、用户量和团队规模会让问题更严重，但它们更适合看作放大器：

```text
状态、异步、边界、变化
          ↓
       规模增长
          ↓
复杂度超过人的认知能力
```

人的认知能力有限，无法同时理解整个大型系统。架构的作用，就是把一个大问题拆成多个可以局部理解的问题。

## 六、必要复杂度与人为复杂度

### 必要复杂度

来自业务和运行环境，不能直接消除：

- 支付确实存在多个状态。
- 网络确实可能失败。
- 权限规则确实存在。
- 多人确实需要协作。

### 人为复杂度

来自不合理的实现：

- 同一份状态保存多次。
- 模块之间循环依赖。
- 业务规则散落在组件中。
- 所有数据都放进全局状态。
- 为简单项目引入微前端。
- 为了复用而制造万能组件。

架构的目标不是消灭所有复杂度，而是：

> 删除人为复杂度，准确表达必要复杂度，并限制复杂度的传播范围。

## 七、怎样控制复杂度

控制复杂度不是单纯减少代码，而是减少开发者在一次修改中必须同时考虑的状态、顺序、边界和依赖。

可以归纳为五种基本动作：

| 动作 | 含义 | 典型做法 |
| --- | --- | --- |
| 减少 | 删除不必要的状态和抽象 | 派生状态、状态就近、YAGNI |
| 约束 | 限制合法状态、转换和依赖 | 状态机、类型、模块接口、依赖规则 |
| 显式 | 把隐藏关系变成可见模型 | 显式事件、单向数据流、契约、错误模型 |
| 隔离 | 阻止变化、副作用和失败扩散 | 模块化、封装、Adapter、依赖倒置 |
| 反馈 | 持续证明系统是否符合预期 | 测试、静态检查、日志、指标、Trace |

对应四种复杂度，控制方向是：

```text
状态多 -> 减少并约束状态
异步多 -> 显式表达并控制顺序
边界多 -> 验证、隔离和恢复
变化多 -> 划分边界，限制传播
```

## 八、由此产生的架构思想

### 1. 控制状态复杂度

- **单一事实来源**：同一事实只有一个权威所有者，避免多个可写副本互相同步。
- **派生状态**：能够从原始状态计算的值不重复保存，减少状态组合。
- **状态就近**：状态放在覆盖使用者的最小范围，不默认进入全局 Store。
- **单向数据流**：把变化组织成“事件 → 决策 → 状态转换 → 界面更新”。
- **状态机**：显式描述合法阶段与转换，排除不可能的状态组合。
- **类型约束**：让非法状态尽量无法被表达。

这些思想共同回答：

> 系统可能处于哪些状态，哪些状态合法，谁有权修改？

### 2. 控制异步复杂度

- **显式生命周期**：表达空闲、执行中、成功、失败、取消和结果未知等阶段。
- **副作用隔离**：把业务计算与请求、存储、导航和计时器分开。
- **并发策略**：明确采用最新结果、首次结果、排队、并行、取消旧任务或请求去重。
- **幂等**：同一个业务操作重复执行，不产生重复业务结果。
- **超时、取消与重试**：分别处理不能无限等待、旧任务失去意义和暂时性失败。

这些思想共同回答：

> 多个事件以不同顺序发生时，系统应该接受哪个结果？

### 3. 控制边界复杂度

- **契约优先**：明确输入、输出、业务语义、错误、权限和版本兼容。
- **运行时校验**：验证服务端响应、URL、本地缓存和第三方消息等外部数据。
- **Adapter 与防腐层**：在边界转换外部模型，避免外部字段和协议穿透内部系统。
- **容错与降级**：提前定义超时、重试、回滚、降级和最终事实来源。
- **可观察性**：用日志、错误上报、指标和 Trace 还原完整因果链。

这些思想共同回答：

> 边界另一侧不符合预期时，怎样阻止问题扩散并恢复？

### 4. 控制变化复杂度

- **模块化**：把系统拆成可以独立理解和修改的业务单元。
- **按变化原因划分边界**：一起变化的代码放在一起，变化原因不同的代码分开。
- **高内聚、低耦合**：聚集同一业务能力，只通过少量稳定接口连接模块。
- **封装与信息隐藏**：暴露业务能力，隐藏内部结构，保留修改实现的自由。
- **依赖倒置**：稳定业务规则定义所需能力，易变技术实现去满足它。
- **组合优于继承**：通过小而稳定的能力构造复杂功能，避免深层隐式依赖。
- **自动化约束**：把重要规则放进类型、Lint、测试和 CI，而不是只依赖记忆。
- **演进式架构**：只为已经出现的真实问题付费，并为不确定决策保留退出路径。

这些思想共同回答：

> 一个需求或技术发生变化时，怎样让修改保持局部？

四类思想可以压缩成一张表：

| 复杂度来源 | 控制目标 | 主要架构思想 |
| --- | --- | --- |
| 状态多 | 减少并约束合法状态 | 单一事实来源、派生状态、状态就近、单向数据流、状态机、类型约束 |
| 异步多 | 显式表达并控制顺序 | 生命周期建模、副作用隔离、并发策略、取消、幂等、重试与回滚 |
| 边界多 | 验证、隔离和恢复 | 契约、运行时校验、Adapter、防腐层、容错、可观察性 |
| 变化多 | 限制变化传播 | 模块化、关注点分离、高内聚低耦合、封装、依赖倒置、组合、演进式架构 |

## 九、为什么同一个问题需要多种思想

真实问题通常同时包含四种复杂度，每种思想只控制其中一个维度。

以“提交订单”为例：

| 问题 | 使用的思想 |
| --- | --- |
| 编辑、提交、成功、失败如何表达 | 状态机 |
| 谁引起状态变化 | 单向数据流 |
| 请求与业务计算怎样分开 | 副作用隔离 |
| 重复请求会不会创建两个订单 | 幂等 |
| 前后端怎样理解同一个操作 | 契约优先 |
| 接口字段变化怎样不影响业务 | Adapter |
| 请求超时后怎样恢复 | 结果查询、容错设计 |
| 线上怎样定位问题 | 可观察性 |

这些思想不是重复解决同一个问题，而是分别控制状态、时间、边界和变化。

## 十、怎样使用这些思想

不要从架构名词出发，而要从系统中反复出现的具体症状出发：

```text
描述症状
  -> 判断复杂度来源
  -> 找到根因
  -> 选择成本最低的思想
  -> 定义预期改善
  -> 用测试和运行信号验证
```

### 1. 描述可以观察的症状

不要直接说“项目架构不好”，而要描述具体事实：

- 修改订单规则要同时修改多个无关目录。
- 同一份用户数据在不同页面不一致。
- 快速切换筛选条件时，旧请求会覆盖新结果。
- 接口字段变化后，大量组件同时报错。
- 线上失败后无法判断请求是否已经成功。

症状越具体，越容易判断应该控制哪一种复杂度。

### 2. 判断主要复杂度来源

依次询问：

| 问题 | 复杂度来源 |
| --- | --- |
| 是否存在多份状态、冗余状态或非法状态组合？ | 状态复杂度 |
| 是否因为延迟、乱序、重复或中断产生错误？ | 异步复杂度 |
| 是否因为外部数据、网络或第三方服务不符合预期？ | 边界复杂度 |
| 是否因为一个修改传播到大量模块？ | 变化复杂度 |

一个问题可能涉及多类复杂度，但应先找到造成当前损失最大的主要根因。

### 3. 选择成本最低的思想

根据根因选择最小方案：

| 看到的症状 | 优先考虑 |
| --- | --- |
| 同一数据在多个地方不一致 | 单一事实来源、派生状态 |
| 多个布尔值产生非法流程 | 状态机或联合类型 |
| 点击之后不知道谁修改了状态 | 单向数据流、显式事件 |
| 搜索结果被旧请求覆盖 | 取消旧请求、Latest wins |
| 重复点击产生重复订单 | 客户端状态约束、服务端幂等 |
| 业务规则离开页面就不能测试 | 副作用隔离 |
| 外部脏数据直接进入页面 | 运行时校验、Adapter |
| 接口或 SDK 变化导致业务大改 | 防腐层、依赖倒置 |
| 改一个需求要修改很多无关文件 | 模块边界、高内聚低耦合 |
| 失败后无法判断是否成功 | 结果查询、错误模型、恢复设计 |
| 线上问题只能靠猜 | 可观察性 |

优先使用能够解决根因的最小机制。例如，一个简单请求用联合类型已经足够时，不必立即引入完整状态机框架。

### 4. 定义预期改善

引入架构思想之前，要说明希望什么发生变化：

```text
修改范围从五个模块减少到一个模块
非法状态在类型检查阶段被发现
旧请求不能覆盖新结果
外部字段变化只修改 Adapter
重复请求只能产生一个订单
线上错误可以通过请求 ID 还原
```

没有明确改善目标，就无法判断新增抽象是否值得。

### 5. 用证据验证

根据问题选择验证方式：

- 状态问题：类型检查、状态转换测试、组件测试。
- 异步问题：乱序、重复、超时、取消和重试测试。
- 边界问题：契约测试、异常数据测试、降级演练。
- 变化问题：检查修改文件数量、依赖方向和模块公开接口。
- 线上问题：日志、指标、Trace 和错误监控。

如果新增结构没有减少修改范围、错误概率或排查成本，它可能只是把复杂度换了一个位置。

### 6. 保持渐进演化

使用这些思想时遵守三个原则：

1. **从症状出发，不从架构名词出发。**
2. **先解决主要根因，再处理次要问题。**
3. **减少的长期成本必须大于新增的理解和维护成本。**

一个实用的最小决策记录是：

```text
症状：发生了什么？
根因：属于哪类复杂度？
方案：采用什么思想，为什么？
代价：新增什么抽象和维护成本？
验证：怎样证明问题得到改善？
```

## 最终记忆

### 前端架构是什么

```text
明确边界
+ 划分职责
+ 控制依赖
+ 确定状态归属
+ 规定数据与事件流
```

### 前端为什么复杂

```text
状态多：可能处于什么情况
异步多：事情以什么顺序发生
边界多：外部世界是否可靠
变化多：修改会传播到哪里
```

### 架构最终要达到什么目标

```text
让状态可以解释
让流程可以追踪
让失败可以隔离
让变化保持局部
```

### 控制复杂度的五个动作

```text
减少、约束、显式、隔离、反馈
```

### 使用顺序

```text
症状 -> 根因 -> 最小方案 -> 预期改善 -> 证据验证
```

> 前端架构，就是通过约束状态、顺序、边界和依赖，让复杂系统仍然处于人的理解范围之内。
