# 35期 AI 全栈课程学习总纲

## 先说结论

这套课程最终要形成六种可交付能力：

1. 用 AI 完成需求、设计、开发、验证、测试与部署闭环。
2. 把前端扩展为 BFF、Serverless、云服务和后端接口能力。
3. 用上下文、角色分工、测试和人工确认组织企业 AI 工作流。
4. 理解交易、Web3、跨境等复杂业务中的状态、权限、风险与审计。
5. 处理性能、可观测性、图形学和复杂交互问题。
6. 正确组合本地模型、RAG、微调、Tool 与 Agent。

学习时不要以“看完了多少节”为目标。每个模块至少留下一个可以运行、解释和验证的产出。

## 学习优先级

| 优先级 | 内容 | 适合谁 | 完成标志 |
| --- | --- | --- | --- |
| P0 | AI 开发工作流、前端架构、Serverless、RAG / Agent | 想提高交付能力或转向 AI 全栈 | 能独立完成并部署一个带 AI 能力的全栈应用 |
| P1 | 企业 AI 工作流、Code Review、AIOps、性能监控 | 想体现工程深度 | 有自动化验证、日志、评审和故障处理证据 |
| P2 | 交易系统、Web3、图形学 | 面向特定业务或差异化岗位 | 有不接真实资金的模拟项目或 3D 项目 |
| P3 | 平台价格、模型榜单、账号与硬件行情 | 仅在实际需要时查询 | 不作为长期学习内容 |

## 学习方法

每篇课程笔记按四步处理：

1. **理解**：不看原稿，先回答笔记开头的核心问题。
2. **解释**：用自己的话说明关键概念、流程和取舍。
3. **实现**：完成实践任务，保留代码、截图、日志或测试结果。
4. **复盘**：回答复习检查，并记录失败原因和改进方案。

只有能解释“为什么这样设计”和“如何证明它有效”，才算真正掌握。

## 六个作品项目

### 1. AI 前端交付流水线

对应课程：02-05、09-10、13-18。

**最小范围**

- 输入一个产品想法，形成需求、设计与任务拆解。
- 生成并整理成可维护的前端代码。
- 使用浏览器验证或 E2E 测试检查关键流程。
- 部署可访问版本并记录一次失败复盘。

**完成标准**

- 需求与实现能互相追溯。
- 测试覆盖核心用户流程。
- 能指出 AI 生成结果中至少一个真实问题及修正过程。

### 2. Serverless 全栈应用

对应课程：05-12、23、28-29、36。

**最小范围**

- 前端页面与类型安全 API。
- 一个 Serverless 或边缘运行时。
- 数据存储、缓存或队列中的至少一种。
- 日志、错误处理、权限和部署说明。

**完成标准**

- 能画出浏览器到数据层的请求链路。
- 能说明缓存位置、权限边界、故障点和成本来源。
- 能通过日志定位一次人为制造的错误。

### 3. AI Code Review / AIOps 工作流

对应课程：13-18、34、43-44。

**最小范围**

- 输入 PR diff、错误日志或监控告警。
- 不同角色分别负责分析、实现建议和验证。
- 输出风险等级、证据、修复建议与人工确认点。

**完成标准**

- 评审结果引用真实代码或日志证据。
- 独立验证者能够拒绝不完整或错误的修复。
- 高权限动作不会自动执行。

### 4. 交易系统模拟器

对应课程：19-33、35。

**最小范围**

- mock WebSocket 行情。
- K 线、盘口或订单状态展示。
- 一个明确的状态机。
- Worker、虚拟列表或批量更新等性能措施。

**完成标准**

- 不接真实资金、私钥或生产交易接口。
- 能解释行情、订单和持仓状态如何同步。
- 有性能数据或故障场景验证。

### 5. 3D 商品或场景展示

对应课程：35、37-39。

**最小范围**

- 加载 GLB / glTF 模型。
- 配置场景、相机、灯光和材质。
- 提供相机控制、选中、动画或标注等交互。
- 记录加载时间、帧率或资源体积。

**完成标准**

- 模型在桌面和移动视口中都能正确呈现。
- 能解释渲染循环、场景图和资产加载过程。
- 至少完成一项有数据支撑的性能优化。

### 6. 本地智能客服系统

对应课程：40-46。

**最小范围**

- 本地模型 HTTP 服务。
- 产品文档 RAG。
- mock 订单或物流 API。
- Agent / Workflow 工具调用。
- 越界拒答、失败回退和人工转接。

**完成标准**

- 能证明 QLoRA、RAG、Tool 与 Agent 各自负责什么。
- 工具选择、参数、业务结果和最终回复可以分别测试。
- 模型不会把未执行的查询描述成已经完成。
- 日志和测试数据不泄露真实用户信息。

## 大模型系统决策表

| 问题 | 优先方案 | 原因 |
| --- | --- | --- |
| 回复语气和格式不稳定 | Prompt，必要时 LoRA / QLoRA | 这是行为模式问题 |
| 产品手册经常更新 | RAG | 文档可独立更新并保留来源 |
| 订单、库存、物流实时变化 | Tool / API | 需要访问业务事实与权限系统 |
| 多步骤任务需要分支和回退 | Workflow / Agent | 需要状态、路由和执行控制 |
| 高风险流程必须确定执行 | 状态机与人工确认 | 不应完全依赖概率模型 |

## 项目证明材料

每个项目至少保留：

- 一页架构说明。
- 一组可运行步骤。
- 一份关键测试或验收记录。
- 一次失败案例与修复过程。
- 一段限制、风险和下一步说明。

这些材料既用于复习，也防止项目表达只剩技术名词。

## 边界

- Web3、交易和跨境内容用于理解系统与风险，不整理成资金操作指南。
- 账号、价格、模型榜单、平台政策和硬件建议具有时效性，使用时重新核实。
- 不把课堂临时硬编码、未完成演示或 mock 数据描述为生产能力。
- 不在简历或项目说明中声称未实际使用的硬件、吞吐、用户量或业务结果。
- 涉及用户数据、浏览器登录态、部署和远程控制时，明确最小权限与人工确认点。
