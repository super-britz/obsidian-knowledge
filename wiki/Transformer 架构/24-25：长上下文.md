# 长上下文：模型怎样保存并使用更多历史

> [!abstract] 长上下文不只是允许输入更多 Token。模型还要能够表示更远的位置、以可接受的成本读取历史，并在大量干扰中真正找到需要的信息。

## 为什么不能只把窗口调大

```text
能接收长输入
≠ 能直接访问每个历史位置
≠ 能可靠找到任意细节
≠ 能正确理解整份文档
≠ 运行成本可以接受
```

长上下文包含三类问题：历史怎样保存和读取、模型怎样表示更远位置、模型是否真正学会使用远处信息。

## 历史怎样保存和访问

- **完整 Attention：** 保存窗口内每个 Token 的 K/V，可以直接读取任意位置，但长输入的计算和缓存成本很高。
- **滑动窗口：** 只直接读取最近一段历史，成本更稳定，但早期细节可能无法直接找到。
- **稀疏 Attention：** 只连接部分位置，例如最近位置和少量全局位置；底层必须真正跳过无关计算才会加速。
- **压缩记忆：** 把旧历史合并成摘要或固定状态，空间不会一直增长，但无法保证恢复每个原始细节。

不存在既保存无限原文、又能任意精确访问、同时成本固定的方案。

## 更远的位置怎样表示

位置编码告诉模型 Token 的先后和距离。现代模型可能使用 RoPE、ALiBi 或其他方案；扩展长度时也可能调整位置尺度。

但位置编号能算到更远处，不代表模型已经学会在那个范围稳定工作：

```text
位置方案支持更远位置
→ 模型还要见过或适应相应长度
→ 推理实现必须正确处理位置和 Cache
→ 最后用真实任务验证
```

只把最大长度配置改大，可能让请求通过，却不能保证答案质量。

## 为什么长窗口仍需要 RAG

长窗口提供容量，RAG 负责从大量资料中挑出当前相关证据，并保留来源。把所有文档一次塞进 Prompt 会增加延迟、费用和干扰，也更难判断答案依据了什么。

如果必须引用合同条款、日志原文或其他证据，应保存和检索原始材料，而不是只依赖模型内部记忆或压缩状态。

## 做项目时记住

1. 当前任务和系统规则优先保留，旧历史按需裁剪或摘要。
2. 大文档优先检索少量相关原文，并让引用能够回查。
3. 把同一条证据放在开头、中间和结尾分别测试。
4. 同时观察回答质量、首 Token 延迟、费用和超时。
5. 为输出预留 Token，不要让输入占满整个窗口。

## 别误解

- **“支持 128k，就能可靠使用其中每个位置。”** 可靠性受位置、任务和干扰影响。
- **“长窗口可以替代 RAG。”** 它不能替代按需取证、更新和来源追踪。
- **“RoPE 可以表示更远位置，所以模型能无限外推。”** 位置机制不等于训练能力。
- **“Flash Attention 已解决所有长上下文成本。”** 长输入仍需要计算，也会产生更大的 KV Cache。

## 一句话复习

> 长上下文要同时解决历史访问、位置表示、模型能力和运行成本；能放进去只是第一步。
