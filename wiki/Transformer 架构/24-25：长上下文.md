# 第 24～25 章：长上下文总览

> [!abstract] 长上下文不是把一个配置数字调大，而是同时解决三个问题：位置编号能否扩展、模型能否以可承受成本访问历史、训练后能否真正利用远处信息。任何一项成立，都不能单独证明“模型可靠理解了 128k Token”。

## 先拆成两条线

| 问题 | 对应笔记 | 主要关注 |
| --- | --- | --- |
| 历史怎样保存和读取 | [[24：长上下文的信息访问|长上下文的信息访问]] | Full、Sparse、Sliding Window、压缩记忆及成本 |
| 更远位置怎样表示 | [[25：位置编码与长度外推|位置编码与长度外推]] | RoPE、ALiBi、位置缩放与训练窗口 |

除此之外还有第三条线：**模型能力**。系统能接收长输入，不等于模型经过训练后能在大量干扰中找到、组合并正确使用远处证据。

```text
标称上下文长度
≠ 可负担的运行成本
≠ 任意位置同等可靠
≠ 对整份文档的真正理解
```

## 前端开发者为什么需要知道

长窗口会直接影响：

- 历史消息、附件和工具结果能放多少；
- 首 Token 延迟、费用和超时概率；
- 中段证据是否容易被忽略；
- 服务端是否需要裁剪、摘要、检索和分段。

所以长上下文是系统资源，不是“把全部数据塞进去”的许可。

## 做项目时先问四个问题

1. **需要哪种长？** 是最近几千 Token 的连续对话，还是随机读取一份超长文档中的任意细节？
2. **信息必须精确保留吗？** 可以摘要的历史与必须逐字引用的合同条款，需要不同处理方式。
3. **模型真的会用吗？** 把证据放在开头、中间、结尾分别测试，而不是只看厂商窗口数字。
4. **成本能接受吗？** 同时测 TTFT、Token 费用、超时、显存和回答质量。

## 应用层默认策略

```text
当前任务必需规则
→ 最近且相关的对话
→ 检索得到的少量证据
→ 必要的工具状态
→ 为输出预留 Token
```

优先提高上下文的信息密度。动态事实继续由检索、数据库或工具提供；关键引用必须回查来源。

## 别误解

- **“支持 128k，所以 128k 内都能可靠召回。”** 可靠性会随位置、任务和干扰变化。
- **“长窗口可以替代 RAG。”** RAG 解决按需取证、更新和可追溯，长窗口只提供容量。
- **“Flash Attention 已解决所有长上下文成本。”** 它减少中间内存和 IO，不取消 Dense Attention 的主要配对计算，也不消除 KV Cache。
