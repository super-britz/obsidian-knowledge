# Tokenization：文字怎样变成模型能计算的编号

> [!abstract] Tokenization 就是把文字切成模型使用的小片段（Token），并换成编号（Token ID）。模型不直接计算“你好”，而是计算这些编号查出来的数字向量。

> [!info] 放回完整生成链
> - **位置：** 消息按 Chat Template 拼好之后、进入神经网络之前。
> - **输入 → 输出：** 文本 → Token ID 序列。
> - **为什么需要：** 矩阵不能直接处理文字；如果使用了不匹配的 Tokenizer，同一编号会指向错误片段，模型读到的输入就变了。

## 先看流程

```text
原始文字
→ Tokenizer 切分
→ Token ID 列表
→ 按 ID 查 Embedding 表
→ 一排数字向量
→ Transformer 继续处理
```

例如一个汉字有时是一个 Token，有时会拆成多个 Token；这由当前模型的 Tokenizer 决定。

## 关键理解

- **Token 不等于字，也不等于词。** 它可能是字、词的一部分、标点、空格、代码片段或字节片段。
- **Token ID 只是字典编号。** `31809` 不比 `31810` 更接近某种含义；真正参与计算的是查表后的 Embedding 向量。
- **现代 Tokenizer 会合并常见片段、拆开罕见片段。** BPE / tiktoken 一类方案用有限词表和字节回退处理更多文本。
- **模型按 Token 计预算。** 同样字数的中文、英文、代码和 JSON，可能占用完全不同的上下文和费用。

## 做项目时记住

1. **按 Token 管上下文，而不是只按字数。** System Prompt、历史、检索资料、工具结果和输出都应有预算。
2. **让工具少返回但返回关键内容。** 搜索返回相关片段和来源，数据库返回必要字段，不把整页 HTML 或完整日志直接塞回模型。
3. **把超限当作正常情况处理。** 需要有截断、摘要、分页、重试或让用户缩小范围的方案。

## 别误解

- **“一个汉字就是一个 Token。”** 不一定；换文字或换 Tokenizer，数量会变。
- **“Embedding 后模型就懂整句话。”** Embedding 只是起点；词与词的关系要靠后面的 Transformer 结合上下文处理。
- **“字符数限制等于模型上下文限制。”** 不等于；真正需要控制的是 Token 数。

## 复习

1. 为什么不能只按字符数估算 Prompt 是否会超限？
2. 为什么完整工具日志可能让 Agent 又慢又不准？
3. 文档问答系统该怎样给规则、检索资料、历史和输出分配 Token 预算？
