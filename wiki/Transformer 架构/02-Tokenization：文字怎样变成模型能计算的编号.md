# Tokenization：文字怎样变成模型能计算的编号

> [!abstract] 先用一句话说清楚
> Tokenization 就是把一段文字切成模型使用的小片段（Token），并给每个片段分配编号（Token ID）。模型不能直接计算“你好”这样的文字，只能先处理这些编号，再把编号查成数字向量。

## 它要解决什么问题？

你看到的是文字，模型要做的是大量数字计算。Tokenization 是两者之间的翻译步骤。

```text
“帮我总结这篇文章”
  ↓
Tokenizer 把文字切成若干 Token
  ↓
每个 Token 换成一个 Token ID
  ↓
模型把每个 ID 查成一组数字（Embedding）
  ↓
Transformer 才能继续处理
```

如果没有这一步，Transformer 没有可以计算的输入；它不能直接理解字符串、汉字或 Emoji。

## 它怎么工作？

### 先看最短流程

```text
原始文字
→ 按当前模型的 Tokenizer 切分
→ 得到 Token ID 列表
→ 按 ID 查 Embedding 表
→ 得到一排数字向量
→ 交给后面的 Transformer
```

### 再一步一步看

1. **Tokenizer 先切分，不是简单“按字分开”**

   一个 Token 可能是一个字、一个词的一部分、标点、空格、代码片段，甚至一个 UTF-8 字符的部分字节。怎样切分取决于模型使用的 Tokenizer。

2. **每个片段会变成一个编号（Token ID）**

   Token ID 只是字典里的编号，例如“某个片段是第 31809 项”。它不是“数字越接近，含义越相近”的分数。

3. **常见内容尽量合并，罕见内容可以拆开**

   现代 Tokenizer 常使用 BPE 一类方法：训练中常见的字节片段更容易被合并成一个 Token；少见文字或符号可以拆成多个字节片段，因此不需要把所有可能字符都提前放进词表。

4. **编号会被查成一组数字（Embedding）**

   模型有一张很大的“编号 → 数字向量”查找表。Token ID 查到的向量是后续计算的起点；真正结合这句话上下文后的含义，要由后面的 Transformer Block 继续形成。

## 它有什么限制？

- **一个 Token 不等于一个字，也不等于一个词。**
  同一句话换一种表达、换一种语言，或换一个 Tokenizer，Token 数可能明显不同。

- **上下文限制和 API 成本通常按 Token 计算。**
  对模型来说，1000 个汉字、1000 个英文字符、1000 个 JSON 字符不是同样大小的输入。

- **输入和输出要共用有限预算。**
  你放进上下文的系统规则、历史消息、检索片段和工具结果越多，留给模型生成答案的空间通常越少。具体输入、输出和总上下文限制要以正在使用的模型文档为准。

- **Tokenizer 必须和模型匹配。**
  用错误的 Tokenizer 估算长度、截断文本或准备本地推理输入，可能得到不准确甚至无法使用的结果。

## 你会在产品或代码中看到什么？

- 看起来差不多长的两段文本，调用成本和可放入的上下文量可能不同。
- 代码、JSON、URL、表格、很长的标识符和工具原始日志，往往会产生比预期更多的 Token。
- 某些少见汉字单独看可能显示为乱码片段；这是因为单个 Token 可能只是一段 UTF-8 字节，整串 Token 合起来解码才能还原原文。
- 用户看到“还剩 2000 字”，不能说明模型还剩多少上下文；真正应控制的是 Token 预算。

## 做项目时该怎么办？

### 适合做的事

- 在发送请求前，用与目标模型兼容的 Tokenizer 估算输入长度。
- 为 System Prompt、历史消息、检索资料、工具结果和模型输出分别预留 Token 预算。
- 在日志中记录每次请求的输入、输出和总 Token，用它分析成本、延迟和失败原因。

### 不能只靠“截断字符数”的地方

- 不要只按字数、单词数或数据库字段长度决定 Prompt 是否安全。
- 不要把完整网页、全部聊天历史或工具原始 JSON 无差别塞给模型；先筛选、提取、结构化或摘要。
- 不要假设一个模型的 Tokenizer 能准确预测另一个模型的费用或上下文占用。

### 写 Agent 时先控制什么

1. **为每类上下文分预算。** 例如先保留任务目标和安全规则，再分配历史、检索和工具结果的空间，并给输出留足余量。
2. **让工具返回“足够完成下一步”的结果。** 搜索工具返回相关片段和来源，不返回整页 HTML；数据库工具返回必要字段，不返回整张表。
3. **把 Token 超限当作正常失败场景。** 需要有截断、摘要、分页、重试或让用户缩小范围的处理，而不是等请求报错。

## 容易误解的地方

- **误解：一个汉字就是一个 Token。**
  - 更好理解的说法：Token 是 Tokenizer 切出的单位；中文字符有时是一个 Token，有时会被拆成多个 Token。

- **误解：Token ID 的数值本身包含语义。**
  - 更好理解的说法：ID 只是查字典用的编号；模型真正参与计算的是查表后的向量，以及后续结合上下文得到的表示。

- **误解：Embedding 查表后，模型就已经“懂了整句话”。**
  - 更好理解的说法：Embedding 是每个 Token 的起点；句子中词与词之间的关系，要靠后面的 Attention 和多层 Transformer 处理。

- **误解：Tokenization 只是一个无关紧要的字符串工具。**
  - 更好理解的说法：它决定模型看到什么输入单位，也直接影响上下文长度、延迟和费用。

## 来源、我的理解与待继续学习

### 来源中明确讲到的内容

- 第 4 章说明，Tokenization 是 Transformer 的起点：文字先被切成 Token 并转换为 Token ID，之后才能进入 Embedding 和后续网络。
- 章节对比了简单字符匹配与字节级 BPE / tiktoken：后者利用常见片段合并和字节回退，在有限词表下处理更广泛的文本。
- 章节说明 Context Length 与 Token 数量相关，Token ID 通过 Embedding Lookup Table 转换为向量；Embedding 层参数量由词表大小和向量维度共同决定。

### 这里做出的整理和工程推论

- 由于模型按 Token 而不是字符处理内容，LLM 应用应该按 Token 预算管理上下文和成本。
- 对 Agent 来说，工具返回内容是上下文的一部分；限制工具结果大小和信息密度，通常比事后盲目压缩整段历史更可靠。

## 最后只记住这五句话

1. **Token 是模型读文字时使用的小片段，不保证等于一个字或一个词。**
2. **Token ID 只是编号；模型真正计算的是编号查出来的数字向量。**
3. **文字长度不等于 Token 长度，所以字数不能准确代表上下文占用或费用。**
4. **长历史、长文档和工具原始输出都会占 Token 预算。**
5. **做 LLM / Agent 时，要按 Token 管上下文：筛选、分配预算、留输出空间，并处理超限。**

## 自测问题
