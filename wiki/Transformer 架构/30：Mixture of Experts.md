# Mixture of Experts：每个 Token 只使用部分参数

> [!abstract] MoE 通常把 Transformer Block 中的一个 FFN 换成多个“专家”FFN，再由 Router 为每个 Token 选择少数专家。它试图把模型的总参数容量与每个 Token 的计算量部分分开。

## 为什么需要 MoE

普通 Dense 模型扩大参数时，每个 Token 都要经过同一套更大的网络：

```text
参数增加
→ 模型可容纳的能力增加
→ 每个 Token 的计算量也增加
→ 训练和推理成本上升
```

MoE 改为准备多个专家，但一次只激活少数专家：

```text
把 FFN 拆成多个专家
→ Router 按 Token 选择少数专家
→ 模型可以拥有更多总参数
→ 每个 Token 不必运行全部专家
```

因此要区分：

- **总参数量：** 模型需要保存的全部参数，代表可用容量。
- **激活参数量：** 处理当前 Token 时实际参与计算的参数。

MoE 的核心不是减少模型拥有的参数，而是用稀疏激活降低每个 Token 的计算增长速度。Attention、Embedding、Router、共享专家等部分仍然会参与计算，因此激活参数量不等于完整计算量。

## 一个 Token 怎样经过 MoE

```text
Token 当前表示
→ Router 计算它与各专家的匹配分数
→ 选择 Top-K 个专家
→ 被选中的专家分别处理 Token
→ 按路由权重合并结果
→ 继续进入后面的网络层
```

不同 Token 可以选择不同专家，同一个 Token 在不同层也可能选择不同专家。

“专家”只是训练得到的子网络，不一定能被稳定命名为中文专家、数学专家或代码专家。

## 新代价是什么

- **权重存储：** 未激活的专家虽然不参与当前计算，但服务仍要让全部专家可用。
- **负载均衡：** 大量 Token 选择同一个专家时，会出现拥堵，而其他专家得不到充分训练。
- **设备通信：** 专家分布在不同 GPU 上时，需要把 Token 发送到相应设备。
- **系统复杂度：** Router、专家容量限制和分布式调度让训练与部署更复杂。

因此，计算量减少不保证端到端延迟一定更低。MoE 把部分计算压力转化成了显存、通信和调度压力。

## 做项目时记住

1. **托管模型：** 直接比较真实质量、延迟和价格，不根据总参数或激活参数推测效果。
2. **本地或小规模部署：** 较小的 Dense 模型配合量化通常更简单；只有硬件和推理框架能够高效调度专家时，MoE 的优势才容易兑现。
3. **问题不要混淆：** MoE 解决模型容量与单次计算的矛盾；GQA 主要减少 KV Cache；量化主要减少权重存储和计算成本。

## 别误解

- **“每次只用两个专家，所以只需加载两个专家。”** 不同 Token 可能选择不同专家。
- **“专家天然按学科分工。”** 分工由训练形成，通常不能稳定命名。
- **“激活参数少，速度一定更快。”** 路由、内存访问和设备通信也有成本。
- **“MoE 会让上下文记得更久。”** 它主要改变 FFN 容量，不改变模型访问历史信息的机制。

## 一句话复习

> MoE 用 Router 为每个 Token 选择少数 FFN 专家，以较少的单次计算使用更大的总参数容量，代价是更高的权重存储、通信和调度复杂度。
