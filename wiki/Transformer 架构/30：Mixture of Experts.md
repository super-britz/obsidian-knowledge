# Mixture of Experts：每个 Token 只使用部分参数

> [!abstract] MoE 通常把 Transformer Block 中的一个 FFN 换成多个“专家”FFN，再为每个 Token 选择少数专家。这样可以增加模型总容量，又不用让每个 Token 运行全部专家。

## 一个 Token 怎样经过 MoE

```text
Token 当前表示
→ Router 判断更适合哪些专家
→ 只运行少数被选中的专家 FFN
→ 合并专家结果
→ 继续进入后面的网络层
```

不同 Token 可以选择不同专家，同一个 Token 在不同层也可能选择不同专家。

“专家”只是训练得到的子网络，不一定能被清楚命名为中文专家、数学专家或代码专家。

## 它解决什么问题

普通模型的每个 Token 都经过同一套 FFN。MoE 可以加入更多专家参数，让模型拥有更大容量，同时每个 Token 只执行其中一小部分。

它换来的是“更多总参数，但每个 Token 不运行全部参数”，并不表示部署时只需要保存少数专家。服务仍要让所有专家可用，因为后面的 Token 可能选择任何一个专家。

## 新代价是什么

- Router 需要决定 Token 去哪个专家。
- 如果大量 Token 选择同一个专家，会出现排队和负载不均。
- 专家分布在多台设备时，Token 需要跨设备传输。
- 总权重仍然很大，内存占用不会等同于每次激活的参数量。

因此，计算量减少不保证实际延迟一定更低。MoE 更依赖成熟的服务调度和硬件环境。

## 做项目时记住

1. 调用托管模型时，直接比较真实质量、延迟和价格，不根据“总参数”或“激活参数”猜测。
2. 本地和小规模部署中，较小的 Dense 模型配合量化往往更简单。
3. MoE 解决参数容量问题；GQA 解决 KV Cache，量化解决权重大小，不要混为一谈。

## 别误解

- **“每次只用两个专家，所以只需加载两个专家。”** 不同 Token 可能选择不同专家。
- **“专家天然按学科分工。”** 分工由训练形成，通常不能稳定命名。
- **“激活参数少，速度一定更快。”** 路由、内存和设备通信也会产生成本。
- **“MoE 会让上下文记得更久。”** 它改变 FFN 容量，不改变历史访问机制。

## 一句话复习

> MoE 用 Router 为每个 Token 选择少数 FFN 专家，以较少的单次计算使用更大的总参数容量，但部署和调度更复杂。
