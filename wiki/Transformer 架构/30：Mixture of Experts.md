# 第 30 章：Mixture of Experts——每个 Token 只运行部分专家

> [!abstract] 稀疏 MoE 通常把 Transformer Block 中的一个 FFN 换成多个 FFN 专家，再由 Router 为每个 Token 选择少数专家。这样可以增加模型总参数容量，而不让每个 Token 执行全部专家；代价是所有专家仍要部署，并引入路由、负载和跨设备通信问题。

> [!info] 放回完整生成链
> MoE 改的是部分 Block 的 FFN 路径。Attention、逐 Token 生成和 KV Cache 仍然存在。调用托管 API 时只需比较效果、延迟和价格；自建大规模服务才需要深入路由系统。

## 一个 Token 怎样经过 MoE

```text
Token 隐藏状态
→ Router 为各专家打分
→ 选择 Top-k 专家
→ 专家分别执行 FFN
→ 按路由权重合并输出
→ 写回 residual stream
```

不同 Token 可以选择不同专家，同一个 Token 在不同层也可以重新选择。专家是训练出来的条件子网络，不能默认解释成固定的“数学专家”或“中文专家”。

## MoE 真正换来了什么

Dense 模型每个 Token 都执行同一套 FFN；MoE 让模型拥有更多专家参数，但一次只激活少量专家。

| 指标 | MoE 的变化 |
| --- | --- |
| 总参数 | 随专家数量增加 |
| 每 Token 专家计算 | 只执行选中的 Top-k |
| 权重内存 | 服务仍需让全部专家可访问 |
| 通信 | Token 可能要跨设备发送给专家 |
| 端到端速度 | 取决于负载、Batch、内核和网络 |

因此“激活参数较少”不能直接等同于同规模 Dense 模型的延迟或显存。

## 为什么 Router 会成为新瓶颈

如果大量 Token 同时选择少数热门专家：

- 热门专家排队，造成 P99 延迟；
- 冷门专家训练不足；
- 设备间负载不均；
- 专家缓冲区可能溢出。

训练通常加入负载均衡机制，但“越均匀越好”也不成立：过强约束可能阻止模型形成有用分工。需要同时观察每层专家负载、溢出率、延迟和任务质量。

## 为什么 FLOPs 少不一定更快

专家分布在多张卡时，Token 需要先按路由结果重新分桶并跨设备发送，专家计算后再送回原位置。小 Batch 或逐 Token Decode 中，每个专家拿到的 Token 很少，矩阵利用率和通信摊销可能很差。

所以 MoE 更适合有高速互联、较大吞吐和成熟调度的大规模系统。单机、端侧、小 Batch 低延迟场景中，Dense 模型配合量化往往更简单。

## 做项目时记住

1. **托管模型按端到端结果选。** 不因“总参数很大”或“激活参数很小”直接判断能力与速度。
2. **自建部署要算完整资源账。** 包括全部专家权重、Router、通信、热点和共享层。
3. **MoE 与其他优化职责不同。** MoE 扩展条件参数容量，GQA 压缩 KV Cache，量化压缩权重表示。
4. **必须测尾延迟。** 平均吞吐可能掩盖专家热点造成的 P99 问题。

## 别误解

- **“每次只用两个专家，所以只需加载两个专家。”** 不同 Token 会选择不同专家，服务整体仍需访问全部专家。
- **“专家天然按学科分工。”** 专门化可能存在，但通常难以稳定命名。
- **“激活 13B 等于 Dense 13B 的全部成本。”** 共享层、内存访问、通信和算子形状都不同。
- **“FLOPs 更少，所以延迟一定更低。”** 路由和跨设备通信可能抵消收益。
