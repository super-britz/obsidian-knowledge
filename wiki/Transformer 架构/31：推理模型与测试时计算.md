# 第 31 章：推理模型与测试时计算——难题为什么需要更多预算

> [!abstract] 推理模型通常仍然逐 Token 生成，只是经过专门后训练，并在回答前使用更多中间 Token、候选、搜索或工具。额外计算增加找到正确路径的机会，但只有候选有效、验证可靠时才有收益。

> [!info] 它在产品里改变什么
> 数学、代码和规划等任务可能更准确，但延迟、Token 和费用也会上升。前端需要展示进行中状态、允许取消，并区分模型计算、排队和工具调用；最终答案仍需测试或业务规则验证。

## 它没有脱离下一个 Token 预测

```text
问题
→ 分配推理预算
→ 生成中间步骤或多个候选
→ 自检、验证或选择
→ 输出最终答案
```

底层仍是自回归语言模型。变化主要在两层：训练让有用的推理轨迹更常出现，运行时允许为难题花更多计算。

普通 CoT Prompt 通过输入诱导分步回答；推理模型则经过专门后训练，并可能由服务系统控制预算。两者都不保证展示出来的自然语言步骤忠实反映内部过程或证明答案正确。

## 额外计算可以花在哪里

| 方式 | 增加什么 | 适合 | 风险 |
| --- | --- | --- | --- |
| 更长单轨迹 | 中间 Token | 分解、回溯和修正 | 循环、冗长、错误累积 |
| 多候选采样 | 多次生成 | 答案可比较的任务 | 成本增长、候选一起犯错 |
| 搜索 + Verifier | 分支和评分 | 数学、代码、规划 | 评分器也会出错 |
| 工具执行 | 外部计算与查询 | 可程序验证的任务 | 权限、环境和工具失败 |

简单题继续“深思”通常浪费预算；基础模型几乎生成不出正确候选的过难题，多采样也帮助有限。最可能获益的是存在多条候选路径、且结果可以验证的中间区域。

## 训练怎样鼓励推理

训练信号可以来自：

- 最终答案或单元测试是否通过；
- 中间步骤是否合理；
- 规则、计算器或执行环境的结果；
- 人类或模型对整体答案的偏好。

GRPO 等方法改变的是怎样利用多条候选的相对奖励更新模型，不会消除奖励函数、采样成本或验证器。蒸馏则把强模型筛选后的回答用于训练小模型，降低部署成本，但也可能复制错误和模板化习惯。

应用开发者不需要掌握训练公式，只需知道模型名里的“reasoning”不是正确性保证。

## 推理轨迹、答案和证明不是一回事

一段流畅的推理文字可能包含探索、遗漏或事后合理化。可靠系统应返回与任务匹配的可检查产物：

- 数学题给关键等式和可验证结果；
- 代码任务给补丁与测试；
- 检索任务给可回查来源；
- Agent 动作给真实工具参数和执行回执。

验证器也要单独测试；如果生成和评分使用相似模型，两者可能共享盲点。

## 什么时候使用推理模型

```text
答案能否由确定性工具直接得到？
├─ 能：优先快速模型 + 工具
└─ 不能：任务是否值得更高成本，并且结果可验证？
   ├─ 否：使用快速模型或请求更多信息
   └─ 是：逐级增加推理、候选和验证预算
```

评测时同时记录成功率、成本、P50 / P99 延迟、无效轨迹和验证器误选率。不能只比较 Benchmark 分数，也不能让简单任务默认使用最高推理预算。

## 别误解

- **“推理模型不再预测下一个 Token。”** 底层通常仍以自回归方式生成。
- **“思考越久一定越准确。”** 错误方向也会消耗更多 Token。
- **“多数候选一致就是事实。”** 多个候选可能共享同一偏差。
- **“隐藏或展示完整 CoT 能证明答案。”** 正确性仍来自外部可检查证据。
