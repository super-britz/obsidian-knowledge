# 第 31 章：推理模型与测试时计算——把计算预算花在难题上

> [!abstract] 推理模型通常仍是自回归语言模型，关键变化不是“不再预测下一个 Token”，而是训练模型产生、评估和修正更有用的中间计算，并在推理时为难题分配更多 Token、采样、验证或工具调用。更多计算扩大搜索机会，却只有在候选与验证有效时才提高正确率。

> [!info] 阅读粒度
> 本页把强化学习训练、Test-Time Compute、验证器、GRPO 和蒸馏放进同一条“生成候选—获得反馈—分配预算—外部验收”链，因此标为“深入机制”；快速阅读时先看计算形态、有效条件和工程决策。

## 推理模型没有脱离自回归 Transformer

对外可见的过程仍是：输入上下文，逐 Token 生成输出。所谓 Reasoning Model，通常表示模型经过专门后训练，能够在最终回答前消耗额外推理 Token，并可能配合并行采样、验证器或工具。OpenAI 官方资料只确认 o1 系列使用强化学习进行复杂推理并在回答前产生内部推理链；参数量、PRM 和搜索实现没有在该资料中公开，不应由外部表现反推。

```text
问题
→ 判断难度并分配推理预算
→ 生成一个或多个候选轨迹
→ 自检、外部验证或候选选择
→ 输出最终答案
```

这和 [[28：Prompt 工程|CoT Prompting]] 的区别主要在训练和系统层：普通 CoT 由输入提示诱导；推理模型通过后训练形成更稳定的长轨迹行为，并由运行时控制预算。两者都不保证中间文字忠实解释内部计算。

## Test-Time Compute 有四种主要形态

| 形态 | 增加的资源 | 适合 | 主要风险 |
| --- | --- | --- | --- |
| 更长单轨迹 | 推理 Token | 分解、回溯、修正 | 冗长循环、错误累积 |
| 并行采样 / Best-of-N | 多个候选 | 答案可比较或投票 | 成本近似随 N 增长、相关性错误 |
| 搜索 + Verifier | 分支与评分 | 数学、代码、规划 | 验证器被攻击或分布外失效 |
| 工具执行 | 计算器、代码、检索 | 可外部计算和核验的任务 | 工具错误、权限与环境差异 |

Snell 等人的实验说明，最优计算分配依赖题目难度：简单题继续搜索浪费预算，过难题若基础模型几乎产生不了正确候选，增加采样也帮助有限；中间区域最可能受益。因此 Test-Time Scaling 不是单调保证，更不是“思考越久越聪明”。

## 训练怎样让有用推理更常出现

训练信号可以只看最终结果，也可以评价中间步骤：

- **Outcome Reward：** 最终答案、单元测试或证明检查通过即可；便宜且客观，但难定位哪一步有效。
- **Process Reward：** 对中间步骤评分；提供更密集反馈，但标注贵，评审器本身也可能错误。
- **规则 / 工具 Reward：** 数学答案、代码测试、格式或约束由程序验证；精确但覆盖范围有限。
- **偏好 Reward：** 比较整体答案质量；适合开放任务，但继承 [[29：RLHF 与偏好学习|偏好代理]] 的偏差。

DeepSeek-R1-Zero 从预训练好的 DeepSeek-V3-Base 出发，没有先做推理 SFT，而以大规模 RL 激励可验证任务上的推理行为；它同时出现语言混杂和可读性问题。最终 R1 加入 Cold-Start 数据和多阶段训练，说明 RL 能探索策略，不等于示范、语言质量和通用对齐都不再需要。

## GRPO 省去 Critic，但没有省去奖励

传统 PPO 常训练 Value / Critic 估计回报。GRPO 对同一 Prompt 采样一组回答，以组内奖励均值和标准差构造相对优势：

```text
A_i ≈ (r_i - mean(r_group)) / std(r_group)
```

高于组均值的轨迹得到正优势，低于均值的轨迹得到负优势，再配合裁剪和参考策略约束更新 Policy。这样不需要与 Policy 同规模的独立 Critic，但仍要为每个 Prompt 生成多个回答、计算奖励并控制策略漂移。

组内全错时，“最好”也可能是错；奖励稀疏或方差过小时，优势信号很弱；规则奖励还可能被格式捷径利用。因此不能把 GRPO 描述成无教师自我进化，也不能假定固定节省一半训练成本。

## 推理轨迹、最终答案与证明是三回事

自然语言推理轨迹可能包含探索、删除、捷径和事后合理化。隐藏轨迹保护系统实现或安全策略，但也不能作为用户审计证据；公开一条流畅 CoT 同样不能证明结论正确。

工程系统应输出与任务相匹配的**可验证产物**：数学给关键等式和可检查结论，代码给补丁与测试，检索给来源，Agent 给工具参数和真实回执。正确性依赖外部验证器，而不是模型声称“我检查过了”。

验证器也必须单独评估。若使用同类模型同时生成和评分，二者可能共享盲点；Best-of-N 会放大评分器偏好。应混合规则、执行环境、独立模型和人工抽检，并针对评分器做对抗样例。

## 蒸馏传递行为，不传递保证

推理蒸馏通常收集强模型生成的轨迹或答案，筛选后用 SFT 训练较小模型。它把昂贵探索转成离线示范，能显著降低部署成本；DeepSeek-R1 报告了多个 Qwen / Llama 蒸馏 Checkpoint。

学生学习的是教师输出分布。错误轨迹、模板化长答案和奖励捷径也会被复制；小模型可能在目标基准上表现很好，却在分布外题目中生成形式流畅但逻辑错误的步骤。学生在个别指标上可能超过一次采样的教师，因此“学生永远不能超过教师”也不是可靠规则。应比较教师、学生和原始基座在同一 Token 预算与验证协议下的质量。

## 工程决策：先判断任务是否值得思考

```text
答案能否低成本直接得到？
├─ 是：快速模型 + 确定性工具
└─ 否：任务是否可验证、基础模型能产生有用候选？
   ├─ 否：补知识、工具、数据或升级模型
   └─ 是：逐级增加轨迹长度、采样、搜索与验证预算
```

简单抽取、分类、闲聊和低延迟交互通常不值得长推理；数学、代码、规划和可检查分析更可能获益。医学、法律等高风险任务虽然需要审慎推理，但模型长想不能代替权威数据、专业人员和责任边界。

评测必须记录精确模型版本、Prompt、工具、最大推理 Token、采样数、选择器、是否多数投票及 Benchmark 版本。除准确率外，至少报告成功请求成本、P50 / P99 延迟、无效轨迹比例、验证器误选率和简单题过度思考率。

## 别误解

- **“推理模型不再做下一个 Token 预测。”** 它仍以自回归生成执行计算，只是训练与预算策略不同。
- **“更多推理 Token 一定更准。”** 错误方向、循环和无有效候选会消耗更多成本而不增益。
- **“R1-Zero 从零开始，只靠 RL 学会知识。”** 它从已预训练的 Base Model 开始，只是没有把 SFT 作为 RL 前置阶段。
- **“GRPO 不需要评判者。”** 它去掉 Critic，不会去掉奖励函数或验证器。
- **“隐藏或公开 CoT 能证明答案。”** 两者都不是外部可执行的正确性证明。
- **“蒸馏把大模型全部能力装进小模型。”** 它传递选定数据分布中的行为，并伴随容量和覆盖损失。
