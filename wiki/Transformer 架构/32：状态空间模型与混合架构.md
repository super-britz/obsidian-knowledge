# 第 32 章：状态空间模型与混合架构——压缩历史还是直接访问

> [!abstract] Attention 保存每个历史 Token 的 K/V，方便当前 Token 直接读取任意位置；SSM 把历史不断压缩到固定状态，换取更稳定的长序列成本。Mamba 让状态更新随输入变化，混合架构则保留少量 Attention 来补充精确访问。

> [!info] 前端开发者可以跳过吗？
> 普通聊天和 API 应用可以跳过。本页主要用于模型选型、长流式数据和端侧部署；需要先记住的只有“逐 Token 保存”和“固定状态压缩”的取舍。

## 两种保存历史的方式

```text
Attention：保留历史 Token 的 K/V
           → 当前 Query 直接匹配具体位置

SSM：旧状态 + 当前 Token
     → 更新固定维度状态
     → 从状态产生输出
```

| 维度 | Attention | SSM |
| --- | --- | --- |
| 历史表示 | 逐 Token K/V | 固定维度状态 |
| 精确访问 | 可以按内容直接读取位置 | 受压缩信息限制 |
| Decode 状态 | 随上下文增长 | 相对上下文长度固定 |
| 长序列成本 | Dense 配对和 Cache 较贵 | 递归扫描通常更稳定 |
| 工具与生态 | 成熟 | 依赖专用 Kernel 和框架支持 |

固定状态不是无限无损记忆。就像把不断增长的日志压成一份固定长度摘要，状态可以持续更新，但早期细节可能无法恢复。

## Mamba 增加了什么

传统静态 SSM 对不同输入使用相同状态更新规则，不容易按内容决定“什么值得保留”。Mamba 让部分写入、读取和时间尺度由当前 Token 决定：

```text
当前 Token
→ 决定怎样更新状态、保留多久、怎样读出
```

它仍然通过递归状态传递历史，不等于 Attention。训练时使用 Selective Scan 等并行与融合实现提高效率；真实速度仍取决于 Kernel、Batch、精度和序列长度。

## 为什么出现混合架构

两种结构擅长不同任务：

- SSM 擅长用固定状态持续处理长序列；
- Attention 擅长按内容直接找回具体历史位置。

Hybrid 会使用较多 SSM 层处理连续历史，再保留少量 Attention 层恢复显式 Token 访问。它可能取得折中，也会同时拥有 SSM State、部分 KV Cache 和更复杂的运行时。

MoE 可以与两者组合，但解决的是参数容量，不是历史访问。

## 怎样选择

- **需要频繁引用任意早期原文：** 优先 Attention、检索，或保留足够 Attention 的 Hybrid。
- **持续流式输入、历史可压缩：** 可以评估 SSM / Mamba。
- **已有成熟 Transformer 服务：** 除非长序列成本确实是主要瓶颈，否则迁移新骨干未必划算。
- **选择托管模型：** 直接比较真实任务质量、延迟、成本和窗口稳定性，不因架构名称预判胜负。

## 怎样验证

同时改变输入长度、关键信息位置、干扰数量和任务类型。性能上分别测 Prefill、Decode、吞吐与状态大小；质量上测精确召回、全文摘要、多事实组合和真实业务任务。

若分块流式处理，还要比较整段输入与不同 Chunk 边界下的输出一致性。

## 别误解

- **“SSM 用固定内存记住无限历史。”** 固定状态会压缩历史，可恢复信息有限。
- **“Mamba 就是线性 Attention。”** 两者有数学联系，但保存和访问历史的机制不同。
- **“线性复杂度保证所有长度都更快。”** 短序列常数项、Kernel 和硬件可能改变结果。
- **“Hybrid 自动兼得全部优点。”** 它也叠加状态、Cache 和运行时复杂度。
