# 状态空间模型与混合架构：压缩历史还是直接读取

> [!abstract] “后 Transformer 架构”不是一种固定架构，也不表示 Transformer 已经过时。它泛指为了降低标准 Attention 的长序列成本，对状态空间模型、线性 Attention、循环结构和混合架构等方向的探索。

> [!tip] 可以跳过吗？
> 普通聊天和 API 应用可以跳过。本页只需要记住：Attention 保存可直接查询的历史，状态空间模型把历史压缩成状态，混合架构在两者之间取舍。

## 第一性原理：问题来自哪里

模型处理当前 Token 时，需要利用前面的历史信息。最直接的办法是保留历史 Token，并让当前 Token 查询它们：

```text
保留更多历史位置
→ 更容易精确找回原文细节
→ Attention 需要处理更多 Token 之间的关系
→ 计算量和 KV Cache 随上下文增长
```

因此出现一个基本矛盾：

> 历史保存得越完整，随机访问越准确，但计算和存储成本越高；历史压缩得越多，成本越稳定，但细节越可能丢失。

所谓后 Transformer 探索，核心不是换一个新名字，而是重新回答：**历史信息应该怎样保存和访问？**

## 两种保存历史的方式

### Attention：保存可查询的历史

```text
逐 Token 保存历史 K/V
→ 当前 Token 与历史位置匹配
→ 直接取回相关信息
```

它类似保留完整笔记，需要时翻回具体页面。优点是容易定位原文细节，代价是上下文越长，Attention 计算和 KV Cache 越大。

### 状态空间模型：维护压缩状态

```text
旧状态 + 当前 Token
→ 更新内部状态
→ 从新状态产生输出
→ 继续处理下一个 Token
```

它类似边阅读边更新一份摘要。递归推理状态不需要随历史长度持续增长，但固定大小的状态无法保证无损保存无限历史。

## Mamba 改进了什么

传统状态空间模型使用较固定的状态更新方式，不容易根据内容决定哪些信息重要。

Mamba 让状态更新依赖当前输入：

```text
读入当前 Token
→ 判断哪些信息值得写入、保留或忽略
→ 有选择地更新状态
```

这让模型能够更灵活地压缩历史，但没有消除压缩本身的边界。Mamba 不是更快版本的 Attention，而是另一种保存和访问历史的机制。

## 为什么会有混合架构

两种机制解决的是不同需求：

- **状态空间层：** 低成本地持续传递被压缩的历史信息。
- **Attention 层：** 按内容直接查询具体历史位置。
- **MoE 层：** 增加参数容量，但每个 Token 只激活部分专家。

混合模型保留少量 Attention，同时使用状态空间层，有些架构还加入 MoE：

```text
状态空间层处理大部分序列
→ 降低长序列成本

Attention 层负责关键位置的精确访问
→ 弥补压缩状态可能丢失细节的问题
```

它不是自动获得全部优点，而是把单一机制的取舍变成系统层面的组合与调度问题。

## 什么时候需要关心

- **频繁精确引用早期原文：** 优先评估 Attention、外部检索，或保留较多 Attention 的混合模型。
- **持续处理长数据流，且历史可以压缩：** 可以评估状态空间模型。
- **短上下文或现有推理框架：** 线性复杂度不保证实际更快，仍要以真实硬件测试为准。
- **调用托管模型：** 直接比较质量、延迟和价格，不根据架构名称预判效果。

## 别误解

- **“后 Transformer 就是淘汰 Transformer。”** 当前更多是替代组件和混合路线。
- **“固定状态能无损记住无限历史。”** 固定空间只能保存压缩结果。
- **“Mamba 就是更快的 Attention。”** 两者保存和访问历史的方式不同。
- **“混合架构自动拥有全部优点。”** 它也会叠加状态、KV Cache 和实现复杂度。

## 一句话复习

> Attention 用不断增长的历史存储换精确访问；状态空间模型用固定状态压缩历史换稳定成本；后 Transformer 架构是在两者之间寻找新的平衡，而不是简单抛弃 Transformer。
