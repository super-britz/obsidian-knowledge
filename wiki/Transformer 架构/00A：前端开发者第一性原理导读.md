# 前端开发者第一性原理导读：大模型为什么需要这些组件

> [!abstract] 先只记住一件事：大模型读取已有 Token，判断下一个 Token 的可能性，选出一个追加到后面，再重复。Transformer 的组件都在帮助这次预测更准确、更稳定或成本更低。

## 大模型到底在做什么

```text
已有 Token
→ 判断下一个 Token 的候选概率
→ 选出一个 Token
→ 追加到已有内容
→ 继续预测
```

模型不是数据库、搜索引擎或 JavaScript 解释器。参数保存的是训练学到的语言和知识模式；回答是在当前上下文中一步步生成出来的。

为了做到这件事，模型必须解决：

1. 文字怎样变成数字？
2. 怎样知道 Token 的顺序？
3. 当前 Token 怎样读取前文？
4. 信息怎样经过很多层持续加工？
5. 训练怎样把错误变成参数更新？
6. 推理怎样把候选概率变成连续文本？

后面的术语，都是这些问题的局部答案。

## 一条消息怎样变成一个新 Token

```text
用户消息 + 系统规则 + 工具结果
→ Chat Template：整理成模型约定的输入格式
→ Tokenization：文字变成 Token ID
→ Embedding + Position：ID 变成带顺序的数字表示
→ 多个 Transformer Block
   ├─ Attention：从前文取得当前需要的信息
   ├─ FFN：加工当前 Token 已有的信息
   └─ Residual + Norm：让信息稳定穿过很多层
→ LM Head：为词表中的候选 Token 打分
→ 解码：选择下一个 Token
→ 追加并重复
→ 通过流式响应返回前端
```

前端看到文字逐渐出现，模型实际在重复预测 Token。推理服务通常使用 KV Cache 复用历史计算，并非每轮都从头处理全部前文。

## 每个组件解决什么问题

- **[[04：Tokenization|Tokenization]]：文字不能直接计算。** 它把文字转换成 Token ID，因此字符数不等于 Token 数、上下文长度或费用。
- **[[05：位置编码|位置编码]]：模型需要知道先后。** 它让相同 Token 在不同位置拥有不同的顺序信息。
- **[[08：线性变换|线性变换]]：数字需要按用途重新组合。** 不同权重可以从同一个表示产生 Q、K、V 等不同版本。
- **[[09-12：Attention|Attention]]：当前 Token 需要读取前文。** 它根据当前需要汇总相关历史，但不保证像数据库一样精确召回。
- **[[07：FFN|FFN]]：取得上下文后还要继续加工。** 它分别改变每个 Token 当前的数字表示。
- **[[13-15：Transformer Block 与前向传播|Residual + Norm]]：很多层计算要保持稳定。** 残差保留信息主干，Norm 控制数值尺度。
- **[[06：LayerNorm 与 Softmax|Softmax]] 与 [[附录：解码与采样策略|解码]]：最终要选出一个 Token。** Temperature、Top-P 等参数改变随机性，不代表事实正确率。

## 训练和推理有什么区别

训练时，正确的下一个 Token 已经存在：

```text
模型预测
→ 与正确 Token 比较
→ 计算误差
→ 更新参数
```

推理时没有现成答案：

```text
预测一个 Token
→ 追加到输入
→ 再预测下一个
```

因此，[[16-17：训练、推理与参数更新|训练]]改变模型长期使用的参数；[[28：Prompt 工程|Prompt]]只改变当前调用的条件。RAG 提供最新事实，Tool 执行确定性查询或动作，它们不能相互替代。

## 性能优化在解决什么

- **长 Prompt 首 Token 慢：** [[21-22：Flash Attention 与 KV Cache|Flash Attention]]减少 Attention 的中间内存和数据搬运。
- **每生成一个 Token 都重算历史：** [[21-22：Flash Attention 与 KV Cache|KV Cache]]保存历史 K/V，用内存换速度。
- **Cache 限制并发：** [[23：MHA、MQA 与 GQA|MQA / GQA]]让多个 Query Head 共享更少的 K/V。
- **微调成本太高：** [[26：LoRA 与 QLoRA|LoRA / QLoRA]]减少需要训练的参数状态。
- **模型权重太大：** [[27：模型量化与 GGUF|量化]]用更少位数保存权重。
- **想增加模型容量：** [[30：Mixture of Experts|MoE]]让每个 Token 只运行少量专家，但所有专家仍需部署。
- **历史状态持续增长：** [[32：状态空间模型与混合架构|SSM / Mamba]]把历史压缩进固定状态，但可能丢失细节。

优化名称不等于用户收益。最终仍要测首 Token 延迟、后续生成速度、并发、内存、费用和回答质量。

## 前端开发 AI 应用要关心什么

- **上下文有预算：** 历史消息、文件和工具结果都会占 Token，需要裁剪、摘要或按需检索。
- **流式输出可能不完整：** UI 要处理取消、超时、断线以及不完整的 Markdown 和 JSON。
- **模型输出不可信：** JSON 要校验 Schema，引用要回查来源，工具动作要读取真实回执。
- **随机性属于产品行为：** 记录模型、Prompt 和解码配置，才能复现和比较问题。
- **权限必须在服务端：** 数据访问、金额和写操作不能只依赖 Prompt。
- **延迟要分阶段测量：** 网络、排队、首 Token、后续生成和工具调用不是同一个瓶颈。

你是在用概率模型构建产品，而不是调用一个保证确定返回值的普通函数。
