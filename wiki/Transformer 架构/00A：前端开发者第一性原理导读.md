# 前端开发者第一性原理导读：大模型为什么需要这些组件

> [!abstract] 先只记住一件事：大模型接收一串 Token，计算“下一个 Token 分别有多大可能”，选出一个后追加到原序列，再重复。Transformer 的所有组件、训练方法和性能优化，都可以从“怎样让下一次预测更准确、更稳定、更便宜”推导出来。

## 第一性原理：模型到底在做什么

语言模型的核心目标可以压缩成：

```text
已有 Token → P(下一个 Token | 已有 Token)
```

它不是数据库、搜索引擎或 JavaScript 解释器。模型参数保存的是从训练数据中学到的统计规律；一次回答则是在当前上下文条件下反复生成 Token。

因此，大模型必须依次解决六个基础问题：

1. 文本怎样变成可以计算的数字？
2. 模型怎样知道 Token 的顺序？
3. 当前 Token 怎样读取前文中有用的信息？
4. 几十层网络怎样持续加工信息而不崩溃？
5. 怎样通过大量样本把错误变成参数更新？
6. 推理时怎样把概率分布变成连续文本？

后面的所有术语，都是这些问题的局部答案。

## 从前端请求到一个新 Token

假设页面调用聊天接口：

```ts
await fetch("/api/chat", {
  method: "POST",
  body: JSON.stringify({ messages }),
});
```

服务端不会把这段字符串直接交给矩阵计算，而是经历：

```text
messages + 系统指令 + 工具结果
→ Chat Template：拼成模型约定的文本格式
→ Tokenization：文本切成 Token ID
→ Embedding + Position：ID 变成带位置信息的向量
→ 多个 Transformer Block
   ├─ Attention：从前文读取当前需要的信息
   ├─ FFN：加工每个 Token 当前已有的信息
   └─ Residual + Norm：让信息和梯度稳定穿过深层网络
→ LM Head：向量映射成整个词表的 Logits
→ Softmax / Sampling：选出下一个 Token
→ 追加 Token，重复以上过程
→ 通过 SSE / Stream 返回前端
```

前端看到的是字符逐渐出现；模型实际进行的是一次次“根据不断增长的 Token 序列预测下一个 Token”。部署时通常会用 KV Cache 复用历史计算，并非每轮都从头计算全部历史。

## 每个组件为什么必然出现

| 原始问题 | 推导出的组件 | 在大模型中的作用 | 前端可观察现象 |
| --- | --- | --- | --- |
| 文本不能直接参与矩阵运算 | [[04：Tokenization|Tokenization]] | 把文本映射为有限词表中的 ID | 字符数不等于 Token 数、费用和截断长度 |
| 相同 Token 在不同位置含义不同 | [[05：位置编码|位置编码]] | 把顺序和相对距离带入表示 | 超长输入可能出现位置外推退化 |
| 当前 Token 需要读取前文 | [[09-12：Attention|Attention]] | 根据当前查询对历史信息加权汇总 | 上下文能影响回答，但不保证精确召回 |
| 汇总后还要进行非线性加工 | [[07：FFN|FFN]] | 独立加工每个 Token 已收集的信息 | 模型容量和计算量大部分来自这些矩阵 |
| 深层网络容易破坏已有信息 | [[13-15：Transformer Block 与前向传播|Residual + Norm]] | 保留信息主干并稳定数值与梯度 | 决定模型能否堆叠很多层并训练稳定 |
| 最终要在词表中选择下一个 Token | [[13-15：Transformer Block 与前向传播|LM Head]] + [[06：LayerNorm 与 Softmax|Softmax]] | 把内部表示变成候选 Token 分布 | Temperature、Top-p 会改变输出随机性 |

可以把 Attention 暂时理解成 `score → normalize → weighted sum`，但它不是数据库精确查询；KV Cache 类似 Memoization，但缓存的是每层 Attention 的 K/V 张量，而不是最终接口响应。类比只帮助定位，不能替代机制边界。

## 训练和推理是同一模型的两种工作方式

训练时，文本中的正确下一个 Token 已知：

```text
整段训练文本
→ 模型同时预测各位置的下一个 Token
→ 与真实 Token 计算 Loss
→ 反向传播计算梯度
→ Optimizer 更新参数
```

推理时没有后续答案，只能生成一个再继续：

```text
Prompt → 下一个 Token → 追加 → 再预测 → 直到停止
```

所以 [[16-17：训练、推理与参数更新|训练]] 改变长期参数，[[28：Prompt 工程|Prompt]] 只改变当前推理条件。RAG 把最新事实加入上下文，Tool 在模型外执行确定性查询或动作；这些责任不能用一个超长 Prompt 相互替代。

## 性能优化都是从瓶颈推导出来的

| 观察到的瓶颈 | 对应方案 | 它真正优化什么 | 它没有解决什么 |
| --- | --- | --- | --- |
| Attention 中间矩阵的显存 IO 很大 | [[21-22：Flash Attention 与 KV Cache|Flash Attention]] | 分块和融合计算，减少 HBM 读写 | 不取消 Dense Attention 的二次算术 |
| 每生成一个 Token 都重复计算历史 | [[21-22：Flash Attention 与 KV Cache|KV Cache]] | 复用历史 K/V | Cache 本身随上下文增长 |
| KV Cache 限制并发 | [[23：MHA、MQA 与 GQA|MQA / GQA]] | 让多个 Query Head 共享较少 K/V Head | 可能改变模型质量与权重兼容性 |
| 训练状态太大 | [[26：LoRA 与 QLoRA|LoRA / QLoRA]] | 减少需要训练和保存的参数状态 | 不适合保存动态事实 |
| 部署权重太大 | [[27：模型量化与 GGUF|模型量化]] | 用低比特表示减少存储和带宽 | 不自动修复模型行为与知识 |
| 希望增加容量但不同比增加每 Token 计算 | [[30：Mixture of Experts|MoE]] | 每个 Token 只执行少量专家 | 所有专家仍需部署，并引入通信 |
| 历史 KV 随长度持续增长 | [[32：状态空间模型与混合架构|SSM / Mamba]] | 用固定状态压缩历史 | 不能保证无损找回任意历史细节 |

优化名称不等于用户收益。最终仍要测首 Token 延迟、后续 Token 速度、并发、显存、费用和回答质量。

## 前端开发 AI 应用时真正需要关心什么

前端通常不需要手写矩阵乘法，但必须理解以下接口边界：

- **上下文有预算：** 历史消息、文件、工具结果都会占 Token；长对话要裁剪、摘要或按需检索。
- **流式输出不等于模型一次生成：** UI 要处理增量 Token、取消、重试、断线恢复和不完整 Markdown。
- **模型输出不可信：** JSON 要做 Schema 校验，引用要回查来源，工具动作要读取真实回执。
- **随机性是产品行为：** 同一输入可能产生不同结果；缓存、快照测试和错误复现要记录模型与参数。
- **权限不能写在 Prompt 里：** 金额、数据访问和写操作必须由服务端鉴权、校验和确认。
- **延迟分阶段：** 网络、排队、Prefill、首 Token、Decode 和工具调用要分别测，不能只看总耗时。

你是在用一个概率模型构建产品，而不是调用一个保证确定返回值的普通函数。

## 用第一性原理阅读每篇笔记

以后读任何概念，都按这个顺序提问：

1. **目标：** 大模型当前要完成哪一步？
2. **约束：** 为什么直接做不行？受准确率、计算、内存还是稳定性限制？
3. **机制：** 输入经过什么变化得到输出？
4. **位置：** 它在训练、Prefill、Decode 还是应用层？
5. **表现：** 用户和开发者会观察到什么？
6. **代价：** 它用什么资源换来什么收益？
7. **决策：** 前端项目什么时候需要关心，什么必须交给服务端或模型团队？

如果一篇笔记还不能回答这七个问题，它就只有知识点，没有形成可用于开发的心智模型。
