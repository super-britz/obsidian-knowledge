# 第 16～17 章：训练、推理与参数更新

> [!abstract] 训练和推理都会先做前向传播、得到 logits，区别发生在 logits 之后：训练把 logits 与正确目标比较，通过反向传播和优化器修改参数；推理保持参数不变，通过解码选出下一个 Token，再把它接回输入继续生成。学习率控制的正是训练分支中每次参数更新的步长。

> [!info] 阅读粒度
> 本页把共享前向、训练分支、推理分支和学习率保留在同一张分叉图中，因此标为“深入机制”；快速复述时，阅读摘要、“共同起点和两条分支”及“别误解”即可。

## 先看共同起点和两条分支

```text
输入 Token
→ Transformer 前向传播
→ logits

├─ 训练分支
│  logits + 正确目标
│  → loss
│  → backward 计算梯度
│  → optimizer.step 按学习率更新参数
│
└─ 推理分支
   最后位置 logits
   → 解码选择下一个 Token
   → 接回输入
   → 再做一次前向传播
   → 重复，参数不更新
```

最重要的边界是：

> **前向传播负责计算预测；训练用预测修改参数，推理用预测继续生成。**

## 训练为什么能并行计算多个位置

训练时通常把完整文本错开一位，构造输入和目标：

```text
完整文本：我 喜欢 学习 AI
输入：    我 喜欢 学习
目标：    喜欢 学习 AI
```

这属于 Teacher Forcing：每个位置都使用数据集提供的正确前文，而不是使用模型刚刚生成的 Token。因为整段输入已经准备好，GPU 可以通过矩阵运算一次计算多个位置的 logits 和 loss。

但“并行”不等于模型能偷看答案。因果 Mask 仍然限制位置 `t` 只能读取位置 `t` 及之前的信息，不能读取后面的 Token：

```text
计算上：多个位置同时处理
信息上：每个位置仍只能看见它的过去
```

因此，更准确的说法不是“训练因为知道所有答案，所以模型能看见未来”，而是：**训练数据一次提供了所有正确前缀，因果 Mask 在保持自回归约束的同时允许矩阵并行。**

## 推理为什么必须逐 Token 生成

推理时，下一个 Token 尚不存在：

```text
Prompt
→ 预测 Token₁
→ Prompt + Token₁
→ 预测 Token₂
→ Prompt + Token₁ + Token₂
→ ……
```

第 `t+1` 步的输入依赖第 `t` 步实际选出的 Token，所以同一条生成序列无法提前并行完成所有生成步骤。

这不代表推理完全没有并行性：

- 一次前向传播内部仍是大规模并行矩阵计算；
- 多个请求可以组成 Batch 并行处理；
- 但同一条回答的不同生成步骤存在先后依赖。

### 解码不是前向传播的一部分

前向传播只给出 logits。还需要解码策略把 logits 变成下一个 Token，例如：

- Greedy：选择分数最高的 Token；
- Temperature：调整概率分布的尖锐程度；
- Top-K：只在分数最高的 K 个候选中采样；
- Top-P：只在累计概率达到阈值的候选集合中采样。

不同解码策略改变的是“如何从预测分布中选 Token”，不会修改模型参数。

## 训练分支如何真正修改参数

概念上，一次普通训练迭代可以拆成五步：

```text
1. optimizer.zero_grad()  清理上一轮梯度
2. logits = model(input)  前向计算
3. loss = criterion(logits, target)
4. loss.backward()        计算每个参数的梯度
5. optimizer.step()       根据梯度更新参数
```

其中：

- **logits** 表示模型当前的预测分数；
- **loss** 衡量预测与正确目标之间的差距；
- **gradient** 表示参数应朝哪个方向变化才能降低 loss；
- **optimizer** 决定如何利用梯度；
- **learning rate** 控制这次更新的总体步长。

用最简化的梯度下降表示：

```text
新参数 = 旧参数 - 学习率 × 梯度
```

实际使用 Adam / AdamW 时，还会结合梯度的一阶矩、二阶矩、Weight Decay 等状态，不能把完整更新过程只理解成简单乘法；但“学习率控制更新尺度”这个直觉仍然成立。

> [!note] 梯度累积是例外流程
> 如果需要累积多个 Micro-batch 的梯度，不会每个 Micro-batch 都执行 `zero_grad()` 和 `optimizer.step()`；但前向、反向和参数更新仍然是不同阶段。

## 学习率为什么需要调度

学习率不是“每次修改百分之多少”，而是优化器更新公式中的尺度参数：

- **过大**：loss 可能震荡、发散或出现 NaN；
- **过小**：loss 下降缓慢，在固定训练预算内学不充分；
- **合适**：在稳定性和收敛速度之间取得平衡。

常见训练配方会让学习率随训练阶段变化：

```text
训练初期：Warmup，从较小值逐渐升高
训练中后期：Decay，逐渐降低学习率
```

Warmup 用来降低训练刚开始时大步更新带来的不稳定风险；Decay 让后期更新更细。具体峰值、Warmup 步数和衰减曲线必须与模型规模、Batch、优化器、数据和总训练步数一起确定，不能脱离训练配置复制一个“万能学习率”。

## 推理模式要分清两个开关

在 PyTorch 中，下面两件事相关但不等价：

```python
model.eval()                 # 切换模块行为，例如关闭 Dropout
with torch.inference_mode(): # 不构建反向传播所需的计算图
    logits = model(input_ids)
```

- `model.eval()` 改变训练期和推理期行为不同的模块；它本身不会关闭自动求导。
- `torch.no_grad()` 或 `torch.inference_mode()` 才是不记录梯度、降低推理内存开销。

因此，“进入 eval 模式”和“不计算梯度”通常都要做，不能把它们当成同一个开关。

## 工程上怎样观察问题

### 训练侧

不要只看一个学习率数字，应同时观察：

- 训练 loss 和验证指标是否持续改善；
- loss 是否震荡、突然上升或出现 NaN / Inf；
- gradient norm 是否异常；
- 当前 Batch、精度、优化器、Weight Decay 和调度配置；
- 在相同 Token 预算下，不同学习率候选的收敛速度。

### 推理侧

可以把一次生成拆成两个性能阶段：

- **Prefill**：处理完整 Prompt，多个 Prompt 位置可以并行计算；
- **Decode**：每轮生成一个新 Token，轮次之间存在串行依赖。

这是本页基于前向传播机制补充的工程划分；来源第 16 章主要使用“训练并行 / 自回归生成”解释运行差异，并未直接使用 Prefill / Decode 术语。

## 别误解

- **“训练能并行，所以没有因果顺序。”** 计算可以并行，但因果 Mask 仍限制每个位置只能读取过去。
- **“调用 `model(input)` 就会让模型学习。”** 没有 loss、反向传播和优化器更新，参数不会改变。
- **“`model.eval()` 会自动关闭梯度。”** 它主要切换模块行为；关闭梯度还需要 `no_grad()` 或 `inference_mode()`。
- **“生成慢是因为一次前向传播不能并行。”** 单次前向内部可以并行，主要串行瓶颈来自一个生成步骤必须等待上一个 Token。
- **“学习率越低越稳定，因此越低越好。”** 过低会让训练在有限预算内几乎没有有效进展。
