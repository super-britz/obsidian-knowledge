# 第 28 章：Prompt 工程——为一次推理设计输入契约

> [!abstract] Prompt 工程不是寻找一句“魔法咒语”，而是在不更新模型参数的前提下，为一次任务组织目标、证据、约束、示例和输出契约。它能改变条件生成的分布，却不能凭空补齐事实、能力、权限或验证；稳定性最终来自评测、程序校验和受控工具链。

> [!info] 阅读粒度
> 本页把基础 Prompt、Few-shot、推理时搜索、上下文工程和 Agent 安全放在同一条输入—执行—验证链中，因此标为“深入机制”；快速阅读时先看输入契约、方案边界表和验证闭环。

## Prompt 在系统中的位置

语言模型在当前上下文条件下生成后续 Token。Prompt 改变的是这次推理的条件，不直接改变模型权重。“训练目标是预测下一个 Token”也不等于已经回答了模型是否“真正理解”这一哲学问题；工程上只需承认输出来自条件概率模型，并用可观察结果验证能力。

```text
任务意图 + 可信指令 + 相关上下文 + 示例 + 输出契约
→ 模型条件生成
→ 解析与程序校验
→ 必要时检索、调用工具、重试或交给人工
→ 可验收结果
```

Prompt 只覆盖其中的输入表达。数据选择、检索结果、对话历史、工具返回和中间状态共同构成上下文；权限、解析器和业务规则则位于模型之外。

| 手段 | 主要改变 | 适合解决 | 不适合代替 |
| --- | --- | --- | --- |
| Prompt / Few-shot | 本次输入条件 | 任务说明、语气、格式、局部示范 | 动态事实、硬权限 |
| RAG / Context Engineering | 模型当次可见的信息 | 私有或变化中的知识、长流程状态 | 事实核验本身 |
| Tool / Workflow | 外部世界的查询与动作 | 计算、搜索、写入、自动化 | 授权和结果验收 |
| Fine-tuning | 模型权重中的稳定行为倾向 | 高频、稳定、可评测的行为适配 | 经常变化的事实 |

## 一个可调试的输入契约

有效 Prompt 通常包含五类信息，但不要求机械套用固定模板：

1. **任务：** 要完成什么，成功标准是什么；避免只给模糊主题。
2. **上下文：** 只提供完成任务所需的事实、定义和当前状态，并注明来源与时间。
3. **边界：** 哪些内容不能假设，哪些工具可用，何时停止或升级给人工。
4. **输出契约：** 字段、类型、枚举、长度和缺失值策略；把“看起来像 JSON”升级为可解析 Schema。
5. **验证：** 结果将怎样检查，失败后允许修复什么，不能把“请确保正确”当验证器。

```text
目标：把工单归入一个现有类别。
证据：工单正文、类别定义、当前产品版本。
约束：不得创建新类别；证据不足返回 unknown。
输出：{"category": enum, "evidence": [string]}。
验收：JSON Schema 通过，evidence 必须能在输入中定位。
```

这类结构比“你是一位有 20 年经验的专家”更可验收。角色描述可以提示表达风格或观察角度，却不会赋予模型真实资历、最新知识或法律责任。

## Zero-shot、One-shot 与 Few-shot

Zero-shot 只给任务说明；One-shot / Few-shot 再给一个或多个输入—输出示例。示例不是训练数据更新，而是 In-Context Learning 的条件：它同时传递标签语义、决策边界、输出格式和回答风格。

选择示例时应覆盖真实的决策边界，而不是机械追求“3～8 个”：

- 格式简单、模型已有稳定能力时，先用 Zero-shot 建立低成本基线；
- 标签含义特殊、输出模式陌生或边界复杂时，再加入最少量高质量示例；
- 同时放入正常、边界、拒绝或 `unknown` 示例，防止模型把所有输入硬塞进已有类别；
- 检查顺序、措辞、类别比例和示例答案是否造成偏差；超长示例还会挤占真正证据的上下文预算。

Few-shot 能否提升必须在目标模型和测试集上实测。原文中的示意准确率和论文中的基准结果都不能成为新任务的预期收益。

## CoT、Self-Consistency 与 ToT 分别增加了什么

### CoT：增加中间计算状态

Chain-of-Thought 用中间步骤把一次大跨度生成拆成较小跨度。原始论文在足够大的模型和若干算术、常识、符号推理基准中观察到收益，但它不是所有任务的默认开关。

生产系统更关心**可检查的中间产物**：子问题、公式、证据引用、测试结果和最终答案。冗长的自然语言推理可能成本更高、仍然合理化错误，也不必作为正确性证明或面向用户完整展示。简单分类、抽取和低延迟任务通常先直接输出，再由确定性规则校验。

### Self-Consistency：增加采样与聚合

Self-Consistency 对同一问题采样多条推理路径，再按最终答案聚合。它适合答案可规范化、候选路径确有多样性的任务；五次调用就是近似五份生成成本，而且同源偏差会让多条路径一起错。

多数票占比只能描述本轮样本的一致程度，不是“答案正确率”或校准置信度。若答案能用计算器、单元测试、约束求解器或数据库直接验证，应优先使用外部验证器。

### ToT：增加显式搜索控制器

Tree-of-Thought 把候选生成、状态评估、分支选择和回溯组成搜索过程。它适合规划、组合搜索等“早期选择会影响后续”的任务，但关键工程问题已从一句 Prompt 变成：状态如何表示、分支如何剪枝、评估器是否可靠、何时终止以及成本上限是多少。

因此 CoT、Self-Consistency、ToT 不是从低到高的固定等级。它们分别用更多中间 Token、更多采样或更多搜索换取潜在质量，应按失败类型选择。

## 从 Prompt Chaining 到上下文工程与 Agent

Prompt Chaining 把复杂任务拆成多个有明确输入输出的阶段。它的价值不只是“多问几次”，而是为每一步建立边界：

```text
检索证据
→ 结构化抽取
→ 规则或模型判断
→ 工具执行
→ 读取真实执行结果
→ 最终汇报
```

步骤一多，问题就不再只是 Prompt 文案，而是 [[wiki/AI 工程化-上下文工程与知识复利|上下文工程]]：哪些信息在何时进入窗口、哪些中间结果需要压缩、哪些来源可信、失败状态怎样传递。与 [[24-25：长上下文|长上下文]] 一样，“装得下”不代表模型能可靠找到和利用关键信息，JIT 加载和高信号摘要通常比把所有历史一次塞入更可控。

Agent 进一步允许模型选择或调用工具。此时自然语言计划只是候选决策，工具 Schema、权限、幂等性、高风险确认和执行后读取才构成真正的动作契约。模型说“已发送”不能证明外部系统确实成功。

## 安全与可靠性边界

外部网页、邮件、文档、用户输入和工具返回都应视为**不可信数据**。它们可能包含看起来像指令的文本；间接 Prompt Injection 正是利用应用把数据与指令放在同一上下文中的混淆。

可采用分层防护，但不要把任何一句防注入 Prompt 当安全边界：

- 明确标记可信指令与不可信内容，按最小必要原则加载外部数据；
- 工具只暴露当前任务需要的最小权限，参数经过类型和业务规则校验；
- 高风险写操作要求用户确认，尽量支持幂等、预览、审计和回滚；
- 输出 Schema 只保证结构可解析，不保证字段真实；引用必须能回指来源，动作必须读取真实回执；
- 测试正常输入之外的越权、注入、缺失证据、冲突指令和异常工具返回。

## 工程决策与验证闭环

```text
定义任务指标和失败样例
→ 建立最简单的 Zero-shot 基线
→ 只针对已观察到的失败增加上下文、示例或分步流程
→ 用程序校验结构、事实或动作结果
→ 比较质量、成本、延迟和安全回归
→ 版本化 Prompt、模型、工具和测试集
```

评测集至少覆盖典型样例、决策边界、长输入、缺失信息和对抗输入。指标应与任务匹配：分类看每类 Precision / Recall，抽取看字段准确率和 Schema 通过率，问答看证据支持率，Agent 看工具调用成功率与未经授权动作，线上还要看 Token、延迟和重试成本。

每次只改一个主要变量，并保留失败样例。若问题是缺少动态事实，接入检索；若是确定性计算，调用工具；若是长期反复出现的稳定行为差距，再考虑 [[26-27：LoRA、QLoRA 与量化|微调]]。不要用不断加长 Prompt 掩盖系统层问题。

## 别误解

- **“Prompt 越长、技巧越高级，效果越好。”** 无关信息会稀释证据，搜索和采样还会增加成本；先从最小基线和真实失败开始。
- **“写了专家角色，模型就具备专家资格。”** 角色只是条件提示，不能补齐知识、执照、责任或实时事实。
- **“展示完整 CoT 就证明答案可靠。”** 中间文本也可能出错或事后合理化；应验证可检查的步骤和最终结果。
- **“多数答案一致就是高置信度。”** 多个样本可能共享同一偏差；一致率不是校准概率。
- **“输出了合法 JSON，内容就可信。”** Schema 约束语法和类型，不验证事实、权限与业务语义。
- **“Prompt 可以阻止所有注入和越权。”** 安全边界必须落在上下文隔离、权限、参数验证、确认和审计上。

## 复习

1. Prompt 工程改变的是模型的什么，没有改变什么？
2. Few-shot 示例同时传递哪些隐含信息，为什么示例越多不一定越好？
3. CoT、Self-Consistency 和 ToT 分别增加了哪一种推理时资源？
4. 为什么 JSON Schema 通过和多数票一致都不能证明答案正确？
5. 一个能调用工具的 Prompt 怎样升级为可审计、安全的执行契约？
