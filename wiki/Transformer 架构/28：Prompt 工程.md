# Prompt 工程：把一次任务交代清楚

> [!abstract] Prompt 工程不是寻找魔法句式，而是为当前请求整理任务、可信资料、限制和输出要求。它只改变本次推理看到的条件，不会修改模型参数，也不能代替事实、权限和程序校验。

## Prompt 在系统中的位置

```text
用户输入
→ 应用补充规则、资料和工具结果
→ 组成模型本次看到的上下文
→ 模型生成候选结果
→ 应用验证后展示或执行
```

Prompt 决定模型“这一次依据什么、要做什么”。模型仍然只是根据这些 Token 继续预测后面的 Token。

## 一个清楚的 Prompt 包含什么

1. **任务：** 要完成什么，成功标准是什么。
2. **资料：** 可以依据哪些事实，来源是什么。
3. **边界：** 哪些内容不能猜，缺少信息时怎么办。
4. **输出：** 需要哪些字段、格式和长度。
5. **验收：** 程序之后怎样判断结果能不能使用。

不需要把每次调用都写得很长。信息越相关、边界越明确，通常越容易调试。

## Prompt 解决不了什么

- **缺最新事实：** 使用 RAG、数据库或搜索工具。
- **需要精确计算：** 使用计算器、代码或业务服务。
- **需要执行动作：** 由服务端校验参数和权限，再调用工具。
- **需要长期改变行为：** 先评测，再考虑 [[26：LoRA 与 QLoRA|微调]]。

在 Prompt 中反复写“请务必准确”，不能补充缺失证据，也不能建立真正的安全边界。

## 示例有什么作用

当标签、格式或判断边界很特殊时，可以给少量输入—输出示例，让模型看到目标模式。但示例也会占用上下文，并可能把错误或偏差带进结果。

先从没有示例的简单版本开始，只有评测发现具体问题时再增加示例。

## 安全和验证必须在模型外

网页、文档、邮件和用户输入都可能包含错误或恶意内容。应用需要：

- 只开放当前任务真正需要的工具；
- 校验字段类型、范围和业务规则；
- 对高风险操作要求确认；
- 根据真实来源验证引用；
- 根据工具回执判断动作是否成功。

合法 JSON 只表示结构正确，不表示内容真实、合理或已经授权。

## 怎样持续改进

```text
收集真实失败样例
→ 建立简单基线
→ 每次只修一种问题
→ 用程序和测试集验证
→ 比较质量、延迟和成本
→ 记录 Prompt 与模型版本
```

没有真实失败样例时，继续堆叠技巧通常只会让 Prompt 更长、更难维护。

## 别误解

- **“Prompt 越长越好。”** 无关内容会消耗预算并干扰重要信息。
- **“模型返回合法 JSON 就可以直接执行。”** 还需要语义、权限和业务校验。
- **“模型写出了推理步骤就证明答案正确。”** 仍要验证证据和结果。
- **“Prompt 能完全防住提示注入。”** 真正的权限边界必须由应用控制。

## 一句话复习

> Prompt 负责把本次任务交代清楚；可信事实、工具权限、结果验证和长期行为改变分别属于其他系统层。
