# 第 24 章：长上下文的信息访问

> [!abstract] 处理更长历史的核心取舍是：保留多少原始 Token、允许当前 Token 直接访问哪些位置、要为此付出多少计算和内存。越强的随机访问通常越贵，越激进的压缩越可能丢失细节。

> [!info] 放回完整生成链
> 这个问题发生在 Attention 读取历史时。前端感知到的是长 Prompt 延迟、上下文费用和远处证据召回率；普通应用无需实现算法，但必须管理输入。

## 四种历史访问方式

| 方式 | 怎样处理历史 | 优势 | 代价 |
| --- | --- | --- | --- |
| Full Attention | 保留窗口内全部 K/V，可直接匹配任意位置 | 精确访问能力强 | 长序列计算和 Cache 昂贵 |
| Sliding Window | 只直接读取最近窗口 | 成本随窗口而非全部历史增长 | 窗外细节不能直接访问 |
| Sparse Attention | 只保留局部、全局等部分连接 | 用连接规则减少位置配对 | 效果依赖连接设计和专用内核 |
| 压缩记忆 | 把旧历史聚合到固定状态 | 状态不会随历史一直增长 | 历史不再逐 Token 保留 |

Sparse Mask 只有在底层真正跳过未连接位置时才省计算；先完成完整矩阵再填 `-∞`，结果正确但没有省掉前面的稠密计算。

## 为什么压缩记忆不是无限记忆

可以把它理解为不断更新摘要：

```text
旧状态 + 当前片段 → 新状态
```

状态大小可以固定，但固定空间必须承载越来越多历史。它适合连续趋势、局部依赖或可压缩信息，不等于能无损找回任意早期 Token。

[[32：状态空间模型与混合架构|SSM / Mamba]] 也使用类似取舍：稳定的递归状态换取更低的长序列成本，但精确随机访问通常不如保留逐 Token K/V 的 Attention。

## 怎样选择

- **需要引用合同中的任意原句：** 优先检索或保留可直接访问的原文，不依赖固定状态记忆。
- **处理持续到来的日志或传感器流：** 局部窗口或递归状态可能更合适。
- **文档有少量关键锚点：** 可考虑局部窗口配合全局位置。
- **普通聊天产品：** 先做好裁剪、摘要和按需检索，再考虑模型架构。

## 怎样验证

不要只做“针在干草堆”测试。至少改变：

- 输入总长度；
- 关键信息位于开头、中间还是结尾；
- 干扰项数量；
- 任务是精确引用、组合多条事实还是全文摘要。

同时记录回答质量、TTFT、TPOT、Token 成本和内存。能找到一个随机字符串，不代表能理解和组合整份长文档。

## 别误解

- **“Sparse Attention 一定更快。”** 需要真实稀疏内核和合适的连接结构。
- **“固定状态保存了全部历史。”** 它保存的是压缩结果，不是逐 Token 档案。
- **“窗口外信息一定彻底消失。”** 多层传播或摘要可能保留部分影响，但不能当作精确直接访问。
