# 第 26～27 章：微调与量化总览

> [!abstract] LoRA / QLoRA 解决“怎样用更少训练资源改变模型行为”，量化解决“怎样用更少存储和内存运行模型”。它们可以组合，但优化对象完全不同；GGUF 又只是保存和分发模型的一种文件格式。

## 先按问题选择

```text
回答行为、格式或稳定任务能力需要改变？
→ [[26：LoRA 与 QLoRA|LoRA / QLoRA]]

模型权重太大，本地或服务端运行成本过高？
→ [[27：模型量化与 GGUF|模型量化]]
```

| 概念 | 所处阶段 | 主要改变 | 不会自动解决 |
| --- | --- | --- | --- |
| LoRA | 微调训练 | 只训练较小 Adapter | 动态事实和权限 |
| QLoRA | 微调训练 | 低比特冻结基座 + LoRA | 全部训练内存 |
| GPTQ / AWQ 等 | 部署前 | 压缩推理权重 | 模型行为缺陷 |
| GGUF | 打包分发 | 保存张量和元数据 | 量化算法与质量保证 |

## 前端开发者何时需要关心

- 调用云端模型 API：通常只比较能力、延迟、价格和数据边界。
- 浏览器或桌面端本地模型：需要理解量化格式、运行时兼容和内存预算。
- 自建垂直模型：需要判断 Prompt / RAG 是否已足够，再决定是否微调。
- 多租户定制：独立 Adapter 可能比每个客户复制完整模型更容易管理。

## 决策顺序

1. 用任务评测确认问题是缺事实、缺工具，还是稳定行为不符合要求。
2. 缺事实用 RAG，确定性动作和计算用 Tool。
3. 稳定行为差距再尝试 LoRA，并保留基座对照。
4. 部署资源超预算时逐级量化，在目标设备复测质量和速度。

微调和量化都会产生新的 Artifact。必须记录基座、Tokenizer、Adapter、量化配置和运行时版本，不能只保留一个文件名。

## 别误解

- **“LoRA、4-bit 和 GGUF 是同级方案。”** 它们分别属于训练参数、数值表示和文件格式。
- **“微调可以保存不断变化的事实。”** 动态事实仍应放在可更新、可追溯的外部系统。
- **“位数更低一定更快。”** 是否加速取决于硬件内核、shape 和反量化开销。
