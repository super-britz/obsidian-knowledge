# 第 26～27 章：LoRA、QLoRA 与量化——训练和部署分别省什么

> [!abstract] LoRA 通过低秩增量减少需要训练和保存的参数；QLoRA 再把冻结基座以 4-bit 保存，降低训练时的基座权重占用；GPTQ、AWQ 等后训练量化主要压缩推理权重；GGUF 则是承载模型张量与元数据的文件格式。它们可以组合，但优化对象、产物和质量风险不同。

> [!info] 阅读粒度
> 本页把“怎样低成本改变模型行为”和“怎样低成本保存、运行模型”放在同一张资源账本中，因此标为“深入机制”；快速阅读时先看资源表、LoRA / QLoRA 流程、量化层级和工程决策。

## 先把四个概念放回正确层级

| 方法 | 所处阶段 | 主要改变 | 主要产物 |
| --- | --- | --- | --- |
| LoRA | 微调训练 | 只训练低秩 Adapter | Adapter；也可验证后合并 |
| QLoRA | 微调训练 | 4-bit 冻结基座 + 可训练 LoRA | Adapter + 对基座和量化配置的依赖 |
| GPTQ / AWQ | 推理部署前 | 用校准数据压缩权重 | 特定量化方案的权重与配置 |
| GGUF | 打包与分发 | 保存模型张量、类型和元数据 | 可供 GGML 生态加载的模型文件 |

`SFT` 是训练目标，`LoRA` 是参数化方式；`4-bit` 是数值表示，`GPTQ / AWQ` 是生成低比特权重的方法；`GGUF` 是容器。它们不能只放在一列比较“谁更好”。

## 资源账本：到底省掉哪一块

| 方案 | 基座权重 | 基座梯度 / 优化器状态 | Adapter 状态 | 激活 |
| --- | --- | --- | --- | --- |
| 全参数微调 | 较高精度、可训练 | 全部参数都需要 | 无 | 仍需保存或重算 |
| LoRA | 较高精度、冻结 | 不需要基座梯度和优化器状态 | 需要 | 仍然存在，受 Batch、长度和检查点策略影响 |
| QLoRA | 通常 4-bit、冻结 | 不需要基座梯度和优化器状态 | 以较高精度训练 | 仍然存在，长上下文时可能成为主要开销 |
| 量化推理 | 低比特权重 | 无训练状态 | 可选 | Prefill / Decode 仍有运行时状态 |

因此“只训练 0.x% 参数”不能直接换算成“训练显存只剩 0.x%”。LoRA 主要省基座梯度和优化器状态；QLoRA 再省基座权重存储，但激活、临时工作区、上下文长度和运行时碎片不会消失。

## LoRA：把权重变化限制在低秩子空间

对冻结权重 `W₀`，LoRA 不直接更新它，而是学习：

```text
W = W₀ + s × B @ A
A: [r, in]    B: [out, r]    r << min(in, out)
```

前向计算等价为 `W₀x + s·B(Ax)`。训练只为 A、B 保存梯度和优化器状态；常见初始化让其中一个因子为零，使训练开始时增量为零，模型行为先与基座一致。

`rank` 决定增量的容量，但不存在跨任务通用的最佳值。目标模块同样重要：只适配 Attention 投影，和同时适配 FFN，会得到不同参数量与能力。应在固定数据和 Token 预算下比较，而不是把社区默认值当成结论。

Adapter 不是完整模型。加载时必须匹配基座版本、Tokenizer、目标模块和配置。LoRA 可以合并进基座以消除额外分支，也可以保持独立以便切换多个 Adapter；两种部署方式对版本管理和内存复用的取舍不同。

## QLoRA：量化的是冻结基座，训练的是 Adapter

```text
4-bit 冻结基座权重
→ 前向时按计算 dtype 反量化并参与矩阵计算
→ 梯度穿过基座计算图
→ 只更新 LoRA Adapter
```

QLoRA 论文使用 NF4 表示近似正态分布的权重，用 Double Quantization 继续压缩量化常数，并用 Paged Optimizer 管理显存峰值。论文在其设置中报告了显著的训练显存下降；这不是任意模型、长度、Batch 和框架上的固定显存数字或质量保证。

QLoRA 不等于“4-bit 全参数训练”，也不表示激活和 LoRA 优化器状态是 4-bit。若最终把 Adapter 合并、再导出为另一种量化格式，实际上经历了新的数值转换，必须重新做质量与加载测试。

## 量化：位数只是配置的一部分

理想化的纯权重下界是：

```text
weight_bytes ≈ parameter_count × bits_per_weight / 8
```

实际文件和显存还包括 Scale、Zero Point、分组元数据、未量化张量、对齐和运行时工作区。因此“7B × 4-bit = 3.5 GB”只是裸权重下界。

量化至少要同时说明：

- **对象：** Weight-Only、Weight + Activation，还是 KV Cache；
- **位数和数据类型：** INT8、INT4、NF4 等；
- **粒度：** Per-Tensor、Per-Channel 或 Per-Group；
- **阶段：** 训练感知量化、后训练量化，还是量化基座上的 Adapter 训练；
- **后端：** 硬件是否有匹配内核，是否需要运行时反量化。

低比特通常减少存储和内存带宽，但不保证更快。若硬件缺少高效内核、Batch / 形状不合适或反量化开销占主导，端到端延迟可能没有改善。

### GPTQ、AWQ 与 GGUF 的边界

- **GPTQ：** 一次性 Weight-Only 后训练量化，利用近似二阶信息逐步补偿量化误差；结果依赖校准样本和实现。
- **AWQ：** 用激活统计识别对输出更敏感的权重通道，并通过缩放保护重要权重；同样依赖校准分布和目标后端。
- **GGUF：** 保存张量类型、模型结构和 Tokenizer 等元数据的格式，可以包含量化或非量化张量。文件名中的 `Q4` 描述编码，不等于 GGUF 本身是一种量化算法，也不保证任意运行时都兼容。

GPTQ 与 AWQ 没有脱离模型、校准集、任务和内核的固定胜负。选择时应以实际 Artifact 能否被目标服务加载，以及质量和性能对照为准。

## 怎样决定是否微调、怎样决定是否量化

```text
行为、格式、稳定任务能力需要改变？
├─ 否：优先 Prompt / RAG / Tool / 工作流
└─ 是：先建立基座评估 → LoRA 或全参数微调对照

部署资源超预算？
├─ 否：保留较高精度基线
└─ 是：逐级尝试量化 → 在目标后端复测质量和性能
```

微调适合改变稳定行为，不适合保存经常变化的事实；事实应由检索、数据库或工具提供。量化解决资源问题，不会修复模型知识、Prompt、数据或训练目标。

## 最值得做的验证

1. **训练链路冒烟测试：** 小数据、少步骤跑通加载、前向、反向、保存、重载；确认只有预期 Adapter 参数可训练。
2. **行为与回归评估：** 在独立测试集对比基座、LoRA / QLoRA，检查目标任务、通用能力、拒答、安全和过拟合。
3. **Artifact 契约测试：** 记录基座、Tokenizer、Adapter、量化方法、位数、Group Size、计算 dtype 与运行时版本；验证冷启动和保存—加载一致性。
4. **量化质量对照：** 对同一 Prompt 集比较 logits / perplexity、任务指标和失败样例；校准数据必须代表真实输入分布。
5. **端到端资源测量：** 分开记录训练峰值显存、训练吞吐，以及部署时 TTFT、TPOT、吞吐、权重与 KV Cache 占用；不拿文件大小代替运行时性能。

## 别误解

- **“LoRA 参数少，所以激活显存也按同一比例下降。”** 激活由模型结构、Batch 和序列长度决定，仍可能主导训练显存。
- **“QLoRA 就是让整个模型用 INT4 训练。”** 4-bit 基座被冻结并在计算时反量化，较高精度 Adapter 才是更新对象。
- **“4-bit 模型一定比 FP16 快四倍。”** 存储比例、计算吞吐与端到端速度不是同一指标。
- **“GPTQ、AWQ、GGUF 是三种同级量化算法。”** 前两者是量化方法，GGUF 是可承载不同张量编码的格式。
- **“微调后就掌握了可靠的新事实。”** 微调改变统计行为，不能替代可更新、可追溯的事实系统。
