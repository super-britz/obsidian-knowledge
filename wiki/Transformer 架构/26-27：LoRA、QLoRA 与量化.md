# LoRA、QLoRA 与量化：改变行为还是降低成本

> [!abstract] 只有需要改变模型长期、重复的行为时，才考虑 LoRA；确定需要 LoRA、但较高精度基座模型占用过大时，再选择 QLoRA。部署量化解决的是运行成本，不等于 QLoRA。

## 第一性原理：应该改变哪一层

模型输出同时受三类因素影响：

```text
模型参数中的行为倾向
+ 当前 Prompt / 检索上下文
+ Tool 返回的外部结果
→ 最终输出
```

因此先按问题来源分流：

| 问题 | 应改变的层 | 方法 |
|---|---|---|
| 缺少文档和最新事实 | 上下文 | RAG |
| 缺少实时状态、精确计算或业务动作 | 外部系统 | Tool / API |
| 当前任务的格式和边界不清楚 | 当前指令 | Prompt、Schema、校验 |
| 长期、重复地不符合某种任务行为 | 模型参数 | LoRA / QLoRA |
| 模型部署时装不下或成本过高 | 权重表示 | 推理量化 |

微调不能代替知识库、数据库和业务接口。

## 什么时候值得用 LoRA

LoRA 适合同时满足以下条件的任务：

1. **目标稳定且高频**：固定格式、语气、分类、抽取、代码风格、拒答或工具选择模式。
2. **Prompt 仍不稳定**：经过提示词、结构化输出和工作流优化后，行为偏差仍反复出现。
3. **基座已有基础能力**：主要是在校正行为，而不是让模型从零获得一种广泛的新能力。
4. **有数据和评测**：能够提供高质量输入—输出样本，并用测试集判断改善与退化。

不满足这些条件时，训练可能只是把问题隐藏进参数，并增加数据、评测和版本维护成本。

## LoRA 为什么能降低训练成本

完整微调会修改大量基座参数。LoRA 冻结基座权重，只学习一个较小的低秩增量：

```text
冻结的基座权重 W
+ 可训练的低秩增量 BA
→ 调整后的任务行为
```

它隐含的假设是：具体任务需要的行为变化，通常只占模型全部能力空间的一小部分。

Adapter 记录的是行为修正，不能脱离对应的基座模型独立运行。LoRA 参数虽然少，训练时仍要经过基座模型，因此激活值、中间计算和上下文长度带来的开销仍然存在。

## 什么时候从 LoRA 换成 QLoRA

普通 LoRA 仍需在训练设备中加载较高精度的冻结基座模型。QLoRA 进一步用低比特保存该基座，只训练 LoRA Adapter：

```text
低比特、冻结的基座模型
+ 较高精度、可训练的 Adapter
→ 更低的训练显存门槛
```

选择原则：

- **基座能装下，并且还留有 Batch Size、上下文和激活值空间：优先 LoRA。**
- **基座装不下，或加载后几乎没有训练余量：选择 QLoRA。**

QLoRA 主要减少基座权重占用，不会消除激活值、上下文和临时计算开销；它也会增加量化算子兼容性、训练速度和质量评测方面的复杂度。QLoRA 不是低比特全参数训练，真正更新的仍然是 Adapter。

## 部署量化解决什么

如果模型行为已经满足要求，只是推理设备装不下，那么需要的是部署量化，而不是 QLoRA。

量化用更少位数近似模型权重，从而降低文件大小、运行内存和带宽需求。位数越低通常越省资源，但误差风险可能更高；真实速度取决于硬件和推理引擎，4-bit 并不代表必然快四倍。

GPTQ、AWQ 等属于量化方法；GGUF 是常用于保存模型权重、数字类型、结构和 Tokenizer 元数据的文件格式，不是量化算法。

## 决策顺序

```text
缺事实？               → RAG
需要实时数据或动作？   → Tool / API
Prompt 能稳定解决？     → 不微调
存在稳定、可评测的行为偏差？
  ├─ 否                 → 继续分析问题和数据
  └─ 是
      ├─ 基座和训练状态能装下 → LoRA
      └─ 基座占用成为瓶颈     → QLoRA

只在部署时装不下？     → 推理量化
```

无论选择哪种方案，都应保存基座模型、Tokenizer、训练配置、Adapter 和评测结果，并与未微调基线比较。

## 一句话复习

> LoRA 回答“是否要低成本修改模型行为”，QLoRA 回答“确定要用 LoRA 后，怎样让冻结基座在有限显存中装得下”，部署量化回答“模型怎样更便宜地运行”。
