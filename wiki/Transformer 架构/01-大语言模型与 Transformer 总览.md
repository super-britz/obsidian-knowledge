# 大语言模型与 Transformer：它怎样根据上下文接着说

> [!abstract] 可以先把 LLM 想成一个不断“接话”的程序：看已有内容，预测下一个 Token，把它接到后面，再重复。Transformer 是它每次决定“现在该重点看什么、下一步接什么”的核心结构。

## 先看流程

```text
系统规则、历史消息、用户问题
→ Token（文字切成模型单位）
→ 向量 + 位置信息
→ 多层 Transformer（找重点、加工信息）
→ 候选 Token 的分数
→ 选一个 Token 接到后面
→ 重复，形成回答
```

模型不是先写好整段答案再显示出来；它通常是一步一步往后生成。

## 关键理解

- **Token 是模型读文字的单位。** 文字先变成编号，再变成数字向量，模型才能计算。
- **Transformer 主要做两件事。** Attention 从上下文找当前相关的信息；前馈网络继续加工这些信息。两者重复多层。
- **模型输出的是“下一步的偏好”。** 它先给候选 Token 打分，再选择或采样其中一个；高分表示更符合当前上下文，不等于现实中一定正确。
- **上下文和输出都不是免费的。** 内容越多、生成越长，通常越慢、越贵，也更容易淹没重要信息。

## 做项目时记住

1. **给模型少而准的上下文。** 当前任务、关键规则、可靠资料优先；不要无差别堆入所有历史和日志。
2. **把事实和动作交给外部系统。** 最新资料用检索、数据库或 API；写文件、付款、删数据等动作由代码校验并按风险要求确认。
3. **把模型当成一个组件。** 它负责理解、归纳、生成候选；应用负责权限、工具执行、验证、日志和用户体验。

## 别误解

- **“模型记得所有事实。”** 参数保存的是训练得到的模式，不是可随时查询、自动更新且保证正确的数据库。
- **“模型说完成了，任务就完成了。”** 真正完成要以工具返回、文件变化或业务系统状态为准。
- **“参数 + 推理代码”就是完整产品。** 这是帮助理解模型本质的简化说法；真实应用还需要 Tokenizer、服务、权限、观测和安全控制。

## 复习

2. 为什么长历史、长文档和工具日志会影响速度、成本和回答质量？
3. Agent 要修改知识库文件时，哪些事必须由模型之外的系统控制？
