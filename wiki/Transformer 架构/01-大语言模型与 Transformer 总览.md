# 大语言模型与 Transformer：它怎样根据上下文接着说

> [!abstract] 先用一句话说清楚
> 可以把大语言模型想成一个不断“接话”的程序：它先看你已经写的内容，猜下一个最可能出现的小片段，再把这个片段接到后面，重复很多次，最后看起来像写出了一整段回答。Transformer 是它每次“看上下文、决定下一步”的核心计算结构。

## 它要解决什么问题？

人能直接理解“你好”“帮我总结这篇文章”这样的文字，但模型只能计算数字。它需要同时解决两件事：

1. **把文字变成能计算的数字。**
2. **根据前面已经出现的内容，决定后面最该接什么。**

以你在聊天框输入问题为例，整条链路可以先记成：

```text
你输入一句话
  ↓
应用把系统规则、历史消息和你的问题放在一起
  ↓
模型把文字切成小片段并转成数字
  ↓
Transformer 从这些数字中找出“现在最该关注什么”
  ↓
模型挑出下一个小片段
  ↓
把它接到已有内容后面，继续重复
  ↓
你看到一段流式出现的回答
```

这里的重点是：**模型不是先在脑中写好完整答案，再一次性输出。它是在不断地往后接。**

## 它怎么工作？

### 先看最短流程

```text
文字
→ 切成 Token
→ 转成数字向量
→ 看上下文中的关系
→ 给每个“下一个 Token 候选项”打分
→ 选一个接到后面
→ 重复
```

先把这条流程记住。后面的章节只是逐步解释其中每一个箭头具体怎样实现。

### 一步一步看

1. **切分文字（Tokenization）**

   模型不会把整句话当成一个单位。它会把文字切成 Token；一个 Token 可能是一个字、一部分词、标点或代码片段。切分结果不是给人看的语义，而是给程序处理的编号。

2. **把编号换成一组数字（Embedding）**

   每个 Token ID 会对应一组数字。可以暂时把它理解为：模型用数字记录“这个 Token 大致有什么特点”。

3. **告诉模型先后顺序（位置信息）**

   同样的词放在句首和句尾，含义可能不同；所以模型还要知道每个 Token 在序列中的位置。

4. **从上下文中挑重点（Transformer Block）**

   每一层 Transformer 都会做两件主要事情：

   - **Attention**：当前这个位置应该重点看前面的哪些内容？
   - **前馈网络（FFN）**：把已经汇总的信息继续加工。

   这两个步骤会重复多层。你现在不需要记住矩阵公式；先把 Attention 理解成“根据当前需要，从上下文里找重点并汇总”。

5. **决定下一个 Token**

   模型最后会给词表中的大量候选 Token 分别打分，再把分数变成概率。它可以选概率最高的一个，也可以按概率随机选一个，因此同一个问题有时会得到不同措辞。

6. **把新 Token 放回上下文，继续生成**

   新生成的 Token 会成为下一轮的已知内容。于是模型再看“原始输入 + 已经生成的部分”，继续猜下一个 Token。这种一步一步往后生成的方式叫**自回归生成**。

## 它有什么限制？

- **它更像“很擅长接话”，不是事实数据库。**
  它生成的是在当前上下文下看起来合理的内容；合理、流畅和事实正确不是一回事。

- **它不能无限记住内容。**
  每个模型一次能处理的 Token 有上限。历史对话、长文档、工具日志放得越多，成本和等待时间通常越高，也越容易让真正重要的信息被埋住。

- **输出越长，等待通常越久。**
  因为它需要一次次生成下一个 Token，而不是一次算完全文。

- **“参数 + 推理代码”只是帮助理解的简化说法。**
  模型参数保存了从训练数据中学到的模式，推理代码让这些参数参与计算；真实应用还需要 Tokenizer、配置、运行环境、服务、权限和日志系统。

## 你会在产品中看到什么？

- 聊天回答像打字一样逐段出现，因为模型在持续生成新 Token；页面一次显示几个字，并不代表模型按“字”生成。
- 同一个问题有时措辞不同，因为系统可能不是每次都选概率最高的 Token，而是会按概率采样。
- 聊天越久、资料越多、工具返回越长，回答可能越慢、越贵，或者开始遗漏先前要求。
- 即使模型语气非常肯定，也仍可能说错，因为“概率高”不等于“已经查证”。

## 做项目时该怎么办？

### 适合交给模型的事

- 概括、改写、分类、提取要点、解释文本。
- 在已提供的资料中归纳和比较。
- 为用户生成候选答案、草稿、查询条件或工具参数。

### 不能只交给模型的事

- 需要实时且准确事实的问题：应查数据库、搜索资料或调用业务 API。
- 精确计算、权限判断、金额处理、删除文件等确定性或高风险动作：应由代码、规则和人工确认负责。
- 判断“任务是否真的完成”：不能只看模型说“已完成”，要检查工具返回和实际结果。

### 写 LLM / Agent 时先记住三件事

1. **少而准地放上下文。** 只给当前任务真正需要的规则、资料和历史，不要把所有内容一股脑塞进去。
2. **把事实和动作交给外部工具。** 用检索、数据库和 API 提供事实；用服务端校验执行动作。
3. **给模型设置边界。** 限制输入长度、输出长度、工具次数、等待时间和权限；高风险写操作要求用户确认。

## 容易误解的地方

- **误解：模型先想好整段答案，再显示出来。**
  - 更接近实际的理解：它通常是预测一个 Token，再根据更新后的上下文预测下一个。

- **误解：模型“记得”训练资料中的每一条事实。**
  - 更接近实际的理解：参数保存的是大量模式，不是可以逐条查询、自动更新且保证正确的数据库记录。

- **误解：只要换一个更大的模型，应用就会可靠。**
  - 更接近实际的理解：模型能力只是系统的一部分；上下文组织、资料来源、工具校验、权限和评测同样决定结果。

## 来源、我的理解与待继续学习

### 来源中明确讲到的内容

- 第 1 章将 Transformer 放在从序列模型到 Attention 架构的演进背景中，说明它为何成为后续大语言模型的重要基础。
- 第 2 章将 GPT 的生成解释为：根据已有内容预测下一个 Token，并把新 Token 追加后继续生成。
- 第 3 章给出整体流程：Tokenization、Embedding、位置信息、重复的 Transformer Block、词表概率分布和下一个 Token 预测。

### 这里做出的整理和工程推论

- 因为模型是按上下文逐步生成，所以长会话、多步 Agent 和大段工具结果都需要控制长度、成本和状态。
- 因为模型的回答不是自动验证过的事实，所以动态事实、外部操作和高风险动作需要检索、工具、代码校验和人工确认。

### 后面会继续补齐的问题

## 最后只记住这六句话

1. **LLM 的基本动作是接话。** 它根据已有内容预测下一个 Token，再重复这个动作，直到形成一段回答。
2. **模型不能直接计算文字。** 文字要先切成 Token，再变成数字，Transformer 才能处理。
3. **Transformer 的工作是从上下文找重点。** Attention 决定当前该重点看哪里，FFN 继续加工已经汇总的信息。
4. **它生成的是“看起来最合理的后续内容”。** 这不等于它已经查证事实，也不等于它真的执行了某个操作。
5. **上下文不是越多越好。** 内容越长，通常越慢、越贵，也越容易淹没真正重要的信息。
6. **模型只是应用的一部分。** 事实查询、权限判断、写入操作和高风险动作要交给检索、工具、代码校验与用户确认。

> [!tip] 用前端的视角记忆
> 可以先把 LLM 想成一个能力极强、会参考整段上下文的“智能补全引擎”；而 LLM 应用或 Agent 则是你围绕它搭建的完整产品：负责给它合适资料、限制权限、展示过程并验证结果。
