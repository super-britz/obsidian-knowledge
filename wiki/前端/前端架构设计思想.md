# 前端架构设计思想

[[wiki/前端/00-索引|← 前端索引]]

**前端架构是对职责、依赖、状态归属和运行流程的关键约束，目的是让一次修改只需理解有限的代码。** 可以用“状态、异步、边界、变化”检查复杂度，再从具体症状选择最小机制。

这四类是本文的理解模型，来自独立工程推导，不是唯一的行业分类，也不是适用于所有项目的定律。

## 按症状找到起点

| 具体症状 | 优先检查与最小机制 | 怎样验证改善 |
| --- | --- | --- |
| 同一数据在不同页面不一致 | 找到权威所有者；删除冗余副本或改为派生值 | 修改一次后，各处显示一致 |
| 加载、成功、失败同时为真 | 用互斥状态或联合类型表达合法阶段 | 非法组合不能出现，转换有测试 |
| 搜索结果被旧请求覆盖 | 明确 Latest wins；取消旧任务或拒绝旧结果 | 人为让旧请求最后返回 |
| 重复点击产生两个订单 | 提交中约束操作，并与服务端约定幂等 | 重复请求只产生一个业务结果 |
| 业务规则离开页面就不能测试 | 分开业务计算与请求、存储等副作用 | 不启动页面也能测试业务规则 |
| 外部数据异常直接破坏界面 | 在入口校验；需要时用 Adapter 转换 | 异常响应有明确处理方式 |
| 接口字段或一个需求变化，牵动很多无关文件 | 检查模型泄漏与模块边界；隔离实际变化点 | 修改范围缩小，依赖方向清楚 |
| 请求失败后不知道是否已成功 | 区分失败与结果未知，设计查询与恢复 | 超时后能确认最终结果 |
| 线上问题只能靠猜 | 补足关键事件、请求标识和错误记录 | 能还原一次操作的因果链 |

先判断造成当前损失的主要根因，不必同时采用表中所有机制。一个简单请求用联合类型就能表达时，无需为此引入完整状态机框架。

## 从前端的基本任务推导

```text
用户事件 + 外部数据 + 当前状态
                ↓
             状态转换
                ↓
       界面 + 请求 + 存储 + 导航
```

如果状态很少、输入确定、没有异步和需求变化，这个过程很简单。现实中，状态会组合，事件会乱序，外部会失败，需求会变化；开发者难以同时追踪所有关系，因此需要约束。

架构的目标是**删除人为复杂度，准确表达必要复杂度，限制问题的传播范围**。支付阶段和网络失败无法靠分目录消除；重复保存状态、循环依赖、万能组件和不必要的分层，则可能是实现额外制造的负担。代码量、用户量和团队规模可视为放大器，但这个归类只是本文的分析视角。

## 四类复杂度与控制机制

### 状态：哪些情况合法，谁有权修改

三个独立布尔值有 `2 × 2 × 2 = 8` 种组合。如果它们表示“请求中、成功、失败”，其中一些组合并不合法。关键不是变量少，而是状态能否准确表达业务。

- **单一事实来源**：同一事实有明确的权威所有者，避免多个可写副本互相同步。
- **派生状态与状态就近**：能计算的值不重复保存；状态放在覆盖使用者的最小范围，不默认放进全局 Store。
- **显式转换**：用“事件 → 决策 → 状态转换 → 界面”追踪修改；必要时用联合类型或状态机限制合法阶段。

例如输入值可由组件拥有，筛选条件可由 URL 表达，登录状态属于应用会话；商品数据的权威来源在服务端，请求缓存只是本地副本。具体归属取决于使用范围和业务语义，不是固定目录规则。

### 异步：顺序改变时，应该接受哪个结果

```text
发出旧请求 A → 发出新请求 B → B 返回 → A 返回
```

如果两个响应都能直接覆盖结果，用户最后看到的可能是旧数据。搜索场景通常需要明确“最新请求的结果才有效”，再选择取消旧任务或检查结果是否仍属于当前请求。验证时要故意让 A 晚于 B 返回，不能只测试正常网络顺序。

其他场景可能需要首次有效、排队、并行或去重，不能一律套 Latest wins。业务计算与请求、存储、导航、计时器分开后，也更容易单独验证规则与时间行为。

**超时、取消、重试处理的是不同问题**：不能无限等待、旧任务失去意义、暂时失败后再次尝试。请求超时也可能发生在服务端已经成功之后，因此超时不自动等于业务失败；是否重试，要结合重复操作是否安全及结果如何确认来决定。

### 边界：外部假设失效时，怎样隔离和恢复

用户输入、URL、接口、本地缓存、第三方消息都可能不符合预期。边界另一侧不受当前模块控制，需要明确输入输出、业务语义、权限、错误和兼容约定，再按实际风险校验。

服务端事实经过网络、缓存才成为界面显示；副本可能暂时过期。发生冲突时，应知道哪个来源具有最终权威，而不是让多个副本互相覆盖。

Adapter 可以在边界转换外部模型，减少外部字段或协议对内部的影响。它有维护成本，只有实际隔离了耦合、歧义或重复转换时才值得引入。失败处理也应说明：显示什么、是否降级、是否恢复，以及用哪些记录定位原因。

### 变化：一个修改会传播多远

如果后端字段调整会一路牵动请求层、状态和多个组件，说明外部模型深入了内部；如果改订单规则要修改许多无关模块，则需要重新检查职责与依赖。

可以按变化原因划分模块：一起变化的代码放在一起，原因不同的代码通过少量明确接口连接。接口暴露业务能力，隐藏内部结构，让实现有修改空间。稳定业务规则需要隔离易变技术时，再考虑由业务定义所需能力、由技术实现满足它的依赖倒置。

这些机制服务于“局部可理解、局部可修改”，不要求所有项目都采用相同层数。用类型、检查和测试约束关键规则，并随着真实问题演进，比预先搭建全部架构更容易衡量收益。

## 用提交订单串起四类问题

一个订单操作会同时遇到状态、时间、边界与变化，因此通常需要几种机制配合；每种机制各自回答一个问题。

| 要回答的问题 | 设计与验证重点 |
| --- | --- |
| 当前处于什么阶段？ | 表达编辑中、提交中、成功、失败、结果未知；验证合法转换 |
| 谁触发了什么动作？ | 事件显式触发业务决策，再执行请求与状态更新，避免隐藏修改 |
| 连续点击或重试会怎样？ | 客户端限制重复提交，服务端幂等保证同一业务操作不重复产生结果；验证重复请求 |
| 超时后能直接重试吗？ | 先区分业务失败与结果未知；按契约查询或恢复，验证“已成功但响应丢失” |
| 接口和订单规则变化会影响哪里？ | 按实际需要隔离外部模型与业务计算，检查修改是否仍然局部 |
| 怎样知道线上发生了什么？ | 用关键状态与请求标识关联操作、响应和错误，验证能还原因果链 |

客户端禁用按钮只约束当前界面的操作，不能单独保证业务幂等；前端也无法凭一次超时判断服务端结果。这是跨边界设计必须明确的责任范围。

四类问题会互相放大，但“相乘”只能作为记忆比喻，不是复杂度的数学公式。不要把问题强行塞进唯一类别；分类是为了找到根因和控制点。

## 怎样做一次值得的架构调整

用五个问题形成最小决策记录：

1. **症状**：什么操作会触发什么可观察的错误或维护成本？
2. **根因**：主要缺少哪种状态、顺序、边界或依赖约束？
3. **方案与代价**：最低成本的机制是什么，新增多少理解和维护负担？
4. **预期改善**：旧结果不再覆盖新结果、重复操作只生成一个订单，或修改范围从五个模块缩到一个？
5. **证据**：怎样复现旧问题并证明新行为，怎样检查修改范围与依赖？

状态问题看非法组合与转换；异步问题覆盖乱序、重复、超时、取消与重试；边界问题检查异常数据和恢复路径；变化问题看实际修改范围与公开接口。只做与当前根因有关的验证。

新增结构如果没有降低错误概率、修改成本或排查成本，就可能只是搬动了复杂度。复习时用自己的话回答：**这次约束了什么，解决了哪个具体症状，如何证明值得？**
