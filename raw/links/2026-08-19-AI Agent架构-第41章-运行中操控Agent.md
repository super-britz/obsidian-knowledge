## 来源摘要

本章讨论运行中的 Agent 如何安全处理追问、撤回和中断。追问的生命周期不能压成“已收到”：`accepted` 是路由器将消息交给活动运行的邮箱，`committed` 是 Loop 在迭代边界把消息写入真实用户轮次和对话转录，`completed` 则是对应回复已成功送达。三者分别失败，必须有明确所有者；持久邮箱记录也只能在 committed 后移除，交付重放记录只能在 completed 后确认。

Loop 应在每轮迭代开头、下一次模型决策之前非阻塞地排空邮箱。此时前一动作的结果已知、下一动作尚未选择；在工具执行中注入会修改已选动作下的上下文，太晚处理又会让 Agent 按旧指令多执行一次。运行结束前还需要由路由锁保护一次原子最终排空：迟到消息要么被当前运行吸收，要么因注入窗口关闭而启动新运行，不能先被接受再失去所有者。

一次物理 Run 可以包含多个逻辑用户轮次，因此回复目标和待确认集合要按入站消息 ID 维护。若追问覆盖了旧回复目标，系统须先保留旧目标、发送中间回复，再推进到新目标。入站传输采用 at-least-once 时，`delivery_ack` 只能在终态回复成功送达后发出；失败则保留重放机会，并依赖持久消息身份去重。追加、撤回、中断和“中断并发送”语义不同：撤回需要墓碑与客户端 ID，中断应走取消信号而非等模型读取 Prompt，替代请求应等待旧路由进入非活动状态后再启动。

## 使用边界

- 本章的源码行号和具体实现来自有日期的 Kocoro 快照；可迁移的是状态分层、原子所有权和交付确认原则，而非具体常量或函数名。
- 合并多条追问是产品决策；若合并，必须明确组合回复归属哪个入站 ID，以及较早消息如何确认。
- 可靠交付不等于 exactly-once 传输；应接受 at-least-once 重放，并用持久身份和幂等处理去重。
