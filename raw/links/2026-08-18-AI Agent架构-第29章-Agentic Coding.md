# AI Agent 架构：第 29 章 Agentic Coding

- **原文标题：** 第 29 章：Agentic Coding
- **URL：** https://waylandz.com/ai-agent-book/%E7%AC%AC29%E7%AB%A0-Agentic-Coding/
- **访问日期：** 2026-08-18
- **资料类型：** 在线书籍章节页

## 来源摘要

本章将 Agentic Coding 定义为从理解需求、检索和分析代码库、规划及编辑代码，到隔离执行测试、依据失败迭代修复、最后以 Git commit 或 Pull Request 交付的端到端任务闭环。它区别于只在当前文件或光标位置生成补全的能力：必须跨文件理解依赖，并对实际执行结果负责。

原章提出代码库理解应按需进行：结合标识符/关键词搜索、AST/LSP 导航、语义搜索和依赖图，只读取与任务及受影响调用链相关的代码。编辑大文件时应以唯一文本锚点定位，而不是依赖会漂移的行号；写入操作需授权且限制在沙箱目录。

章节强调 Agent 生成或修改的代码必须在隔离环境运行，并限制可读写路径、网络、权限、内存和超时。质量验证采用“编辑 → 测试 → 分析失败 → 修复 → 再测试”的循环，同时以最大迭代次数和相似修复检测避免死循环；测试文件、数据和环境要隔离，防止 Agent 通过改测试制造虚假通过。

交付前还要保护 Git 工作区与供应链：避免在用户已有未提交改动中混入 Agent 变更，输出可审查的 diff、测试证据和 PR；新增依赖应经过白名单、审计或人工审批。删除、生产配置、安全规则、密钥、网络访问和依赖安装等高风险操作需要明确授权。

## 使用边界

- 沙箱限制代码运行时能接触的能力，但不能替代依赖供应链审查、Git 审查、策略授权或人工审批。
- 测试通过只说明已执行的测试在该环境中通过；覆盖不足、测试污染和生产差异仍可能使变更错误。
- 多模型路由可以优化成本或专业性，但不改变同一条责任链：理解、最小变更、验证证据和可审查交付都不可省略。
