# AI Agent 架构：第 26 章 多租户设计

- **原文标题：** 第 26 章：多租户设计
- **URL：** https://waylandz.com/ai-agent-book/%E7%AC%AC26%E7%AB%A0-%E5%A4%9A%E7%A7%9F%E6%88%B7%E8%AE%BE%E8%AE%A1/
- **访问日期：** 2026-08-18
- **资料类型：** 在线书籍章节页

## 来源摘要

本章讨论 Agent SaaS 的多租户隔离：共享基础设施时，任一数据访问遗漏 `tenant_id` 都可能造成跨组织泄露。原文列出共享 Schema（成本最低）、独立 Schema 与独立数据库（隔离最强）三种策略；共享 Schema 需要在每个业务表保存非空 `tenant_id`，并在所有查询中强制过滤。

租户身份应从已认证的 JWT 或 API Key 解析后写入请求 Context，而不信任请求参数。原文分别在认证、会话、工作流、向量检索和数据库五层校验租户归属；跨租户资源返回 NotFound，以避免泄露资源是否存在。Temporal Workflow 需通过 Memo 保存租户元数据；向量搜索需要显式 tenant filter，不能只依赖相似度。

章节还覆盖按套餐区分 Token、速率、会话和向量文档配额，API Key 的哈希存储、禁用和过期检查，以及审计日志与跨租户回归测试。开发模式跳过认证不得进入生产环境。

## 使用边界

- 多租户隔离保证组织间的数据与配额边界；它不替代第 24 章的操作授权，也不替代第 25 章对单次不可信代码执行的能力和资源隔离。
- 中间件只能建立可信租户上下文，不能保证后续每个独立存储或异步工作流都自动带上范围；会话、工作流、向量库与数据库仍须各自执行校验。
- 独立数据库、Schema 和共享 Schema 是安全、成本与运维复杂度的取舍，不存在脱离数据敏感度、客户规模和合规要求的唯一选择。
