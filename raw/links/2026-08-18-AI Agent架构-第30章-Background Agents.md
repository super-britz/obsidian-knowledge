# AI Agent 架构：第 30 章 Background Agents

- **原文标题：** 第 30 章：Background Agents
- **URL：** https://waylandz.com/ai-agent-book/%E7%AC%AC30%E7%AB%A0-Background-Agents/
- **访问日期：** 2026-08-18
- **资料类型：** 在线书籍章节页

## 来源摘要

本章讨论脱离用户在线会话而独立运行的 Agent：用户创建定时任务后立即获得任务 ID，后台系统在指定时间触发执行、记录状态和历史，并支持暂停、恢复、查询、失败重试与告警。它适用于长时研究、批处理和持续监控等无法由同步 HTTP 请求承载的任务。

原章以 Schedule Manager、Temporal、PostgreSQL 和 Worker 分层：工作流引擎保存调度与执行状态、触发任务并恢复失败；业务数据库保存用户配置、元数据和执行历史，以支持 UI 查询、分析与审计。创建调度时校验 Cron、最小触发间隔、用户配额、单次预算、超时和 IANA 时区；暂停/恢复操作保持幂等，并明确返回下一次执行时间。

章节强调后台任务要把每次执行的成本、状态和错误写入历史；预算同时受系统上限、用户单次上限和可选累计上限约束。由于业务库与工作流引擎可能在创建、删除或人工操作时失去一致性，需要在失败时补偿回滚，并定期检测孤儿调度和修正状态。

后台执行因缺少实时人工监督而风险更高。原章建议限制重试、超时、并发与调度数量，使用最小权限和完整审计；删除数据、发送邮件、购买、修改权限等敏感操作不应在后台无额外授权地执行。

## 使用边界

- 持久化调度解决“任务能否在用户离线和进程故障后继续”，不等于任务语义必然正确；每次运行仍需验收、观测与失败处理。
- Cron 只描述触发时刻；时区、夏令时、重叠执行、错过触发和结果通知需要作为独立产品与运行时规则明确。
- 重试和恢复会提高完成率，也可能重复执行副作用；外部写操作仍要使用幂等键、去重和人工审批。
